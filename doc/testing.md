# 回帰試験

```
make test            全部
make test T=piano    1 件だけ
make test-update     指紋を焼き直す（意図して音を変えたとき）
```

**ROM が無い機械では verify だけが走る。** ROM は同梱できないので、それが
正しい振る舞い。ROM の置き場は `--roms`、環境変数 `SMU2000_ROMS`、`roms/`、
`../MU2000/roms` の順に探す。

## 何を見るか

| | 見るもの | ROM |
|---|---|---|
| 1 | `verify.exe` — SWP30 のレジスタ素通しと乱数の数列 | 不要 |
| 2 | `statetest.exe` — 状態の保存と復元。写し忘れがあれば落ちる | 要 |
| 3 | 鳴らし比べ — `tests/*.json` の指紋と突き合わせる | 要 |
| 4 | スレーブを別の糸で回しても同じ音が出るか（`--single` と比べる） | 要 |
| 5 | `xgtest.exe` — パラメータの層の定義表を firmware に読み返させる（[doc/params.md](params.md)） | 要 |

合否は **起動後の PCM そのもののハッシュ**で決める。違っていたら「どこが
どれだけ違うか」を出す。

## WAV を置かない理由

基準の波形を置けば確かに楽だが、置かない。

* 1 件 4MB で、7 件置けば音源本体より大きくなる
* **ROM から起こした音なので、配るのは ROM を配るのに近い**。このリポジトリが
  ROM を同梱しない立場と噛み合わない

代わりに、音から測った数だけを `tests/*.json` に置く（全部で 40KB ほど）。
音そのものは `build/tests/` に出るので、聞きたいときはそれを聞く。

## 指紋の中身

doc/design.md の「音の正しさを何で見るか」に沿っている。包絡線だけで
合っていると判断してはいけない、というのがそこでの結論。

| | 何のために |
|---|---|
| `pcm_sha1` | **合否はこれで決まる。** 起動後の PCM のハッシュ |
| `keyon` | keyon の時刻・チャンネル・サンプル番地・形式。音色が合っているか |
| `envelope` | 50ms ごとの最大振幅。音が抜けていないか |
| `dc` | 直流。整数の総和なので誤差が無い（doc/todo.md 3 番で使う） |
| `slow_rms` | 441 サンプル平均した波形の実効値 ÷ 全体。低いところの量の**目安**。「30Hz 以下の割合」ではないので実機と比べる数には使えない |
| `boot_samples` `frames` `rate` `peak` `rms` | 食い違ったときの手がかり |

道具は標準ライブラリだけで動く（`tools/fingerprint.py`）。MSYS2 の python でも
素の Windows の python でも同じ数が出るように、外の部品は使っていない。

## 鳴らすもの

`tools/make_test_midi.py` が毎回組む。**MIDI もリポジトリに置かない。**
中身が一目で分かり、直したいときに直せるほうがよい。

| 名前 | 狙い |
|---|---|
| `piano` | 一番素朴な一音。keyon のサンプル番地・形式、エンベロープ、減衰 |
| `chord` | 和音。声の取り合いと重なり |
| `drums` | 8bit 圧縮サンプルを通る経路（MAME の展開器が不正確な場所） |
| `effects` | MEG を通す。リバーブ Hall1 + コーラス + バリエーション |
| `dense` | 16 パート同時。声がスレーブ側の SWP30 まで溢れる |
| `port_b` | MIDI IN B（パート 17-32）。口の振り分け |
| `bend` | ピッチベンドとモジュレーション。LFO とピッチの道 |

足すときは `CASES` に関数を 1 つ増やして `make test-update` で焼く。

## MIDI を流し始める時刻を固定している

`render` は既定では「firmware が受信を有効にした瞬間」を待ってから流す。
その瞬間は実測 7.8801 秒だが、**呼び方によって数サンプルずれることがあった**
ので、試験では `--boot 8.0` で固定している。

`--reset gm`、`--reset gs`、`--reset xg` を指定すると、ファイル内のリセットを
取り除き、指定したリセットを先頭に入れる。指定しなければ MIDI ファイルの内容を
そのまま流し、暗黙のリセットは加えない。

MIDI 入力は既定では実機と同じ 31250bps の直列で流す。`render`、`gui`、`live` で
`--fast-midi` を指定すると、線の待ち時間を省き、firmware が前のバイトを読んだ
直後に次のバイトを渡す。

## 前提: 同じものを入れたら同じ音が出ること

これは一度壊れていた。デバイスの状態に初期値が書かれていない要素があり、
firmware がそれを読む経路があったため、**起動時の引数の文字列がそこに残って
いると音が変わった**（パスの区切りが `\` か `/` かで keyon が 1 サンプル
ずれた）。`swp30.h` と `sh_*.h`、`sci4.h`、`hd44780.h` の要素に初期値を
書いて直してある。

指紋が合わないときは、まず**同じ呼び方で 2 回走らせて同じ結果になるか**を
見る。ここが揺れていたら、それが先。

## 焼き直すとき

意図して音を変えたら `make test-update`。**変更の前に `make test` を通して
おく**こと。そうしないと、焼き直した指紋が「直す前の音」なのか「直した後の
音」なのか分からなくなる。

食い違いの報告はこういう形で出る。

```
  chord が変わった:
  keyon の中身が違う（消えた 3 / 増えた 3）
    - [   57379] ch 01 [7dd2 0000177a 0000641e fe40b8fc] sample 00177a-00641e ...
    + [   57380] ch 01 [7dd2 0000177a 0000641e fe40b8fc] sample 00177a-00641e ...
  包絡線  最大差 418 (5.25%) @ 2.55 秒、平均差 50.98
  peak [7838, 7960] → [7978, 8098]
  dc   [24.7743, 24.7122] → [24.7854, 24.7145]
  pcm_sha1  4941b3500f8e → b50b73aa5af0
```

## native の口を実機と突き合わせる

`make test` の外に、**SWP30 のレジスタを 1 本ずつ比べる**道具が 2 つある。
どちらも firmware を走らせた結果と native の口の結果を直に比べるので、
「音が変わっていない」ではなく「**実機と同じ値を書いている**」が見られる。

```bash
# 鍵を押した瞬間。128 音色 × 鍵 3 通り
SMU2000_CUT_EXACT=1 python tools/native/regsweep.py ../MU2000/roms - 36,60,84 100

# 鳴らしたままつまみを動かす。CC91 を 0-127 で
SMU2000_CUT_EXACT=1 python tools/native/ccregsweep.py ../MU2000/roms 91 0,40,80,127
```

気をつけること:

* **減衰する音色で「持ったまま振る」測り方はしない。** 実機は声が鳴り
  終わるとレジスタを書かなくなるので、最後の値が凍る（`doc/native-engine.md`
  の 6.105）。伸びる音色（Strings1 など）を使うか、鍵を押した瞬間で測る
* `SMU2000_CUT_EXACT=1` を立てないと `0x00`（切る高さ）は写し取り前提の
  値のままなので食い違う

## 「合っている」こととの違い

`make test` が見ているのは**変わっていないこと**だけで、実機と合っている
ことは見ていない。合っているかどうかは MAME の録音や実機の録音と突き合わせる
ほうの話で、手順は doc/design.md にある。指紋を焼いた時点の音は、その
突き合わせを通ったもの（発音指示 2851 件一致、振幅 88.7% が 10% 以内）。

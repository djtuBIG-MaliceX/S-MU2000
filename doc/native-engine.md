# firmware を走らせない線（設計の下書き）

いまの S-MU2000 は、**実機の firmware をそのまま走らせて**、その firmware が SWP30 のレジスタを
叩いて音を出している。この文書は「firmware をやめて、XG の処理そのものを C++ で書く」道の設計。
まだ**作っていない**。何が要るか、どう確かめるか、何を失うかを先に並べておくためのもの。

軽くする話の全体像は [native-dsp.md](native-dsp.md)（エフェクトを C++ にする線）と対になる。

## 1. どこが重いのか（実測）

dense（16 パート・60 音）を鳴らしたときの、1 サンプルあたりの内訳（Ryzen 7 9700X）。

| | 時間 | 割合 |
|---|---|---|
| **SH-2（firmware）を回す** | 2.3µs | 55% |
| SWP30 の声を作る（AWM2＋波形 ROM） | 1.4µs | 33% |
| MEG（エフェクト） | 0.5µs | 12% |

エフェクトを C++ にしても消えるのは 0.5µs で、**いちばん大きいのは firmware**。
やめれば全体が半分以下になり、[goal](todo.md) の「PFM のインスタンスを何枚も同時に」に効く。

## 2. 何を捨てて、何を残すのか

**残すもの: SWP30 の声を作るところ（AWM2）と波形 ROM。** 音色そのものはここで決まるので、
ここを残す限り**音は実機のまま**にできる。native にするのは「レジスタに何を書くか」を決める側だけ。

```
  いま:   MIDI → [SH-2 が firmware を実行] → SWP30 のレジスタ → 音
  この線: MIDI → [C++ で書いた XG の処理]  → SWP30 のレジスタ → 音
                                             ^^^^^^^^^^^^ ここは同じものを使う
```

だから、**正しさの物差しは「レジスタに同じ値を書けたか」**になる。音を比べるより厳密で、
自動で確かめられる（下の 5.）。

## 3. firmware が今やっていること

| やっていること | native 側で要るか |
|---|---|
| MIDI を受けて解く（チャンネルメッセージ・SysEx・RPN/NRPN） | **要る**（src/xg/model.h の表が使える） |
| パートの状態を持つ（音色・音量・パン・送り・フィルタ・EG…64 パート） | **要る**（xg/ram.h と同じ並びを C++ の構造体で） |
| 音色の記録を ROM から引く（バンク・プログラム → 記録） | **要る**（xg/voices.h の lookup がもうある） |
| 記録から SWP30 のスロットのレジスタを組み立てる | **要る。ここが最大の未知**（下の 4.） |
| 声の取り合い（空きスロット探し・古い声を止める） | **要る**（実機と同じ挙動にするのが難しい） |
| ドラムキット（音ごとの音程・音量・パン・EG・NRPN） | **要る** |
| ポルタメント・ダンパ・モノ/ポリ・ベンド・コントローラ | **要る** |
| エフェクトの設定（MEG のプログラムを ROM から積む） | 要らない（C++ のエフェクトに置き換え済み） |
| LCD・パネル・つまみ・レベルメーター | **要らない**（native モードでは機械ではなく音源になる） |
| シーケンサ・サンプリング・SmartMedia・ユーティリティ | **要らない**（要るなら firmware の側で使う） |
| ダンプ要求への返事（SysEx の送り返し） | 当面要らない |

## 4. いちばんの難所: 音色の記録 → レジスタ

音色の記録は ROM の `0x200EE0` から 1635 個並んでいて、形は
「要素の印 1 バイト・1 バイト・名前 10 文字」＋ **要素ごとに 84 バイト**（`xg/voices.h`）。
この 84 バイトの中身はまだ解いていない。**ここを解くのがこの線の 8 割**。

解き方は、firmware に教えてもらうのが早い。

1. 音色を 1 つ選び、1 音だけ鳴らす。`mu2000::set_swp_trace()` で **SWP30 への書き込みを全部記録**する
   （どのスロットの何番のレジスタに何を書いたか。`render --swp-trace`）
2. 同じ音色の 84 バイトを ROM から取り出す
3. 1635 音色 × いくつかの鍵・強さで 1. と 2. を集め、**バイトとレジスタの対応**を機械的に探す
   （そのまま入る／表を引く／鍵や強さで補間する、のどれか）
4. 分かった対応で組み立てたレジスタ列と、firmware が書いた列を突き合わせる

この掃引は既にある道具の延長でできる（`tools/fxsweep`・`voicesweep.py` と同じ作り）。
1 音色あたり数百ミリ秒として、1635 音色 × 3 鍵 × 2 強さで 1 時間ほど。

**記録の量を測った**（`render --trace-swp`、11 秒・1 音）: SWP30 への書き込みは **126,318 件**。
段 0 の実験（下の 6.）で、そのうち **16,956 件（13.4%）だけ**で音が 1 サンプルも違わずに出ることが
分かった。残りの 9 割近くは firmware が同じ値を書き直しているだけで、SWP30 の側でも
`vol_w` が「同じ値なら何もしない」と書いてある通り、鳴りには関わらない。

16,956 件の内訳:

| | 件数 | 何か |
|---|---|---|
| `0x44e`/`0x44f`/`0x48e`/`0x48f` | 11,392 | **MEG のプログラムを積む**（エフェクトの中身。native では丸ごと要らない） |
| スロットのパラメータ（`0x09` 音量 EG、`0x21`-`0x2b`、`0x30`-`0x3d` ほか） | 4,449 | **ここが native driver の作る値**。11 秒で 4,449 件 ＝ **1 秒に 400 件** |
| `0x04e`（内部 RAM の番地）ほか | 1,115 | ワークの読み書き |

つまり **native driver が本当に書かないといけないのは 1 秒に 400 件ほど**。
1 サンプル（44,100 分の 1 秒）あたり 0.01 件で、firmware を回す 2.3µs とは桁がいくつも違う。

**分かっているとっかかり**

* パートの塊の `+0xF8` に、firmware が引いた音色の記録の位置が入っている（`xg/ram.h`）。
  つまりバンク・プログラムの引き方は真似しなくてよく、**記録の中身だけ**が問題
* SWP30 のレジスタの意味は MAME 由来の実装で分かっている（`src/mame/sound/swp30.h`。
  波形の番地・ループ・音量 EG・フィルタ・LFO・パン・送り）
* 「声 1 つ」は 1 要素。要素が 2 つ以上ある音色は、声も 2 つ以上使う（`sounding_voices()` の数え方と同じ）

## 5. 確かめ方（ここが肝）

**レジスタ列の突き合わせ**を回帰試験にする。

```
同じ MIDI を
  (a) firmware 版で流して、SWP30 への書き込み列を記録
  (b) native 版で流して、同じものを記録
→ 2 つの列を比べる（時刻・スロット・番号・値）
```

* 音を鳴らさずに比べられるので速い
* 違いが出たら「どのパラメータの計算が違うか」がそのまま分かる
* 音での比較（`make test` のゴールデン波形）も今までどおり残す。レジスタが合えば波形も合うはず

段階ごとに「何割のレジスタが一致したか」を数字にすれば、進み具合が見える。

## 6. 進め方

| 段 | やること | 終わりの目印 |
|---|---|---|
| 0 | レジスタ列の記録と再生。firmware が書いた列を記録して、SH-2 を止めたまま同じ時刻に流し込む | **済み**（下の 6.1） |
| 1 | 84 バイトの意味を掃引で割り出す（上の 4.） | **途中**（6.2 で波形、6.3 で包絡線の半分） |
| 2 | native driver の骨。MIDI → パート状態 → 音色選び → スロット割り当て → レジスタ | **済み**。音階と和音が鳴り、1 音の写し取りを足すと大きさの差 0.06dB・波形の残差 -25dB（6.8・6.10） |
| 3 | 和音と声の取り合い、複数要素、ドラムキット | dense のような曲でレジスタ列が 99% 一致 |
| 4 | コントローラ（CC・ベンド・ポルタメント・ダンパ・NRPN・RPN） | doc/todo.md の「コントローラの効き方」の試験が native でも通る |
| 5 | PFM（パフォーマンス）と複数インスタンス | PFM の 100 個が鳴り、1 枚あたり 1.5µs 以下 |

### 6.1 段 0 の結果（済み）

`render --trace-swp <file>` で書き込みを記録し、`render --replay-swp <file> --boot <秒>` で
**SH-2 を 1 サイクルも回さずに**、記録したサンプル番号のところで同じ値を SWP30 へ入れ直す。

* 記録は 1 行が「どちらのチップ・レジスタ番号・値・PC・時刻・サンプル番号」。
  サンプル番号で合わせるのが肝で、時刻で合わせると 1 サンプルずれる
  （`run_sample` は 1 サンプルぶんの CPU を回してから SWP30 を進めるので、
  そのサンプルの**頭**で入れ直せば実機と同じ順になる）
* 結果: **966,544 サンプルが 1 つも違わず一致**（差の最大 0）。読み出しは要らない
* 間引きの実験: 「値が変わった書き込みだけ」に絞ると**音が変わった**（最大差 2,471）。
  番地が自動で進むレジスタ（下位 6bit が `0x0e`/`0x0f`。MEG のプログラム・内部 RAM・keyon）は、
  同じ値でも**書くこと自体に意味がある**。それらを残して間引くと、126,318 → 16,956 件で
  **また 1 サンプルも違わず一致**した

**分かったこと**: 音は SWP30 だけで作れる。firmware は「レジスタに何を書くか」を決めているだけで、
その中身は 1 秒に 400 件ほどしかない。段 1（音色の 84 バイト）へ進んでよい。

### 6.2 段 1 の途中経過: 波形の組の引き方が分かった

`build/voicesweep.exe` で「音色を選ぶ → 1 音鳴らす → SWP30 のスロットに書かれた値を全部拾う」を
繰り返し、ROM の 84 バイトと突き合わせた（`tools/voicesweep/`）。

**84 バイトの中の 2 バイト（`elem[2]`・`elem[3]`）が波形の組の番号**だった。
7bit ずつの組で、`set = (elem[2] << 7) | elem[3]`（MIDI 風の詰め方）。そこから 2 段引く。

```
  音色の記録 +12 の 84 バイト
      elem[2],[3]  ->  組の番号（0-502）
                        |
        0x200AF0 の表（16bit を 503 個、終わりは ffff）
                        |  = 波形の並びの中の位置（バイト）
        0x1F55A0 から 16 バイトずつの「波形の記録」
```

**波形の記録（16 バイト）**

| 位置 | 中身 | 行き先 |
|---|---|---|
| +0 | 印（0 が多い。04/16/1f などもある） | ? |
| +1,+2 | もとの音程（16bit。上の桁が鍵、下が細かい調整） | レジスタ `0x11`（音程）の元 |
| +3 | **この記録を使う鍵の上限**（最後の記録が 0x7f） | 鍵で記録を選ぶ |
| +4..+7 | ループ前のサンプル数（32bit） | レジスタ `0x12`/`0x13` |
| +8..+11 | ループの長さ（32bit） | レジスタ `0x14`/`0x15` |
| +12..+15 | 形式＋波形 ROM の番地（32bit） | レジスタ `0x16`/`0x17` |

**確かめ**: 1 要素の音色 128 個 × 鍵 36/60/84（と鍵 0-127 の 1 音色）で、
`0x12`-`0x17` の 3 つの 32bit が **530 組のうち 516 組（97%）で完全に一致**した。
合わないのは鍵をずらして鳴らす音色（組の中で鍵の上限の並びが 1 度 0x7f で終わって、
また始まるものがある＝層が複数）と、ループ前の数だけずれるもの。ここは段 1 の残り。

### 6.3 段 1: 包絡線の作り方

84 バイトが**そのまま**レジスタに入っている所は 1 つも無い。けれど「同じバイトの値には
必ず同じレジスタの値」という見方（`solve.py` の `as_function`）をすると、表を引いているものが見つかる。

| レジスタ | 元 | 形 |
|---|---|---|
| `0x07` の下位（減衰 1 の目標） | byte 77 | **`(0x7f - byte) * 2`**（ぴったり。12 個の値で確かめた） |
| `0x08` の下位（減衰 2 の目標） | byte 78 | **`(0x7f - byte) * 2`**（同じく 10 個） |
| `0x06` の上位（アタックの速さ） | byte 73 | 表を引く。だいたい `2 * byte` で、上のほうが詰まる（`3e`/`3f` が同じ `77`） |
| `0x07`/`0x08` の上位（減衰の速さ） | byte 74 ほか | **鍵で変わる**（下） |

つまり**記録は XG と同じ 0-127 の目盛りで持っていて、レジスタは「減衰の量」に直している**。

**確かめた広さ**: バンク 26 種 × 128 プログラム（3,328 の口）を鳴らして、中身の違う記録 216 個で
上の 4 つが全部成り立った（`build/voicesweep.exe ... picks_big.txt -n 60 -v 100`、30 分ほど）。

**減衰の速さは鍵で変わる**。鍵 36/60/84 で測ると、音色によって増え方が違う。

```
  減衰 1 の速さ ≒ 2 * byte74 + 係数 * (鍵 - その鍵で使う波形のもとの音程)
```

* 「もとの音程」は 6.2 の波形の記録の +1,+2（16bit。上の桁が鍵）。**鍵の区画ごとに違う**ので、
  鍵 36 と 84 では引き算の相手が変わる。だから「鍵 48 個ぶんの増え方」は音色ごとにばらばらに見える
* 67 音色で当てはめると、**49 音色が誤差 1 以内**。40 音色は係数 0（鍵で変わらない）
* 切片は 25 音色で `2 * byte74` ちょうど。残りは ±6 ほどずれる（別のバイトが混ざっている）

**まだ分からないところ**（※音量は 6.5 で解けた）: フィルタ（`0x00`・`0x04`）・LFO（`0x05`・`0x0a`）。
216 個の記録で次を試して、**どれも外れた**（同じところを二度調べないように書いておく）。

* 84 バイトのどれか 1 つで決まるか → 外れ
* 84 バイトのどれか 2 つの組で決まるか → 外れ
* 記録の頭 12 バイト（印・名前）を足しても → 外れ
* 波形の記録（6.2 の 16 バイト）のどれかと組にしても → 外れ
* 2 つのバイトの**和**や**差**で書けるか → 外れ

分かっていること:

* 音量は**全部偶数**で、鍵 60・強さ 100 では 20〜62（22 通り）。減衰の目標と同じ「× 2」の目盛り
* 強さとの関係は**足し算**。強さ 40 と 100 の差が、67 音色のうち 65 音色で 42 ちょうど
* だから `音量 = 2 × (記録から決まる何か + 強さの項 + 鍵の項)` の形
* 1 音色（GrandPno）で鍵を 0-127 まで振ると、音量は**波形の切り替わり目で跳ぶ**。
  区画の中ではゆっくり増える（鍵 72→32、78→34、84→36、92→38）が、
  鍵 56 で 40、59 で 32、62 で 28 と、区画をまたぐたびに段差がある。
  並べ直すと、**ほとんどは鍵そのものの折れ線**だった:
  鍵 0-38 で 32、39-71 で 30、72 から 6 鍵ごとに +2（72→32、78→34、84→36、92→38）。
  途中の鍵 56-58（40）と 62（28）だけ外れるが、これは声の取り合いの写り込みかもしれない。
  つまり「下に平ら・真ん中が谷・上で持ち上がる」形のレベルキースケーリングで、
  曲がり角は鍵 39 と 72。**ここから先は掃引より firmware の中身を読むほうが早い**
  （0x134AA8 のあたりから、音色の記録を読んでレジスタを組み立てる所をたどる）

**強さ（ベロシティ）で動くもの**（GrandPno・鍵 60・強さ 1-127 で測った）

| レジスタ | 動き |
|---|---|
| `0x09` の下の桁（全体の音量） | 強さ 1 で 212、127 で 20（減衰の目盛り。値は全部偶数）。強さ 16 以上は「振幅が強さの 2 乗に比例」とほぼ合う（0.375dB きざみで計算した値の 0.96 倍）。弱い所はそれより浅い＝表か折れ線 |
| `0x00` の下 11bit（フィルタ 1 の主パラメータ） | 強さ 1 で 0x528、127 で 0x688。強さで開く |
| `0x05`（LFO の深さ） | `fa00`/`aa00` を行き来する。強さとは関係なく、掛けるたびに変わる（LFO の位相をばらしている） |
| `0x06`-`0x08`（包絡線の頭・減衰） | 強さでは動かない |

### 6.6.1 鍵の効き方の共通の形

`0x127FD8` のあたりに、鍵で値を増減させる共通の形があった。

```
  depth = ram[音色の塊 +22]            ; 0-127（64 が「効かない」）
  k = 0x80 + (((depth - 64) * (鍵 - 100)) >> 4)
  値 = ((値 * k) * 2 & 0xFFFF) >> 8     ; ＝ (値 * k) >> 7 の 16bit 版
  値が負なら 0、上限で頭打ち
```

「64 が中立、そこからの差を鍵との差に掛ける」という XG のいつもの形。
**基準の鍵は 100**（0x64）で、音量の折れ線（6.3 の曲がり角 39 と 72）とは別の所。

### 6.7 検算

分かった規則を掃引の結果で検算する道具を置いた。段 1 を進めるたびに回せば、

| 波形の番地・ループの長さ（`0x14`-`0x17`） | 1662 | 3 |
| ループ前の数（`0x12`/`0x13`） | 1604 | 61 |

ループ前の数がずれるのは、鍵をずらして鳴らす音色と「ループ位置の微調整」が入るもの。


### 6.4 firmware を読む（ここからが本筋）

掃引だけでは音量・フィルタ・LFO が解けなかったので、**firmware の中身を読む**道具を足した
（`tools/dump/sh2dis.py`。`sh2asm.py` の対になる SH-2 の逆アセンブラ）。

**入口は記録の `pc=`**。`render --trace-swp` の 1 行 1 行に「どの番地の命令が書いたか」が
入っているので、知りたいレジスタを書いている所がすぐ分かる。

```
python -c "…trace.txt を読んで、スロットのレジスタ 0x06-0x09 を書いた pc を数える…"
  → 鍵を押したときに 1 回だけ書く所が pc=0012DEE0（0x06）、0012DF00（0x07）、0012DF1E（0x09）
python tools/dump/sh2dis.py <rom> 0x12dec0 0x90
```

読めたこと。

**包絡線の速さは「RAM の値 × 2 を表で曲げる」**

```
  0x12DEE0:  R7 = ram[0x43E972]          ; 減衰 1 の速さの元（鍵の補正まで入った値）
             R7 = ROM[0x1F4E38 + R7]     ; 表で曲げる
             R2 = ram[0x43E988]          ; 減衰 1 の目標
             レジスタ 0x07 = (R7 << 8) | (R2 << 1)
```

* **アタックの表は ROM の `0x1F4DB8`、減衰の表は `0x1F4E38`**（どちらも 128 バイト）。
  中身はほぼそのままで、上のほう（0x60 から先）だけ詰まる
* 記録の byte73（アタック）・byte74（減衰）は**2 倍してから表を引く**。
  掃引の実測と合う: byte73=0x0a → `表[0x14]` = 0x14、byte73=0x3e → `表[0x7c]` = 0x77
* 目標の `× 2` は `SHLL`（1 ビット左）そのもの。6.3 の `(0x7f - byte) * 2` の正体は、
  **RAM には既に `0x7f - byte` が入っていて、レジスタに入れるときに 2 倍している**というだけ

**音量は足し算**

```
  0x12DF1E:  R4 = ram[0x43E96A] + ram[0x4226A8]   ; 声ごとの減衰 ＋ 全体の減衰
             if (R4 > 0xFF) R4 = 0xFF
             レジスタ 0x09 = R4
```

`0x4226A8` は XG のワーク RAM の中（`xg/ram.h` の並びのすぐ手前）。
`0x43E96A` は**鍵を押すたびに `0x12AC44` で書かれ**、その値は**関数 `0x12A404` の戻り値**。
その関数は `MULS.W` と `>> 7` を何段も重ねる形で、XG のいつもの
「0-127 の掛け算（`(a * b) >> 7`）」を、パート音量（`+0x12F`）・エクスプレッション（`+0x130`）・
強さの効き（`+0x4E`）…と順に掛けている。**段 1 の残りはこの関数を写すこと**で、
掃引より確実で速い。

### 6.5 音量の式（解けた）

`0x12A404` を最後まで読むと、こうなっていた。

```
  level = ram[声+118]                       ; 元（0-127）
  if (level == 0 または 音が無い) level = 0
  else {
      k = ram[音色の塊 +2] + 1 + ram[別の塊 +29]    ; 1..127 に丸める
      level = (level * k) >> 7                     ; XG のいつもの掛け算
      if (level == 0) level = 1
      level = (level * ram[パート +0x12F]) >> 7     ; パート音量
      if (ram[声+126] == 49) …  +0x130 を使う       ; エクスプレッション
      … 強さの効き（パート +0x4E、64 なら素通し）…
      level += パートの補正（+0x122 か、関数 0x12C7FC の戻り）
      level を 0..127 に丸める
  }
  att = 表[0x1E6818 + level] + ram[声+120] + ram[声+119]
  if (att > 127) att = 127
  att = att * 2                              ; ← 必ず偶数になる理由
```

そして

```
  レジスタ 0x09 = min(0xFF, att + ram[0x4226A8])     ; 後ろは全体の減衰
```

**これで 6.3 の実測が全部説明できる**。

| 実測 | 理由 |
|---|---|
| 音量が**必ず偶数** | 最後の `att * 2` |
| 鍵 60・強さ 100 で 20〜62（2 きざみ） | `att` が 10〜31 の範囲に収まっている |
| 強さを変えても**差が一定**（67 音色中 65 で 42） | 強さは `level`（掛け算の側）に効き、表 `0x1E6818` が対数なので**掛け算が足し算に変わる** |
| 1〜2 バイトで書けない | `level` に 5 段の掛け算と足し算が入り、そのあと表を引いてから 2 つのバイトを足すから |

**表 `0x1E6818`**（128 バイト）は「音量 0-127 → 減衰」の対数の曲線で、
`0x00` で 0x7f、`0x7f` で 0x00。`0x40` で 0x10（＝16。1 目盛り 0.375dB として 6dB）。

### 6.6 スロットを組み立てる所（`0x12DE50`-`0x12DF60`）

鍵を押したときに 1 回だけ走る、**スロットのレジスタを全部書く一続きの所**。
中身は「ワーク RAM の 0x43E95C から並ぶ値を、レジスタの形に詰め直す」だけだった。

| レジスタ | 式 | 元 |
|---|---|---|
| `0x00` フィルタ 1 | `0x1000 \| clamp(ram16[0x43E95E])` | 上 4bit の形は**この道では 1 固定**。下は切る高さ |
| `0x01` 素通しの量 | `(ram[0x43E960] << 8) \| 0x80FF` | |
| `0x02` フィルタ 2 | `ram16[0x43E99E] \| 0x8000` | |
| `0x03` フィルタ後の音量 | **`0x5010` の定数** | 掃引の実測と一致 |
| `0x04` フィルタの第 2 | `ram[0x43E95C] << 11` | 上 5bit にそのまま |
| `0x05` LFO の深さ | `(ram[0x43E963] \| 0xFA00) & 0xFF7F` | |
| `0x06`-`0x09` | 6.4・6.5 の通り | |

`clamp` は `0x12E79C`: **形（`ram[0x43E95C]`）が 4 未満のときだけ、切る高さを `0x7C0` で頭打ち**にする。

**スロットの置き場**は ROM の `0x1F4F58` に「スロット番号 → レジスタの先頭番地」が
4 バイトずつ 64 個並んでいる。`R4 = 0x1F4F58 + スロット * 4` を引いてから `+0`・`+2`・… と書く。

つまり **firmware の最後の一歩は詰め替えだけ**で、値そのものは `0x43E95C` から始まるワーク RAM に、
鍵を押す処理のもっと手前で作られている。段 1 の残りは、そこをこの方法（記録の `pc=` →
逆アセンブル）で 1 つずつたどること。**フィルタと LFO がそれ**。

### 6.8 段 2: SH-2 を止めたまま音が出た

`build/nativeplay.exe` を足した。やることは 4 つだけ。

1. firmware で起動して、SWP30 を実機と同じ初期状態にする
2. **CPU を止める**（`set_cpu_enabled(false)`。ここから先、firmware は 1 命令も走らない）
3. 音色の記録から `xg::nv::build_note`（`src/xg/native_voice.h`）でレジスタを組み立て、
   スロットに書いて keyon のマスクと引き金を叩く
4. WAV に書き出す

```
build/nativeplay.exe <rom> out.wav -b 0,0,0 -n 60            # SH-2 なしで 1 音
build/nativeplay.exe <rom> out.wav -b 0,0,0 --song           # SH-2 なしで音階と和音
build/nativeplay.exe <rom> out.wav -b 0,0,0 -n 60 --firmware # 比べる用
build/nativeplay.exe <rom> nul     -b 0,0,0 -n 60 --compare  # レジスタを突き合わせる
build/nativeplay.exe <rom> nul     -b 0,0,0 --sweep 128      # まとめて一致率を出す
```

**`--song` で音階（ド-ド）と和音を鳴らす**。スロットを順に割り当てて keyon し、
離すときは `0x09` に「離せ」の印を書く。出てきた音を測ると

* 8 音の基音が **262 295 331 350 392 441 494 524Hz**（狙いは 261 293 329 349 392 440 493 523）
* 音を離すと 0.2 秒ほどで静かになり、和音のあと完全に 0 まで落ちる

**離すときの値**（`0x09`）は

```
  上位 = 0x80 | ROM[0x1F4E38 + clamp(byte76 + 鍵の補正, 1, 63) * 2]
  下位 = 鳴らしたときと同じ減衰
```

上位のビット 15 が「離せ」の印（`swp30.cpp` の `release_glo_w`）。速さは減衰と同じ表を
**byte76** で引き、鍵の補正も同じだけ乗る。実機が離すときに書く値（GrandPno の鍵 60 で `0xBE1E`）と一致する。

`--compare` は、firmware に同じ音を鳴らさせて**そのとき書かれたレジスタを拾い**、
こちらが組み立てたものと 1 つずつ比べる（段 2 の「レジスタ列が一致」の物差し）。
GrandPno で:

| 鍵 | 一致 | 違い | 違っているもの |
|---|---|---|---|
| 36 | 30 | 2 | `0x00`（フィルタ）・`0x09`（音量の鍵での増減） |
| 60 | **31** | **1** | `0x00` |
| 84 | 29 | 3 | `0x00`・`0x01`・`0x09` |

**式が分かっているものは全部合っている**（波形の番地・ループ・音程・包絡線の目標と速さ・
声の EQ・ミキサ）。残りはフィルタ（`0x00`・`0x01`）と、音量の鍵での増減。

**まとめて測る**（`--sweep 128`。バンク 0 の 128 音色 × 鍵 36/60/84 のうち、
1 要素・1 スロットで鳴ったもの）: レジスタの **87.2% が一致**。合わないものの内訳は

| レジスタ | 合わない割合 | なぜ |
|---|---|---|
| `0x09` 音量 | 100% | 強さと鍵の効き方がまだ（6.5 の式の途中まで） |
| `0x01` 素通しの量 | 100% | **前の値からの傾き**で決まる（状態を持つ）。式ではない |
| `0x00` フィルタ 1 | 85% | 表は分かったが、鍵と強さの倍率がまだ（下） |
| `0x0b`・`0x10` | 36% | 何のレジスタか分かっていない |
| `0x11` 音程 | 19% | 音色ごとの移調が残り |
| `0x04` フィルタ 2 | 14% | `((byte35 >> 1) & 31) << 11`（`0x1280FC`） |
| `0x05` LFO の深さ | 7% | 掛けるたびに位相をばらしている（`fa00`/`aa00`） |
| `0x02` | 3% | `0x8000 \| byte82` |
| `0x0a` LFO | 2% | `0x40 \| byte11` |
| `0x06` アタック | **0%** | 上位も下位もぴったり |

**音の比べ**（GrandPno・鍵 60、firmware に鳴らさせたものと）:

| 帯 | 差 | | 0.1 秒ごとの大きさ |
|---|---|---|---|
| 125Hz | +1.2dB | 実機 | 971 857 797 741 667 591 547 496 450 |
| 250Hz | +0.4dB | SH-2 なし | 872 764 724 684 631 568 529 478 432 |
| 500Hz | -4.5dB | | |
| 1kHz | +8.8dB | | 全体で -0.9dB、減り方はほぼ平行 |
| 2kHz | +4.0dB | | |
| 4kHz | -1.2dB | | |
| 8kHz | +1.7dB | | |

残っている山は 500Hz〜2kHz で、フィルタの鍵・強さの倍率がまだ入っていないぶん。

**音はもう出る**。firmware に鳴らさせた同じ音と比べると、基音（250Hz）は 0.4dB 差、
包絡線の形もほぼ同じ（0.1 秒ごとの大きさが 971→331 対 1117→366）。違うのは高い所で、
1kHz が +14dB・4kHz が +15dB 明るい。**フィルタを開き切りにしている**からで、
上の表の `0x00` がそのまま音に出ている。

#### アタック（`0x06`）

```
  上位 = ROM[0x1F4DB8 + min(byte73, 63) * 2]
  下位 = byte73 が 63（最速）なら 0、そうでなければ 0x7e
```

402 組で**上位も下位も 100% 一致**。パートの「EG アタック」を触ると `byte73` に足されるが
（`0x127054`）、初期値の 64 では何も足さない。

#### LFO（`0x0a`）

```
  上位 = 0x40 | byte11     下位 = 0
```

402 組で例外なし（`0x05` の深さのほうは、掛けるたびに `fa00`/`aa00` を行き来する＝位相をばらしている）。

#### フィルタ（`0x00`）— 途中まで

```
  索引 = byte37（パートのカットオフを触ると ±される）
  索引 = clamp((索引 * (0x80 + ((depth - 64) * (鍵 - 100) >> 4))) >> 7, 0, 127)
  切る高さ = ROM16[0x1E5B58 + 索引 * 2] + パートの補正、0..0xFFF で頭打ち
  レジスタ = 0x1000 | (切る高さ & 0x7FF)
```

* **表は ROM の `0x1E5B58`**（16bit。索引 0 で 1536、64 で 3237、127 で 4095、200 で 16191）
* 索引は記録の **byte37**。鍵で動かない音色（depth = 64）なら、表を引くだけで
  firmware と**完全に一致**する（402 組のうち 41 組がそれ）
* `depth` がどのバイトから来るかはまだ。強さでも動く（`0x1528` → `0x1688`）ので、
  `0x127FA4` をもう一段読む必要がある

いまは「倍率 1」として表を引くだけにしてある。レジスタの一致率は下がる（72% → 85% が不一致）が、
**音は開き切りよりずっと実機に近い**。

| 帯 | 開き切りのとき | 表を引くとき |
|---|---|---|
| 1kHz | +14.2dB | +8.8dB |
| 2kHz | +7.8dB | +4.0dB |
| 4kHz | +15.3dB | **-1.2dB** |
| 8kHz | -3.1dB | +1.7dB |

#### 音量（`0x09`）— 強さの効き方は解けた

6.5 の `att = 表[level] + ram[声+120] + ram[声+119]` のうち、**`+119`（強さのぶん）が解けた**。

```
  強さの減衰 = 表2[0x1E6798 + 表1[0x1E5E5E + 曲線 * 128 + 強さ]]
```

* `表1`（`0x1E5E5E`）は**強さの曲線**。128 バイトの行が並び、**行 0 はそのまま**（`00 01 02 …`）
* `表2`（`0x1E6798`）は「0-127 → 減衰」の対数の曲線。128 バイトの行が並び、
  6.5 で見つけた `0x1E6818` は**この表の行 1**
* GrandPno の強さ 1-127 を**全段で試して、127/127 がぴったり一致**（曲線 0、下駄 10）
* 67 音色のうち **65 が曲線 0**

残りは音色ごとの下駄（`表[level] + ram[+120]`）で、実測では 5〜19 の幅がある。
`+120` は `0x1275C4` が足し込む値で、その元は **16bit の利得表 `0x1E5554`**（記録のバイトで引き、
`(値 * 利得) >> 16` と掛け算を重ねる）。ここはまだ解けていない。

いまは中央値の 12 を置いてある（絶対の音量が最大 ±7 目盛り ＝ ±2.6dB ずれる）が、
**強さを変えたときの動きは実機と完全に同じ**。

#### 音程（`0x11`）

```
  目盛り = ((鍵 - 波形のもとの音程) * 追従率 + 細調のセント) * 1024 / 1200
  ビット 14 = 波形の形式が 3 のとき 1
```

* 1 オクターブ = 1024。細調は波形の記録の +2（符号付き、セント）で、**足す**
* 整数の割り算（**0 の側へ切り捨て**）にすると firmware と 1 の位まで合う。
  floor や四捨五入にすると合わない（402 組で 83% 対 22%・35%）
* **追従率は記録の byte19**: 0 が普通の 100 セント/半音、1 が 50、2 が 20、3 が 10。
  効果音の音色でよく使う（ヘリコプター・拍手・銃声など）
* **ビット 14** は音程とは関係なく、波形の**形式**（レジスタ `0x16` の上 2bit）が
  3 のときだけ立つ。402 組で例外なし

これで 128 組の掃引で、音程が合わないのは 19%（前は 46%）。
残りは音色ごとの移調（prog 14 で -690 目盛り ＝ -8 半音ほど）で、どのバイトから来るかはまだ。

#### 減衰の速さ（`0x07`/`0x08` の上位）

firmware の `0x12ADD0` と `0x1272F4` を読むと、こうだった。

```
  補正   = ((鍵 - byte71) * ((byte70 - 64) * 16)) >> 8      // 負のときは先に +255（0 の側へ）
  目盛り = clamp(記録の速さ + 補正, 1, 63) * 2
  レジスタの上位 = ROM[0x1F4E38 + 目盛り]
```

* **byte70 が深さ**（64 が「鍵で変わらない」）、**byte71 が折れ点の鍵**
* 減衰 1 は byte74、減衰 2 は byte75。補正はどちらにも同じだけ乗る
* アタック（`0x06` の上位）には**この補正が無い**（`ROM[0x1F4DB8 + byte73 * 2]` のまま）

### 6.10 音色の写し取り — ここで実機と並んだ

式が分かっていないレジスタ（フィルタの倍率・素通しの量・音色ごとの音量）を追うのは、
まだ時間がかかる。そこで**残りを「1 音だけ実機に鳴らしてもらって写し取る」**ことにした。

```
  起動 → firmware で SWP30 を初期化
       → 使う音色ごとに 1 音（40ms ぶん）だけ firmware に鳴らさせ、
          そのときのスロットのレジスタと音量を覚える（voice_cal）
       → **CPU を止める**
       → あとは式で組み立て、覚えた値で上書きして鳴らす
```

覚えるのは**利用者の ROM から起こした値**なので、配布物には入らない（起動のたびに作る）。
鍵と強さで動くもの（音程・波形・包絡線・音量）は式で出すので、**1 音の写し取りで
全部の鍵・全部の強さが出せる**。

**どの時点の値を写すか**が効いた。

* `0x05`・`0x0a`・`0x11` は LFO が動かし続けるので**引き金を引いた瞬間**
* `0x01`（素通しの量）は**鳴らしてから上がっていく**。引き金の瞬間は `0xFFFF` で、
  そこを写すと高い音が 13dB 明るくなる。落ち着いた値（`0xDCFF`）を写す
* `0x38`-`0x3d` は**書いてはいけない**。あれは入力 0x40 から先＝ MEG の戻りや A/D のぶんで、
  声のスロットのものではない

#### 結果

`build/nativeplay.exe <rom> nul -b 0,0,0 --levels 40` が、音色ごとに
「firmware で鳴らした音」と「SH-2 を止めて鳴らした音」を同じ状態から作って比べる。

| | |
|---|---|
| 大きさの差 | **平均 0.06dB・最大 0.22dB**（23 音色） |
| 波形の残差（時間を合わせたあと） | **平均 -25.1dB** |

1 音を細かく見ると（GrandPno・鍵 60、0.5-0.7 秒の帯）:

| 帯 | 125 | 250 | 500 | 1k | 2k | 4k | 8k |
|---|---|---|---|---|---|---|---|
| 差 | +0.21 | +0.05 | -0.06 | -0.07 | +0.59 | +0.49 | -0.55 dB |

**時間を合わせると波形そのものが -24.7dB まで一致する**。残るのは、
鳴り始めの位置が 1.66ms 違う（実機は MIDI のバイトを受け取る時間がかかる）ことと、
LFO の位相。

### 6.11 どれだけ軽くなるか（これが本題）

`build/nativeplay.exe <rom> nul -b 0,0,0 --bench` が、同じ音を
「firmware を走らせたまま」と「SH-2 を止めて」で鳴らして、1 サンプルあたりの
実時間を測る（Ryzen 7 9700X、1 スレッド）。

| 同時に鳴らす声 | firmware あり | SH-2 なし | 速さの比 |
|---|---|---|---|
| 1 | 2972 ns | 1040 ns | **2.86 倍** |
| 8 | 3390 ns | 1253 ns | **2.71 倍** |
| 16 | 3799 ns | 1479 ns | **2.57 倍** |
| 32 | 4417 ns | 1898 ns | **2.33 倍** |

**2.3〜2.9 倍**。声を増やすほど SWP30 の側（声を作る所）が効いてくるので比は下がるが、
それでも 2 倍を切らない。

`blocktime` で測った「dense（16 パート・60 音）が実時間に入るのは 4〜5 台」は、
この線なら **10〜12 台**になる計算。[goal](todo.md) の「PFM のインスタンスを何枚も同時に」は、
エフェクトを C++ にする線（1 割）ではなく**こちらが本命**だと、数字で確かめられた。

#### 多い声での内訳

声が 32 でも SH-2 なしが 1898ns なのは、SWP30 の声を作る所（AWM2）と MEG が残るため。
そこは実機の音そのものなので削らない。

### 6.12 128 音色でどこまで合っているか

`--levels 128`（バンク 0 の全音色・鍵 60・強さ 100、要素の鍵/強さの範囲も見る）:

| | |
|---|---|
| 大きさの差 | 平均 **1.05dB**、0.5dB 以内が 81 音色、1dB 以内が 96、3dB 以内が 118 |
| 波形の残差 | 平均 -15.3dB、**-10dB 以下（波形まで合っている）が 75 音色** |

**要素のこと**が分かった。

* 記録の先頭のバイトは**要素のビットマスク**（1/3/7/15 ＝ 1〜4 要素）で、数ではない
* 要素の **byte4,5 が鍵の範囲、byte6,7 が強さの範囲**。
  E.Piano1 は強さ 1-127 と 80-127 の 2 要素、Church Organ は鍵 0-97 と 98-127 の 2 要素
* 写し取りは**要素ごと**に要る（スロットに書かれた `0x09` が、その要素の減衰そのもの）

残っている大きめのずれは、2 要素の音色（シンセ系）が中心。

### 6.13 本体に入れた（`render --native-engine`）

`src/xg/native_driver.h` を足して、`mu2000` の MIDI の入口に挟んだ。

```
  MIDI → native_driver
           ├ 鍵の上げ下げで、その音色の写し取りが有る  → **自分で鳴らす**（CPU は止めたまま）
           ├ 写し取りがまだ無い                        → firmware に鳴らさせて、writes を写し取る
           └ それ以外（音色の指定・CC・SysEx）          → firmware へ回す
```

* **firmware を回すのは、渡した MIDI が溜まっている間＋少しだけ**。
  `midi_pending()` を見て、空になってから 10ms で止める
* スロットは**上から**取る。firmware は下から使うので、写し取りのために
  firmware が鳴らしている音とぶつからない
* 起動は firmware がやる（SWP30 の初期化に要る）。`--native-engine` は起動が終わってから入る

#### 速さ（30 秒ぶんの書き出しにかかった実時間、Ryzen 7 9700X）

| 曲 | 既定 | native の口 |
|---|---|---|
| piano | 3.92 秒 | 1.39 秒（**2.82 倍**） |
| dense（16 パート・60 音） | 4.29 秒 | 1.75 秒（**2.45 倍**） |
| lofi（インサーションを SysEx で切り替える） | 5.18 秒 | 2.82 秒（**1.84 倍**） |

軽量エフェクト（`--native-fx-full`）も足すと、piano 3.43 倍・dense 2.96 倍。

**firmware を回す長さの決め方**が効く。

* ふだんは、渡した MIDI が溜まっている間＋10ms
* **SysEx のあとは 0.5 秒**。エフェクトの種類を変える SysEx は MEG のプログラムを
  1 万件以上書き直すので、途中で止めると音が出なくなる（lofi が無音になって気づいた）
* 音色の写し取りは 20ms。短くすると `0x01`（鳴らしてから上がる）が落ち着く前に切れる

#### 音（試験の 7 曲、既定の道と比べた大きさの差）

| piano | chord | dense | drums | effects | bend | lofi |
|---|---|---|---|---|---|---|
| +0.06 | +0.14 | -0.00 | +0.00 | +0.00 | +0.25 | +0.01 dB |

音が出ている区間だけで見ても、いちばん大きい差が **0.33dB**（bend）。

ドラムと効果音は、まだ native では鳴らさず firmware に回している（だから 0.00）。

#### まだ足りないもの

* **ドラム**（バンク 127/126）。音色の記録の引き方が違う（`xg/voices.h` の kit）
* **コントローラ**。音量・パン・ベンドなどが動くと、いまは firmware に回って
  そのぶん CPU が回る。ミキサのレジスタを自分で作れば止めたままにできる
* **スロットの取り合い**。firmware 側と 2 つの割り当てが同居しているので、
  64 声を使い切る曲では衝突しうる

### 6.14 ドラムとコントローラ

#### ドラム

打楽器は「音色」ではなく**音ごと**に中身が違うので、`(バンク, プログラム, 鍵)` を鍵にして
**1 打ごとに写し取る**。同じ音を何度も叩くので、数小節で打楽器のほとんどが native になる。

* ドラムのパートかどうかは、XG の**パートモード**（`08 pp 07`。0 が普通、1 以上がドラム）で見る。
  「音色の記録が引けない＝ドラム」では、音色を選び終える前の旋律パートまで拾ってしまった
* 強さは減衰（`0x09`）を足し算でずらすだけで合う（6.5 と同じ理屈）
* 写し取りの窓は**鍵が鳴ってから 5ms**。ここを長くすると、その間ほかの音色が写し取りを
  始められず、ドラムの多い曲で旋律がいつまでも native にならなかった

#### コントローラ

DAW の自動演奏でつまみが動くたびに SH-2 が起きるのでは意味が無いので、
**実機がどのレジスタを書くか**を `nativeplay --ccwatch` で見て、同じものを自分で書く。

| MIDI | レジスタ | 実機のやっていること |
|---|---|---|
| CC7（音量）・CC11（表現） | `0x09` の下位バイト | 減衰を足す（0.1875dB 目盛り） |
| CC10（パン） | `0x32`（上が左・下が右） | 中央で両側 -3dB の **cos 則**。128 点すべて 0.1875dB 以内で合う |
| ピッチベンド | `0x11` | セントに直して足す。`(bend-8192)*幅*100/8192` を 0 の側へ切り捨て、さらに `*1024/1200` |
| CC64（ダンパー） | — | 離しを待たせるだけなので、こちらで持てる |

* 減衰の曲線は `0x1E6798`（level→減衰、0.375dB 目盛り）を `cc-1` で引いて 2 倍。
  実測との差は **cc≥8 で 0.375dB 以内**、いちばん外れる cc=10 で 0.75dB
* **写し取ったときのつまみの位置**（`08 pp 0B` 音量・`+0x7E` 表現・`08 pp 0E` パン）を
  voice_cal に一緒に覚えて、そこからの**差ぶん**だけ動かす。だから写し取った音そのものは必ず合う
* CC は firmware にも渡す（次の写し取りを同じ位置で鳴らしてほしいので）が、
  回す時間は 2ms でよい。ピッチベンドは**渡さない**（そのパートを firmware が鳴らしている間だけ渡す）
* firmware を止める直前に、パートの音量・表現・パンをワーク RAM から取り直す。
  SysEx やパネルで変えられても追い付く

#### 速さ（30 秒ぶんの書き出し、3 回の最良。Ryzen 7 9700X）

| 曲 | 既定 | `--native-engine` | 比 |
|---|---|---|---|
| piano | 4.10 秒 | 1.41 秒 | **2.91 倍** |
| dense（16 パート・60 音） | 4.34 秒 | 1.72 秒 | **2.52 倍** |
| つまみを 201 回動かす曲 | 4.06 秒 | 1.58 秒 | **2.57 倍** |

つまみを動かし続けても 2.5 倍が保てる。ここを firmware に投げていた頃は、
CC 1 つにつき 20ms 走らせていたので、自動演奏の多い曲ほど遅かった。

#### 音（試験の 7 曲、既定の道と比べた大きさの差）

| piano | chord | dense | drums | effects | bend | lofi |
|---|---|---|---|---|---|---|
| +0.06 | +0.14 | -0.29 | -0.00 | +0.00 | +0.25 | +0.02 dB |

### 6.15 多段サンプルの段ごとの音量（波形の記録の先頭のバイト）

`nativeplay --attsweep` を足した。鍵 12-108 を 1 つずつ firmware に鳴らさせて、
`0x09` に入る減衰を式の値と並べる。GrandPno で**合わない鍵が 61/64、最大 1.50dB** だった。

原因は**波形の記録の先頭のバイト**。`read_wave` が読んでいなかったが、これが
**その段ぶんの減衰**（0.375dB 目盛り）だった。

| 鍵 | 波形の[0] | 実機の減衰 | 直す前の式 |
|---|---|---|---|
| 53-55 | 0 | 30 | 30 |
| **56-58** | **5** | **40** | **32** |
| 59-61 | 1 | 32 / 30 | 32 |
| 62- | 0 | 28 | 30 |

ピアノは鍵 56-58 だけ別の段（波形）で、そこが 1.5dB 大きい。段の切り替わりで
音量が飛ぶのは、多段サンプルの音色ではごく普通のこと。

直したあとの合わない鍵（強さ 100、鍵 12-108）:

| 音色 | 直す前 | 直したあと |
|---|---|---|
| 0 GrandPno | 61 / 64、1.50dB | 31 / 64、**0.38dB** |
| 24 Nylon Gt | — | **0 / 64、0.00dB** |
| 48 Strings | — | 16 / 64、0.38dB |
| 56 Trumpet | — | **0 / 64、0.00dB** |
| 73 Flute | — | 17 / 64、0.75dB |

残る差はすべて**減衰の表の段の境目**（`level_from_att` が同じ減衰になる目盛りの
真ん中を返すため）。鍵の曲線の倍率は 1・2・3 を試して **2 が最良**だった。

### 6.16 鳴らす**時刻**を実機に合わせる（効きが大きかった）

大きさ（dB）は合っているのに、波形を引き算すると全然合っていない曲があった。
原因は**時刻**。

* firmware は MIDI を受けてから **74 サンプル（1.68ms）**後に鳴らす
  （`nativeplay --ccwatch` が測る）。native はその場で鳴らしていた
* MIDI は 1 バイト 10 ビット・31250 baud なので **1 バイト 14.1 サンプル**かかる。
  和音のように何音も続けて来ると、あとの音ほど遅れて鳴る

そこで native の鍵・CC・ベンドを**待ち行列**に入れ、
「その口が最後のバイトを受け終える時刻 ＋ 32 サンプル」に実行するようにした。
firmware に回す音は待たせない（そちらは実機の道をそのまま通るので）。

波形の残差（既定の道との引き算。時間合わせののち）:

| 曲 | 直す前 | 直したあと |
|---|---|---|
| chord | -2.8dB（72%） | **-26.0dB（5.0%）** |
| lofi | -1.3dB（86%） | **-27.6dB（4.2%）** |
| drums | -2.2dB（78%） | -8.0dB（40%） |
| effects | -63.9dB | -63.9dB |
| piano | -21.6dB | -21.6dB |

`drums` を 100ms ごとに見ると、**ほとんどの窓が -40〜-66dB** で、
native で鳴らした打楽器の当たった瞬間だけ -3〜-14dB になる。
`dense`（60 音同時）はまだ合わない。64 声を firmware と native で分け合うので、
どの音を捨てるかが実機と違うためと見ている（6.9 の宿題）。

### 6.17 要素の粗調と離調（byte17・byte18）

パッドや重ねの音色が **3dB 大きい**（Warm Pad +3.17、Square Lead +2.88dB）のが直った。

* **byte18 はセント単位の離調**（64 が中央）。重ねの音色は 2 つの層をここで
  ±5 セントずらしている。入れないと層がぴったり重なり、うなりが消えて
  電力が 2 倍（＝+3dB）になる
* **byte17 は半音単位の粗調**（64 が中央）。dense のチャンネル 15（Crystal）の
  要素 1 は byte17=83 で、**19 半音**上げていた。ここを入れないと音程ごと違う

どちらも `pitch_reg` の `cents_extra` に足すだけ。実機の `0x11` とぴったり合う。

| | 直す前 | 直したあと |
|---|---|---|
| Warm Pad(89) | +3.17dB | **+0.38dB** |
| Square Lead(81) | +2.88dB | **+0.16dB** |
| dense ch15 | +2.76dB | **+0.25dB** |
| バンク 0 の 128 音色 | 平均 1.05dB / 残差 -15.3dB | **平均 0.56dB / 残差 -21.3dB** |

同じ波形を鳴らす要素が 2 つあるとき、両方が同じ写し取りを掴まないように
`match_cal` に「もう使った」印を付けた。

### 6.18 フィルタの包絡線も写し取る

firmware は**フィルタをソフトで動かしている**（1 音につき 10ms ごとに
`0x00`・`0x01`・`0x04` を書き直す。GrandPno の 1 音で 66 回）。

そこで、写し取った音が鳴っている 1 秒間、その書き直しを**時刻つきで覚えて**、
あとの音でも同じ時刻に同じ値を書くようにした（`voice_cal::filter_env`）。
録りながらその場で写し取りに足すので、写し取り中に鳴り始めた音にも間に合う。

**LFO（`0x05`・`0x0a`）も同じ**だった。ビブラートの「かかり始めるまでの間」と
深さの増やし方は firmware がソフトでやっている（dense のチャンネル 6 では
鍵を押した 136ms 後から `0x0a` の下位が 0→6→12→17… と増えていく）。
これを入れて、そのパートの残差が **-0.3dB → -5.9dB** になった。

### 6.19 要素を遅らせて鳴らす（byte72）

MusicBox（音色 10）は**2 つ目の要素を 37ms 遅らせて**鳴らしていた。
写し取りの窓が 5ms だったので 2 つ目を取り逃がし、こちらは同時に鳴らしていた。

* 遅らせる段は要素の **byte72**。実測（`--trace-swp` の 0x20e の間隔）:

| byte72 | 遅れ | 式 `441 * 2^(n-1) - 130` |
|---|---|---|
| 1 | 311 サンプル（7.1ms） | 311 |
| 2 | 752〜753（17.1ms） | 752 |
| 3 | 1634（37.1ms） | 1634 |

* 写し取りの窓も「**要素がそろうまで待つ**（最大 62ms）、そろったら 5ms で切り上げ」に直した

| | 直す前 | 直したあと |
|---|---|---|
| 10 MusicBox | -2.01dB | **-0.23dB** |
| 37 SlapBass2 | -5.59dB | **+0.13dB** |
| 50 SynStr1 | 残差 +1.8dB | 残差 **-5.4dB** |
| 60 FrenchHorn | 残差 +1.2dB | 残差 **-3.9dB** |

`SMU2000_NATIVE_ENGINE=1 build/blocktime.exe <rom> <midi> 512 6 3 <台数>`。
Ryzen 7 9700X・512 フレーム・スレーブは別糸。

**実曲（still_more_fighting_lead）**

* `render <rom> <midi> <wav> --native-engine`
* `gui.exe <rom> --native-engine` / `live.exe <rom> --native-engine`

### 6.21 SH-2 を回している理由の内訳

`render --native-engine` が、演奏中に firmware を回した理由を出すようにした。

```
native の口: 演奏中に firmware を回したのは 5.0%
  内訳: firmware の音 0.4% / SysEx 1.7% / 写し取り 0.0% / MIDI の受け取り 0.0% / そのほか 3.0%
```

これで分かったこと:

* **「溜まっている間は回す」が一番重かった**。渡した MIDI は 1 バイト 14 サンプル
  かけて線を流れ、それを待つために実時間の 2 割を SH-2 に持っていかれていた。
  メッセージごとに置く待ちで足りるので、この仕掛けはやめた
* **SysEx は中身で見分ける**。`43 1n 4C hh` の `hh` が 00（システム）・02（エフェクト）・
  03（インサーション）のときだけ 0.5 秒回す。パートの設定（08 pp xx）は 5ms でよい。
  MEG のプログラムを書き直す SysEx を途中で止めると音が出なくなるので、ここは慎重に
* **音色の指定は 10ms**。ワーク RAM に入るのは 30 サンプル（0.68ms）で済むが
  （`nativeplay --ccwatch`）、firmware の中の下ごしらえはもっとかかる。
  5ms に詰めたら piano の残差が -59dB から -53dB に落ちたので 10ms にした
* **ベンド幅はワーク RAM から読む**（パートの塊 +0x23。64 が 0 半音）。
  RPN で設定されても SysEx で設定されても追いつく
* **フィルタの包絡線を流す `tick` は「つぎの段の時刻」まで何もしない**。
  毎サンプル 64 スロット見ていると、SH-2 を止めた意味が薄れるくらい重かった

### 6.22 写し取りを取っておく（`voicecache.h`）

写し取りの中身は (ROM) が同じなら毎回同じなので、ファイルに残せば
**2 回目からは 1 音目も native で鳴らせる**。DAW に何枚も挿したときも、
2 枚目からは写し取りをやり直さない。

* 置き場は `<設定>/S-MU2000/voicecal/<鍵>.bin`。鍵はプログラム ROM と波形 ROM から
* 中身は写し取ったレジスタ・素の音量・写したときのつまみの位置・フィルタと LFO の段
* **利用者の ROM から起こした値なので、配らない**（bootcache と同じ扱い）
* **既定では使わない。** 写し取りにはパートのエフェクト経路（素通しの量・
  インサーションの掛かり方）が入っているので、**別の曲で取った写しを使うと
  その曲の音にならない**。実際 `lofi` をほかの曲の写しで鳴らすと **3.85dB** 違い、
  波形の残差も -30.1dB から -7.7dB に落ちた
* 同じ曲を何度も鳴らすとき・同じ設定で何枚も挿すときだけ効く。
  `render --voicecache` / plugin.ini の `voicecache=1` / `SMU2000_VOICECACHE=1`
* 同じ曲で 2 回目を鳴らすと、dense は **firmware を回したのが 36.0% → 5.1%**、
  鍵は **native 48 / firmware 0**。大きさの差もむしろ縮む（-0.46dB → **-0.23dB**）

still_more_fighting_lead を 30 秒書き出したとき、**firmware に鳴らさせる音が 1 つも
無くなった**（`鍵: native 20 / firmware 0`）。

### 6.23 残っている「SH-2 が要る所」

`render --native-engine` の内訳で、まだ回している所はこれだけになった。

| 理由 | still_more_fighting（30 秒） | なぜ要るか |
|---|---|---|
| SysEx | 1.7% | XG On は全部を組み直すので 0.5 秒回す。エフェクトの種類を変える SysEx も同じ |
| 知らない CC | 2.5% | **CC1（モジュレーション）は firmware がソフトで揺れを増やしている**。
5ms に詰めたら bend の残差が -35.8dB から -14dB に落ちた |
| firmware の音 | 0.4% | 写し取りの 1 音目。voicecache があれば 0 になる |
| 音色の指定 | わずか | ワーク RAM に入るのは 0.68ms だが、下ごしらえに 20ms かかる |
| 合計 | **4.7%（写しがあれば 4.2%）** | |

`replay_note` が渡すたびに一律 20ms 回していたのをやめ、呼ぶ側が要るぶんだけ
置くようにした。これが曲の出だしの重さの正体だった。

### 6.24 モジュレーション（CC1）

**native で鳴らしている音には、こちらが持っていない CC はいっさい効かない。**
firmware は CC を受け取っても、自分のスロットにしか書かないからだ。
いちばん効くのがモジュレーション（ビブラート）だったので入れた。

* CC1 → レジスタ `0x0a` の**下位バイト（LFO の深さ）**に足す
* 深さは **10 段（0, 9, 17, 26, 35, 43, 52, 60, 72, 84）**で、
  **音色によらない**（GrandPno・Strings・SawLead の 3 つで同じ）。
  切り替わる CC の値は 13, 26, 39, 52, 64, 77, 90, 103, 116
* 写し取ったときの CC1（パートの塊 +0x7D）を `cal_mod` に覚えて、そこからの差ぶんで動かす
* 包絡線の段（6.18）で `0x0a` を書き直すときも、同じだけ足す

モジュレーションを上げ下げする曲での波形の残差:

| 音色 | 入れる前 | 入れたあと |
|---|---|---|
| 48 Strings | -0.4dB（95%） | **-16.2dB（15%）** |
| 73 Flute | -2.9dB（72%） | **-13.4dB（21%）** |
| 0 GrandPno | -9.1dB（35%） | **-26.5dB（4.7%）** |

CC1 だけは firmware にも長く（20ms）渡す。firmware が鳴らしている音のぶんは
firmware がソフトで揺れを増やしていくので、短くすると bend の残差が
-35.8dB から -15.6dB に落ちた。

### 6.25 エフェクトの送り（CC91 リバーブ・CC93 コーラス）

これも native の音には効いていなかった。`nativeplay --ccwatch` で見ると:

* **リバーブ（CC91）は `0x33` の下位バイト**、**コーラス（CC93）は `0x34` の上位バイト**。
  `0x32`-`0x37` は 1 つで 2 本ぶんの送りを持っている（`0x32` は左右の素通し）
* 減衰は **16 ＋ level→減衰の表**（`0x1E6798` を cc-1 で引く）。**音色によらない**
  （GrandPno・Strings・Flute で同じ）
* 写し取ったときの送り（パートの塊 +0x13 リバーブ・+0x12 コーラス）を
  `cal_rev` / `cal_cho` に覚えて、そこからの差ぶんで動かす。
  写し取ったときに切れていた（0xff）送りは差が取れないので、下駄 16 を使う

送りを上げ下げする曲での波形の残差:

| | 入れる前 | 入れたあと |
|---|---|---|
| CC91 GrandPno | -9dB 相当 | **-26.5dB** |
| CC91 Strings | | **-22.2dB** |
| CC93 GrandPno | -11.2dB | **-24.7dB** |
| CC93 Strings | -4.8dB | **-23.1dB** |

### 6.26 明るさ（CC74）と共振（CC71）

`nativeplay --ccfilter` を足した。CC を振るたびに鳴らし直して、**包絡線が動く前**の
`0x00`・`0x04` を拾う（持ったまま振ると、フィルタの包絡線の動きと混ざって読めない）。

* **CC74（明るさ）→ `0x00` の下 12bit（切る高さ）**。`16 × (値 - 64)` でまっすぐ動き、
  **1984 で頭打ち**。音色によらない
* **CC71（共振）→ `0x04` の上 5bit**。**2 きざみで 1 段**（64 まで 0、67 で 1、127 で 31）
* 写し取ったときの値はパートの塊の **+0x18（明るさ）・+0x19（共振）**から読む
  （XG の 08 pp 18 / 19 そのまま。+0x1A が EG アタック、+0x1C が EG リリース）

CC を振る曲での波形の残差:

| | 入れる前 | 入れたあと |
|---|---|---|
| CC74 GrandPno | -5.5dB（53%） | **-38.4dB（1.2%）** |
| CC74 Strings | -9.8dB（32%） | **-21.6dB（8.3%）** |
| CC71 Strings | -16.8dB（15%） | **-21.4dB（8.6%）** |

`0x01`（フィルタのもう 1 つの係数）は切る高さと一緒に動くが、その式はまだ。
写し取った値のままなので、切る高さを大きくずらしたときだけわずかに違う。

### 6.27 SysEx のあと何秒回せばいいか（実測）

`nativeplay --ccwatch` が、SysEx を渡してから **SWP30 を触り終わるまで**を測る。

| SysEx | 触り終わるまで |
|---|---|
| XG On（`43 1n 4C 00 00 7E 00`） | **224ms** |
| リバーブの種類（`02 01 00`） | **168ms** |
| インサーションの種類（`03 0n 00`） | **176ms** |

500ms 回していたのを **300ms** に詰めた。still_more_fighting_lead の出だし 6 秒が
11.9% → **8.6%**、30 秒が 2.5% → **1.9%**。
`bend` の残差はむしろ良くなった（-35.8dB → **-50.7dB**）。

#### いま SH-2 を回している理由（still_more_fighting_lead）

| | 6 秒 | 30 秒 |
|---|---|---|
| firmware の音（写し取りの 1 音目） | 2.0% | 0.2% |
| SysEx（XG On） | 5.0% | 1.4% |
| そのほか（音色の指定・知らない CC） | 1.3% | 0.3% |
| **合計** | **8.6%** | **1.9%** |

写し取りを取ってあれば（6.22）、1 行目も 0 になる。

### 6.28 鍵の追従は**鍵 60 が支点**（波形の基準鍵ではない）

`nativeplay --sweep 128` が、写し取りを使わずに式だけで作ったレジスタを
firmware と突き合わせる。音程（`0x11`）が 16/128 で合っていなかった。

合わないのは**鍵の追従が 100 でない音色**（記録の byte19 が 1 なら 50、2 なら 20）。

| 音色 | 基準鍵 | ずれ |
|---|---|---|
| 115 Woodblock（追従 50） | 75 | -749 セント |
| 116 TaikoDrum（追従 50） | 94 | -1700 セント |

どちらも **50 × (60 - 基準鍵)** でぴったり。つまり firmware は

```
セント = (鍵 - 60) * 追従 + (60 - 基準鍵) * 100 + 波形の微調 + 要素のずらし
```

と計算している。追従が 100 のときは今までの式と同じになるので気づかなかった。

* 合わない音程 **16 → 1**（残り 1 つは prog 31 で、波形の形式のビットも違う）
* バンク 0 の 128 音色: 大きさの差 平均 0.56 → **0.49dB**、
  波形の残差 -21.3 → **-23.6dB**

#### 試したが入れなかったもの: 強さの帯ごとの写し取り

フィルタの切る高さは強さで大きく動く（GrandPno で 368 目盛り＝4 分の 1 オクターブ）。
写し取りを「音色 × 強さの帯（4 段）」で持てば、その音色の強さごとの明るさが合う。
やってみたが、**残差は -15.2dB から -16.3dB にしかならなかった**のに
firmware に鳴らさせる音が 4 倍になるので、入れないことにした。

### 6.29 試したが入れなかったもの（同じ道を二度通らないために）

#### SysEx のあと「SWP30 を触らなくなるまで」回す

固定の 300ms（6.27）ではなく、firmware が SWP30 を触るたびに待ちを伸ばす作り。
`still_more_fighting_lead` の出だし 6 秒が 8.6% → **4.1%** まで落ちたが、
**`effects` の残差が -63.9dB から -3.4dB に壊れた**。エフェクトの種類を変える
SysEx（MEG のプログラムを 1 万件以上書き直す）の途中に 60ms 以上の隙があって、
そこで止めてしまうため。伸ばす時間を 62ms にしても直らなかったので戻した。

**ここで分かったこと**: 声のスロットの `0x38`-`0x3f`（MEG の戻りのミキサ）と
`0x0e`・`0x0f` は、**鳴っていなくても毎サンプル書き直されている**。
「firmware が働いているか」を書き込みで測るときは、この 3 つを除かないと
永久に止まらない。

#### 残差（波形の引き算）はピッチに厳しすぎる

`dense` のチャンネル 13 は、要素 1 の音程が実機と **1 目盛り（1.2 セント）**しか
違わないのに、波形の残差は 93% になる。3 秒の音では 1 周期ぶん位相がずれるからで、
**耳には分からない差**。オクターブごとの帯で比べると ±3dB に収まる。

音を比べるときは、残差だけでなく**大きさ（rms）と帯ごとの中身**も見ること。

#### 強さの帯ごとの写し取り

6.28 の末尾に書いたとおり、効果が小さいわりに firmware に鳴らさせる音が 4 倍になる。

### 6.30 さばけない CC が来たパートは firmware に任せる

native で鳴らしている音には、こちらが持っていない CC は**何も起きない**。
黙って無視すると「ポルタメントが掛からない」「EG の設定が効かない」音になる。
そこで、**音に効く「知らない CC」が既定から外れている間は、そのパートの音を
firmware に鳴らしてもらう**ようにした（正しさを取って、そのぶん重くする）。

| CC | 既定 |
|---|---|
| 5 ポルタメントの速さ / 65 入切 / 84 コントロール | 0 |
| 72 EG リリース / 73 EG アタック / 75 EG ディケイ | 64 |
| 94 バリエーション送り | 0 |
| アフタータッチ（チャンネル・ポリ） | — |

既定に戻れば印も下りて、また native で鳴らす。

* `lofi` の残差が **-30.1dB → -38.6dB**（そのぶん firmware は 32.7% → 50.1%）
* CC73 を振る曲は、振り始めたところから firmware に移る
* `still_more_fighting_lead` は これらを使わないので 1.9% のまま

### 6.31 波形は「粗調で移した鍵」で選ぶ

6.28 で残った最後の 1 件（音色 31 GtHarmonics、鍵 84）が解けた。

実機の音程は `0x7c3e`（下 14bit で -962）。こちらは `0x3b27`（-1241）。
波形の組 78 を見ると、

| | 基準鍵 | 上限鍵 | 形式 |
|---|---|---|---|
| [0] | 69 | 63 | 圧縮 |
| [1] | 83 | **74** | 圧縮 |
| [2] | 87 | 100 | 8bit |

こちらは「上限鍵 ≧ 鍵」で [2] を選ぶ。ところが **[1] の基準鍵 83・微調 -28 で
計算すると実機の -962 にぴったり合う**。この要素は byte17=52、つまり
**12 半音下げて鳴らす**ので、`84 - 12 = 72` → 上限鍵 74 の [1] が選ばれていた。

つまり**波形は「粗調で移した鍵」で選び、音程は元の鍵で計算する**。

* 音程の不一致 **1 → 0**。波形の番地（`0x16`・`0x17`）の不一致も消えた
* バンク 0 の 128 音色: 大きさの差 平均 0.49 → **0.48dB**、
  波形の残差 -23.6 → **-23.9dB**

これで `--sweep 128` の音程・波形まわりは**全部一致**になった。
残るのはフィルタ（`0x00`・`0x01`・`0x04`）と音量（`0x09`）と `0x0b`・`0x10` で、
どれも写し取りで埋めている所。

### 6.32 firmware に回した音が 7 サンプル遅れる（直せないぶん）

SawLead（音色 81）の**写し取りの 1 音目**（firmware が鳴らす音）が、既定の道と
波形で合わない。レジスタを 1 つずつ突き合わせたら**全部同じ**で、違うのは
**鳴らし始めが 7 サンプル（0.16ms）遅い**ことだけだった。

原因は **MIDI の線の時計が CPU のサイクルで進む**こと。SH-2 を止めている間は
線のビットも止まるので、渡したバイトがそのぶん遅れて届く。線のビットだけ
先に進めても、受ける側（SCI）の時計も CPU で動いているので意味が無い。

* 効くのは **firmware に回した音だけ**（その音色の 1 音目）。ずれは 1 バイトぶん
  （14 サンプル＝0.3ms）以内で、耳には分からない
* ただし**離調した 2 層の音色**（SawLead など）では、うなりの位相が変わるので
  波形の残差は 100% 近くになる。大きさは ±0.4dB で合っている

### 6.33 フィルタの強さ依存は、測ったら耳に響かなかった

写し取りは 1 つの強さで取るので、**その音色のほかの強さでの明るさ**は合っていない。
実機を測ると確かに動く（`nativeplay --cutsweep`、鍵 60）:

| 音色 | 表の値 | 強さ 1 | 強さ 61 | 強さ 121 |
|---|---|---|---|---|
| 0 GrandPno | 1243 | +80 | +160 | +432 |
| 48 Strings | 1475 | +160 | +384 | +572（2047 で頭打ち） |

**音色ごとに形が違う**（深さだけの違いではない）ので、式は起こせていない。

ただし**耳に響く差ではなかった**。強さ 10〜127 を振る曲で、オクターブごとの
帯を比べると **ほとんど ±0.6dB、いちばん外れて +2.3dB**。切る高さの目盛りは
周波数に対してかなり細かいので、170 目盛りずれても中身はあまり変わらない。

強さの帯ごとに写し取る案（6.28 の末尾）も、この理由で効かなかった。
**式が要るとすれば、それは「正しさ」のためで、音のためではない。**

### 6.34 音色は自分で引く（firmware のワーク RAM を待たない）

これまでは「どの音色か」を **firmware がワーク RAM（パートの塊 +0xF8）に
書いてくれるのを待って**読んでいた。これが最後に残った**作りの上での**
エミュレータ頼みだった（速さではなく、そもそも分からない）。

`xg::voice_rom::lookup`（firmware の `0x134AA8` と同じ手順）で自分で引けるので、
バンクとプログラムをパートごとに覚えて、そこから記録を出すようにした。

* `nativeplay --list` に突き合わせを足して確かめた。
  **旋律系のバンク（0,0 / 8,0 / 32,0 / 64,0 / 0,1 / 0,2）の 640 音色で食い違い 0**
* ドラムのバンク（126・127）は `lookup` が 0 を返す。そこは MSB で見分けて
  ドラムの道（鍵ごとの写し取り）へ回す
* 引けなかったときは、これまでどおりワーク RAM を読む

音色の指定は firmware にも渡す（写し取りの 1 音目を鳴らしてもらうため）。
渡す時間を 5ms に詰めると piano の残差が -58dB から -53dB に落ちたので、
**20ms のまま**にした。firmware の中の下ごしらえは RAM に書くより長くかかる。

### 6.35 64 声の分け合い

`render --native-engine` が「いちばん多いときに使ったスロット」を出すようにした。

| 曲 | こちらが使ったスロット |
|---|---|
| dense（16 パート・60 音） | **36 / 64** |
| chord | 5 |
| still_more_fighting_lead | 2 |

firmware は写し取りの 1 音目だけを鳴らすので、同時に使うのはせいぜい数声。
dense でも 36 ＋ 数声なので、いまのところぶつかっていない。

それでも**下の 8 スロットは firmware のために空けて**おくことにした
（こちらは 63 番から下へ、firmware は 0 番から上へ使う）。
こちらが使えるのは 56 声になるが、dense でも 36 なので足りる。

### 6.36 残ったレジスタは、写し取りで埋まっていた（確かめた）

`--sweep 128`（写し取りを使わず式だけで作る道）で合わないのは
`0x00`・`0x01`・`0x04`・`0x09`・`0x0b`・`0x10` だけになった。
これらが**鳴らすときに問題になるか**を、実機の書き込みを追って確かめた。

| レジスタ | 鍵・強さで動くか | 鳴らすときの扱い |
|---|---|---|
| `0x0b` | **動かない**（GrandPno は鍵・強さを変えても 0x7f00 のまま） | 写し取りでそのまま |
| `0x10` | **動かない**（同じく 0x4000 のまま） | 写し取りでそのまま |
| `0x01` | 音の間に 0xffff → 0xdcff → 0xb6ff と動く | **包絡線の写し取り**（6.18）で再現 |
| `0x04` | CC71 で動く | CC71 を入れた（6.26） |
| `0x09` | 鍵・強さで動く | 式で出す（6.5・6.15） |
| `0x00` | 鍵ではほぼ動かない。強さで動くが**帯で ±2dB**（6.33） | 写し取り＋包絡線＋CC74 |

つまり **`--sweep` の不一致は「式が無い」というだけで、鳴らすときには埋まっている**。
式を起こす値は「写し取りをやめて firmware なしで鳴らす」ときに初めて要る。

### 6.37 いまの姿（2026-09-18 の終わり）

| | |
|---|---|
| SH-2 を回す割合（実曲 30 秒） | **1.9%**（SysEx 1.4 / 写し取り 0.2 / そのほか 0.3） |
| 30 秒の書き出し | dense 4.35→**1.87 秒**、実曲 4.09→**1.45 秒**、piano 4.07→**1.58 秒** |

| 波形の残差 | piano -58.3 / effects -63.9 / bend -50.7 / lofi -38.6 / chord -26.6dB |

### 6.38 写し取りに「パートの経路」の印を付けた

6.22 の写し取りのファイルは、別の曲で取った写しを使うと音が変わった
（`lofi` で 3.85dB）。原因は、写し取りにパートの**エフェクト経路**が
入っていること。そこで写し取りに**経路の印**（`voice_cal::cal_ctx`）を
一緒に入れて、合わないときは写し取りをやり直すようにした。

印に混ぜるもの（どれも写し取った `0x20`-`0x2b`・`0x32`-`0x37` に効く）:

* 素通しの量（`08 pp 11`）・バリエーション送り（`14`）
* パートの EQ（塊の +0x6A-0x6F）
* インサーション 4 つの掛かり先（`03 0n 0C`）

これで**別の曲の写しが混ざっても安全**になった。`lofi` は写しがあっても
-38.6dB のまま（前は -7.7dB に落ちていた）。

#### それでも既定は「使わない」

写しがあると**その音色の 1 音目も native で鳴る**ので、
「1 音目だけは実機そのまま」という強みが無くなる。

| | 写し無し | 写しあり |
|---|---|---|
| piano の残差 | **-58.3dB** | -21.5dB |
| bend の残差 | **-50.7dB** | +1.9dB（大きさは +0.29dB） |
| dense で SH-2 を回す割合 | 35.7% | **5.1%**（鍵は native 48 / firmware 0） |

**速さを取りたいときだけ**入れる（`render --voicecache` /
plugin.ini の `voicecache=1` / `SMU2000_VOICECACHE=1`）。

### 6.39 速さの数字は、起動を除いて測ること

`render` は既定で毎回 firmware を起動する（音の時間で 8 秒、実時間で **0.55 秒**）。
30 秒の書き出しが 1.45 秒だったうちの**3 分の 1 以上が起動**だった。
DAW ではプラグインが `bootcache` で起動を飛ばすので、そちらが実態に近い。

`render --bootcache` で測り直すと（Ryzen 7 9700X・30 秒ぶん）:

| 曲 | 既定 | native の口 | ＋写し取り | ＋軽量エフェクト |
|---|---|---|---|---|
| still_more_fighting_lead | 3.70 秒 | **1.03 秒（3.59 倍）** | 1.02 秒 | 0.89 秒（4.2 倍） |
| dense（16 パート・60 音） | 3.93 秒 | **1.43 秒（2.75 倍）** | 1.20 秒（3.3 倍） | 0.97 秒（4.1 倍） |

起動を含めて測ると 2.8 倍・2.3 倍に見えるが、**DAW で効くのは上の数字**。

### 6.9 次の一手（どこから続けるか）

残っているのは 3 つだけ。どれも「どの番地を読めばいいか」までは分かっている。

**(1) 音色ごとの音量の下駄**（`0x09` の残り）

* `att = 表[level] + ram[声+120] + ram[声+119]` の `+119` は解けた（6.5）
* `+120` は `0x1275C4` が足し込む。その呼び元は `0x1274AE`・`0x127524`・`0x127548` の 3 か所で、
  どれも「記録のバイトで **16bit の利得表 `0x1E5554`** を引いて、`(値 * 利得) >> 16` を重ねる」形
* **利得表は 64 段**（索引 0-63 で 1 → 0xFA18。1 段およそ 1.5dB）。64 から先は別の表
* 実測では下駄は 5〜19 の幅。`0x127496` の前後（どのバイトを何回掛けるか）を読めば決まるはず

**(2) フィルタの鍵・強さの倍率**（`0x00` の残り）

* 表（`0x1E5B58`）と索引（`byte37`）は分かった。倍率の形は `0x127FA4` で
  `k = 0x80 + ((depth - 64) * (鍵 - 100) >> 4)`、`索引 = (索引 * k) >> 7`
* ただし**この形だけでは 67 音色中 7 つしか説明できない**。強さのぶんが同じ形では無いか、
  パートの値が別に入る。`0x127FA4` の全体（`0x127FA4`-`0x12801C`）をもう一度、
  分岐込みで読み直すのが早い

**(3) 音量つまみ（CC7・CC11）の曲線そのもの**

* いまは `0x1E6798` を `cc-1` で引いて 2 倍している。実測とは cc≥8 で 0.375dB 以内だが、
  **実機はこれとは別の曲線を使っている**（ROM をバイト列で探しても見つからない＝計算している）
* 鍵を押したときの減衰は `ram[0x43E96A] + ram[0x4226A8]` を `0x12DF40` が書く。
  その `0x43E96A` を作るのは `0x1274B2` で、そこへ来る値は
  `0x127594`（`level = max(0, 127 - byte75)` を 16bit 利得表 `0x1E5554` と `0x14523C` で割る）と
  `0x1275C4`（`減衰 += 2 * 値` の足し込み）を通る。**つまみのぶんがどこで入るかはまだ**
* `0x43E96A` を指す所は `0x1274DC`・`0x127608`・`0x12862C`・`0x12AC94`・`0x12DFD0`・`0x12E428`。
  残り 3 か所を読めば決まるはず

**(4) `0x0b` と `0x10`**

* `0x10` は `byte83 << 8` で 96% 合う。`0x0b` は 20 通りの値を取り、どのバイトでも決まらない
* どちらも MAME の対応表で「?」になっている所なので、**まず何のレジスタかを調べる**ほうが早い
  （`swp30.cpp` の読み書きをたどる）

**測り方**: `build/nativeplay.exe <rom> nul -b 0,0,0 --sweep 128` が一致率を出す。
1 つ式を入れたら毎回これを回す。

0 と 1 は**調べもの**で、失敗しても今の作りには何の影響も無い。2 以降は新しい口
（`mu2000::set_native_engine(true)` のような切り替え）の中だけで動かし、既定は firmware のまま。

### 6.40 CC73（EG アタック）の式を追って、**式より写し取り直しが正しい**と分かった

まず実機のコードを読んで式は解けた。`0x127288` がそのものずばりで、

```
R3 = ram[パートの塊 + 26]          // CC73 の値
R4 = R3 - 64
if (R4 <= 0) { R4 = R5 - (R4 >> 1); if (R4 > 63) R4 = 63; }   // SHAR（算術）
else         { R4 = min(rom[0x1E54A4 + R4], R5); }
if (R4 == 0) R4 = 4;
R4 <<= 1; if (R4 == 126) R4 = 0xFF;
→ レジスタ 0x06 の上位 = ATTACK_TAB[R4 & 0x7f]
```

`R5` は**要素の byte73**（CC73=64 のとき `R4 = R5` になり、実測の
GrandPno 47・Strings 43・Trumpet 48 と一致）。ROM 表 `0x1E54A4`（64 バイト）も
実測と 1 つ違わず合った（cc65→41・cc81→21・cc97→13・cc113→6 …）。

**それでも式は入れなかった。** `nativeplay --ccreg 73` で見ると、CC73 は
`0x06` だけでなく **`0x00`（切る高さ）・`0x07`・`0x0b`（フィルタの包絡線）も
動かす**多目標のつまみだった。`0x06` だけ式にすると、かえって実機から離れる。

#### 代わりに: つまみが動いたら**写し取り直す**

6.38 の「経路の印」（`cal_ctx`）に、EG のつまみを混ぜるだけでよかった。

| つまみ | パートの塊 | 中身 |
|---|---|---|
| CC73 | +0x1A | EG アタック |
| CC75 | +0x1B | EG ディケイ |
| CC72 | +0x1C | EG リリース |
| CC94 | （RAM に出ない） | バリエーション送り。**口の側で覚える** |

対応するバイトは `nativeplay --ccbyte <番号>` で探した（その CC を振って、
動いたワーク RAM のバイトを出す）。CC94 だけはワーク RAM に出てこない
（掛かり先がパートに繋がっていないと firmware が何も書かない）ので、
`part_cc::var` として口の側で覚えて印に混ぜている。

覚え先の鍵も変えた。**音色の記録（下 32bit）＋経路の印（上 32bit）**にしたので、
つまみを行き来しても取り直しは経路ごとに 1 度で済む（`native_driver::cal_key`）。
天井は 512 件（`CAL_MAX`。DAW がつまみを掃いても膨らまない。溢れたぶんは
firmware が鳴らす）。

これで **CC72・CC73・CC75・CC94 はパートを firmware に任せきりにしなくなった**。

#### 測った結果（新しい試験 `egcc`）

Strings で 6 音、間で CC73→20・CC73→100・CC75→20・CC72→100 と振り、
最後に既定へ戻す。

* 写し取りは **5 回**（経路が 5 通り）。最後の 1 音は最初の写しを使い回して native
* 波形の残差（時刻を合わせたあと）: 1 音目 -69.9dB / 2 -38.9 / 3 -25.0 /
  4 -52.6 / 5 -55.1 / **6 音目（native）-53.0dB**

`lofi`（CC94 を使う）で SH-2 を回す割合が **57.1% → 28.6%**、
`effects` は写し取りが動くようになった（前は 0 回）。
実曲（still_more_fighting_lead 30 秒）は **1.9% のまま**で悪化なし。

#### 残っているもの

ポルタメント（CC5 +0x61・CC65 +0x60・CC84 +0xD3）とアフタータッチは、
**1 音の写し取りでは足りない**（音が鳴っている間ずっと音程を動かす）ので、
今も firmware に任せている。ここは式を起こすしかない。

### 6.41 ポルタメントの滑り方を測った（表は `0x1E6698`）

`nativeplay --porta <CC5>` と `--portasweep <刻み>` で、ポルタメントを入れて
低い鍵から高い鍵へ移ったときの**音程レジスタ `0x11`** を時刻つきで録った。

分かったこと:

* 滑りは**レジスタの値の上で線形**（＝対数周波数で線形。セントで一定速度）
* firmware は **10 ms ごと**に一定量を足す
* 新しい音は**前の音の音程で鳴り始める**（鍵を押した時点で `0x11` は前の音の値）
* 速さは ROM の表 **`0x1E6698`**（16bit・128 語・CC5 で直に引く）

目盛りが 2 通りある:

| CC5 | 読み方 | 例 |
|---|---|---|
| 24-127 | **表 ÷ 128 = 10ms あたりのセント** | CC5=64 → 2560/128 = **20 セント** |
| 0-23 | **表 × 2 = 10ms あたりのセント**（256 倍の目盛り） | CC5=16 → 120×2 = **240 セント** |

CC5=127 は 16/128 = 0.125 セント/10ms（1 オクターブに 16 分）、
CC5=3 は 600×2 = 1200 セント/10ms（1 オクターブが 1 刻み）。
測った 28 点は全部この式と 1% 以内で合った（速い側は刻みが数回しかないので
測りの精度がそこまで）。

レジスタの単位に直すと `刻み = セント × 1024 / 1200`。

これで**ポルタメントを native で鳴らす材料はそろった**（あとは前の鍵を
パートごとに覚えて、スロットごとに滑らせるだけ）。

### 6.42 ポルタメントを native で鳴らせるようにした

6.41 で分かった式をそのまま入れた（`nv::porta_step`・`slot_use::glide`）。

* スロットは「**まだ残っている音程のずれ**」（セント × 256）を持つ
* 鳴らし始めは `ずれ = (前の鍵 - いまの鍵) * 追従 * 256`
* `tick()` が 10ms ごとに `porta_step(ROM, CC5)` だけ 0 へ寄せ、
  そのたびに `0x11` を書き直す（ベンドと要素の離調も入れて作る）
* 刻みは**世界共通の格子**（`clock / 441`）に乗せる。firmware の 10ms タイマも
  世界共通なので、同時に始まった音の滑りがそろう

つまみは CC5（速さ）・CC65（入切）・CC84（滑り出す鍵を指定。1 度で使い切る）。
どれも `handles_cc` に入れて、firmware 任せの印（`unknown_bit`）から外した。

#### 落とし穴: firmware が鳴らした音の鍵も覚えること

最初に作ったとき、**写し取りの 1 音目のつぎの音だけが滑らなかった**。
写し取りの音は firmware が鳴らすので口の `note_on` を通らず、
「最後に押した鍵」が入らないままだった。`note_fw(part, note)` を足して、
firmware に回した音でも鍵を覚えるようにした。

#### 測った結果（新しい試験 `porta`）

Square Lead で 5 音、ポルタメントを入れて上下に滑らせ、途中で速さを変え、
最後に切る。**5 音のうち 4 音が native**（前はパートごと firmware 任せで 0 音）。

| | 値 |
|---|---|
| 全体の大きさ | **-0.28 dB** |
| オクターブ帯ごと | **全部 ±1.1 dB 以内** |
| 音程（自己相関で追った） | 測りの刻み 1 つぶん以内で一致 |

**波形の残差は使えない**。滑り終わったあとも位相が揃わない（firmware の 10ms
タイマの位相が分からないので、滑る道が最大 10ms ぶんずれる）。周波数が同じで
位相だけ違う 2 つの音の残差は +3dB になるので、ここは大きさと帯で見る。

これで**パートまるごと firmware に任せる場面はアフタータッチだけ**になった。

### 6.43 つまみの割り当てを見て、firmware に任せる場面を絞った

アフタータッチは「native では何も起きないから」という理由で、
**そのパートを丸ごと firmware に任せて**いた。しかも一度でも触れた強さの
メッセージが来たら印が立ちっぱなしで、曲の最後まで戻らなかった。

#### 測ったら、既定では本当に何も起きない

`nativeplay --at`（音を伸ばしたまま触れた強さを **0 と 127 で行き来**させ、
スロットのレジスタとパートの塊を見る）で 3 音色を調べた:

* 動くのは**パートの塊の +0x7F**（受け取った値そのもの）だけ
* SWP30 のレジスタは 1 つも動かない
  （最初 `0x00` が動いて見えたのは、フィルタの包絡線がひとりでに
   減っていただけ。行き来させたら値は単調に減り続けた）

#### 割り当ての場所を `--xgmap` で突き止めた

XG のパート parameter（`08 pp rr`）を 0x00 から 0x7F まで 1 つずつ書いて、
**ワーク RAM のどのバイトに入るか**と書く前の値（＝既定）を出す道具を足した。

| XG | ワーク RAM | 中身 |
|---|---|---|
| `08 pp 00`-`28` | +0x00-+0x28（そのまま） | 音量・パン・EG・**MW**（+0x1D-22）・**ベンド**（+0x23-28） |
| `08 pp 29`-`40` | （受け取りスイッチ。0/1 しか取らない） | |
| `08 pp 41`-`77` | **+（XG − 7）** | 音律（+0x3A-45）以降 |
| `08 pp 4D`-`52` | **+0x46-+0x4B** | **アフタータッチ（CAT）** |
| `08 pp 53`-`58` | +0x4C-+0x51 | 鍵ごとのアフタータッチ（PAT） |
| `08 pp 59` / `5A`-`5F` | +0x52 / +0x53-+0x58 | **AC1** の CC 番号（既定 16）と割り当て |
| `08 pp 60` / `61`-`66` | +0x59 / +0x5A-+0x5F | **AC2** の CC 番号（既定 17）と割り当て |

どれも**6 つ組**（音程・フィルタ・音量・LFO の PMOD/FMOD/AMOD）で、
既定は `64,64,64,0,0,0`（モジュレーションだけ `64,64,64,10,0,0`）。

`08 pp 4E`（CAT フィルタ）を 0 にしてから同じ掃引をすると、
今度は `0x00`・`0x09`・`0x11` がはっきり動いた。**割り当てが既定から
外れているときだけ効く**と裏が取れた。

#### 直したこと

* アフタータッチ（`0xD0`）・鍵ごとのアフタータッチ（`0xA0`）は、
  **CAT / PAT の割り当てが既定のあいだは firmware に任せない**
* **AC1・AC2 を見るようにした**。割り当てられた CC 番号が来て、かつ
  割り当てが既定から外れていれば任せる。前は黙って無視していた（抜け穴）
* **モジュレーション（CC1）とベンド**も、割り当てが既定から外れていたら任せる。
  こちらの式は既定の割り当てを前提にしているので、そこは合わない

#### 測った結果（新しい試験 `at`）

GrandPno で 5 音。途中で触れた強さを送り（既定なので効かない）、
そのあと `08 pp 4E` で CAT フィルタを既定から外して、また触れる。

| 音 | どこで鳴ったか | 残差 |
|---|---|---|
| 1（写し取り） | firmware | -67.1dB |
| 2 | **native** | -48.2dB |
| 3（触れた強さあり・既定） | **native** | -31.0dB |
| 4（CAT を外したあと） | firmware | -9.1dB（ほぼ無音の音） |
| 5 | firmware | -49.1dB |

前は 3 音目から最後まで firmware だった。

### 6.44 残った SH-2 は「曲の頭の 0.55 秒」だった／SysEx の待ちを実測で絞った

まず、残っている割合が**曲の長さに比例しない**ことを確かめた。
still_more_fighting_lead を長さだけ変えて鳴らすと:

| 長さ | SH-2 を回した割合 | 実時間に直すと |
|---|---|---|
| 15 秒 | 3.7% | 0.56 秒 |
| 30 秒 | 1.9% | 0.57 秒 |
| 60 秒 | 0.9% | 0.54 秒 |
| 120 秒 | 0.4% | 0.48 秒 |

倍にすると割合がきれいに半分になる。**残りは曲の頭の約 0.55 秒ぶん**
（XG リセットの SysEx・音色の指定・音色ごとの 1 音目）で、鳴らし続けても増えない。

#### SysEx の待ちが粗すぎた

それまでの判定は「XG のパラメータチェンジで hh が 00（システム）・02（エフェクト）・
03（インサーション）なら 300ms 待つ」。つまり**値を変えるだけのものまで 300ms**
待っていた。新しい口 `nativeplay --sxsettle hh,mm,ll,dd` で
「SWP30 を触り終わるまで」を測ると、はっきり 2 群に分かれる:

| SysEx | 何をする | 触り終わるまで |
|---|---|---|
| `00 00 7E` | XG システムオン | **212 ms** |
| `02 01 00` | リバーブの種類 | **176 ms** |
| `02 01 20` | コーラスの種類 | **177 ms** |
| `02 01 40` | バリエーションの種類 | **182 ms** |
| `03 0n 00` | インサーションの種類 | **182 ms** |
| `00 00 04` | マスターボリューム | 0 ms |
| `02 01 02` | リバーブのパラメータ | 3.9 ms |
| `02 01 22` | コーラスのパラメータ | 0 ms |
| `03 0n 02` | インサーションのパラメータ | 3.1 ms |
| `08 pp xx` | パートの設定 | 0 ms |

**重いのは MEG のプログラムを書き直すものだけ**。そこで判定を
「システムオン／全パラメータリセット、エフェクト 3 種の**種類**、
インサーションの**種類**」に絞った（種類は 2 バイトなので下位の番地も含める）。

判定に使うバイトが 1 つ増えるので、XG のパラメータチェンジ（`43 1n 4C`）と
分かったときだけ 6 バイト目まで待つ。**そうでないもの（GM システムオンなど）は
5 バイトのままで重い扱い**——ここを一律 6 バイトにすると、5 バイトで終わる
GM システムオンが判定に届かず軽く扱われてしまう。

#### 測った結果（新しい試験 `sxparam`）

Strings で短い音を 12 個並べ、鳴らしている間ずっとリバーブの**パラメータ**を
振る（種類は頭で 1 回だけ）。

| | 直す前 | 直したあと |
|---|---|---|
| SysEx で回した割合 | **63.1%** | **9.2%** |
| 合計 | 67.7% | **19.7%** |
| 大きさの差 | -0.18 dB | **-0.18 dB** |
| オクターブ帯ごと | +7.29 +0.09 -0.12 -0.18 -0.25 -0.24 -0.22 -0.13 dB | **同じ（0.02dB 以内）** |

**音は 1 つも変わっていない**（残差も帯ごとの差も直す前と同一）。
`effects` と `lofi` は種類を変える曲なので、絞りすぎればここで落ちる。

#### ついでに見つけた、まだ直していないもの

この曲では native の口の **62-125Hz の帯が +7.3dB 高い**（直す前から同じ）。
鍵 60 以上の Strings なのでその帯に基音は無く、リバーブの尾のはず。
`effects` は通っているので、この曲に固有の何か。別途調べる。

### 6.45 窓から入切できるようにした（聞き比べ用）

音がどこまで実機に近づいたかは**耳で確かめるしかない**ので、軽量エフェクトと
同じように、鳴らしたまま入切できるようにした。

* 窓を右クリック →「firmware を走らせずに鳴らす（速い・まだ音が違う）」
* **F4** でも同じ
* いま入っているかは、メニューの印で分かる

切り替えは軽量エフェクトと同じ道（`engine::want_native_engine` に頼んで、
音声の糸が `fill()` の頭で `set_native_engine()` を呼ぶ）。

#### 切るときは、こちらで鳴らしている音を離すこと

切ったあと firmware はそのスロットを知らないので、**離さないと鳴りっぱなしに
なる**。`native_driver::silence()` を足して、`set_native_engine(0)` の頭で呼ぶ。
ぶつ切りではなく、離しの速さで鳴り終わる。

確かめ方も足した。`render --native-engine --native-off <秒>` でその時刻に切れる
（窓の F4 と同じ道を通る）。`chord` を 2.0 秒で切ると:

| 秒 | 切らない | 2.0 秒で切る |
|---|---|---|
| 1.60 | 1737 | 1737 |
| 2.00 | 1579 | 1018 |
| 2.80 | 1729 | 635 |
| 3.60 | 950 | 247 |
| 4.40 | 27 | 6 |
| 5.60 | 0.5 | **0.0** |

素直に減衰して 0 になる。窓でも、鳴らしながら F4 を 8 回（入切 4 往復）
叩いても落ちないことを確かめた。

**入れ直すと写し取りは白紙に戻る**（`set_native_engine(1)` が
`native_driver::reset()` を呼ぶ）ので、その音色の 1 音目はまた firmware が鳴らす。
往復するたびに写し取り直すが、聞き比べには困らない。

### 6.46 写し取りが「別の音のスロット」を掴んでいた

利用者から「切り替えてしばらく鳴らしていると、急に EG が壊れる。
ストリングスの立ち上がりが極端に遅くなったり、逆にエレピのリリースが
無くなってミュート奏法のような響きになる」という報告。**一度壊れると
その音色にずっと残る**のが手がかりだった。

原因は `native_learn_finish` のここ:

```cpp
if (idx < 0)
    idx = int(cals.size()) < nel ? int(cals.size()) : 0;   // ← 黙って採用していた
```

写し取りは「どの要素か」を**そのスロットが鳴らしている波形の番地**で見分ける。
番地がその音色のどの要素とも合わない＝**別の音のスロットを掴んでいる**のに、
そのまま採用していた。掴んだ音の `0x06`/`0x07`/`0x08`（包絡線）がその音色の
写し取りとして覚えられ、以後その音色の全部の音に焼き付く。症状と一致する。

**直し方**: 波形の番地が取れているのにどの要素とも合わなければ、その写しを
捨てる（次の音でやり直す）。全部捨てれば写し取り自体が残らないので、
その音色はまた firmware が鳴らす。番地が取れていないときは今まで通り。

#### なぜ `render` では出なかったか: MIDI の配り方

`render` は MIDI を**サンプル単位**で配るが、**窓もプラグインも音声のブロック
単位**でまとめて配る。同じ時刻に音が重なると、firmware がどのスロットを
どの順で鳴らすかが変わり、写し取りが関係ないスロットを掴む。

そこで `render --midi-block <フレーム>` を足した。そのブロックぶんの MIDI を
ブロックの頭でまとめて渡す＝窓やプラグインと同じ並びになる。

```
dense.mid  サンプル単位   … 掴み違い 0 回
dense.mid  --midi-block 512 … **掴み違い 1 回**（前はこれが焼き付いていた）
```

数えられるように `render --native-engine` の表示にも足した:

* `写し取りで別の音のスロットを掴んで捨てた N 回`
* `写し取りが汚れた N 回`（窓の中で別の音が同じスロットに鳴り始めた）
* `スロットの奪い合い N 回`（firmware がこちらの鳴っているスロットを取った）

後ろ 2 つは今のところ 0 のままだが、置いておけば次に出たときすぐ分かる。

#### まだ分かっていないこと

上の直しで**掴み違いは起きなくなった**が、利用者の症状そのものは手元の
曲では再現できていない。`dense` は声が多いと波形の残差が 0dB（＝位相が
まるで合わない）まで落ちるが、大きさは ±1dB で追従していて、
試験（大きさで見る）では通ってしまう。**多声のときの 1 音ずつの確かめ方**が
足りていないので、そこが次の宿題。

### 6.47 利用者の曲で追い込んだ（液晶が固まる／音色が壊れる）

利用者から 3 つの手がかりが出た。どれも同じ根に繋がっていた。

1. 切り替えてしばらく鳴らすと急に EG が壊れる（立ち上がりが極端に遅い、
   リリースが無い）。**一度壊れるとその音色にずっと残る**
2. **液晶が途中で固まり、前面のボタンも一切効かない**
3. アプリを開き直しても**曲の頭から**壊れている（状態が残っている？）

#### 2 の答え: firmware を完全に止めていた

`run_sample` は `m_fw_hold == 0` なら CPU を回さない。全部 native で鳴る曲では
MIDI が来たときしか回らないので、**firmware が丸ごと止まる**。液晶を描くのも
ボタンを読むのも firmware なので、どちらも死ぬ。

100ms ごとに 5ms だけ回す（`KEEPALIVE_EVERY` / `KEEPALIVE_RUN`）ようにした。
実曲で SH-2 は 7% → 11.7%（そのうち 4.6% がこのぶん）。

#### 3 の答え: NVRAM がワーク RAM 丸ごとだった

`nvram` は 0x400000-0x43ffff の 256KB をそのまま残し、次の起動で戻す。
firmware の**生きた状態も一緒に残る**。native の口で firmware を飢えさせた
まま窓を閉じると、中途半端な状態が保存されて次回に持ち越される。

`engine::settle_for_save()` を足して、残す前に native を切り（鳴っている音は
離される）0.5 秒回してから保存するようにした。すでに壊れた NVRAM は
`gui --factory` で捨てられる。

#### 1 の答え: 包絡線を写し取りから取っていなかった

利用者の曲（DQ2_121.mid）を借りて、**firmware と native の SWP30 書き込みを
1 つずつ突き合わせた**。そのための道具も足した:

* `render --trace-swp` に **native の書き込みも残す**（`N ` 付きの行）。
  それまでは firmware のバス書き込みしか記録に残らず、比べようがなかった
* `render --midi-block <フレーム>` で、窓やプラグインと同じ
  「ブロック単位で MIDI をまとめて配る」並びを作れる
* 突き合わせは scratchpad の `trdiff.py`（鍵を押した時刻で対応づけ、
  その直前 20ms に書かれたレジスタだけを比べる）

出てきた 1 位が **`0x06`（立ち上がり）で 56 音中 56 回**。
`firmware=417e` に対し `native=387e` ＝ **こちらの方がずっと遅い**。

原因は `build_note` の「写し取りで上書きするレジスタ」の一覧に
**`0x06` が入っていなかった**こと。包絡線は常に ROM の式だけで決まっていて、
**パート側の EG 設定（CC73 など）が native の音に一切効いていなかった**。
この曲は CC73 を 16 パート全部に送っている（55・60・64・65）。

立ち上がりは鍵でも強さでも変わらないと測ってあるので
（`nativeplay --egwatch` を鍵 36-96・強さ 1-127 で確認）、写し取った値を
そのまま使える。`0x07`・`0x08`（減衰）は鍵で変わるのでまだ入れられない。

#### ついでに出た 2 位: firmware が裏でつまみを書き替えていた

次に多いのが `0x33`（リバーブ送り）で 46 回。調べると、曲は CC91=40 を
1 回送るだけなのに、**パートの塊 +0x13 は 33 や 31 になっていた**。
音色を替えると firmware がつまみを音色の既定値で上書きするため。

`sync_cc()` は「こちらが触っていない（-1）ものだけ RAM から拾う」だったので、
**firmware が裏で書き替えたことに気づけなかった**。前に見た RAM の値を
覚えておき、**RAM が動いていたら firmware が書き替えたとみなして取り込む**
形に変えた（`take_ram`）。

#### いまの残り（利用者の曲・12 秒・55 音で）

| レジスタ | 前 | いま | 何 |
|---|---|---|---|
| `0x06` | 56 | **10** | 立ち上がり（残りは写し取り前の音） |
| `0x33` | 46 | **7** | リバーブ送り（残りは同期が効く前） |
| `0x09` | 16 | 16 | 音量の減衰 |
| `0x00` | 15 | 15 | フィルタの切る高さ |
| `0x08` | 10 | 10 | 減衰 2 |

**差分器の落とし穴**: 最初は「そのスロットに過去書かれた値」を持ち越して
比べていたので、`0x21`・`0x23`・`0x2b`・`0x30`・`0x31` が大量に違って見えた。
記録を追うと **firmware はこれらを一度も書かない**（0x20-0x2b は偶数番だけ）。
鍵の直前 20ms に書かれたものだけを比べるようにして消えた。

### 6.48 フィルタの強さ依存の式を実機のコードから起こした（`0x127FA4`）

6.6 から「実機はフィルタの切る高さに鍵と強さの倍率を掛けるが、その係数が
分からない」と書いてあった所。`tools/dump/sh2dis.py` で読んだら出た。

```
127FA4  ; 入口: R6 = 切る高さの目盛り（0-127）、R5 = 鍵の情報、R4 = パートの塊
127FB2  R1 = [R4+44]
127FB4  R6 += R1[11] - 64            ; つまみのぶん（0-127 に丸める）
...
127FE0  R1 = R1[22]                  ; **強さ→フィルタの深さ**（ドラムは [R4+48]）
127FE4  R0 = R5[3]                   ; 強さ（velocity）
127FEC  R4 = R1 - 64
127FEE  R0 = R0 - 100                ; **基準は強さ 100**
127FF0  R4 = R4 * R0
127FF4  R4 >>= 4                     ; 符号つき（SHAR ×4）
127FFC  R4 += 128
127FFE  R6 = R6 * R4                 ; 16bit 符号つき
128008  負なら 0
12800A  R6 = (R6 * 2) >> 8           ; ＝ / 128
128016  127 で頭打ち
```

つまり

```
倍率   = 128 + ((深さ - 64) * (強さ - 100)) >> 4      （符号つき・0 の側へ）
目盛り = clamp(元の目盛り * 倍率 / 128, 0, 127)
```

**強さ 100 が基準**（そこで倍率がちょうど 128 ＝ 等倍）。写し取りの
`cal_vel` の既定が 100 なのと辻褄が合う。

#### 測った形（`nativeplay --egwatch` に 0x00 を足した）

GrandPno・鍵 60 でレジスタ `0x00` の下 12bit:

| 強さ | 1 | 16 | 32 | 48 | 64 | 80 | 96 | 112 | 127 |
|---|---|---|---|---|---|---|---|---|---|
| 値 | 0x52b | 0x53b | 0x54b | 0x56b | 0x57b | 0x5ab | 0x5cb | 0x64b | 0x69b |

鍵は **60 を底にした V 字**（vel 64 で 鍵 24→0x5bb、48→0x59b、60→0x57b、
72→0x59b、96→0x5db、108→0x61b）。Strings は開き切りで飽和して動かない。

#### まだ入れていない理由

鍵を押した時点の `0x00` は **`16k + 11` の形**で、`CUTOFF_TAB` を直に引いた値
ではない（表の値は端数がばらばら）。つまりここはフィルタの包絡線の出発値で、
上の式で出した「目盛り」がさらに一段加工されている。その一段が分かるまでは
写し取り（その音の値をそのまま使う）の方が近い。

いまは `0x00` を写し取りから取っているので、**写し取ったときの強さでは合う**。
利用者の曲の残りの食い違い 15 回は、写し取りと違う強さで鳴らした音。

### 6.49 いまどこまで合っているか（利用者の曲で測った）

一晩かけて、利用者の曲（DQ2_121.mid）で firmware と native の書き込みを
突き合わせて詰めた。12 秒・時刻で対応づいた 55 音での食い違い:

| レジスタ | はじめ | いま | 何をしたか |
|---|---|---|---|
| `0x06` 立ち上がり | 56 | **0** | 写し取りから取るようにした（6.47） |
| `0x33` 送り | 46 | **7** | firmware の裏の書き替えを取り込むようにした（6.47） |
| `0x09` 音量 | 16 | **6** | （まだ） |
| `0x00` フィルタ | 15 | **5** | （まだ） |
| `0x08` 減衰 | 10 | **0** | 写し取り時のずれを覚えて足す（6.50 の下） |

合計 143 → 18。

#### 音でどうなったか

| 区間 | 直す前 | いま |
|---|---|---|
| 4-12 秒 | -1.27 dB | **-0.96 dB** |
| 12-24 秒 | -1.52 dB | **-1.16 dB** |
| 24-36 秒 | -0.89 dB | **-0.63 dB** |
| 36-48 秒 | -0.10 dB | -0.07 dB |
| 48-59 秒 | +0.01 dB | -0.01 dB |
| 全体 | -0.60 dB | **-0.45 dB** |

#### 残っているものの正体（オクターブ帯で切り分けた）

* **12-24 秒**: 125Hz-16kHz が**一様に -1dB**。帯で偏らないので**音量**の問題。
  `0x09` の食い違いは「こちらが 2 段（0.75dB）静か」で、桁が合う
* **48-59 秒**: 中域は ±0.05dB で合っているのに **8-16kHz が +4.9dB**。
  こちらのフィルタが開きすぎている（差分でも `firmware=1747` に対し
  `native=1767` ＝ こちらの方が開いている）

つまり残りは **音量（`0x09`）とフィルタ（`0x00`）の 2 つ**にきれいに分かれた。

#### 音量（`0x09`）について分かっていること

* 実機が `0x09` を書く所は `0x12E484`。
  `0x09 = (上位そのまま) | clamp255(値 + ram[0x4226A8])`。
  この「全体に効く下駄」は測ったら **0** だったので、原因ではない
* CC7 → `0x09` の対応を実測した（`nativeplay --ccreg 7`）。
  こちらの式 `2 * LEVEL_TAB[cc-1]` は **64 点中 22 点でずれる**（ずれは ±2）
* **ROM 全体を探しても、この対応を出す表は無い**（`scratchpad/findtab.py`
  で 4MB 全部を係数 1/2/4・添字 cc/cc-1 で総当たり）。表引きではなく計算らしい
* つまり音量と表現を掛けてから一度に対数に直している可能性がある。
  そこは `0x12E484` の呼び出し元（`0x127B60` などに番地が置いてある）を
  読むしかない

#### フィルタ（`0x00`）について分かっていること

6.48 の式（`倍率 = 128 + ((深さ-64)*(強さ-100))>>4`）まで出ている。
残っているのは「その目盛りから鍵を押した時点の `0x00`（`16k+11` の形）を
どう作るか」と、「深さ」がどの塊の byte22 か。

#### 気をつけること: firmware は同じ値を何度も書き直す

記録の書き込み回数は firmware 6965 回に対し native 1513 回（`0x00`）だが、
**中身は同じ値の書き直し**（鍵から 8-126ms の間に数回、値は変わらない）。
回数の差は音の差ではない。ここを勘違いすると「包絡線を再生し切れていない」
と誤診する。

### 6.50 音量の式を実機と並べる道具と、そこで分かったこと

`nativeplay --levelcheck` を足した。鍵 60・強さ 100 で 1 音鳴らして校正し
（写し取りと同じ手順）、そのあと鍵と強さを振って**実機が `0x09` に入れる値と
こちらの式を並べる**。内訳（曲線・段の音量・目盛り）も一緒に出る。

#### 直したこと: 鍵の曲線の倍率が 2 倍になっていた

Strings で 24 点中 16 点がずれていた。ずれは**強さに依らず鍵だけ**で決まり、
鍵 60 から離れるほど +2・+4 と増える。`LEVEL_CURVE_MUL` はコメントに
「実測では 1 倍」と書いてあるのに **2** だった。1 にすると:

| | 直す前 | いま |
|---|---|---|
| ずれた点 | 16 / 24 | **8 / 24** |
| 鍵 60-96 | ずれる | **完全に一致** |

利用者の曲（172 秒）でいちばん悪い区間が -1.23dB → **-1.00dB**、
48-64 秒は **±0.00dB** になった。

#### 強さの曲線は元から完全に合っていた

念のため測ったら、`2 * LEVEL_TAB[VEL_CURVE[強さ]]` は **17 点すべて一致**。
ここは疑わなくてよい。

#### 残っている鍵 36・48 の +2：足し算の形では説明できない

残るずれは鍵 60 より下だけ。Strings は `byte60 == 0xFF` なので ROM の曲線
（番号 668）をちゃんと引いている。曲線は 鍵36→0、48→-1、60→-2、72→-3、
84→-5、96→-7。

いまの式は `目盛り = 素の音量 + 曲線` として `LEVEL_TAB[0x80 + 目盛り]` を引く。
**この形では全部の鍵が合う「素の音量」が存在しない**（0-127 を総当たりして
解なし）。実機が必要とするのは 曲線0→11、-1→11、-2→12、-3→12、-5→13、-7→14
だが、表の平ら（77-79→11、73-76→12、70-72→13、67-69→14）と噛み合わない。

実機は音量まわりを**線形の値で掛けて `>>7`** する形（6.49 の `0x12A404`）
なので、鍵の曲線も足し算ではなく**掛け算**とみるのが筋。そこが次の宿題。

#### 校正の曖昧さも効いている

`level_from_att` は表を逆に引くとき、同じ減衰になる目盛りが並ぶので
**真ん中**を返している。平らが 3-4 段あるので、実機の本当の目盛りとは
最大 ±2 ずれる。掛け算の形が分かれば、この逆引き自体が要らなくなる。

## 7. 失うもの・気をつけること

* **パネル・LCD・サンプリング・SmartMedia・シーケンサは動かない。** native モードは「音源」で、
  「機械」ではなくなる。DAW で鳴らすぶんには困らないが、窓の LCD は firmware 版でしか出せない
* **「実機の firmware をそのまま走らせている」という強みが、その口では無くなる。**
  音が違ったときに「こちらの写し間違い」が原因になりうる。だから 5. の突き合わせを必ず持つ
* 音色の記録の解釈を間違えると、**特定の音色だけ違う**という形で出る。1635 音色ぶんの回帰が要る
* 実機由来のデータ（ROM）の扱いは今までどおり。native driver は ROM を**読む**だけで、中身は配らない

## 8. 折衷の案

| 案 | 中身 | 効き目 |
|---|---|---|
| A | エフェクトだけ C++（[native-dsp.md](native-dsp.md)。**もうある**） | 1 割 |
| B | 起動のときだけ firmware を走らせ、設定が固まったらレジスタを写し取って以後は native | 曲の途中で音色やコントローラが動かない用途なら有効。動くと破綻する |
| C | 全部 native（この文書） | 半分以下（複数インスタンスに効く） |
| D | firmware を走らせる時間を削る（SH-2 の JIT をさらに詰める） | JIT 済みなので、あと 1〜2 割が上限とみている |

順番としては **A（済み）→ 0 と 1 の調べもの → C の 2 段目**が素直。0 と 1 が終われば、
C に進むかどうかを数字で判断できる（84 バイトの何割が機械的に説明できたか）。

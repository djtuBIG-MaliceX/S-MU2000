# firmware を走らせない線（設計の下書き）

いまの S-MU2000 は、**実機の firmware をそのまま走らせて**、その firmware が SWP30 のレジスタを
叩いて音を出している。この文書は「firmware をやめて、XG の処理そのものを C++ で書く」道の設計。
まだ**作っていない**。何が要るか、どう確かめるか、何を失うかを先に並べておくためのもの。

軽くする話の全体像は [native-dsp.md](native-dsp.md)（エフェクトを C++ にする線）と対になる。

## 1. どこが重いのか（実測）

dense（16 パート・60 音）を鳴らしたときの、1 サンプルあたりの内訳（Ryzen 7 9700X）。

| | 時間 | 割合 |
|---|---|---|
| **SH-2（firmware）を回す** | 2.3µs | 55% |
| SWP30 の声を作る（AWM2＋波形 ROM） | 1.4µs | 33% |
| MEG（エフェクト） | 0.5µs | 12% |

エフェクトを C++ にしても消えるのは 0.5µs で、**いちばん大きいのは firmware**。
やめれば全体が半分以下になり、[goal](todo.md) の「PFM のインスタンスを何枚も同時に」に効く。

## 2. 何を捨てて、何を残すのか

**残すもの: SWP30 の声を作るところ（AWM2）と波形 ROM。** 音色そのものはここで決まるので、
ここを残す限り**音は実機のまま**にできる。native にするのは「レジスタに何を書くか」を決める側だけ。

```
  いま:   MIDI → [SH-2 が firmware を実行] → SWP30 のレジスタ → 音
  この線: MIDI → [C++ で書いた XG の処理]  → SWP30 のレジスタ → 音
                                             ^^^^^^^^^^^^ ここは同じものを使う
```

だから、**正しさの物差しは「レジスタに同じ値を書けたか」**になる。音を比べるより厳密で、
自動で確かめられる（下の 5.）。

## 3. firmware が今やっていること

| やっていること | native 側で要るか |
|---|---|
| MIDI を受けて解く（チャンネルメッセージ・SysEx・RPN/NRPN） | **要る**（src/xg/model.h の表が使える） |
| パートの状態を持つ（音色・音量・パン・送り・フィルタ・EG…64 パート） | **要る**（xg/ram.h と同じ並びを C++ の構造体で） |
| 音色の記録を ROM から引く（バンク・プログラム → 記録） | **要る**（xg/voices.h の lookup がもうある） |
| 記録から SWP30 のスロットのレジスタを組み立てる | **要る。ここが最大の未知**（下の 4.） |
| 声の取り合い（空きスロット探し・古い声を止める） | **要る**（実機と同じ挙動にするのが難しい） |
| ドラムキット（音ごとの音程・音量・パン・EG・NRPN） | **要る** |
| ポルタメント・ダンパ・モノ/ポリ・ベンド・コントローラ | **要る** |
| エフェクトの設定（MEG のプログラムを ROM から積む） | 要らない（C++ のエフェクトに置き換え済み） |
| LCD・パネル・つまみ・レベルメーター | **要らない**（native モードでは機械ではなく音源になる） |
| シーケンサ・サンプリング・SmartMedia・ユーティリティ | **要らない**（要るなら firmware の側で使う） |
| ダンプ要求への返事（SysEx の送り返し） | 当面要らない |

## 4. いちばんの難所: 音色の記録 → レジスタ

音色の記録は ROM の `0x200EE0` から 1635 個並んでいて、形は
「要素の印 1 バイト・1 バイト・名前 10 文字」＋ **要素ごとに 84 バイト**（`xg/voices.h`）。
この 84 バイトの中身はまだ解いていない。**ここを解くのがこの線の 8 割**。

解き方は、firmware に教えてもらうのが早い。

1. 音色を 1 つ選び、1 音だけ鳴らす。`mu2000::set_swp_trace()` で **SWP30 への書き込みを全部記録**する
   （どのスロットの何番のレジスタに何を書いたか。`render --swp-trace`）
2. 同じ音色の 84 バイトを ROM から取り出す
3. 1635 音色 × いくつかの鍵・強さで 1. と 2. を集め、**バイトとレジスタの対応**を機械的に探す
   （そのまま入る／表を引く／鍵や強さで補間する、のどれか）
4. 分かった対応で組み立てたレジスタ列と、firmware が書いた列を突き合わせる

この掃引は既にある道具の延長でできる（`tools/fxsweep`・`voicesweep.py` と同じ作り）。
1 音色あたり数百ミリ秒として、1635 音色 × 3 鍵 × 2 強さで 1 時間ほど。

**記録の量を測った**（`render --trace-swp`、11 秒・1 音）: SWP30 への書き込みは **126,318 件**。
段 0 の実験（下の 6.）で、そのうち **16,956 件（13.4%）だけ**で音が 1 サンプルも違わずに出ることが
分かった。残りの 9 割近くは firmware が同じ値を書き直しているだけで、SWP30 の側でも
`vol_w` が「同じ値なら何もしない」と書いてある通り、鳴りには関わらない。

16,956 件の内訳:

| | 件数 | 何か |
|---|---|---|
| `0x44e`/`0x44f`/`0x48e`/`0x48f` | 11,392 | **MEG のプログラムを積む**（エフェクトの中身。native では丸ごと要らない） |
| スロットのパラメータ（`0x09` 音量 EG、`0x21`-`0x2b`、`0x30`-`0x3d` ほか） | 4,449 | **ここが native driver の作る値**。11 秒で 4,449 件 ＝ **1 秒に 400 件** |
| `0x04e`（内部 RAM の番地）ほか | 1,115 | ワークの読み書き |

つまり **native driver が本当に書かないといけないのは 1 秒に 400 件ほど**。
1 サンプル（44,100 分の 1 秒）あたり 0.01 件で、firmware を回す 2.3µs とは桁がいくつも違う。

**分かっているとっかかり**

* パートの塊の `+0xF8` に、firmware が引いた音色の記録の位置が入っている（`xg/ram.h`）。
  つまりバンク・プログラムの引き方は真似しなくてよく、**記録の中身だけ**が問題
* SWP30 のレジスタの意味は MAME 由来の実装で分かっている（`src/mame/sound/swp30.h`。
  波形の番地・ループ・音量 EG・フィルタ・LFO・パン・送り）
* 「声 1 つ」は 1 要素。要素が 2 つ以上ある音色は、声も 2 つ以上使う（`sounding_voices()` の数え方と同じ）

## 5. 確かめ方（ここが肝）

**レジスタ列の突き合わせ**を回帰試験にする。

```
同じ MIDI を
  (a) firmware 版で流して、SWP30 への書き込み列を記録
  (b) native 版で流して、同じものを記録
→ 2 つの列を比べる（時刻・スロット・番号・値）
```

* 音を鳴らさずに比べられるので速い
* 違いが出たら「どのパラメータの計算が違うか」がそのまま分かる
* 音での比較（`make test` のゴールデン波形）も今までどおり残す。レジスタが合えば波形も合うはず

段階ごとに「何割のレジスタが一致したか」を数字にすれば、進み具合が見える。

## 6. 進め方

| 段 | やること | 終わりの目印 |
|---|---|---|
| 0 | レジスタ列の記録と再生。firmware が書いた列を記録して、SH-2 を止めたまま同じ時刻に流し込む | **済み**（下の 6.1） |
| 1 | 84 バイトの意味を掃引で割り出す（上の 4.） | **途中**（6.2 で波形、6.3 で包絡線の半分） |
| 2 | native driver の骨。MIDI → パート状態 → 音色選び → スロット割り当て → レジスタ | **済み**。音階と和音が鳴り、1 音の写し取りを足すと大きさの差 0.06dB・波形の残差 -25dB（6.8・6.10） |
| 3 | 和音と声の取り合い、複数要素、ドラムキット | dense のような曲でレジスタ列が 99% 一致 |
| 4 | コントローラ（CC・ベンド・ポルタメント・ダンパ・NRPN・RPN） | doc/todo.md の「コントローラの効き方」の試験が native でも通る |
| 5 | PFM（パフォーマンス）と複数インスタンス | PFM の 100 個が鳴り、1 枚あたり 1.5µs 以下 |

### 6.1 段 0 の結果（済み）

`render --trace-swp <file>` で書き込みを記録し、`render --replay-swp <file> --boot <秒>` で
**SH-2 を 1 サイクルも回さずに**、記録したサンプル番号のところで同じ値を SWP30 へ入れ直す。

* 記録は 1 行が「どちらのチップ・レジスタ番号・値・PC・時刻・サンプル番号」。
  サンプル番号で合わせるのが肝で、時刻で合わせると 1 サンプルずれる
  （`run_sample` は 1 サンプルぶんの CPU を回してから SWP30 を進めるので、
  そのサンプルの**頭**で入れ直せば実機と同じ順になる）
* 結果: **966,544 サンプルが 1 つも違わず一致**（差の最大 0）。読み出しは要らない
* 間引きの実験: 「値が変わった書き込みだけ」に絞ると**音が変わった**（最大差 2,471）。
  番地が自動で進むレジスタ（下位 6bit が `0x0e`/`0x0f`。MEG のプログラム・内部 RAM・keyon）は、
  同じ値でも**書くこと自体に意味がある**。それらを残して間引くと、126,318 → 16,956 件で
  **また 1 サンプルも違わず一致**した

**分かったこと**: 音は SWP30 だけで作れる。firmware は「レジスタに何を書くか」を決めているだけで、
その中身は 1 秒に 400 件ほどしかない。段 1（音色の 84 バイト）へ進んでよい。

### 6.2 段 1 の途中経過: 波形の組の引き方が分かった

`build/voicesweep.exe` で「音色を選ぶ → 1 音鳴らす → SWP30 のスロットに書かれた値を全部拾う」を
繰り返し、ROM の 84 バイトと突き合わせた（`tools/voicesweep/`）。

**84 バイトの中の 2 バイト（`elem[2]`・`elem[3]`）が波形の組の番号**だった。
7bit ずつの組で、`set = (elem[2] << 7) | elem[3]`（MIDI 風の詰め方）。そこから 2 段引く。

```
  音色の記録 +12 の 84 バイト
      elem[2],[3]  ->  組の番号（0-502）
                        |
        0x200AF0 の表（16bit を 503 個、終わりは ffff）
                        |  = 波形の並びの中の位置（バイト）
        0x1F55A0 から 16 バイトずつの「波形の記録」
```

**波形の記録（16 バイト）**

| 位置 | 中身 | 行き先 |
|---|---|---|
| +0 | 印（0 が多い。04/16/1f などもある） | ? |
| +1,+2 | もとの音程（16bit。上の桁が鍵、下が細かい調整） | レジスタ `0x11`（音程）の元 |
| +3 | **この記録を使う鍵の上限**（最後の記録が 0x7f） | 鍵で記録を選ぶ |
| +4..+7 | ループ前のサンプル数（32bit） | レジスタ `0x12`/`0x13` |
| +8..+11 | ループの長さ（32bit） | レジスタ `0x14`/`0x15` |
| +12..+15 | 形式＋波形 ROM の番地（32bit） | レジスタ `0x16`/`0x17` |

**確かめ**: 1 要素の音色 128 個 × 鍵 36/60/84（と鍵 0-127 の 1 音色）で、
`0x12`-`0x17` の 3 つの 32bit が **530 組のうち 516 組（97%）で完全に一致**した。
合わないのは鍵をずらして鳴らす音色（組の中で鍵の上限の並びが 1 度 0x7f で終わって、
また始まるものがある＝層が複数）と、ループ前の数だけずれるもの。ここは段 1 の残り。

### 6.3 段 1: 包絡線の作り方

84 バイトが**そのまま**レジスタに入っている所は 1 つも無い。けれど「同じバイトの値には
必ず同じレジスタの値」という見方（`solve.py` の `as_function`）をすると、表を引いているものが見つかる。

| レジスタ | 元 | 形 |
|---|---|---|
| `0x07` の下位（減衰 1 の目標） | byte 77 | **`(0x7f - byte) * 2`**（ぴったり。12 個の値で確かめた） |
| `0x08` の下位（減衰 2 の目標） | byte 78 | **`(0x7f - byte) * 2`**（同じく 10 個） |
| `0x06` の上位（アタックの速さ） | byte 73 | 表を引く。だいたい `2 * byte` で、上のほうが詰まる（`3e`/`3f` が同じ `77`） |
| `0x07`/`0x08` の上位（減衰の速さ） | byte 74 ほか | **鍵で変わる**（下） |

つまり**記録は XG と同じ 0-127 の目盛りで持っていて、レジスタは「減衰の量」に直している**。

**確かめた広さ**: バンク 26 種 × 128 プログラム（3,328 の口）を鳴らして、中身の違う記録 216 個で
上の 4 つが全部成り立った（`build/voicesweep.exe ... picks_big.txt -n 60 -v 100`、30 分ほど）。

**減衰の速さは鍵で変わる**。鍵 36/60/84 で測ると、音色によって増え方が違う。

```
  減衰 1 の速さ ≒ 2 * byte74 + 係数 * (鍵 - その鍵で使う波形のもとの音程)
```

* 「もとの音程」は 6.2 の波形の記録の +1,+2（16bit。上の桁が鍵）。**鍵の区画ごとに違う**ので、
  鍵 36 と 84 では引き算の相手が変わる。だから「鍵 48 個ぶんの増え方」は音色ごとにばらばらに見える
* 67 音色で当てはめると、**49 音色が誤差 1 以内**。40 音色は係数 0（鍵で変わらない）
* 切片は 25 音色で `2 * byte74` ちょうど。残りは ±6 ほどずれる（別のバイトが混ざっている）

**まだ分からないところ**（※音量は 6.5 で解けた）: フィルタ（`0x00`・`0x04`）・LFO（`0x05`・`0x0a`）。
216 個の記録で次を試して、**どれも外れた**（同じところを二度調べないように書いておく）。

* 84 バイトのどれか 1 つで決まるか → 外れ
* 84 バイトのどれか 2 つの組で決まるか → 外れ
* 記録の頭 12 バイト（印・名前）を足しても → 外れ
* 波形の記録（6.2 の 16 バイト）のどれかと組にしても → 外れ
* 2 つのバイトの**和**や**差**で書けるか → 外れ

分かっていること:

* 音量は**全部偶数**で、鍵 60・強さ 100 では 20〜62（22 通り）。減衰の目標と同じ「× 2」の目盛り
* 強さとの関係は**足し算**。強さ 40 と 100 の差が、67 音色のうち 65 音色で 42 ちょうど
* だから `音量 = 2 × (記録から決まる何か + 強さの項 + 鍵の項)` の形
* 1 音色（GrandPno）で鍵を 0-127 まで振ると、音量は**波形の切り替わり目で跳ぶ**。
  区画の中ではゆっくり増える（鍵 72→32、78→34、84→36、92→38）が、
  鍵 56 で 40、59 で 32、62 で 28 と、区画をまたぐたびに段差がある。
  並べ直すと、**ほとんどは鍵そのものの折れ線**だった:
  鍵 0-38 で 32、39-71 で 30、72 から 6 鍵ごとに +2（72→32、78→34、84→36、92→38）。
  途中の鍵 56-58（40）と 62（28）だけ外れるが、これは声の取り合いの写り込みかもしれない。
  つまり「下に平ら・真ん中が谷・上で持ち上がる」形のレベルキースケーリングで、
  曲がり角は鍵 39 と 72。**ここから先は掃引より firmware の中身を読むほうが早い**
  （0x134AA8 のあたりから、音色の記録を読んでレジスタを組み立てる所をたどる）

**強さ（ベロシティ）で動くもの**（GrandPno・鍵 60・強さ 1-127 で測った）

| レジスタ | 動き |
|---|---|
| `0x09` の下の桁（全体の音量） | 強さ 1 で 212、127 で 20（減衰の目盛り。値は全部偶数）。強さ 16 以上は「振幅が強さの 2 乗に比例」とほぼ合う（0.375dB きざみで計算した値の 0.96 倍）。弱い所はそれより浅い＝表か折れ線 |
| `0x00` の下 11bit（フィルタ 1 の主パラメータ） | 強さ 1 で 0x528、127 で 0x688。強さで開く |
| `0x05`（LFO の深さ） | `fa00`/`aa00` を行き来する。強さとは関係なく、掛けるたびに変わる（LFO の位相をばらしている） |
| `0x06`-`0x08`（包絡線の頭・減衰） | 強さでは動かない |

### 6.6.1 鍵の効き方の共通の形

`0x127FD8` のあたりに、鍵で値を増減させる共通の形があった。

```
  depth = ram[音色の塊 +22]            ; 0-127（64 が「効かない」）
  k = 0x80 + (((depth - 64) * (鍵 - 100)) >> 4)
  値 = ((値 * k) * 2 & 0xFFFF) >> 8     ; ＝ (値 * k) >> 7 の 16bit 版
  値が負なら 0、上限で頭打ち
```

「64 が中立、そこからの差を鍵との差に掛ける」という XG のいつもの形。
**基準の鍵は 100**（0x64）で、音量の折れ線（6.3 の曲がり角 39 と 72）とは別の所。

### 6.7 検算

分かった規則を掃引の結果で検算する道具を置いた。段 1 を進めるたびに回せば、

| 波形の番地・ループの長さ（`0x14`-`0x17`） | 1662 | 3 |
| ループ前の数（`0x12`/`0x13`） | 1604 | 61 |

ループ前の数がずれるのは、鍵をずらして鳴らす音色と「ループ位置の微調整」が入るもの。


### 6.4 firmware を読む（ここからが本筋）

掃引だけでは音量・フィルタ・LFO が解けなかったので、**firmware の中身を読む**道具を足した
（`tools/dump/sh2dis.py`。`sh2asm.py` の対になる SH-2 の逆アセンブラ）。

**入口は記録の `pc=`**。`render --trace-swp` の 1 行 1 行に「どの番地の命令が書いたか」が
入っているので、知りたいレジスタを書いている所がすぐ分かる。

```
python -c "…trace.txt を読んで、スロットのレジスタ 0x06-0x09 を書いた pc を数える…"
  → 鍵を押したときに 1 回だけ書く所が pc=0012DEE0（0x06）、0012DF00（0x07）、0012DF1E（0x09）
python tools/dump/sh2dis.py <rom> 0x12dec0 0x90
```

読めたこと。

**包絡線の速さは「RAM の値 × 2 を表で曲げる」**

```
  0x12DEE0:  R7 = ram[0x43E972]          ; 減衰 1 の速さの元（鍵の補正まで入った値）
             R7 = ROM[0x1F4E38 + R7]     ; 表で曲げる
             R2 = ram[0x43E988]          ; 減衰 1 の目標
             レジスタ 0x07 = (R7 << 8) | (R2 << 1)
```

* **アタックの表は ROM の `0x1F4DB8`、減衰の表は `0x1F4E38`**（どちらも 128 バイト）。
  中身はほぼそのままで、上のほう（0x60 から先）だけ詰まる
* 記録の byte73（アタック）・byte74（減衰）は**2 倍してから表を引く**。
  掃引の実測と合う: byte73=0x0a → `表[0x14]` = 0x14、byte73=0x3e → `表[0x7c]` = 0x77
* 目標の `× 2` は `SHLL`（1 ビット左）そのもの。6.3 の `(0x7f - byte) * 2` の正体は、
  **RAM には既に `0x7f - byte` が入っていて、レジスタに入れるときに 2 倍している**というだけ

**音量は足し算**

```
  0x12DF1E:  R4 = ram[0x43E96A] + ram[0x4226A8]   ; 声ごとの減衰 ＋ 全体の減衰
             if (R4 > 0xFF) R4 = 0xFF
             レジスタ 0x09 = R4
```

`0x4226A8` は XG のワーク RAM の中（`xg/ram.h` の並びのすぐ手前）。
`0x43E96A` は**鍵を押すたびに `0x12AC44` で書かれ**、その値は**関数 `0x12A404` の戻り値**。
その関数は `MULS.W` と `>> 7` を何段も重ねる形で、XG のいつもの
「0-127 の掛け算（`(a * b) >> 7`）」を、パート音量（`+0x12F`）・エクスプレッション（`+0x130`）・
強さの効き（`+0x4E`）…と順に掛けている。**段 1 の残りはこの関数を写すこと**で、
掃引より確実で速い。

### 6.5 音量の式（解けた）

`0x12A404` を最後まで読むと、こうなっていた。

```
  level = ram[声+118]                       ; 元（0-127）
  if (level == 0 または 音が無い) level = 0
  else {
      k = ram[音色の塊 +2] + 1 + ram[別の塊 +29]    ; 1..127 に丸める
      level = (level * k) >> 7                     ; XG のいつもの掛け算
      if (level == 0) level = 1
      level = (level * ram[パート +0x12F]) >> 7     ; パート音量
      if (ram[声+126] == 49) …  +0x130 を使う       ; エクスプレッション
      … 強さの効き（パート +0x4E、64 なら素通し）…
      level += パートの補正（+0x122 か、関数 0x12C7FC の戻り）
      level を 0..127 に丸める
  }
  att = 表[0x1E6818 + level] + ram[声+120] + ram[声+119]
  if (att > 127) att = 127
  att = att * 2                              ; ← 必ず偶数になる理由
```

そして

```
  レジスタ 0x09 = min(0xFF, att + ram[0x4226A8])     ; 後ろは全体の減衰
```

**これで 6.3 の実測が全部説明できる**。

| 実測 | 理由 |
|---|---|
| 音量が**必ず偶数** | 最後の `att * 2` |
| 鍵 60・強さ 100 で 20〜62（2 きざみ） | `att` が 10〜31 の範囲に収まっている |
| 強さを変えても**差が一定**（67 音色中 65 で 42） | 強さは `level`（掛け算の側）に効き、表 `0x1E6818` が対数なので**掛け算が足し算に変わる** |
| 1〜2 バイトで書けない | `level` に 5 段の掛け算と足し算が入り、そのあと表を引いてから 2 つのバイトを足すから |

**表 `0x1E6818`**（128 バイト）は「音量 0-127 → 減衰」の対数の曲線で、
`0x00` で 0x7f、`0x7f` で 0x00。`0x40` で 0x10（＝16。1 目盛り 0.375dB として 6dB）。

### 6.6 スロットを組み立てる所（`0x12DE50`-`0x12DF60`）

鍵を押したときに 1 回だけ走る、**スロットのレジスタを全部書く一続きの所**。
中身は「ワーク RAM の 0x43E95C から並ぶ値を、レジスタの形に詰め直す」だけだった。

| レジスタ | 式 | 元 |
|---|---|---|
| `0x00` フィルタ 1 | `0x1000 \| clamp(ram16[0x43E95E])` | 上 4bit の形は**この道では 1 固定**。下は切る高さ |
| `0x01` 素通しの量 | `(ram[0x43E960] << 8) \| 0x80FF` | |
| `0x02` フィルタ 2 | `ram16[0x43E99E] \| 0x8000` | |
| `0x03` フィルタ後の音量 | **`0x5010` の定数** | 掃引の実測と一致 |
| `0x04` フィルタの第 2 | `ram[0x43E95C] << 11` | 上 5bit にそのまま |
| `0x05` LFO の深さ | `(ram[0x43E963] \| 0xFA00) & 0xFF7F` | |
| `0x06`-`0x09` | 6.4・6.5 の通り | |

`clamp` は `0x12E79C`: **形（`ram[0x43E95C]`）が 4 未満のときだけ、切る高さを `0x7C0` で頭打ち**にする。

**スロットの置き場**は ROM の `0x1F4F58` に「スロット番号 → レジスタの先頭番地」が
4 バイトずつ 64 個並んでいる。`R4 = 0x1F4F58 + スロット * 4` を引いてから `+0`・`+2`・… と書く。

つまり **firmware の最後の一歩は詰め替えだけ**で、値そのものは `0x43E95C` から始まるワーク RAM に、
鍵を押す処理のもっと手前で作られている。段 1 の残りは、そこをこの方法（記録の `pc=` →
逆アセンブル）で 1 つずつたどること。**フィルタと LFO がそれ**。

### 6.8 段 2: SH-2 を止めたまま音が出た

`build/nativeplay.exe` を足した。やることは 4 つだけ。

1. firmware で起動して、SWP30 を実機と同じ初期状態にする
2. **CPU を止める**（`set_cpu_enabled(false)`。ここから先、firmware は 1 命令も走らない）
3. 音色の記録から `xg::nv::build_note`（`src/xg/native_voice.h`）でレジスタを組み立て、
   スロットに書いて keyon のマスクと引き金を叩く
4. WAV に書き出す

```
build/nativeplay.exe <rom> out.wav -b 0,0,0 -n 60            # SH-2 なしで 1 音
build/nativeplay.exe <rom> out.wav -b 0,0,0 --song           # SH-2 なしで音階と和音
build/nativeplay.exe <rom> out.wav -b 0,0,0 -n 60 --firmware # 比べる用
build/nativeplay.exe <rom> nul     -b 0,0,0 -n 60 --compare  # レジスタを突き合わせる
build/nativeplay.exe <rom> nul     -b 0,0,0 --sweep 128      # まとめて一致率を出す
```

**`--song` で音階（ド-ド）と和音を鳴らす**。スロットを順に割り当てて keyon し、
離すときは `0x09` に「離せ」の印を書く。出てきた音を測ると

* 8 音の基音が **262 295 331 350 392 441 494 524Hz**（狙いは 261 293 329 349 392 440 493 523）
* 音を離すと 0.2 秒ほどで静かになり、和音のあと完全に 0 まで落ちる

**離すときの値**（`0x09`）は

```
  上位 = 0x80 | ROM[0x1F4E38 + clamp(byte76 + 鍵の補正, 1, 63) * 2]
  下位 = 鳴らしたときと同じ減衰
```

上位のビット 15 が「離せ」の印（`swp30.cpp` の `release_glo_w`）。速さは減衰と同じ表を
**byte76** で引き、鍵の補正も同じだけ乗る。実機が離すときに書く値（GrandPno の鍵 60 で `0xBE1E`）と一致する。

`--compare` は、firmware に同じ音を鳴らさせて**そのとき書かれたレジスタを拾い**、
こちらが組み立てたものと 1 つずつ比べる（段 2 の「レジスタ列が一致」の物差し）。
GrandPno で:

| 鍵 | 一致 | 違い | 違っているもの |
|---|---|---|---|
| 36 | 30 | 2 | `0x00`（フィルタ）・`0x09`（音量の鍵での増減） |
| 60 | **31** | **1** | `0x00` |
| 84 | 29 | 3 | `0x00`・`0x01`・`0x09` |

**式が分かっているものは全部合っている**（波形の番地・ループ・音程・包絡線の目標と速さ・
声の EQ・ミキサ）。残りはフィルタ（`0x00`・`0x01`）と、音量の鍵での増減。

**まとめて測る**（`--sweep 128`。バンク 0 の 128 音色 × 鍵 36/60/84 のうち、
1 要素・1 スロットで鳴ったもの）: レジスタの **87.2% が一致**。合わないものの内訳は

| レジスタ | 合わない割合 | なぜ |
|---|---|---|
| `0x09` 音量 | 100% | 強さと鍵の効き方がまだ（6.5 の式の途中まで） |
| `0x01` 素通しの量 | 100% | **前の値からの傾き**で決まる（状態を持つ）。式ではない |
| `0x00` フィルタ 1 | 85% | 表は分かったが、鍵と強さの倍率がまだ（下） |
| `0x0b`・`0x10` | 36% | 何のレジスタか分かっていない |
| `0x11` 音程 | 19% | 音色ごとの移調が残り |
| `0x04` フィルタ 2 | 14% | `((byte35 >> 1) & 31) << 11`（`0x1280FC`） |
| `0x05` LFO の深さ | 7% | 掛けるたびに位相をばらしている（`fa00`/`aa00`） |
| `0x02` | 3% | `0x8000 \| byte82` |
| `0x0a` LFO | 2% | `0x40 \| byte11` |
| `0x06` アタック | **0%** | 上位も下位もぴったり |

**音の比べ**（GrandPno・鍵 60、firmware に鳴らさせたものと）:

| 帯 | 差 | | 0.1 秒ごとの大きさ |
|---|---|---|---|
| 125Hz | +1.2dB | 実機 | 971 857 797 741 667 591 547 496 450 |
| 250Hz | +0.4dB | SH-2 なし | 872 764 724 684 631 568 529 478 432 |
| 500Hz | -4.5dB | | |
| 1kHz | +8.8dB | | 全体で -0.9dB、減り方はほぼ平行 |
| 2kHz | +4.0dB | | |
| 4kHz | -1.2dB | | |
| 8kHz | +1.7dB | | |

残っている山は 500Hz〜2kHz で、フィルタの鍵・強さの倍率がまだ入っていないぶん。

**音はもう出る**。firmware に鳴らさせた同じ音と比べると、基音（250Hz）は 0.4dB 差、
包絡線の形もほぼ同じ（0.1 秒ごとの大きさが 971→331 対 1117→366）。違うのは高い所で、
1kHz が +14dB・4kHz が +15dB 明るい。**フィルタを開き切りにしている**からで、
上の表の `0x00` がそのまま音に出ている。

#### アタック（`0x06`）

```
  上位 = ROM[0x1F4DB8 + min(byte73, 63) * 2]
  下位 = byte73 が 63（最速）なら 0、そうでなければ 0x7e
```

402 組で**上位も下位も 100% 一致**。パートの「EG アタック」を触ると `byte73` に足されるが
（`0x127054`）、初期値の 64 では何も足さない。

#### LFO（`0x0a`）

```
  上位 = 0x40 | byte11     下位 = 0
```

402 組で例外なし（`0x05` の深さのほうは、掛けるたびに `fa00`/`aa00` を行き来する＝位相をばらしている）。

#### フィルタ（`0x00`）— 途中まで

```
  索引 = byte37（パートのカットオフを触ると ±される）
  索引 = clamp((索引 * (0x80 + ((depth - 64) * (鍵 - 100) >> 4))) >> 7, 0, 127)
  切る高さ = ROM16[0x1E5B58 + 索引 * 2] + パートの補正、0..0xFFF で頭打ち
  レジスタ = 0x1000 | (切る高さ & 0x7FF)
```

* **表は ROM の `0x1E5B58`**（16bit。索引 0 で 1536、64 で 3237、127 で 4095、200 で 16191）
* 索引は記録の **byte37**。鍵で動かない音色（depth = 64）なら、表を引くだけで
  firmware と**完全に一致**する（402 組のうち 41 組がそれ）
* `depth` がどのバイトから来るかはまだ。強さでも動く（`0x1528` → `0x1688`）ので、
  `0x127FA4` をもう一段読む必要がある

いまは「倍率 1」として表を引くだけにしてある。レジスタの一致率は下がる（72% → 85% が不一致）が、
**音は開き切りよりずっと実機に近い**。

| 帯 | 開き切りのとき | 表を引くとき |
|---|---|---|
| 1kHz | +14.2dB | +8.8dB |
| 2kHz | +7.8dB | +4.0dB |
| 4kHz | +15.3dB | **-1.2dB** |
| 8kHz | -3.1dB | +1.7dB |

#### 音量（`0x09`）— 強さの効き方は解けた

6.5 の `att = 表[level] + ram[声+120] + ram[声+119]` のうち、**`+119`（強さのぶん）が解けた**。

```
  強さの減衰 = 表2[0x1E6798 + 表1[0x1E5E5E + 曲線 * 128 + 強さ]]
```

* `表1`（`0x1E5E5E`）は**強さの曲線**。128 バイトの行が並び、**行 0 はそのまま**（`00 01 02 …`）
* `表2`（`0x1E6798`）は「0-127 → 減衰」の対数の曲線。128 バイトの行が並び、
  6.5 で見つけた `0x1E6818` は**この表の行 1**
* GrandPno の強さ 1-127 を**全段で試して、127/127 がぴったり一致**（曲線 0、下駄 10）
* 67 音色のうち **65 が曲線 0**

残りは音色ごとの下駄（`表[level] + ram[+120]`）で、実測では 5〜19 の幅がある。
`+120` は `0x1275C4` が足し込む値で、その元は **16bit の利得表 `0x1E5554`**（記録のバイトで引き、
`(値 * 利得) >> 16` と掛け算を重ねる）。ここはまだ解けていない。

いまは中央値の 12 を置いてある（絶対の音量が最大 ±7 目盛り ＝ ±2.6dB ずれる）が、
**強さを変えたときの動きは実機と完全に同じ**。

#### 音程（`0x11`）

```
  目盛り = ((鍵 - 波形のもとの音程) * 追従率 + 細調のセント) * 1024 / 1200
  ビット 14 = 波形の形式が 3 のとき 1
```

* 1 オクターブ = 1024。細調は波形の記録の +2（符号付き、セント）で、**足す**
* 整数の割り算（**0 の側へ切り捨て**）にすると firmware と 1 の位まで合う。
  floor や四捨五入にすると合わない（402 組で 83% 対 22%・35%）
* **追従率は記録の byte19**: 0 が普通の 100 セント/半音、1 が 50、2 が 20、3 が 10。
  効果音の音色でよく使う（ヘリコプター・拍手・銃声など）
* **ビット 14** は音程とは関係なく、波形の**形式**（レジスタ `0x16` の上 2bit）が
  3 のときだけ立つ。402 組で例外なし

これで 128 組の掃引で、音程が合わないのは 19%（前は 46%）。
残りは音色ごとの移調（prog 14 で -690 目盛り ＝ -8 半音ほど）で、どのバイトから来るかはまだ。

#### 減衰の速さ（`0x07`/`0x08` の上位）

firmware の `0x12ADD0` と `0x1272F4` を読むと、こうだった。

```
  補正   = ((鍵 - byte71) * ((byte70 - 64) * 16)) >> 8      // 負のときは先に +255（0 の側へ）
  目盛り = clamp(記録の速さ + 補正, 1, 63) * 2
  レジスタの上位 = ROM[0x1F4E38 + 目盛り]
```

* **byte70 が深さ**（64 が「鍵で変わらない」）、**byte71 が折れ点の鍵**
* 減衰 1 は byte74、減衰 2 は byte75。補正はどちらにも同じだけ乗る
* アタック（`0x06` の上位）には**この補正が無い**（`ROM[0x1F4DB8 + byte73 * 2]` のまま）

### 6.10 音色の写し取り — ここで実機と並んだ

式が分かっていないレジスタ（フィルタの倍率・素通しの量・音色ごとの音量）を追うのは、
まだ時間がかかる。そこで**残りを「1 音だけ実機に鳴らしてもらって写し取る」**ことにした。

```
  起動 → firmware で SWP30 を初期化
       → 使う音色ごとに 1 音（40ms ぶん）だけ firmware に鳴らさせ、
          そのときのスロットのレジスタと音量を覚える（voice_cal）
       → **CPU を止める**
       → あとは式で組み立て、覚えた値で上書きして鳴らす
```

覚えるのは**利用者の ROM から起こした値**なので、配布物には入らない（起動のたびに作る）。
鍵と強さで動くもの（音程・波形・包絡線・音量）は式で出すので、**1 音の写し取りで
全部の鍵・全部の強さが出せる**。

**どの時点の値を写すか**が効いた。

* `0x05`・`0x0a`・`0x11` は LFO が動かし続けるので**引き金を引いた瞬間**
* `0x01`（素通しの量）は**鳴らしてから上がっていく**。引き金の瞬間は `0xFFFF` で、
  そこを写すと高い音が 13dB 明るくなる。落ち着いた値（`0xDCFF`）を写す
* `0x38`-`0x3d` は**書いてはいけない**。あれは入力 0x40 から先＝ MEG の戻りや A/D のぶんで、
  声のスロットのものではない

#### 結果

`build/nativeplay.exe <rom> nul -b 0,0,0 --levels 40` が、音色ごとに
「firmware で鳴らした音」と「SH-2 を止めて鳴らした音」を同じ状態から作って比べる。

| | |
|---|---|
| 大きさの差 | **平均 0.06dB・最大 0.22dB**（23 音色） |
| 波形の残差（時間を合わせたあと） | **平均 -25.1dB** |

1 音を細かく見ると（GrandPno・鍵 60、0.5-0.7 秒の帯）:

| 帯 | 125 | 250 | 500 | 1k | 2k | 4k | 8k |
|---|---|---|---|---|---|---|---|
| 差 | +0.21 | +0.05 | -0.06 | -0.07 | +0.59 | +0.49 | -0.55 dB |

**時間を合わせると波形そのものが -24.7dB まで一致する**。残るのは、
鳴り始めの位置が 1.66ms 違う（実機は MIDI のバイトを受け取る時間がかかる）ことと、
LFO の位相。

### 6.11 どれだけ軽くなるか（これが本題）

`build/nativeplay.exe <rom> nul -b 0,0,0 --bench` が、同じ音を
「firmware を走らせたまま」と「SH-2 を止めて」で鳴らして、1 サンプルあたりの
実時間を測る（Ryzen 7 9700X、1 スレッド）。

| 同時に鳴らす声 | firmware あり | SH-2 なし | 速さの比 |
|---|---|---|---|
| 1 | 2972 ns | 1040 ns | **2.86 倍** |
| 8 | 3390 ns | 1253 ns | **2.71 倍** |
| 16 | 3799 ns | 1479 ns | **2.57 倍** |
| 32 | 4417 ns | 1898 ns | **2.33 倍** |

**2.3〜2.9 倍**。声を増やすほど SWP30 の側（声を作る所）が効いてくるので比は下がるが、
それでも 2 倍を切らない。

`blocktime` で測った「dense（16 パート・60 音）が実時間に入るのは 4〜5 台」は、
この線なら **10〜12 台**になる計算。[goal](todo.md) の「PFM のインスタンスを何枚も同時に」は、
エフェクトを C++ にする線（1 割）ではなく**こちらが本命**だと、数字で確かめられた。

#### 多い声での内訳

声が 32 でも SH-2 なしが 1898ns なのは、SWP30 の声を作る所（AWM2）と MEG が残るため。
そこは実機の音そのものなので削らない。

### 6.12 128 音色でどこまで合っているか

`--levels 128`（バンク 0 の全音色・鍵 60・強さ 100、要素の鍵/強さの範囲も見る）:

| | |
|---|---|
| 大きさの差 | 平均 **1.05dB**、0.5dB 以内が 81 音色、1dB 以内が 96、3dB 以内が 118 |
| 波形の残差 | 平均 -15.3dB、**-10dB 以下（波形まで合っている）が 75 音色** |

**要素のこと**が分かった。

* 記録の先頭のバイトは**要素のビットマスク**（1/3/7/15 ＝ 1〜4 要素）で、数ではない
* 要素の **byte4,5 が鍵の範囲、byte6,7 が強さの範囲**。
  E.Piano1 は強さ 1-127 と 80-127 の 2 要素、Church Organ は鍵 0-97 と 98-127 の 2 要素
* 写し取りは**要素ごと**に要る（スロットに書かれた `0x09` が、その要素の減衰そのもの）

残っている大きめのずれは、2 要素の音色（シンセ系）が中心。

### 6.13 本体に入れた（`render --native-engine`）

`src/xg/native_driver.h` を足して、`mu2000` の MIDI の入口に挟んだ。

```
  MIDI → native_driver
           ├ 鍵の上げ下げで、その音色の写し取りが有る  → **自分で鳴らす**（CPU は止めたまま）
           ├ 写し取りがまだ無い                        → firmware に鳴らさせて、writes を写し取る
           └ それ以外（音色の指定・CC・SysEx）          → firmware へ回す
```

* **firmware を回すのは、渡した MIDI が溜まっている間＋少しだけ**。
  `midi_pending()` を見て、空になってから 10ms で止める
* スロットは**上から**取る。firmware は下から使うので、写し取りのために
  firmware が鳴らしている音とぶつからない
* 起動は firmware がやる（SWP30 の初期化に要る）。`--native-engine` は起動が終わってから入る

#### 速さ（30 秒ぶんの書き出しにかかった実時間、Ryzen 7 9700X）

| 曲 | 既定 | native の口 |
|---|---|---|
| piano | 3.92 秒 | 1.39 秒（**2.82 倍**） |
| dense（16 パート・60 音） | 4.29 秒 | 1.75 秒（**2.45 倍**） |
| lofi（インサーションを SysEx で切り替える） | 5.18 秒 | 2.82 秒（**1.84 倍**） |

軽量エフェクト（`--native-fx-full`）も足すと、piano 3.43 倍・dense 2.96 倍。

**firmware を回す長さの決め方**が効く。

* ふだんは、渡した MIDI が溜まっている間＋10ms
* **SysEx のあとは 0.5 秒**。エフェクトの種類を変える SysEx は MEG のプログラムを
  1 万件以上書き直すので、途中で止めると音が出なくなる（lofi が無音になって気づいた）
* 音色の写し取りは 20ms。短くすると `0x01`（鳴らしてから上がる）が落ち着く前に切れる

#### 音（試験の 7 曲、既定の道と比べた大きさの差）

| piano | chord | dense | drums | effects | bend | lofi |
|---|---|---|---|---|---|---|
| +0.06 | +0.14 | -0.00 | +0.00 | +0.00 | +0.25 | +0.01 dB |

音が出ている区間だけで見ても、いちばん大きい差が **0.33dB**（bend）。

ドラムと効果音は、まだ native では鳴らさず firmware に回している（だから 0.00）。

#### まだ足りないもの

* **ドラム**（バンク 127/126）。音色の記録の引き方が違う（`xg/voices.h` の kit）
* **コントローラ**。音量・パン・ベンドなどが動くと、いまは firmware に回って
  そのぶん CPU が回る。ミキサのレジスタを自分で作れば止めたままにできる
* **スロットの取り合い**。firmware 側と 2 つの割り当てが同居しているので、
  64 声を使い切る曲では衝突しうる

### 6.14 ドラムとコントローラ

#### ドラム

打楽器は「音色」ではなく**音ごと**に中身が違うので、`(バンク, プログラム, 鍵)` を鍵にして
**1 打ごとに写し取る**。同じ音を何度も叩くので、数小節で打楽器のほとんどが native になる。

* ドラムのパートかどうかは、XG の**パートモード**（`08 pp 07`。0 が普通、1 以上がドラム）で見る。
  「音色の記録が引けない＝ドラム」では、音色を選び終える前の旋律パートまで拾ってしまった
* 強さは減衰（`0x09`）を足し算でずらすだけで合う（6.5 と同じ理屈）
* 写し取りの窓は**鍵が鳴ってから 5ms**。ここを長くすると、その間ほかの音色が写し取りを
  始められず、ドラムの多い曲で旋律がいつまでも native にならなかった

#### コントローラ

DAW の自動演奏でつまみが動くたびに SH-2 が起きるのでは意味が無いので、
**実機がどのレジスタを書くか**を `nativeplay --ccwatch` で見て、同じものを自分で書く。

| MIDI | レジスタ | 実機のやっていること |
|---|---|---|
| CC7（音量）・CC11（表現） | `0x09` の下位バイト | 減衰を足す（0.1875dB 目盛り） |
| CC10（パン） | `0x32`（上が左・下が右） | 中央で両側 -3dB の **cos 則**。128 点すべて 0.1875dB 以内で合う |
| ピッチベンド | `0x11` | セントに直して足す。`(bend-8192)*幅*100/8192` を 0 の側へ切り捨て、さらに `*1024/1200` |
| CC64（ダンパー） | — | 離しを待たせるだけなので、こちらで持てる |

* 減衰の曲線は `0x1E6798`（level→減衰、0.375dB 目盛り）を `cc-1` で引いて 2 倍。
  実測との差は **cc≥8 で 0.375dB 以内**、いちばん外れる cc=10 で 0.75dB
* **写し取ったときのつまみの位置**（`08 pp 0B` 音量・`+0x7E` 表現・`08 pp 0E` パン）を
  voice_cal に一緒に覚えて、そこからの**差ぶん**だけ動かす。だから写し取った音そのものは必ず合う
* CC は firmware にも渡す（次の写し取りを同じ位置で鳴らしてほしいので）が、
  回す時間は 2ms でよい。ピッチベンドは**渡さない**（そのパートを firmware が鳴らしている間だけ渡す）
* firmware を止める直前に、パートの音量・表現・パンをワーク RAM から取り直す。
  SysEx やパネルで変えられても追い付く

#### 速さ（30 秒ぶんの書き出し、3 回の最良。Ryzen 7 9700X）

| 曲 | 既定 | `--native-engine` | 比 |
|---|---|---|---|
| piano | 4.10 秒 | 1.41 秒 | **2.91 倍** |
| dense（16 パート・60 音） | 4.34 秒 | 1.72 秒 | **2.52 倍** |
| つまみを 201 回動かす曲 | 4.06 秒 | 1.58 秒 | **2.57 倍** |

つまみを動かし続けても 2.5 倍が保てる。ここを firmware に投げていた頃は、
CC 1 つにつき 20ms 走らせていたので、自動演奏の多い曲ほど遅かった。

#### 音（試験の 7 曲、既定の道と比べた大きさの差）

| piano | chord | dense | drums | effects | bend | lofi |
|---|---|---|---|---|---|---|
| +0.06 | +0.14 | -0.29 | -0.00 | +0.00 | +0.25 | +0.02 dB |

### 6.15 多段サンプルの段ごとの音量（波形の記録の先頭のバイト）

`nativeplay --attsweep` を足した。鍵 12-108 を 1 つずつ firmware に鳴らさせて、
`0x09` に入る減衰を式の値と並べる。GrandPno で**合わない鍵が 61/64、最大 1.50dB** だった。

原因は**波形の記録の先頭のバイト**。`read_wave` が読んでいなかったが、これが
**その段ぶんの減衰**（0.375dB 目盛り）だった。

| 鍵 | 波形の[0] | 実機の減衰 | 直す前の式 |
|---|---|---|---|
| 53-55 | 0 | 30 | 30 |
| **56-58** | **5** | **40** | **32** |
| 59-61 | 1 | 32 / 30 | 32 |
| 62- | 0 | 28 | 30 |

ピアノは鍵 56-58 だけ別の段（波形）で、そこが 1.5dB 大きい。段の切り替わりで
音量が飛ぶのは、多段サンプルの音色ではごく普通のこと。

直したあとの合わない鍵（強さ 100、鍵 12-108）:

| 音色 | 直す前 | 直したあと |
|---|---|---|
| 0 GrandPno | 61 / 64、1.50dB | 31 / 64、**0.38dB** |
| 24 Nylon Gt | — | **0 / 64、0.00dB** |
| 48 Strings | — | 16 / 64、0.38dB |
| 56 Trumpet | — | **0 / 64、0.00dB** |
| 73 Flute | — | 17 / 64、0.75dB |

残る差はすべて**減衰の表の段の境目**（`level_from_att` が同じ減衰になる目盛りの
真ん中を返すため）。鍵の曲線の倍率は 1・2・3 を試して **2 が最良**だった。

### 6.16 鳴らす**時刻**を実機に合わせる（効きが大きかった）

大きさ（dB）は合っているのに、波形を引き算すると全然合っていない曲があった。
原因は**時刻**。

* firmware は MIDI を受けてから **74 サンプル（1.68ms）**後に鳴らす
  （`nativeplay --ccwatch` が測る）。native はその場で鳴らしていた
* MIDI は 1 バイト 10 ビット・31250 baud なので **1 バイト 14.1 サンプル**かかる。
  和音のように何音も続けて来ると、あとの音ほど遅れて鳴る

そこで native の鍵・CC・ベンドを**待ち行列**に入れ、
「その口が最後のバイトを受け終える時刻 ＋ 32 サンプル」に実行するようにした。
firmware に回す音は待たせない（そちらは実機の道をそのまま通るので）。

波形の残差（既定の道との引き算。時間合わせののち）:

| 曲 | 直す前 | 直したあと |
|---|---|---|
| chord | -2.8dB（72%） | **-26.0dB（5.0%）** |
| lofi | -1.3dB（86%） | **-27.6dB（4.2%）** |
| drums | -2.2dB（78%） | -8.0dB（40%） |
| effects | -63.9dB | -63.9dB |
| piano | -21.6dB | -21.6dB |

`drums` を 100ms ごとに見ると、**ほとんどの窓が -40〜-66dB** で、
native で鳴らした打楽器の当たった瞬間だけ -3〜-14dB になる。
`dense`（60 音同時）はまだ合わない。64 声を firmware と native で分け合うので、
どの音を捨てるかが実機と違うためと見ている（6.9 の宿題）。

### 6.17 要素の粗調と離調（byte17・byte18）

パッドや重ねの音色が **3dB 大きい**（Warm Pad +3.17、Square Lead +2.88dB）のが直った。

* **byte18 はセント単位の離調**（64 が中央）。重ねの音色は 2 つの層をここで
  ±5 セントずらしている。入れないと層がぴったり重なり、うなりが消えて
  電力が 2 倍（＝+3dB）になる
* **byte17 は半音単位の粗調**（64 が中央）。dense のチャンネル 15（Crystal）の
  要素 1 は byte17=83 で、**19 半音**上げていた。ここを入れないと音程ごと違う

どちらも `pitch_reg` の `cents_extra` に足すだけ。実機の `0x11` とぴったり合う。

| | 直す前 | 直したあと |
|---|---|---|
| Warm Pad(89) | +3.17dB | **+0.38dB** |
| Square Lead(81) | +2.88dB | **+0.16dB** |
| dense ch15 | +2.76dB | **+0.25dB** |
| バンク 0 の 128 音色 | 平均 1.05dB / 残差 -15.3dB | **平均 0.56dB / 残差 -21.3dB** |

同じ波形を鳴らす要素が 2 つあるとき、両方が同じ写し取りを掴まないように
`match_cal` に「もう使った」印を付けた。

### 6.18 フィルタの包絡線も写し取る

firmware は**フィルタをソフトで動かしている**（1 音につき 10ms ごとに
`0x00`・`0x01`・`0x04` を書き直す。GrandPno の 1 音で 66 回）。

そこで、写し取った音が鳴っている 1 秒間、その書き直しを**時刻つきで覚えて**、
あとの音でも同じ時刻に同じ値を書くようにした（`voice_cal::filter_env`）。
録りながらその場で写し取りに足すので、写し取り中に鳴り始めた音にも間に合う。

**LFO（`0x05`・`0x0a`）も同じ**だった。ビブラートの「かかり始めるまでの間」と
深さの増やし方は firmware がソフトでやっている（dense のチャンネル 6 では
鍵を押した 136ms 後から `0x0a` の下位が 0→6→12→17… と増えていく）。
これを入れて、そのパートの残差が **-0.3dB → -5.9dB** になった。

### 6.19 要素を遅らせて鳴らす（byte72）

MusicBox（音色 10）は**2 つ目の要素を 37ms 遅らせて**鳴らしていた。
写し取りの窓が 5ms だったので 2 つ目を取り逃がし、こちらは同時に鳴らしていた。

* 遅らせる段は要素の **byte72**。実測（`--trace-swp` の 0x20e の間隔）:

| byte72 | 遅れ | 式 `441 * 2^(n-1) - 130` |
|---|---|---|
| 1 | 311 サンプル（7.1ms） | 311 |
| 2 | 752〜753（17.1ms） | 752 |
| 3 | 1634（37.1ms） | 1634 |

* 写し取りの窓も「**要素がそろうまで待つ**（最大 62ms）、そろったら 5ms で切り上げ」に直した

| | 直す前 | 直したあと |
|---|---|---|
| 10 MusicBox | -2.01dB | **-0.23dB** |
| 37 SlapBass2 | -5.59dB | **+0.13dB** |
| 50 SynStr1 | 残差 +1.8dB | 残差 **-5.4dB** |
| 60 FrenchHorn | 残差 +1.2dB | 残差 **-3.9dB** |

`SMU2000_NATIVE_ENGINE=1 build/blocktime.exe <rom> <midi> 512 6 3 <台数>`。
Ryzen 7 9700X・512 フレーム・スレーブは別糸。

**実曲（still_more_fighting_lead）**

* `render <rom> <midi> <wav> --native-engine`
* `gui.exe <rom> --native-engine` / `live.exe <rom> --native-engine`

### 6.21 SH-2 を回している理由の内訳

`render --native-engine` が、演奏中に firmware を回した理由を出すようにした。

```
native の口: 演奏中に firmware を回したのは 5.0%
  内訳: firmware の音 0.4% / SysEx 1.7% / 写し取り 0.0% / MIDI の受け取り 0.0% / そのほか 3.0%
```

これで分かったこと:

* **「溜まっている間は回す」が一番重かった**。渡した MIDI は 1 バイト 14 サンプル
  かけて線を流れ、それを待つために実時間の 2 割を SH-2 に持っていかれていた。
  メッセージごとに置く待ちで足りるので、この仕掛けはやめた
* **SysEx は中身で見分ける**。`43 1n 4C hh` の `hh` が 00（システム）・02（エフェクト）・
  03（インサーション）のときだけ 0.5 秒回す。パートの設定（08 pp xx）は 5ms でよい。
  MEG のプログラムを書き直す SysEx を途中で止めると音が出なくなるので、ここは慎重に
* **音色の指定は 10ms**。ワーク RAM に入るのは 30 サンプル（0.68ms）で済むが
  （`nativeplay --ccwatch`）、firmware の中の下ごしらえはもっとかかる。
  5ms に詰めたら piano の残差が -59dB から -53dB に落ちたので 10ms にした
* **ベンド幅はワーク RAM から読む**（パートの塊 +0x23。64 が 0 半音）。
  RPN で設定されても SysEx で設定されても追いつく
* **フィルタの包絡線を流す `tick` は「つぎの段の時刻」まで何もしない**。
  毎サンプル 64 スロット見ていると、SH-2 を止めた意味が薄れるくらい重かった

### 6.22 写し取りを取っておく（`voicecache.h`）

写し取りの中身は (ROM) が同じなら毎回同じなので、ファイルに残せば
**2 回目からは 1 音目も native で鳴らせる**。DAW に何枚も挿したときも、
2 枚目からは写し取りをやり直さない。

* 置き場は `<設定>/S-MU2000/voicecal/<鍵>.bin`。鍵はプログラム ROM と波形 ROM から
* 中身は写し取ったレジスタ・素の音量・写したときのつまみの位置・フィルタと LFO の段
* **利用者の ROM から起こした値なので、配らない**（bootcache と同じ扱い）
* **既定では使わない。** 写し取りにはパートのエフェクト経路（素通しの量・
  インサーションの掛かり方）が入っているので、**別の曲で取った写しを使うと
  その曲の音にならない**。実際 `lofi` をほかの曲の写しで鳴らすと **3.85dB** 違い、
  波形の残差も -30.1dB から -7.7dB に落ちた
* 同じ曲を何度も鳴らすとき・同じ設定で何枚も挿すときだけ効く。
  `render --voicecache` / plugin.ini の `voicecache=1` / `SMU2000_VOICECACHE=1`
* 同じ曲で 2 回目を鳴らすと、dense は **firmware を回したのが 36.0% → 5.1%**、
  鍵は **native 48 / firmware 0**。大きさの差もむしろ縮む（-0.46dB → **-0.23dB**）

still_more_fighting_lead を 30 秒書き出したとき、**firmware に鳴らさせる音が 1 つも
無くなった**（`鍵: native 20 / firmware 0`）。

### 6.23 残っている「SH-2 が要る所」

`render --native-engine` の内訳で、まだ回している所はこれだけになった。

| 理由 | still_more_fighting（30 秒） | なぜ要るか |
|---|---|---|
| SysEx | 1.7% | XG On は全部を組み直すので 0.5 秒回す。エフェクトの種類を変える SysEx も同じ |
| 知らない CC | 2.5% | **CC1（モジュレーション）は firmware がソフトで揺れを増やしている**。
5ms に詰めたら bend の残差が -35.8dB から -14dB に落ちた |
| firmware の音 | 0.4% | 写し取りの 1 音目。voicecache があれば 0 になる |
| 音色の指定 | わずか | ワーク RAM に入るのは 0.68ms だが、下ごしらえに 20ms かかる |
| 合計 | **4.7%（写しがあれば 4.2%）** | |

`replay_note` が渡すたびに一律 20ms 回していたのをやめ、呼ぶ側が要るぶんだけ
置くようにした。これが曲の出だしの重さの正体だった。

### 6.24 モジュレーション（CC1）

**native で鳴らしている音には、こちらが持っていない CC はいっさい効かない。**
firmware は CC を受け取っても、自分のスロットにしか書かないからだ。
いちばん効くのがモジュレーション（ビブラート）だったので入れた。

* CC1 → レジスタ `0x0a` の**下位バイト（LFO の深さ）**に足す
* 深さは **10 段（0, 9, 17, 26, 35, 43, 52, 60, 72, 84）**で、
  **音色によらない**（GrandPno・Strings・SawLead の 3 つで同じ）。
  切り替わる CC の値は 13, 26, 39, 52, 64, 77, 90, 103, 116
* 写し取ったときの CC1（パートの塊 +0x7D）を `cal_mod` に覚えて、そこからの差ぶんで動かす
* 包絡線の段（6.18）で `0x0a` を書き直すときも、同じだけ足す

モジュレーションを上げ下げする曲での波形の残差:

| 音色 | 入れる前 | 入れたあと |
|---|---|---|
| 48 Strings | -0.4dB（95%） | **-16.2dB（15%）** |
| 73 Flute | -2.9dB（72%） | **-13.4dB（21%）** |
| 0 GrandPno | -9.1dB（35%） | **-26.5dB（4.7%）** |

CC1 だけは firmware にも長く（20ms）渡す。firmware が鳴らしている音のぶんは
firmware がソフトで揺れを増やしていくので、短くすると bend の残差が
-35.8dB から -15.6dB に落ちた。

### 6.25 エフェクトの送り（CC91 リバーブ・CC93 コーラス）

これも native の音には効いていなかった。`nativeplay --ccwatch` で見ると:

* **リバーブ（CC91）は `0x33` の下位バイト**、**コーラス（CC93）は `0x34` の上位バイト**。
  `0x32`-`0x37` は 1 つで 2 本ぶんの送りを持っている（`0x32` は左右の素通し）
* 減衰は **16 ＋ level→減衰の表**（`0x1E6798` を cc-1 で引く）。**音色によらない**
  （GrandPno・Strings・Flute で同じ）
* 写し取ったときの送り（パートの塊 +0x13 リバーブ・+0x12 コーラス）を
  `cal_rev` / `cal_cho` に覚えて、そこからの差ぶんで動かす。
  写し取ったときに切れていた（0xff）送りは差が取れないので、下駄 16 を使う

送りを上げ下げする曲での波形の残差:

| | 入れる前 | 入れたあと |
|---|---|---|
| CC91 GrandPno | -9dB 相当 | **-26.5dB** |
| CC91 Strings | | **-22.2dB** |
| CC93 GrandPno | -11.2dB | **-24.7dB** |
| CC93 Strings | -4.8dB | **-23.1dB** |

### 6.26 明るさ（CC74）と共振（CC71）

`nativeplay --ccfilter` を足した。CC を振るたびに鳴らし直して、**包絡線が動く前**の
`0x00`・`0x04` を拾う（持ったまま振ると、フィルタの包絡線の動きと混ざって読めない）。

* **CC74（明るさ）→ `0x00` の下 12bit（切る高さ）**。`16 × (値 - 64)` でまっすぐ動き、
  **1984 で頭打ち**。音色によらない
* **CC71（共振）→ `0x04` の上 5bit**。**2 きざみで 1 段**（64 まで 0、67 で 1、127 で 31）
* 写し取ったときの値はパートの塊の **+0x18（明るさ）・+0x19（共振）**から読む
  （XG の 08 pp 18 / 19 そのまま。+0x1A が EG アタック、+0x1C が EG リリース）

CC を振る曲での波形の残差:

| | 入れる前 | 入れたあと |
|---|---|---|
| CC74 GrandPno | -5.5dB（53%） | **-38.4dB（1.2%）** |
| CC74 Strings | -9.8dB（32%） | **-21.6dB（8.3%）** |
| CC71 Strings | -16.8dB（15%） | **-21.4dB（8.6%）** |

`0x01`（フィルタのもう 1 つの係数）は切る高さと一緒に動くが、その式はまだ。
写し取った値のままなので、切る高さを大きくずらしたときだけわずかに違う。

### 6.27 SysEx のあと何秒回せばいいか（実測）

`nativeplay --ccwatch` が、SysEx を渡してから **SWP30 を触り終わるまで**を測る。

| SysEx | 触り終わるまで |
|---|---|
| XG On（`43 1n 4C 00 00 7E 00`） | **224ms** |
| リバーブの種類（`02 01 00`） | **168ms** |
| インサーションの種類（`03 0n 00`） | **176ms** |

500ms 回していたのを **300ms** に詰めた。still_more_fighting_lead の出だし 6 秒が
11.9% → **8.6%**、30 秒が 2.5% → **1.9%**。
`bend` の残差はむしろ良くなった（-35.8dB → **-50.7dB**）。

#### いま SH-2 を回している理由（still_more_fighting_lead）

| | 6 秒 | 30 秒 |
|---|---|---|
| firmware の音（写し取りの 1 音目） | 2.0% | 0.2% |
| SysEx（XG On） | 5.0% | 1.4% |
| そのほか（音色の指定・知らない CC） | 1.3% | 0.3% |
| **合計** | **8.6%** | **1.9%** |

写し取りを取ってあれば（6.22）、1 行目も 0 になる。

### 6.28 鍵の追従は**鍵 60 が支点**（波形の基準鍵ではない）

`nativeplay --sweep 128` が、写し取りを使わずに式だけで作ったレジスタを
firmware と突き合わせる。音程（`0x11`）が 16/128 で合っていなかった。

合わないのは**鍵の追従が 100 でない音色**（記録の byte19 が 1 なら 50、2 なら 20）。

| 音色 | 基準鍵 | ずれ |
|---|---|---|
| 115 Woodblock（追従 50） | 75 | -749 セント |
| 116 TaikoDrum（追従 50） | 94 | -1700 セント |

どちらも **50 × (60 - 基準鍵)** でぴったり。つまり firmware は

```
セント = (鍵 - 60) * 追従 + (60 - 基準鍵) * 100 + 波形の微調 + 要素のずらし
```

と計算している。追従が 100 のときは今までの式と同じになるので気づかなかった。

* 合わない音程 **16 → 1**（残り 1 つは prog 31 で、波形の形式のビットも違う）
* バンク 0 の 128 音色: 大きさの差 平均 0.56 → **0.49dB**、
  波形の残差 -21.3 → **-23.6dB**

#### 試したが入れなかったもの: 強さの帯ごとの写し取り

フィルタの切る高さは強さで大きく動く（GrandPno で 368 目盛り＝4 分の 1 オクターブ）。
写し取りを「音色 × 強さの帯（4 段）」で持てば、その音色の強さごとの明るさが合う。
やってみたが、**残差は -15.2dB から -16.3dB にしかならなかった**のに
firmware に鳴らさせる音が 4 倍になるので、入れないことにした。

### 6.29 試したが入れなかったもの（同じ道を二度通らないために）

#### SysEx のあと「SWP30 を触らなくなるまで」回す

固定の 300ms（6.27）ではなく、firmware が SWP30 を触るたびに待ちを伸ばす作り。
`still_more_fighting_lead` の出だし 6 秒が 8.6% → **4.1%** まで落ちたが、
**`effects` の残差が -63.9dB から -3.4dB に壊れた**。エフェクトの種類を変える
SysEx（MEG のプログラムを 1 万件以上書き直す）の途中に 60ms 以上の隙があって、
そこで止めてしまうため。伸ばす時間を 62ms にしても直らなかったので戻した。

**ここで分かったこと**: 声のスロットの `0x38`-`0x3f`（MEG の戻りのミキサ）と
`0x0e`・`0x0f` は、**鳴っていなくても毎サンプル書き直されている**。
「firmware が働いているか」を書き込みで測るときは、この 3 つを除かないと
永久に止まらない。

#### 残差（波形の引き算）はピッチに厳しすぎる

`dense` のチャンネル 13 は、要素 1 の音程が実機と **1 目盛り（1.2 セント）**しか
違わないのに、波形の残差は 93% になる。3 秒の音では 1 周期ぶん位相がずれるからで、
**耳には分からない差**。オクターブごとの帯で比べると ±3dB に収まる。

音を比べるときは、残差だけでなく**大きさ（rms）と帯ごとの中身**も見ること。

#### 強さの帯ごとの写し取り

6.28 の末尾に書いたとおり、効果が小さいわりに firmware に鳴らさせる音が 4 倍になる。

### 6.30 さばけない CC が来たパートは firmware に任せる

native で鳴らしている音には、こちらが持っていない CC は**何も起きない**。
黙って無視すると「ポルタメントが掛からない」「EG の設定が効かない」音になる。
そこで、**音に効く「知らない CC」が既定から外れている間は、そのパートの音を
firmware に鳴らしてもらう**ようにした（正しさを取って、そのぶん重くする）。

| CC | 既定 |
|---|---|
| 5 ポルタメントの速さ / 65 入切 / 84 コントロール | 0 |
| 72 EG リリース / 73 EG アタック / 75 EG ディケイ | 64 |
| 94 バリエーション送り | 0 |
| アフタータッチ（チャンネル・ポリ） | — |

既定に戻れば印も下りて、また native で鳴らす。

* `lofi` の残差が **-30.1dB → -38.6dB**（そのぶん firmware は 32.7% → 50.1%）
* CC73 を振る曲は、振り始めたところから firmware に移る
* `still_more_fighting_lead` は これらを使わないので 1.9% のまま

### 6.31 波形は「粗調で移した鍵」で選ぶ

6.28 で残った最後の 1 件（音色 31 GtHarmonics、鍵 84）が解けた。

実機の音程は `0x7c3e`（下 14bit で -962）。こちらは `0x3b27`（-1241）。
波形の組 78 を見ると、

| | 基準鍵 | 上限鍵 | 形式 |
|---|---|---|---|
| [0] | 69 | 63 | 圧縮 |
| [1] | 83 | **74** | 圧縮 |
| [2] | 87 | 100 | 8bit |

こちらは「上限鍵 ≧ 鍵」で [2] を選ぶ。ところが **[1] の基準鍵 83・微調 -28 で
計算すると実機の -962 にぴったり合う**。この要素は byte17=52、つまり
**12 半音下げて鳴らす**ので、`84 - 12 = 72` → 上限鍵 74 の [1] が選ばれていた。

つまり**波形は「粗調で移した鍵」で選び、音程は元の鍵で計算する**。

* 音程の不一致 **1 → 0**。波形の番地（`0x16`・`0x17`）の不一致も消えた
* バンク 0 の 128 音色: 大きさの差 平均 0.49 → **0.48dB**、
  波形の残差 -23.6 → **-23.9dB**

これで `--sweep 128` の音程・波形まわりは**全部一致**になった。
残るのはフィルタ（`0x00`・`0x01`・`0x04`）と音量（`0x09`）と `0x0b`・`0x10` で、
どれも写し取りで埋めている所。

### 6.32 firmware に回した音が 7 サンプル遅れる（直せないぶん）

SawLead（音色 81）の**写し取りの 1 音目**（firmware が鳴らす音）が、既定の道と
波形で合わない。レジスタを 1 つずつ突き合わせたら**全部同じ**で、違うのは
**鳴らし始めが 7 サンプル（0.16ms）遅い**ことだけだった。

原因は **MIDI の線の時計が CPU のサイクルで進む**こと。SH-2 を止めている間は
線のビットも止まるので、渡したバイトがそのぶん遅れて届く。線のビットだけ
先に進めても、受ける側（SCI）の時計も CPU で動いているので意味が無い。

* 効くのは **firmware に回した音だけ**（その音色の 1 音目）。ずれは 1 バイトぶん
  （14 サンプル＝0.3ms）以内で、耳には分からない
* ただし**離調した 2 層の音色**（SawLead など）では、うなりの位相が変わるので
  波形の残差は 100% 近くになる。大きさは ±0.4dB で合っている

### 6.33 フィルタの強さ依存は、測ったら耳に響かなかった

写し取りは 1 つの強さで取るので、**その音色のほかの強さでの明るさ**は合っていない。
実機を測ると確かに動く（`nativeplay --cutsweep`、鍵 60）:

| 音色 | 表の値 | 強さ 1 | 強さ 61 | 強さ 121 |
|---|---|---|---|---|
| 0 GrandPno | 1243 | +80 | +160 | +432 |
| 48 Strings | 1475 | +160 | +384 | +572（2047 で頭打ち） |

**音色ごとに形が違う**（深さだけの違いではない）ので、式は起こせていない。

ただし**耳に響く差ではなかった**。強さ 10〜127 を振る曲で、オクターブごとの
帯を比べると **ほとんど ±0.6dB、いちばん外れて +2.3dB**。切る高さの目盛りは
周波数に対してかなり細かいので、170 目盛りずれても中身はあまり変わらない。

強さの帯ごとに写し取る案（6.28 の末尾）も、この理由で効かなかった。
**式が要るとすれば、それは「正しさ」のためで、音のためではない。**

### 6.34 音色は自分で引く（firmware のワーク RAM を待たない）

これまでは「どの音色か」を **firmware がワーク RAM（パートの塊 +0xF8）に
書いてくれるのを待って**読んでいた。これが最後に残った**作りの上での**
エミュレータ頼みだった（速さではなく、そもそも分からない）。

`xg::voice_rom::lookup`（firmware の `0x134AA8` と同じ手順）で自分で引けるので、
バンクとプログラムをパートごとに覚えて、そこから記録を出すようにした。

* `nativeplay --list` に突き合わせを足して確かめた。
  **旋律系のバンク（0,0 / 8,0 / 32,0 / 64,0 / 0,1 / 0,2）の 640 音色で食い違い 0**
* ドラムのバンク（126・127）は `lookup` が 0 を返す。そこは MSB で見分けて
  ドラムの道（鍵ごとの写し取り）へ回す
* 引けなかったときは、これまでどおりワーク RAM を読む

音色の指定は firmware にも渡す（写し取りの 1 音目を鳴らしてもらうため）。
渡す時間を 5ms に詰めると piano の残差が -58dB から -53dB に落ちたので、
**20ms のまま**にした。firmware の中の下ごしらえは RAM に書くより長くかかる。

### 6.35 64 声の分け合い

`render --native-engine` が「いちばん多いときに使ったスロット」を出すようにした。

| 曲 | こちらが使ったスロット |
|---|---|
| dense（16 パート・60 音） | **36 / 64** |
| chord | 5 |
| still_more_fighting_lead | 2 |

firmware は写し取りの 1 音目だけを鳴らすので、同時に使うのはせいぜい数声。
dense でも 36 ＋ 数声なので、いまのところぶつかっていない。

それでも**下の 8 スロットは firmware のために空けて**おくことにした
（こちらは 63 番から下へ、firmware は 0 番から上へ使う）。
こちらが使えるのは 56 声になるが、dense でも 36 なので足りる。

### 6.36 残ったレジスタは、写し取りで埋まっていた（確かめた）

`--sweep 128`（写し取りを使わず式だけで作る道）で合わないのは
`0x00`・`0x01`・`0x04`・`0x09`・`0x0b`・`0x10` だけになった。
これらが**鳴らすときに問題になるか**を、実機の書き込みを追って確かめた。

| レジスタ | 鍵・強さで動くか | 鳴らすときの扱い |
|---|---|---|
| `0x0b` | **動かない**（GrandPno は鍵・強さを変えても 0x7f00 のまま） | 写し取りでそのまま |
| `0x10` | **動かない**（同じく 0x4000 のまま） | 写し取りでそのまま |
| `0x01` | 音の間に 0xffff → 0xdcff → 0xb6ff と動く | **包絡線の写し取り**（6.18）で再現 |
| `0x04` | CC71 で動く | CC71 を入れた（6.26） |
| `0x09` | 鍵・強さで動く | 式で出す（6.5・6.15） |
| `0x00` | 鍵ではほぼ動かない。強さで動くが**帯で ±2dB**（6.33） | 写し取り＋包絡線＋CC74 |

つまり **`--sweep` の不一致は「式が無い」というだけで、鳴らすときには埋まっている**。
式を起こす値は「写し取りをやめて firmware なしで鳴らす」ときに初めて要る。

### 6.37 いまの姿（2026-09-18 の終わり）

| | |
|---|---|
| SH-2 を回す割合（実曲 30 秒） | **1.9%**（SysEx 1.4 / 写し取り 0.2 / そのほか 0.3） |
| 30 秒の書き出し | dense 4.35→**1.87 秒**、実曲 4.09→**1.45 秒**、piano 4.07→**1.58 秒** |

| 波形の残差 | piano -58.3 / effects -63.9 / bend -50.7 / lofi -38.6 / chord -26.6dB |

### 6.38 写し取りに「パートの経路」の印を付けた

6.22 の写し取りのファイルは、別の曲で取った写しを使うと音が変わった
（`lofi` で 3.85dB）。原因は、写し取りにパートの**エフェクト経路**が
入っていること。そこで写し取りに**経路の印**（`voice_cal::cal_ctx`）を
一緒に入れて、合わないときは写し取りをやり直すようにした。

印に混ぜるもの（どれも写し取った `0x20`-`0x2b`・`0x32`-`0x37` に効く）:

* 素通しの量（`08 pp 11`）・バリエーション送り（`14`）
* パートの EQ（塊の +0x6A-0x6F）
* インサーション 4 つの掛かり先（`03 0n 0C`）

これで**別の曲の写しが混ざっても安全**になった。`lofi` は写しがあっても
-38.6dB のまま（前は -7.7dB に落ちていた）。

#### それでも既定は「使わない」

写しがあると**その音色の 1 音目も native で鳴る**ので、
「1 音目だけは実機そのまま」という強みが無くなる。

| | 写し無し | 写しあり |
|---|---|---|
| piano の残差 | **-58.3dB** | -21.5dB |
| bend の残差 | **-50.7dB** | +1.9dB（大きさは +0.29dB） |
| dense で SH-2 を回す割合 | 35.7% | **5.1%**（鍵は native 48 / firmware 0） |

**速さを取りたいときだけ**入れる（`render --voicecache` /
plugin.ini の `voicecache=1` / `SMU2000_VOICECACHE=1`）。

### 6.39 速さの数字は、起動を除いて測ること

`render` は既定で毎回 firmware を起動する（音の時間で 8 秒、実時間で **0.55 秒**）。
30 秒の書き出しが 1.45 秒だったうちの**3 分の 1 以上が起動**だった。
DAW ではプラグインが `bootcache` で起動を飛ばすので、そちらが実態に近い。

`render --bootcache` で測り直すと（Ryzen 7 9700X・30 秒ぶん）:

| 曲 | 既定 | native の口 | ＋写し取り | ＋軽量エフェクト |
|---|---|---|---|---|
| still_more_fighting_lead | 3.70 秒 | **1.03 秒（3.59 倍）** | 1.02 秒 | 0.89 秒（4.2 倍） |
| dense（16 パート・60 音） | 3.93 秒 | **1.43 秒（2.75 倍）** | 1.20 秒（3.3 倍） | 0.97 秒（4.1 倍） |

起動を含めて測ると 2.8 倍・2.3 倍に見えるが、**DAW で効くのは上の数字**。

### 6.9 次の一手（どこから続けるか）

残っているのは 3 つだけ。どれも「どの番地を読めばいいか」までは分かっている。

**(1) 音色ごとの音量の下駄**（`0x09` の残り）

* `att = 表[level] + ram[声+120] + ram[声+119]` の `+119` は解けた（6.5）
* `+120` は `0x1275C4` が足し込む。その呼び元は `0x1274AE`・`0x127524`・`0x127548` の 3 か所で、
  どれも「記録のバイトで **16bit の利得表 `0x1E5554`** を引いて、`(値 * 利得) >> 16` を重ねる」形
* **利得表は 64 段**（索引 0-63 で 1 → 0xFA18。1 段およそ 1.5dB）。64 から先は別の表
* 実測では下駄は 5〜19 の幅。`0x127496` の前後（どのバイトを何回掛けるか）を読めば決まるはず

**(2) フィルタの鍵・強さの倍率**（`0x00` の残り）

* 表（`0x1E5B58`）と索引（`byte37`）は分かった。倍率の形は `0x127FA4` で
  `k = 0x80 + ((depth - 64) * (鍵 - 100) >> 4)`、`索引 = (索引 * k) >> 7`
* ただし**この形だけでは 67 音色中 7 つしか説明できない**。強さのぶんが同じ形では無いか、
  パートの値が別に入る。`0x127FA4` の全体（`0x127FA4`-`0x12801C`）をもう一度、
  分岐込みで読み直すのが早い

**(3) 音量つまみ（CC7・CC11）の曲線そのもの**

* いまは `0x1E6798` を `cc-1` で引いて 2 倍している。実測とは cc≥8 で 0.375dB 以内だが、
  **実機はこれとは別の曲線を使っている**（ROM をバイト列で探しても見つからない＝計算している）
* 鍵を押したときの減衰は `ram[0x43E96A] + ram[0x4226A8]` を `0x12DF40` が書く。
  その `0x43E96A` を作るのは `0x1274B2` で、そこへ来る値は
  `0x127594`（`level = max(0, 127 - byte75)` を 16bit 利得表 `0x1E5554` と `0x14523C` で割る）と
  `0x1275C4`（`減衰 += 2 * 値` の足し込み）を通る。**つまみのぶんがどこで入るかはまだ**
* `0x43E96A` を指す所は `0x1274DC`・`0x127608`・`0x12862C`・`0x12AC94`・`0x12DFD0`・`0x12E428`。
  残り 3 か所を読めば決まるはず

**(4) `0x0b` と `0x10`**

* `0x10` は `byte83 << 8` で 96% 合う。`0x0b` は 20 通りの値を取り、どのバイトでも決まらない
* どちらも MAME の対応表で「?」になっている所なので、**まず何のレジスタかを調べる**ほうが早い
  （`swp30.cpp` の読み書きをたどる）

**測り方**: `build/nativeplay.exe <rom> nul -b 0,0,0 --sweep 128` が一致率を出す。
1 つ式を入れたら毎回これを回す。

0 と 1 は**調べもの**で、失敗しても今の作りには何の影響も無い。2 以降は新しい口
（`mu2000::set_native_engine(true)` のような切り替え）の中だけで動かし、既定は firmware のまま。

### 6.40 CC73（EG アタック）の式を追って、**式より写し取り直しが正しい**と分かった

まず実機のコードを読んで式は解けた。`0x127288` がそのものずばりで、

```
R3 = ram[パートの塊 + 26]          // CC73 の値
R4 = R3 - 64
if (R4 <= 0) { R4 = R5 - (R4 >> 1); if (R4 > 63) R4 = 63; }   // SHAR（算術）
else         { R4 = min(rom[0x1E54A4 + R4], R5); }
if (R4 == 0) R4 = 4;
R4 <<= 1; if (R4 == 126) R4 = 0xFF;
→ レジスタ 0x06 の上位 = ATTACK_TAB[R4 & 0x7f]
```

`R5` は**要素の byte73**（CC73=64 のとき `R4 = R5` になり、実測の
GrandPno 47・Strings 43・Trumpet 48 と一致）。ROM 表 `0x1E54A4`（64 バイト）も
実測と 1 つ違わず合った（cc65→41・cc81→21・cc97→13・cc113→6 …）。

**それでも式は入れなかった。** `nativeplay --ccreg 73` で見ると、CC73 は
`0x06` だけでなく **`0x00`（切る高さ）・`0x07`・`0x0b`（フィルタの包絡線）も
動かす**多目標のつまみだった。`0x06` だけ式にすると、かえって実機から離れる。

#### 代わりに: つまみが動いたら**写し取り直す**

6.38 の「経路の印」（`cal_ctx`）に、EG のつまみを混ぜるだけでよかった。

| つまみ | パートの塊 | 中身 |
|---|---|---|
| CC73 | +0x1A | EG アタック |
| CC75 | +0x1B | EG ディケイ |
| CC72 | +0x1C | EG リリース |
| CC94 | （RAM に出ない） | バリエーション送り。**口の側で覚える** |

対応するバイトは `nativeplay --ccbyte <番号>` で探した（その CC を振って、
動いたワーク RAM のバイトを出す）。CC94 だけはワーク RAM に出てこない
（掛かり先がパートに繋がっていないと firmware が何も書かない）ので、
`part_cc::var` として口の側で覚えて印に混ぜている。

覚え先の鍵も変えた。**音色の記録（下 32bit）＋経路の印（上 32bit）**にしたので、
つまみを行き来しても取り直しは経路ごとに 1 度で済む（`native_driver::cal_key`）。
天井は 512 件（`CAL_MAX`。DAW がつまみを掃いても膨らまない。溢れたぶんは
firmware が鳴らす）。

これで **CC72・CC73・CC75・CC94 はパートを firmware に任せきりにしなくなった**。

#### 測った結果（新しい試験 `egcc`）

Strings で 6 音、間で CC73→20・CC73→100・CC75→20・CC72→100 と振り、
最後に既定へ戻す。

* 写し取りは **5 回**（経路が 5 通り）。最後の 1 音は最初の写しを使い回して native
* 波形の残差（時刻を合わせたあと）: 1 音目 -69.9dB / 2 -38.9 / 3 -25.0 /
  4 -52.6 / 5 -55.1 / **6 音目（native）-53.0dB**

`lofi`（CC94 を使う）で SH-2 を回す割合が **57.1% → 28.6%**、
`effects` は写し取りが動くようになった（前は 0 回）。
実曲（still_more_fighting_lead 30 秒）は **1.9% のまま**で悪化なし。

#### 残っているもの

ポルタメント（CC5 +0x61・CC65 +0x60・CC84 +0xD3）とアフタータッチは、
**1 音の写し取りでは足りない**（音が鳴っている間ずっと音程を動かす）ので、
今も firmware に任せている。ここは式を起こすしかない。

### 6.41 ポルタメントの滑り方を測った（表は `0x1E6698`）

`nativeplay --porta <CC5>` と `--portasweep <刻み>` で、ポルタメントを入れて
低い鍵から高い鍵へ移ったときの**音程レジスタ `0x11`** を時刻つきで録った。

分かったこと:

* 滑りは**レジスタの値の上で線形**（＝対数周波数で線形。セントで一定速度）
* firmware は **10 ms ごと**に一定量を足す
* 新しい音は**前の音の音程で鳴り始める**（鍵を押した時点で `0x11` は前の音の値）
* 速さは ROM の表 **`0x1E6698`**（16bit・128 語・CC5 で直に引く）

目盛りが 2 通りある:

| CC5 | 読み方 | 例 |
|---|---|---|
| 24-127 | **表 ÷ 128 = 10ms あたりのセント** | CC5=64 → 2560/128 = **20 セント** |
| 0-23 | **表 × 2 = 10ms あたりのセント**（256 倍の目盛り） | CC5=16 → 120×2 = **240 セント** |

CC5=127 は 16/128 = 0.125 セント/10ms（1 オクターブに 16 分）、
CC5=3 は 600×2 = 1200 セント/10ms（1 オクターブが 1 刻み）。
測った 28 点は全部この式と 1% 以内で合った（速い側は刻みが数回しかないので
測りの精度がそこまで）。

レジスタの単位に直すと `刻み = セント × 1024 / 1200`。

これで**ポルタメントを native で鳴らす材料はそろった**（あとは前の鍵を
パートごとに覚えて、スロットごとに滑らせるだけ）。

### 6.42 ポルタメントを native で鳴らせるようにした

6.41 で分かった式をそのまま入れた（`nv::porta_step`・`slot_use::glide`）。

* スロットは「**まだ残っている音程のずれ**」（セント × 256）を持つ
* 鳴らし始めは `ずれ = (前の鍵 - いまの鍵) * 追従 * 256`
* `tick()` が 10ms ごとに `porta_step(ROM, CC5)` だけ 0 へ寄せ、
  そのたびに `0x11` を書き直す（ベンドと要素の離調も入れて作る）
* 刻みは**世界共通の格子**（`clock / 441`）に乗せる。firmware の 10ms タイマも
  世界共通なので、同時に始まった音の滑りがそろう

つまみは CC5（速さ）・CC65（入切）・CC84（滑り出す鍵を指定。1 度で使い切る）。
どれも `handles_cc` に入れて、firmware 任せの印（`unknown_bit`）から外した。

#### 落とし穴: firmware が鳴らした音の鍵も覚えること

最初に作ったとき、**写し取りの 1 音目のつぎの音だけが滑らなかった**。
写し取りの音は firmware が鳴らすので口の `note_on` を通らず、
「最後に押した鍵」が入らないままだった。`note_fw(part, note)` を足して、
firmware に回した音でも鍵を覚えるようにした。

#### 測った結果（新しい試験 `porta`）

Square Lead で 5 音、ポルタメントを入れて上下に滑らせ、途中で速さを変え、
最後に切る。**5 音のうち 4 音が native**（前はパートごと firmware 任せで 0 音）。

| | 値 |
|---|---|
| 全体の大きさ | **-0.28 dB** |
| オクターブ帯ごと | **全部 ±1.1 dB 以内** |
| 音程（自己相関で追った） | 測りの刻み 1 つぶん以内で一致 |

**波形の残差は使えない**。滑り終わったあとも位相が揃わない（firmware の 10ms
タイマの位相が分からないので、滑る道が最大 10ms ぶんずれる）。周波数が同じで
位相だけ違う 2 つの音の残差は +3dB になるので、ここは大きさと帯で見る。

これで**パートまるごと firmware に任せる場面はアフタータッチだけ**になった。

### 6.43 つまみの割り当てを見て、firmware に任せる場面を絞った

アフタータッチは「native では何も起きないから」という理由で、
**そのパートを丸ごと firmware に任せて**いた。しかも一度でも触れた強さの
メッセージが来たら印が立ちっぱなしで、曲の最後まで戻らなかった。

#### 測ったら、既定では本当に何も起きない

`nativeplay --at`（音を伸ばしたまま触れた強さを **0 と 127 で行き来**させ、
スロットのレジスタとパートの塊を見る）で 3 音色を調べた:

* 動くのは**パートの塊の +0x7F**（受け取った値そのもの）だけ
* SWP30 のレジスタは 1 つも動かない
  （最初 `0x00` が動いて見えたのは、フィルタの包絡線がひとりでに
   減っていただけ。行き来させたら値は単調に減り続けた）

#### 割り当ての場所を `--xgmap` で突き止めた

XG のパート parameter（`08 pp rr`）を 0x00 から 0x7F まで 1 つずつ書いて、
**ワーク RAM のどのバイトに入るか**と書く前の値（＝既定）を出す道具を足した。

| XG | ワーク RAM | 中身 |
|---|---|---|
| `08 pp 00`-`28` | +0x00-+0x28（そのまま） | 音量・パン・EG・**MW**（+0x1D-22）・**ベンド**（+0x23-28） |
| `08 pp 29`-`40` | （受け取りスイッチ。0/1 しか取らない） | |
| `08 pp 41`-`77` | **+（XG − 7）** | 音律（+0x3A-45）以降 |
| `08 pp 4D`-`52` | **+0x46-+0x4B** | **アフタータッチ（CAT）** |
| `08 pp 53`-`58` | +0x4C-+0x51 | 鍵ごとのアフタータッチ（PAT） |
| `08 pp 59` / `5A`-`5F` | +0x52 / +0x53-+0x58 | **AC1** の CC 番号（既定 16）と割り当て |
| `08 pp 60` / `61`-`66` | +0x59 / +0x5A-+0x5F | **AC2** の CC 番号（既定 17）と割り当て |

どれも**6 つ組**（音程・フィルタ・音量・LFO の PMOD/FMOD/AMOD）で、
既定は `64,64,64,0,0,0`（モジュレーションだけ `64,64,64,10,0,0`）。

`08 pp 4E`（CAT フィルタ）を 0 にしてから同じ掃引をすると、
今度は `0x00`・`0x09`・`0x11` がはっきり動いた。**割り当てが既定から
外れているときだけ効く**と裏が取れた。

#### 直したこと

* アフタータッチ（`0xD0`）・鍵ごとのアフタータッチ（`0xA0`）は、
  **CAT / PAT の割り当てが既定のあいだは firmware に任せない**
* **AC1・AC2 を見るようにした**。割り当てられた CC 番号が来て、かつ
  割り当てが既定から外れていれば任せる。前は黙って無視していた（抜け穴）
* **モジュレーション（CC1）とベンド**も、割り当てが既定から外れていたら任せる。
  こちらの式は既定の割り当てを前提にしているので、そこは合わない

#### 測った結果（新しい試験 `at`）

GrandPno で 5 音。途中で触れた強さを送り（既定なので効かない）、
そのあと `08 pp 4E` で CAT フィルタを既定から外して、また触れる。

| 音 | どこで鳴ったか | 残差 |
|---|---|---|
| 1（写し取り） | firmware | -67.1dB |
| 2 | **native** | -48.2dB |
| 3（触れた強さあり・既定） | **native** | -31.0dB |
| 4（CAT を外したあと） | firmware | -9.1dB（ほぼ無音の音） |
| 5 | firmware | -49.1dB |

前は 3 音目から最後まで firmware だった。

### 6.44 残った SH-2 は「曲の頭の 0.55 秒」だった／SysEx の待ちを実測で絞った

まず、残っている割合が**曲の長さに比例しない**ことを確かめた。
still_more_fighting_lead を長さだけ変えて鳴らすと:

| 長さ | SH-2 を回した割合 | 実時間に直すと |
|---|---|---|
| 15 秒 | 3.7% | 0.56 秒 |
| 30 秒 | 1.9% | 0.57 秒 |
| 60 秒 | 0.9% | 0.54 秒 |
| 120 秒 | 0.4% | 0.48 秒 |

倍にすると割合がきれいに半分になる。**残りは曲の頭の約 0.55 秒ぶん**
（XG リセットの SysEx・音色の指定・音色ごとの 1 音目）で、鳴らし続けても増えない。

#### SysEx の待ちが粗すぎた

それまでの判定は「XG のパラメータチェンジで hh が 00（システム）・02（エフェクト）・
03（インサーション）なら 300ms 待つ」。つまり**値を変えるだけのものまで 300ms**
待っていた。新しい口 `nativeplay --sxsettle hh,mm,ll,dd` で
「SWP30 を触り終わるまで」を測ると、はっきり 2 群に分かれる:

| SysEx | 何をする | 触り終わるまで |
|---|---|---|
| `00 00 7E` | XG システムオン | **212 ms** |
| `02 01 00` | リバーブの種類 | **176 ms** |
| `02 01 20` | コーラスの種類 | **177 ms** |
| `02 01 40` | バリエーションの種類 | **182 ms** |
| `03 0n 00` | インサーションの種類 | **182 ms** |
| `00 00 04` | マスターボリューム | 0 ms |
| `02 01 02` | リバーブのパラメータ | 3.9 ms |
| `02 01 22` | コーラスのパラメータ | 0 ms |
| `03 0n 02` | インサーションのパラメータ | 3.1 ms |
| `08 pp xx` | パートの設定 | 0 ms |

**重いのは MEG のプログラムを書き直すものだけ**。そこで判定を
「システムオン／全パラメータリセット、エフェクト 3 種の**種類**、
インサーションの**種類**」に絞った（種類は 2 バイトなので下位の番地も含める）。

判定に使うバイトが 1 つ増えるので、XG のパラメータチェンジ（`43 1n 4C`）と
分かったときだけ 6 バイト目まで待つ。**そうでないもの（GM システムオンなど）は
5 バイトのままで重い扱い**——ここを一律 6 バイトにすると、5 バイトで終わる
GM システムオンが判定に届かず軽く扱われてしまう。

#### 測った結果（新しい試験 `sxparam`）

Strings で短い音を 12 個並べ、鳴らしている間ずっとリバーブの**パラメータ**を
振る（種類は頭で 1 回だけ）。

| | 直す前 | 直したあと |
|---|---|---|
| SysEx で回した割合 | **63.1%** | **9.2%** |
| 合計 | 67.7% | **19.7%** |
| 大きさの差 | -0.18 dB | **-0.18 dB** |
| オクターブ帯ごと | +7.29 +0.09 -0.12 -0.18 -0.25 -0.24 -0.22 -0.13 dB | **同じ（0.02dB 以内）** |

**音は 1 つも変わっていない**（残差も帯ごとの差も直す前と同一）。
`effects` と `lofi` は種類を変える曲なので、絞りすぎればここで落ちる。

#### ついでに見つけた、まだ直していないもの

この曲では native の口の **62-125Hz の帯が +7.3dB 高い**（直す前から同じ）。
鍵 60 以上の Strings なのでその帯に基音は無く、リバーブの尾のはず。
`effects` は通っているので、この曲に固有の何か。別途調べる。

### 6.45 窓から入切できるようにした（聞き比べ用）

音がどこまで実機に近づいたかは**耳で確かめるしかない**ので、軽量エフェクトと
同じように、鳴らしたまま入切できるようにした。

* 窓を右クリック →「firmware を走らせずに鳴らす（速い・まだ音が違う）」
* **F4** でも同じ
* いま入っているかは、メニューの印で分かる

切り替えは軽量エフェクトと同じ道（`engine::want_native_engine` に頼んで、
音声の糸が `fill()` の頭で `set_native_engine()` を呼ぶ）。

#### 切るときは、こちらで鳴らしている音を離すこと

切ったあと firmware はそのスロットを知らないので、**離さないと鳴りっぱなしに
なる**。`native_driver::silence()` を足して、`set_native_engine(0)` の頭で呼ぶ。
ぶつ切りではなく、離しの速さで鳴り終わる。

確かめ方も足した。`render --native-engine --native-off <秒>` でその時刻に切れる
（窓の F4 と同じ道を通る）。`chord` を 2.0 秒で切ると:

| 秒 | 切らない | 2.0 秒で切る |
|---|---|---|
| 1.60 | 1737 | 1737 |
| 2.00 | 1579 | 1018 |
| 2.80 | 1729 | 635 |
| 3.60 | 950 | 247 |
| 4.40 | 27 | 6 |
| 5.60 | 0.5 | **0.0** |

素直に減衰して 0 になる。窓でも、鳴らしながら F4 を 8 回（入切 4 往復）
叩いても落ちないことを確かめた。

**入れ直すと写し取りは白紙に戻る**（`set_native_engine(1)` が
`native_driver::reset()` を呼ぶ）ので、その音色の 1 音目はまた firmware が鳴らす。
往復するたびに写し取り直すが、聞き比べには困らない。

### 6.46 写し取りが「別の音のスロット」を掴んでいた

利用者から「切り替えてしばらく鳴らしていると、急に EG が壊れる。
ストリングスの立ち上がりが極端に遅くなったり、逆にエレピのリリースが
無くなってミュート奏法のような響きになる」という報告。**一度壊れると
その音色にずっと残る**のが手がかりだった。

原因は `native_learn_finish` のここ:

```cpp
if (idx < 0)
    idx = int(cals.size()) < nel ? int(cals.size()) : 0;   // ← 黙って採用していた
```

写し取りは「どの要素か」を**そのスロットが鳴らしている波形の番地**で見分ける。
番地がその音色のどの要素とも合わない＝**別の音のスロットを掴んでいる**のに、
そのまま採用していた。掴んだ音の `0x06`/`0x07`/`0x08`（包絡線）がその音色の
写し取りとして覚えられ、以後その音色の全部の音に焼き付く。症状と一致する。

**直し方**: 波形の番地が取れているのにどの要素とも合わなければ、その写しを
捨てる（次の音でやり直す）。全部捨てれば写し取り自体が残らないので、
その音色はまた firmware が鳴らす。番地が取れていないときは今まで通り。

#### なぜ `render` では出なかったか: MIDI の配り方

`render` は MIDI を**サンプル単位**で配るが、**窓もプラグインも音声のブロック
単位**でまとめて配る。同じ時刻に音が重なると、firmware がどのスロットを
どの順で鳴らすかが変わり、写し取りが関係ないスロットを掴む。

そこで `render --midi-block <フレーム>` を足した。そのブロックぶんの MIDI を
ブロックの頭でまとめて渡す＝窓やプラグインと同じ並びになる。

```
dense.mid  サンプル単位   … 掴み違い 0 回
dense.mid  --midi-block 512 … **掴み違い 1 回**（前はこれが焼き付いていた）
```

数えられるように `render --native-engine` の表示にも足した:

* `写し取りで別の音のスロットを掴んで捨てた N 回`
* `写し取りが汚れた N 回`（窓の中で別の音が同じスロットに鳴り始めた）
* `スロットの奪い合い N 回`（firmware がこちらの鳴っているスロットを取った）

後ろ 2 つは今のところ 0 のままだが、置いておけば次に出たときすぐ分かる。

#### まだ分かっていないこと

上の直しで**掴み違いは起きなくなった**が、利用者の症状そのものは手元の
曲では再現できていない。`dense` は声が多いと波形の残差が 0dB（＝位相が
まるで合わない）まで落ちるが、大きさは ±1dB で追従していて、
試験（大きさで見る）では通ってしまう。**多声のときの 1 音ずつの確かめ方**が
足りていないので、そこが次の宿題。

### 6.47 利用者の曲で追い込んだ（液晶が固まる／音色が壊れる）

利用者から 3 つの手がかりが出た。どれも同じ根に繋がっていた。

1. 切り替えてしばらく鳴らすと急に EG が壊れる（立ち上がりが極端に遅い、
   リリースが無い）。**一度壊れるとその音色にずっと残る**
2. **液晶が途中で固まり、前面のボタンも一切効かない**
3. アプリを開き直しても**曲の頭から**壊れている（状態が残っている？）

#### 2 の答え: firmware を完全に止めていた

`run_sample` は `m_fw_hold == 0` なら CPU を回さない。全部 native で鳴る曲では
MIDI が来たときしか回らないので、**firmware が丸ごと止まる**。液晶を描くのも
ボタンを読むのも firmware なので、どちらも死ぬ。

100ms ごとに 5ms だけ回す（`KEEPALIVE_EVERY` / `KEEPALIVE_RUN`）ようにした。
実曲で SH-2 は 7% → 11.7%（そのうち 4.6% がこのぶん）。

#### 3 の答え: NVRAM がワーク RAM 丸ごとだった

`nvram` は 0x400000-0x43ffff の 256KB をそのまま残し、次の起動で戻す。
firmware の**生きた状態も一緒に残る**。native の口で firmware を飢えさせた
まま窓を閉じると、中途半端な状態が保存されて次回に持ち越される。

`engine::settle_for_save()` を足して、残す前に native を切り（鳴っている音は
離される）0.5 秒回してから保存するようにした。すでに壊れた NVRAM は
`gui --factory` で捨てられる。

#### 1 の答え: 包絡線を写し取りから取っていなかった

利用者の曲（DQ2_121.mid）を借りて、**firmware と native の SWP30 書き込みを
1 つずつ突き合わせた**。そのための道具も足した:

* `render --trace-swp` に **native の書き込みも残す**（`N ` 付きの行）。
  それまでは firmware のバス書き込みしか記録に残らず、比べようがなかった
* `render --midi-block <フレーム>` で、窓やプラグインと同じ
  「ブロック単位で MIDI をまとめて配る」並びを作れる
* 突き合わせは scratchpad の `trdiff.py`（鍵を押した時刻で対応づけ、
  その直前 20ms に書かれたレジスタだけを比べる）

出てきた 1 位が **`0x06`（立ち上がり）で 56 音中 56 回**。
`firmware=417e` に対し `native=387e` ＝ **こちらの方がずっと遅い**。

原因は `build_note` の「写し取りで上書きするレジスタ」の一覧に
**`0x06` が入っていなかった**こと。包絡線は常に ROM の式だけで決まっていて、
**パート側の EG 設定（CC73 など）が native の音に一切効いていなかった**。
この曲は CC73 を 16 パート全部に送っている（55・60・64・65）。

立ち上がりは鍵でも強さでも変わらないと測ってあるので
（`nativeplay --egwatch` を鍵 36-96・強さ 1-127 で確認）、写し取った値を
そのまま使える。`0x07`・`0x08`（減衰）は鍵で変わるのでまだ入れられない。

#### ついでに出た 2 位: firmware が裏でつまみを書き替えていた

次に多いのが `0x33`（リバーブ送り）で 46 回。調べると、曲は CC91=40 を
1 回送るだけなのに、**パートの塊 +0x13 は 33 や 31 になっていた**。
音色を替えると firmware がつまみを音色の既定値で上書きするため。

`sync_cc()` は「こちらが触っていない（-1）ものだけ RAM から拾う」だったので、
**firmware が裏で書き替えたことに気づけなかった**。前に見た RAM の値を
覚えておき、**RAM が動いていたら firmware が書き替えたとみなして取り込む**
形に変えた（`take_ram`）。

#### いまの残り（利用者の曲・12 秒・55 音で）

| レジスタ | 前 | いま | 何 |
|---|---|---|---|
| `0x06` | 56 | **10** | 立ち上がり（残りは写し取り前の音） |
| `0x33` | 46 | **7** | リバーブ送り（残りは同期が効く前） |
| `0x09` | 16 | 16 | 音量の減衰 |
| `0x00` | 15 | 15 | フィルタの切る高さ |
| `0x08` | 10 | 10 | 減衰 2 |

**差分器の落とし穴**: 最初は「そのスロットに過去書かれた値」を持ち越して
比べていたので、`0x21`・`0x23`・`0x2b`・`0x30`・`0x31` が大量に違って見えた。
記録を追うと **firmware はこれらを一度も書かない**（0x20-0x2b は偶数番だけ）。
鍵の直前 20ms に書かれたものだけを比べるようにして消えた。

### 6.48 フィルタの強さ依存の式を実機のコードから起こした（`0x127FA4`）

6.6 から「実機はフィルタの切る高さに鍵と強さの倍率を掛けるが、その係数が
分からない」と書いてあった所。`tools/dump/sh2dis.py` で読んだら出た。

```
127FA4  ; 入口: R6 = 切る高さの目盛り（0-127）、R5 = 鍵の情報、R4 = パートの塊
127FB2  R1 = [R4+44]
127FB4  R6 += R1[11] - 64            ; つまみのぶん（0-127 に丸める）
...
127FE0  R1 = R1[22]                  ; **強さ→フィルタの深さ**（ドラムは [R4+48]）
127FE4  R0 = R5[3]                   ; 強さ（velocity）
127FEC  R4 = R1 - 64
127FEE  R0 = R0 - 100                ; **基準は強さ 100**
127FF0  R4 = R4 * R0
127FF4  R4 >>= 4                     ; 符号つき（SHAR ×4）
127FFC  R4 += 128
127FFE  R6 = R6 * R4                 ; 16bit 符号つき
128008  負なら 0
12800A  R6 = (R6 * 2) >> 8           ; ＝ / 128
128016  127 で頭打ち
```

つまり

```
倍率   = 128 + ((深さ - 64) * (強さ - 100)) >> 4      （符号つき・0 の側へ）
目盛り = clamp(元の目盛り * 倍率 / 128, 0, 127)
```

**強さ 100 が基準**（そこで倍率がちょうど 128 ＝ 等倍）。写し取りの
`cal_vel` の既定が 100 なのと辻褄が合う。

#### 測った形（`nativeplay --egwatch` に 0x00 を足した）

GrandPno・鍵 60 でレジスタ `0x00` の下 12bit:

| 強さ | 1 | 16 | 32 | 48 | 64 | 80 | 96 | 112 | 127 |
|---|---|---|---|---|---|---|---|---|---|
| 値 | 0x52b | 0x53b | 0x54b | 0x56b | 0x57b | 0x5ab | 0x5cb | 0x64b | 0x69b |

鍵は **60 を底にした V 字**（vel 64 で 鍵 24→0x5bb、48→0x59b、60→0x57b、
72→0x59b、96→0x5db、108→0x61b）。Strings は開き切りで飽和して動かない。

#### まだ入れていない理由

鍵を押した時点の `0x00` は **`16k + 11` の形**で、`CUTOFF_TAB` を直に引いた値
ではない（表の値は端数がばらばら）。つまりここはフィルタの包絡線の出発値で、
上の式で出した「目盛り」がさらに一段加工されている。その一段が分かるまでは
写し取り（その音の値をそのまま使う）の方が近い。

いまは `0x00` を写し取りから取っているので、**写し取ったときの強さでは合う**。
利用者の曲の残りの食い違い 15 回は、写し取りと違う強さで鳴らした音。

### 6.49 いまどこまで合っているか（利用者の曲で測った）

一晩かけて、利用者の曲（DQ2_121.mid）で firmware と native の書き込みを
突き合わせて詰めた。12 秒・時刻で対応づいた 55 音での食い違い:

| レジスタ | はじめ | いま | 何をしたか |
|---|---|---|---|
| `0x06` 立ち上がり | 56 | **0** | 写し取りから取るようにした（6.47） |
| `0x33` 送り | 46 | **7** | firmware の裏の書き替えを取り込むようにした（6.47） |
| `0x09` 音量 | 16 | **6** | （まだ） |
| `0x00` フィルタ | 15 | **5** | （まだ） |
| `0x08` 減衰 | 10 | **0** | 写し取り時のずれを覚えて足す（6.50 の下） |

合計 143 → 18。

#### 音でどうなったか

| 区間 | 直す前 | いま |
|---|---|---|
| 4-12 秒 | -1.27 dB | **-0.96 dB** |
| 12-24 秒 | -1.52 dB | **-1.16 dB** |
| 24-36 秒 | -0.89 dB | **-0.63 dB** |
| 36-48 秒 | -0.10 dB | -0.07 dB |
| 48-59 秒 | +0.01 dB | -0.01 dB |
| 全体 | -0.60 dB | **-0.45 dB** |

#### 残っているものの正体（オクターブ帯で切り分けた）

* **12-24 秒**: 125Hz-16kHz が**一様に -1dB**。帯で偏らないので**音量**の問題。
  `0x09` の食い違いは「こちらが 2 段（0.75dB）静か」で、桁が合う
* **48-59 秒**: 中域は ±0.05dB で合っているのに **8-16kHz が +4.9dB**。
  こちらのフィルタが開きすぎている（差分でも `firmware=1747` に対し
  `native=1767` ＝ こちらの方が開いている）

つまり残りは **音量（`0x09`）とフィルタ（`0x00`）の 2 つ**にきれいに分かれた。

#### 音量（`0x09`）について分かっていること

* 実機が `0x09` を書く所は `0x12E484`。
  `0x09 = (上位そのまま) | clamp255(値 + ram[0x4226A8])`。
  この「全体に効く下駄」は測ったら **0** だったので、原因ではない
* CC7 → `0x09` の対応を実測した（`nativeplay --ccreg 7`）。
  こちらの式 `2 * LEVEL_TAB[cc-1]` は **64 点中 22 点でずれる**（ずれは ±2）
* **ROM 全体を探しても、この対応を出す表は無い**（`scratchpad/findtab.py`
  で 4MB 全部を係数 1/2/4・添字 cc/cc-1 で総当たり）。表引きではなく計算らしい
* つまり音量と表現を掛けてから一度に対数に直している可能性がある。
  そこは `0x12E484` の呼び出し元（`0x127B60` などに番地が置いてある）を
  読むしかない

#### フィルタ（`0x00`）について分かっていること

6.48 の式（`倍率 = 128 + ((深さ-64)*(強さ-100))>>4`）まで出ている。
残っているのは「その目盛りから鍵を押した時点の `0x00`（`16k+11` の形）を
どう作るか」と、「深さ」がどの塊の byte22 か。

#### 気をつけること: firmware は同じ値を何度も書き直す

記録の書き込み回数は firmware 6965 回に対し native 1513 回（`0x00`）だが、
**中身は同じ値の書き直し**（鍵から 8-126ms の間に数回、値は変わらない）。
回数の差は音の差ではない。ここを勘違いすると「包絡線を再生し切れていない」
と誤診する。

### 6.50 音量の式を実機と並べる道具と、そこで分かったこと

`nativeplay --levelcheck` を足した。鍵 60・強さ 100 で 1 音鳴らして校正し
（写し取りと同じ手順）、そのあと鍵と強さを振って**実機が `0x09` に入れる値と
こちらの式を並べる**。内訳（曲線・段の音量・目盛り）も一緒に出る。

#### 直したこと: 鍵の曲線の倍率が 2 倍になっていた

Strings で 24 点中 16 点がずれていた。ずれは**強さに依らず鍵だけ**で決まり、
鍵 60 から離れるほど +2・+4 と増える。`LEVEL_CURVE_MUL` はコメントに
「実測では 1 倍」と書いてあるのに **2** だった。1 にすると:

| | 直す前 | いま |
|---|---|---|
| ずれた点 | 16 / 24 | **8 / 24** |
| 鍵 60-96 | ずれる | **完全に一致** |

利用者の曲（172 秒）でいちばん悪い区間が -1.23dB → **-1.00dB**、
48-64 秒は **±0.00dB** になった。

#### 強さの曲線は元から完全に合っていた

念のため測ったら、`2 * LEVEL_TAB[VEL_CURVE[強さ]]` は **17 点すべて一致**。
ここは疑わなくてよい。

#### 残っている鍵 36・48 の +2：足し算の形では説明できない

残るずれは鍵 60 より下だけ。Strings は `byte60 == 0xFF` なので ROM の曲線
（番号 668）をちゃんと引いている。曲線は 鍵36→0、48→-1、60→-2、72→-3、
84→-5、96→-7。

いまの式は `目盛り = 素の音量 + 曲線` として `LEVEL_TAB[0x80 + 目盛り]` を引く。
**この形では全部の鍵が合う「素の音量」が存在しない**（0-127 を総当たりして
解なし）。実機が必要とするのは 曲線0→11、-1→11、-2→12、-3→12、-5→13、-7→14
だが、表の平ら（77-79→11、73-76→12、70-72→13、67-69→14）と噛み合わない。

実機は音量まわりを**線形の値で掛けて `>>7`** する形（6.49 の `0x12A404`）
なので、鍵の曲線も足し算ではなく**掛け算**とみるのが筋。そこが次の宿題。

#### 校正の曖昧さも効いている

`level_from_att` は表を逆に引くとき、同じ減衰になる目盛りが並ぶので
**真ん中**を返している。平らが 3-4 段あるので、実機の本当の目盛りとは
最大 ±2 ずれる。掛け算の形が分かれば、この逆引き自体が要らなくなる。

### 6.51 残っているのは「多段サンプルの段ごとの音量」

6.50 で鍵の曲線を直したあと、16 音色 × 24 点（鍵 6 × 強さ 4）で測り直した。

| | 食い違い |
|---|---|
| 目盛りに足す形（`LEVEL_CURVE_MUL=1`） | 166 / 384 |
| **減衰に足す形（いま）** | **104 / 384** |

完全に一致した音色: Strings・11・19・30・40・48・56・65。
残る食い違いは**多段サンプルの音色**に集中している。

#### 電子ピアノ（音色 4）で見た中身

```
 鍵  実機  こちら   ずれ   曲線  基準鍵  波形の番地
 60    38     38    +0      -3     73    40320263
 72    54     36   -18      +0     81    4032174d
 84    64     40   -24      -5     90    40321f0e
```

鍵 72 で波形（段）が変わり、そこから大きくずれる。波形の記録の 16 バイトを
見ると、段ごとに **byte11** が 78 → 50 → 30 と変わっている（こちらが
段の音量として読んでいる byte0 はどの段も 0）。

ただし byte11 をそのまま使う形は、どれも合わなかった:

* `LEVEL_TAB[0x80 + byte11]` を減衰に足す → 必要な値は 11/20/23、表は 11/21/33
* `目盛り = (素の目盛り * byte11) >> 7` → 必要な目盛りは 71/48/42、
  この式では 71/45/27

必要な目盛りは 78→71、50→48、30→42 で、**byte11 に比例していない**
（78→50 で 23 下がるのに、50→30 では 6 しか下がらない）。段の音量は
別の所から来ているか、もう一段の変換が挟まっている。ここが次の宿題。

### 6.52 音量の式を最後まで詰めた（`0x09` の食い違いが 0 になった）

6.50・6.51 の続き。道具を直しながら 2 つ直した。

#### 道具の直し その 1: 要素ごとに対応づける

`--levelcheck` は「最初に鳴ったスロットの `0x09`」を見ていた。要素が 2 つ
ある音色では別の要素の値と比べてしまう。波形の番地で結び付けるようにしたら、
EPiano1 のずれは -18〜-24 から **-2〜-10** に縮んだ（半分以上が計測の誤り）。

#### 道具の直し その 2: 先に測ってから総当たりする

「効き具合」を総当たりするとき、候補ごとに鳴らし直していた。firmware の声が
64 で枯れるので、途中から比較点が無くなり**どの候補も「外れ 0」に見えて**
いた。先に 1 回測ってから候補を回す形に直した。

#### 直し その 1: 鍵の曲線の効き具合は 1.5 倍

16 音色で総当たりすると、外れがいちばん少ないのは 5/4〜7/4、多くは **6/4**。
1 倍でも 2 倍でもなかった（`LEVEL_CURVE_NUM / LEVEL_CURVE_DEN`）。

#### 直し その 2: 逆引きは「平らな範囲の上端」

Strings を長く鳴らして並べると、校正した鍵 60 は完全に一致するのに
**鍵 48 だけ -0.61dB** 静かだった。素の音量が 77 ではなく **79** なら
鍵 6 つとも合う。`level_from_att` が平らな範囲（3-4 段）の**真ん中**を
返していたのが原因。上端を返すようにした。真ん中だと、鍵の曲線を足した
あとで表の段を 1 つ踏み外す。

#### 結果

利用者の曲（12 秒・55 音）でのレジスタの食い違い:

| レジスタ | 夜のはじめ | いま |
|---|---|---|
| `0x06` 立ち上がり | 56 | **0** |
| `0x33` 送り | 46 | 7 |
| `0x09` 音量 | 16 | **0** |
| `0x00` フィルタ | 15 | 5 |
| `0x08` 減衰 | 10 | **0** |
| **ずれの合計** | — | **199**（試した全案で最小） |

音は 172 秒で:

| 区間 | 夜のはじめ | いま |
|---|---|---|
| 0-16 秒 | -0.81 | **-0.79** |
| 32-48 秒 | -0.16 | **-0.13** |
| 48-64 秒 | +0.00 | **+0.02** |
| 80-96 秒 | -1.23 | **-0.98** |
| 128-144 秒 | -0.00 | **+0.01** |

#### 比べ方の教訓

指標が 3 つ（音色掃引・曲のレジスタのずれ・曲の音）あって、**食い違いを
「回数」でしか見ていなかったときは判断がぶれた**。`tools/trace_diff.py` に
**ずれの大きさの合計**を出すようにしてから、どの案が良いかが安定して決まる
ようになった。回数だけ見ると「小さなずれが多い案」が不当に悪く見える。

### 6.53 つまみを SysEx で決める曲（`0x33` の食い違いが 0 になった）

6.52 で残っていた `0x33`（リバーブの送り）7 件の正体。

#### 見えていたもの

利用者の曲で、最初の 7 音だけ送りが違った。こちらは `40`、firmware は
`33`（パート 0）と `31`（パート 1・2）。曲の MIDI を見ると、送っているのは
**CC91 = 40 だけ**。どのパートも同じ値なのに、firmware は違う値を持っていた。

#### 遠回りした 2 つの読み違い

1. **「音色の指定が既定値に戻しているのだろう」** と考えて、音色の指定を
   CC と同じ待ち行列に乗せた（順番の入れ替わりを直した）。順番は直ったが
   値は変わらなかった。音色の記録（`Strngs2#`）を覗いても 33 も 31 も無い。
2. **「同期が古い RAM を掴んでいるのだろう」** と考えて、音色を替えた直後は
   ワーク RAM を無条件に信じる窓を作った。これも値は変わらなかった。

どちらも外れ。`sync_cc()` に印を入れて**毎回の同期を並べた**ら分かった:

```
sync#16 clock=172209 RAM=40 …
sync#17 clock=227441 RAM=33 …   ← ここでやっと変わる
```

最初の音は `s=189044`。**firmware が値を書き替えるのは、最初の音より
あと**だった。native の口では firmware を 100ms につき 5ms しか回さないので、
firmware が受け取った MIDI を処理し終えるのが 1 秒以上遅れる。
つまり「firmware の書き替えを待って取り込む」やり方では原理的に間に合わない。

#### 本当の原因

曲の SysEx を並べたら出てきた:

```
43 10 4C 08 00 13 21    ← XG パート 0 のリバーブ送り = 0x21 = 33
43 10 4C 08 01 13 1F    ← パート 1 = 31
43 10 4C 08 02 13 1F    ← パート 2 = 31
```

**つまみを CC ではなく SysEx で決めていた**。native は SysEx を一切見て
いなかったので、CC91 の 40 を握ったままだった。

#### 直し

`mu2000::native_sysex()` を足して、`43 1n 4C 08 pp ll dd…` を自分でも解釈する
ようにした。番地はワーク RAM のパートの塊の並びと同じなので、そのまま
`native_driver::set_part_param()` に渡す。CC と同じ待ち行列（`m_nq`）に
乗せるので、線を流れる遅れも CC と同じ扱いになる。

* 1 回の SysEx で `ll` から続けて何バイトも書けるので、並びの全部を回す
* `08 pp 01/02/03`（バンクと音色）は音色の指定と同じ扱いにする
* **`m_seen` は触らない**。ワーク RAM はまだ firmware が書き替えていないので、
  ここで「見た」ことにすると、次の同期で古い値を取り込み直してしまう

#### 結果

| レジスタ | 前 | いま |
|---|---|---|
| `0x33` 送り | 7 回・ずれ 39 | **0** |
| `0x00` フィルタ | 5 回・ずれ 160 | 5 回・ずれ 160 |
| **ずれの合計** | 199 | **160** |

#### 教訓

**「firmware がいずれ書くから、それを読めばよい」は native の口では成り立たない。**
firmware を細切れにしか回さない以上、曲が送った情報は**こちらが直接読む**必要が
ある。CC・ベンド・アフタータッチはそうしていたのに、SysEx だけ抜けていた。

### 6.54 `0x00`（フィルタ）に残っているものは「鍵の追従」だった

残る食い違いは 5 件、全部**同じ音色・同じ値**（`firmware=1747 native=1767`）で、
ほかの 31 本のレジスタは全部一致している。

#### 外した見立て 2 つ

1. **「強さが写し取りと違うから」**（6.48 にそう書いてあった）。写し取りの鍵に
   強さを入れて測り直したが**まったく変わらなかった**。この曲は全部
   `vel=100` で、そもそも強さは動いていない。
2. **「写し取りの鍵に音の高さも入れれば済む」**（ドラムはそうしている）。
   やってみたら、写し取りが間に合わずに firmware 送りの音が激増して、
   ずれの合計は **160 → 129120** と大幅に悪化した。旋律の音色では
   「1 音色 1 回」の写し取りが効いているので、そこを細かくしてはいけない。

#### 実際に測った形（`nativeplay --keycut` を足した）

鍵を 0 から順に 1 つずつ鳴らして、`0x00` の下 12bit を並べる道具を足した。

| 音色 | 鍵 0-40 | 41 | 46 | 51 | 55- |
|---|---|---|---|---|---|
| Strngs2 | 1767 | 1799 | 1831 | 1863 | 1895 |

| 音色 | 鍵 0-45 | 46 | 60 |
|---|---|---|---|
| GrandPno | 1563 | 1531 | 1499 |

**32 ずつの階段**で、上がる音色と下がる音色がある。段の位置も音色ごとに違う。
利用者の曲で食い違っていた 5 音は**鍵 51-54**（`1863` ＝ `0x747`）で、
写し取りは鍵 55 以上（`1895` ＝ `0x767`）から取っていた。

#### 実機のコードは読めた（`0x128542` → `0x127FA4` → `0x127E08`）

```
128558  R13 = [R14+44]          ; 音色の設定への指し先（ドラムは +48）
12855A  R6  = R13[11]           ; 切る高さの目盛り
128560  JSR 127FA4              ; 強さの倍率をかける（6.48 の式）
128568  R5 = CUTOFF_TAB[R0]     ; 表を引く（0x1E5B58、16bit）
12857C  JSR 127E08              ; ← ここで鍵のぶんが入る
```

`0x127E08` の中身:

```
127E24  R5 = 12C834(R11)              ; R11 = [R12+32]。覚え込み付きの取り出し
127E3A  R4 = [R12+3] - 36             ; 鍵 - 36
127E42  0 <= R4 < 62 でなければ素通り
127E54  R4 = R11[0x82 + R4]           ; **62 バイトの表**（鍵 36 から）
127E5E  R1 = R11[77] - 64             ; 効き具合（符号つき）
127E64  R4 = R4 * R1
127E6E  負なら +3 してから >>2         ; ＝ 0 の側へ /4
127E74  R5 += R4
127E76  R14 = 表の値 + R5
127E82  R14 += [R12+80]
127E88  R14 <= 0x800 なら R14 = 1
127E98  レジスタの値 = R14 & 0x7FF
```

測った階段から逆に解くと、効き具合は **Strngs2 が +4、GrandPno が -8**。
記録の `byte71`（60 と 72）と `128 - byte71`（68 と 56 ＝ 64±4、64∓8）が
合うので、`R11[77]` は `byte71` から作られていそうだが確証は無い。

#### まだ解けていないこと

62 バイトの表（`R11 + 0x82`）が ROM のどこから来るか。`R11 = [R12+32]` は
**音の構造体**（`+2` が印、`+3` が鍵、`+80` が語）の中の指し先で、パートの塊
ではない。要素の 84 バイトには 62 バイトの表は入らないので、ROM の別の所か、
音色を選んだときに作る RAM のコピーのはず。

**次にやること**: `0x12C834` が覚え込んでいる値（`0x128166`）と、
`R11` が指す構造体の正体。`R11[77]` と `R11[0x82]` が読めれば、
`0x00` は写し取りから鍵ぶんずらすだけで出せる（`cutoff_reg` に 1 行足す形）。
それまでは、写し取った鍵の近くでは合い、離れた鍵で最大 2 段（32）ずれる。

### 6.55 曲を最後まで比べた（171 秒）。残りの正体は `0x00` の鍵追従

いままで比べていたのは頭の 12 秒だけだった。**最後まで比べたら別のものが出た**。

#### 直したもの: 終わりのフェードアウト（6.55 の commit）

最後の 11 秒だけ native が **+7.86 dB 大きい**。曲は 160 秒から 168 秒まで
CC7 を 45 → 0 まで下げてフェードアウトするが、native はそれを**鳴っている
音にしか反映していなかった**。離しの長いストリングスが元の音量のまま
鳴り続けていた。離したスロットにも印を付けて追うようにして **+6.15 dB**。

**静かになる方向だけ追う**のが要点。`0x09` を書き直すと離しの坂がそこから
引き直しになるので、いま鳴っているより大きい音を書くと音が生き返る。

#### 残りの本体: `0x00` の鍵追従

94 秒ぶんのレジスタを突き合わせた結果:

| レジスタ | 回数 | 1 回あたりのずれ |
|---|---|---|
| `0x00` フィルタ | **73** | 64 |
| `0x08` 減衰 | 20 | 1049 |
| `0x09` 音量 | 15 | 3 |
| `0x33` 送り | 5 | 3 |

（`0x11`・`0x15`-`0x17` の大きなずれは、音の対応づけが外れた分。
要素の数が違うと数えた 17 件と同じ原因）

**`0x00` が飛び抜けて多い**。そして音の差の形とも合う。78-96 秒の
オクターブ帯を見ると:

| 帯 | 差 |
|---|---|
| 31-125 Hz | ±0.0 dB |
| 250-500 Hz | -0.92 dB |
| 1-2 kHz | -1.06 dB |
| 8-16 kHz | -0.14 dB |

低い所は合っていて**中域だけ 1 dB 足りない**。音量の問題なら全帯域が
同じだけ動くので、これはフィルタの問題。写し取った鍵と違う鍵で鳴らすと
切る高さがずれる、という 6.54 の話がそのまま出ている。

#### 12 音色で測った鍵の曲線（`nativeplay --keycut`）

| 音色 | 平らな値 | 段の位置と向き |
|---|---|---|
| GrandP  | 1563 | 46:-32 60:-32 |
| DrawOrg | 1897 | 79:-32 85:-32 87:-32 88:-32 90:-32 91:-32 |
| Strngs2 | 1767 | 41:+32 46:+32 51:+32 55:+32 |
| BrssSec | 1681 | 66:+32 69:+32 72:+32 |
| Violin  | 1575 | 50:+32 52:+32 54:+32 56:+32 58:+32 60:+32 |
| Flute   | 794  | 50:+32 51:+32 53:+32 54:+32 56:+32 … |

**段はいつも 32**（レジスタの下 12bit が `32q + 一定` の形）。
間隔は音色ごとに違い、向きも上下どちらもある。

#### 試して駄目だったこと

* 記録の `byte70`・`byte71`（減衰の鍵補正に使うバイト）では説明できない。
  GrandP（66/72）は下がり、Strngs2（66/60）は上がる。DrawOrg（64/60）は
  下がり、BrssSec（64/60）は上がる。**同じバイトで向きが逆**
* 実機のコード（`0x127E3A`）が引く 62 バイトの表を、ROM からも
  ワーク RAM からも段の形で探したが見つからない。表は滑らかで、
  32 刻みは別の所（`0x7FF` で切るあたり）で出ているらしい

#### 掴んだ手掛かり: 基準は `CUTOFF_TAB[byte37]` そのもの

段がいつも 32、強さの段がいつも 16 なので、レジスタは
**「ある基準 ＋ 16 の倍数」**の形をしている。その基準を探したら出た。

| 音色 | byte37 | `CUTOFF_TAB[byte37] & 0x7FF` | 測った平らな値 | 差 |
|---|---|---|---|---|
| DrawOrg | 116 | **1897** | **1897** | 0 |
| GrandP  | 68  | 1243 | 1563 | +320 ＝ 16×20 |
| BrssSec | 72  | 1297 | 1681 | +384 ＝ 16×24 |
| Strngs2 | 34  | 391  | 1767 | +1376 ＝ 16×86 |

DrawOrg は**ぴったり一致**し、ほかも差はすべて 16 の倍数。
`bright_shift`（CC74）も 16 × (値 - 64) なので、**足し込みはすべて 16 きざみ**。

つまり実機のコードのとおり

```
レジスタ = (CUTOFF_TAB[目盛り] + 鍵のぶん + パートのぶん) & 0x7FF
```

で、`目盛り` は `0x127FA4` が返す 0-127。あとは「鍵のぶん」の表だけ。

#### 次にやること

`0x127E08` が呼ぶ `0x12C834`（覚え込み付き。中身は `0x128166`）と、
`R11 = [R12+32]` が指す構造体。`R12` は**音の構造体**（`+2` が印、
`+3` が鍵、`+80` が語）で、パートの塊ではない。ここが読めれば、
`0x00` を写し取りから鍵ぶんずらすだけで出せる。

### 6.56 フィルタの鍵追従（`0x00` の食い違いが 0 になった）

6.54 で「62 バイトの表の在りかが分からない」と書いた所。エミュレータ側に
仕掛けを入れて突き止めた。

#### 使った仕掛け

ワーク RAM と ROM を region（素通し）ではなく device として繋ぎ直して、

* `SMU2000_RAMTRACE=<命令の番地>` … その辺りの命令が読んだワーク RAM の番地
* `SMU2000_RAMWRITE=<番地>` … その番地に書いた命令の番地と値
* `SMU2000_ROMTRACE=<番地>` … その辺りの ROM を読んだ命令の番地

を出せるようにした（既定では今までどおり素通しなので、ふだんの速さは変わらない）。
JIT は `SMU2000_SH2_JIT=0` で切る。

#### 分かった道すじ

読み違えていたのは**入口**だった。6.54 で追っていた `0x128542` は、
鍵を押したときの `0x00` を作る所ではなかった。

```
12ACAA  目盛り = 音色の設定[35]         ; ＝ 記録の byte37
12ACBC  JSR 127FA4                       ; 強さの倍率（6.48）
12ACC4  R14 = CUTOFF_TAB[目盛り]         ; 索引は鍵では変わらない
12ACCE  JSR 12C1E4                       ; ← 鍵のぶんを作る
12ACD4  R14 += 音の構造体[4]             ; それを足す
12ACEC  0x0FFF で頭打ちして [R13+24] へ
12DE70  そこから 0x00 を書く（1984 で切って 0x1000 を足すだけ）
```

`0x12C1E4` は

```
12C1F2  R0 = 音の構造体[1]               ; 鍵
12C1F8  BSR 12C20E(R4 = 設定+36, R5 = 鍵)
12C1FE  R0 = (符号つき)R0 << 5           ; **32 倍**
12C204  音の構造体[4] = R0
```

そして `0x12C20E` は**音量の鍵曲線とまったく同じ仕掛け**だった。

```
12C21E  設定+36 の [0] が 0xFF なら
12C22C    表 0x23CED0（LEVEL_CURVE）を
12C236    ([6]<<8 | [7]) 行目で引いて、鍵で索引する
          （0xFF でなければ折れ線の枝）
```

`設定` は要素の 2 バイト先を指しているので、`設定+36` は**記録の byte38**。
つまり

```
鍵のぶん = (符号つき)LEVEL_CURVE[(byte44<<8 | byte45) 行][鍵] × 32
```

音量の方は `byte60` が 0xFF なら `byte66,byte67` 行、という同じ形
（`level_key_curve`）。**同じ仕掛けが 2 か所で使われていた**。

32 倍なので、鍵を上げ下げすると 32 きざみの階段になる。実測
（`nativeplay --keycut`）と Strngs2・GrandPno・DrawOrg の 3 音色で
差が完全に一定になった。

写し取りに「写したときの鍵」を覚えて、そこからの差ぶんだけずらす。

| 測り方 | 前 | いま |
|---|---|---|
| 曲の頭 12 秒・55 音 | ずれの合計 160 | **0** |
| 94 秒・波形がそろった 380 音 | `0x00` 1 回あたり 64 | **12** |

折れ線の枝（byte38 が 0xFF でないとき）はまだ起こしていない。

### 6.57 離しの扱い（曲ぜんぶで実機と ±0.06 dB）

`0x00` を直しても音の差は -0.30 dB のまま動かなかった。
**鍵を押すときのレジスタは合っているのに音が違う**、という状態。

#### 切り分け: 1 チャンネルずつ鳴らす

曲を 1 チャンネルだけ残したファイルに分けて比べたら、はっきりした。

| チャンネル | 音色 | 差 |
|---|---|---|
| 0 | Strngs2 | **-1.05 dB** |
| 1 | Strngs2 | -0.51 dB |
| 2 | Strngs2 | -0.41 dB |
| 3-6 | ほか | ±0.06 dB |

ch0 だけで比べると、64 音でレジスタの食い違いは 2 回しか無い。

#### いちばん効いた直し: 離し中のスロットを空きにしない

こちらは鍵を離した瞬間にスロットを「空き」として配り直していた。
実機は鳴り終わるまでスロットを持ち続ける。この曲は同じパートに
**144ms おき**に音が来るのに離しは **1.1 秒**あるので、実機が 8 声で
鳴らす所をこちらは 1〜2 声で鳴らし、離しの尾が次の音でぶつ切りになっていた。

空きが無いときだけ、離しの古いものから取る。これだけで
**ch0 が -1.05 dB → +0.01 dB**。

#### 離しのときの減衰は「いまのつまみ」で

`note_off` が使っていた `s.att` は鳴らし始めたときの値。途中で音量を
絞られた音を離すと、絞る前の大きさで鳴り終わっていた。

#### 離しの最中もつまみを追ってよい

`0x09` の下位は「素の減衰」で、離しの坂の位置とは別に持たれている
（`swp30.cpp` の `envelope_block`: 出る値は `level + (glo & 0xff) << 6`）。
書き直しても坂は引き直しにならないので、安心して追える。
ここを「触らない」にすると、終わりのフェードアウトで **+13dB** になった。

#### 録る間は firmware を全速で回す

包絡線を動かしているのは firmware のソフトで、10ms ごとに
`0x00`・`0x01`・`0x04` を書き直す。細く回している（100ms につき 5ms）
ままだと firmware の時間が 20 分の 1 しか進まず、**1 秒の窓で実機の
5% ぶんしか録れていなかった**（25 段しか録れていないのに実機は 117 段）。

#### 離しに入ってからの段も録る

実機は離しのあいだもフィルタを動かす。元にした音が短いと、録れる段の
ほとんどがそちら側になる（実測で 314 段のうち 303 段）。押してからの
並びと離してからの並びを分けて持ち、鳴らすときもそれぞれの時刻から流す。

#### 結果（利用者の曲・171 秒）

| 区間 | 一晩の前 | いま |
|---|---|---|
| 0-16 秒 | -0.81 | **+0.03** |
| 16-32 秒 | -0.72 | **-0.02** |
| 80-96 秒 | -1.23 | **-0.00** |
| 144-160 秒 | -0.19 | **+0.01** |
| 160-171 秒 | +7.86 | **+0.15** |
| 全体 | -0.60 | **+0.01** |

最後の 11 秒は 19.3% のサンプルが 1 ビットも違わない。

### 6.58 「1 ビットも違わない」までに残っていること

ch4 を単独で鳴らすと、**音が鳴り出すまでは 1 ビットも違わない**。
鳴り出したあとのずれは ±3〜6（1000 に対して）で、原因は**書き込みの時刻**。

実機と native で、フィルタの段が書かれる時刻が 10〜19 サンプル
（0.2〜0.4ms）ずれている。

```
実機   +146 サンプル  スロット0 = 1605
こちら +135 サンプル  スロット0 = 1605      ← 値は同じ、時刻が 11 早い
```

理由ははっきりしている。**段の時刻は firmware に鳴らさせた 1 音から
録っている**が、そのとき firmware は native の口の上で動いていて、
firmware だけで鳴らすときとは走る間合いが違う。録った時刻そのものが
数サンプルずれる。

ここを 1 ビットまで詰めるには、**フィルタの包絡線を写し取らずに式で出す**
必要がある。firmware がソフトでやっている EG（10ms ごとに `0x00`・`0x01`・
`0x04` を書き直す）を、記録のバイトから起こす作業になる。

### 6.59 フィルタの包絡線を式で出すには（次にやること）

6.58 で「包絡線を写し取らずに式で出す必要がある」と書いた所を、
どこまで追えたか残しておく。

#### 鳴っている間、切る高さがどう作られるか

```
129AE6  R5 = [音+24]                  ; 鍵を押したときに決めた表の値（動かない）
129AE0  JSR 127E08
127E24    R11 = [音+32]               ; パートごとの音色の設定（0x134 とび）
127E26    R5 = 12C834(R11)            ; ← ここが時間で動く
127E3A    ＋ 鍵のぶん（6.56）
127E76    R14 = 表の値 + R5
127E82    ＋ [音+80]
127E98    [0x43E95E] = R14 & 0x7FF
12E73A  そこから 10ms ごとに 0x00 を書く
```

利用者の曲の ch4 の音色（バンク 0,72 / 音色 5）では、この `R5` が
**10ms ごとに 14 ずつ下がっていた**。表の値は動かないので、動いているのは
`12C834` の戻り値だけ。

#### `12C834` → `128166` の中身

`12C834` は覚え込み付きの取り出しで、中身は `0x128166`。そこは

```
128166  R5 = R4[24] を曲線表 0x1E5854 で引く   ; つまみ（64 なら 0）
1281A0  R7 = R4[36] - 64
1281A4  R6 = [R4+128] + 0xE000
1281B0  R6 != 0 なら R5 += ((R7<<8) * R6) >> 16
1281BA  R6 = R4[30];  R7 = R4[125];  R5 += ((R6-64) * R7) >> 2
1281DE  R6 = R4[71];  R7 = R4[127];  R5 += 同じ形
128202  R6 = R4[84];  R7 = R4[212]; R5 += 同じ形
        …（この形が何本か続く）
```

つまり**変調の行列**そのもので、

```
切る高さのずれ = Σ (深さ[i] - 64) × 源の値[i] / 4
```

の形をしている。「深さ」は音色の設定の中の固定値、「源の値」は
LFO・包絡線・アフタータッチなどが 10ms ごとに書き替えるバイト。
フィルタの包絡線はそのうちの 1 本。

#### だから残っている作業は

**源の値を作っている所**（10ms ごとに `R4[125]`・`R4[127]`・`R4[212]` …を
書き替えるコード）を起こすこと。`SMU2000_RAMWRITE=<その番地>` でどの命令が
書いているかはすぐ分かるので、道具は揃っている。

* `[R4+128]` は今回の音色では 0x2000 のまま（＝ `+0xE000` で 0 になり、
  その枝は素通り）だった。音色によっては動くはず
* 源が 1 本ずつ起きれば、写し取り無しで `0x00` を出せる。そうなれば
  段の時刻も実機と同じ格子（10ms）に乗るので、6.58 の 10〜19 サンプルの
  ずれも消える

#### 分かった大事なこと: `R11` は**パートの塊そのもの**

`R11 = [音+32]` が指す先は 0x428D64・0x428E98・0x428FCC・0x429100 と
**0x134 とび**で並んでいる。これは `xg::ram::part_base()` と同じ並びで、
つまり `R11` は**パートの塊**（こちらが `m_ram` から読んでいるもの）。

深さ（`R4[30]`・`R4[71]`・`R4[84]` …）も源の値（`R4[125]`・`R4[127]`・
`R4[212]` …）も、全部パートの塊の中にある。**こちらから読める**。

鳴らしっぱなしの音で 0.3 秒と 0.6 秒のワーク RAM を取って差を見ると、
パートの塊で動いていたのは **+305（0x131）だけ**（76 → 74）。
ここが源の 1 本。ただし native の口では firmware を細く回すので、
**この値が実機どおりに進まない**。これも写し取りに頼っている理由。

#### いまの折り合い

写し取りで **±0.06 dB**（利用者の曲・171 秒の全区間）まで来ているので、
聞いて分かる差ではない。1 ビットまで詰めるには

1. 源の値（パートの塊の +125・+127・+212・+305 …）を 10ms ごとに
   こちらで進める
2. 深さと合わせて上の式で切る高さを出す

の 2 つが要る。1 は firmware の包絡線・LFO をこちらで持つということで、
写し取りをやめる方向の作業になる。

#### ただし包絡線の途中の値はワーク RAM に無い

鳴り始めの **50ms と 100ms** でワーク RAM を取って差を見ると、
パートの塊で違うバイトは **1 つも無かった**（切る高さはその間に
10ms ごとに 14 ずつ動いているのに）。RAM 全体でも違うのは 136 バイトで、
どれも 0x401xxx・0x405xxx の作業用の場所だけ。

つまり**包絡線の途中の値は、SH-2 の内蔵 RAM（0xFFFFF000-）にある**。
こちらの `m_ram`（0x400000-0x43FFFF）には出てこないので、
「firmware が持っている値を覗いて使う」やり方は取れない。

包絡線そのものを ROM のコードから起こすしかない、というのが結論。

#### 道具

* `nativeplay --ramdump <ファイル> -s <秒>` … その時刻のワーク RAM を丸ごと
  書き出す。2 回取って差を見れば「時間で動いているバイト」がすぐ分かる
* `SMU2000_RAMWRITE=<番地>` … そのバイトを書いている命令の番地

### 6.60 「1 ビットも違わない」は、いまの作りでは届かない所がある

一晩詰めた結論として、**どこまでが届く話で、どこからが届かない話か**を
はっきりさせておく。

#### 実機の包絡線は 441 サンプルの格子に乗っている（測った）

利用者の曲の ch4 を firmware だけで鳴らして、`0x00` を書いた時刻を 521 個
集めて円統計にかけると、**周期 440.9985 サンプルで集中度 0.954**。
つまり 10ms（441 サンプル）の全体共通の格子。

1 回の格子の中まで完全に規則的だった:

```
s=1793851 +0  スロット0 0x00=1583
          +1  スロット0 0x01=beff
          +1  スロット0 0x04=0000
          +3  スロット1 0x00=1602
          +3  スロット1 0x01=beff
          +4  スロット1 0x04=3000
（つぎの格子は s=1794292 ＝ +441。以下同じ形）
```

**値はこちらと完全に一致している**（写し取った段をそのまま流すので当然）。
違うのは時刻だけで、その差は 10〜19 サンプル。

#### なぜ時刻が合わないか

格子を動かしているのは firmware のタイマで、**firmware の時間**で進む。
native の口では firmware を 100ms につき 5ms しか回さないので、
firmware の時間は実時間の 20 分の 1 でしか進まない。写し取った段の時刻は
その上で測ったものなので、firmware だけで鳴らしたときの格子とは合わない。

#### 届かない所

もっと根の深い話がある。**音色の 1 音目は firmware に鳴らさせる**（写し取り）
のが、この作りの土台になっている。その音の書き込みは firmware 自身が出すので、
native の口の上で走る firmware と、firmware だけで走る firmware とで、
命令の間合いが違えば時刻がずれる。実測でも、利用者の曲の ch4 で
**最初に音がずれるのは写し取りの音の中**（鍵を押してから 576 サンプル）で、
そこは native が書いた段ではない。段を何サンプルずらしても動かなかった。

つまり **写し取りを使う限り、その音だけは 1 ビットまで合わせられない**。

#### 届く所

2 音目以降（native が鳴らす音）は、

1. 段の**値**は既に完全に一致している
2. 段の**時刻**は、441 サンプルの格子をこちらで持ち、起動時に測った位相から
   実時間で進めれば合わせられる（格子の中の +0/+1/+3k も規則的）

の 2 つで届く見込みがある。ただし位相は起動のときにしか測れない
（そのあとは firmware の時間が遅れる）ので、起動中に firmware が書く
`0x00` から拾っておく必要がある。

#### 試して駄目だったこと（同じ道を通らないように）

1. **段の時刻を一定量ずらす**（0〜18 サンプルを総当たり）。ch4 で最初に
   波形がずれる位置が **1 サンプルも動かなかった**。ずれの出どころは
   こちらが書いた段ではなく、**写し取りの音（firmware が鳴らしている音）の中**。
2. **段を 441 サンプルの格子に載せ直す**（位相を 0・110・220・330 で総当たり）。
   出てくる音が**まったく変わらなかった**。45-60 秒の一致率も dB も同じ。

2 が効かなかった理由も分かっている。その区間の書き込みを数えると

```
firmware  0x00 を 565 回
こちら    0x00 を 1190 回   ← 2 倍以上
```

で、**段の数そのものが違う**。離しの最中のスロットを長く持つように
したぶん（6.57）、離しの並びを流し続けているため。段の時刻を揃える前に、
**どの段をいくつ流すか**が実機と合っていない。

#### いまの立ち位置

利用者の曲・171 秒で**全区間 ±0.06 dB**、全体 +0.01 dB。
聞いて分かる差ではない。1 ビットまで詰めるなら、上の「届く所」を
やったうえで、写し取りをやめて包絡線を式で出す（6.59）ところまで行く。

### 6.61 **2 音目は乾いた音なら 100% 一致する**（残りの正体が全部割れた）

いちばん小さい再現を作って詰めた。GrandPno を 1 音（写し取り用、1.0-2.5 秒）、
そのあと間を空けてもう 1 音（native が鳴らす、12.0-13.5 秒）だけの MIDI。

#### まず: 鍵を押すときのレジスタは**完全に一致している**

```
実機（スロット1）              こちら（スロット63）
-23  0x00 = 15db               +0  0x00 = 15db
-22  0x01 = ffff               +0  0x01 = ffff
-22  0x02 = 8000               +0  0x02 = 8000
…（0x17 まで 20 本すべて同じ値）…
 -9  0x32 = 0808               +0  0x32 = 0808
```

違うのは**書く時刻**（実機は鍵の 9〜30 サンプル前に散らす、こちらは同じ
サンプルにまとめる）と**スロット番号**だけ。

#### 差の正体 その 1: 効果（MEG）— ±1 LSB

そのままだと 12-13 秒の一致は 77%。差の内訳は **±1 が 12%、2 以上が 11%**。
ところが**リバーブとコーラスの送りを 0 にすると**

| 区間 | 送りあり | 送り 0 |
|---|---|---|
| 12-13 秒 | 77.4% | **99.8%** |
| 14-15 秒 | 82.9% | **100%** |
| 15-16 秒 | 99.0% | **100%** |

つまり **±1 LSB のざらつきは全部 MEG（効果）の側**。実機は MEG の状態
レジスタ（`sy02`・`sy22`-`sy25`）を毎秒 4300 回書き替えているが、native の
口では firmware を細く回すのでその 5% しか書かれない。

**乾いた音は 1 ビットも違わない。**

#### 差の正体 その 2: 写し取りの窓が 1 秒で切れる

送りを 0 にしても 13-14 秒だけ 31.6% だった。最初に違うのは **12.0097 秒 ＝
鍵を押してから 1.0 秒**。写し取りの窓（`m_traj_left = 44100`）がそこで
終わり、そこから先はこちらの包絡線が止まるため。

窓を 3 秒にすると **31.6% → 93.9%**（6 秒にしても同じなので 3 秒で足りる）。

#### ただし窓を延ばすと曲が悪くなる

利用者の曲で窓を 3 秒にすると、

| | 窓 1 秒 | 窓 3 秒 |
|---|---|---|
| 全体 | +0.01 dB | **+1.00 dB** |
| いちばん違う区間 | +0.15 dB | **+2.18 dB** |
| 写し取り | 11 回 | 33 回 |
| firmware が鳴らした音 | 49 | 136 |

録っている間は次の写し取りを始められない（SWP30 の覗き口が 1 つしか無い）
ので、窓を 3 倍にすると写し取りの順番待ちが延びて、曲の頭が崩れる。

**だから窓は 1 秒のままにしてある。**

#### 残っている作業（順番）

1. **覗き口を 1 つにしない** — 写し取りと録りを 1 つのコールバックで
   さばけるようにすれば、窓を延ばしても順番待ちが起きない。
   そうすれば 13-14 秒の 31.6% → 93.9% を曲でも取れる
2. **MEG の状態を native でも進める** — `sy22`-`sy25` を 10ms ごとに
   書いているコードを起こす。これで ±1 LSB のざらつきが消える
3. 1 と 2 が済めば、**写し取りの音（音色ごとに 1 音）以外は 1 ビットまで
   合う**見込み。写し取りの音そのものは firmware が鳴らすので、
   走る間合いの違いが残る（6.60）

### 6.62 「1 ビットも違わない」の最終的な答え

6.61 の続きを詰めて、**どこまでが届いて、どこからが原理的に届かないか**が
確定した。

#### 届いた: 乾いた音の 2 音目は 1 ビットも違わない

写し取り用の 1 音＋native が鳴らす 2 音目だけの MIDI で、リバーブと
コーラスの送りを 0 にすると

| 区間 | 録りが 1 本だったころ | 録りを同時に走らせたあと |
|---|---|---|
| 12-13 秒（2 音目） | 99.8% | **99.8%** |
| 13-14 秒 | 31.6% | **93.9%** |
| 14-15 秒 | 100% | **100%** |
| 15-16 秒 | 100% | **100%** |

鳴らしているレジスタ 20 本はすべて同じ値。残る 13-14 秒の 6% も、
窓をさらに延ばせば詰まる種類のもの。

#### 届かない: 効果（MEG）を通した音

送りを入れると 12-13 秒は 68%、差は最大 6（信号の山 2449 に対して −52dB）。
理由が割れた。

**swp30 の乱数は、MEG のディザと LFO のキーオンで同じ数列を共有している**
（`lfo_block::keyon` が `swp.rand()` を引く。実機も雑音源は 1 つという読み）。
そして

```
写し取りの音のキーオン:  実機 s=44173  /  native の口 s=44175
```

**2 サンプルずれる**。写し取りの音を鳴らすのは firmware 自身で、native の
口の上では細切れにしか回らないから、MIDI をさばく間合いがずれる。

そのぶんディザの数列が永久にずれ、リバーブの中を回り続ける。だから
**そのあとの音は、レジスタが 1 本残らず同じでも、濡れた成分だけ数 LSB 違う**。

写し取り（音色ごとに 1 音を firmware に鳴らさせる）をやめない限り、
ここは詰まらない。

#### 試して外れた見立て: 乱数の数列

`lfo_block::keyon` の `swp.rand()` を引かないようにして試した
（`SMU2000_NO_LFO_RAND`）。**まったく変わらなかった**（68.1% → 67.9%）。
ディザの数列のずれが原因ではない。

#### 本当の理由: firmware に渡す MIDI が違う

写し取りの音の区間（1-3 秒）を見ると、そもそも**そこが合っていない**。

| 区間 | 一致 |
|---|---|
| 0-1 秒（無音） | 100% |
| **1-2 秒（写し取りの音）** | **0.5%** |
| 2-3 秒 | 4.9% |
| 3-4 秒 | 74.2% |

キーオンが 2 サンプルずれる理由も割れた。native の口は MIDI を
**1 バイトずつ自分で読んで**、firmware に回すと決めてから
`replay_note()` で 3 バイトまとめて流し直す。firmware だけで鳴らすときは
3 バイトが線の速さで順に届くので、届き終わる時刻が変わる。

これは**直せない**。native の口は「firmware に渡すかどうか」を
強さのバイトまで読まないと決められないし、先に流してしまうと
native で鳴らす音まで firmware が鳴らして二重になる。
つまり **native の口は firmware に違う MIDI を渡している**ので、
firmware の走り方が変わるのは避けられない。

そして写し取りの音は効果を通るので、そのずれがリバーブの中に入り、
そのあとの音にも数 LSB 残る。

#### まとめ

| | 1 ビット一致 |
|---|---|
| 乾いた音・native が鳴らす音 | **届く（実測で 100%）** |
| 乾いた音・写し取りの音 | 届かない（firmware の間合い） |
| 効果を通した音 | 届かない（ディザの数列が上のせいでずれる） |

利用者の曲は全パートが効果を通っているので、**全区間 ±0.06 dB** が
いまの上限。ここから先は「写し取りをやめて、音色の設定を全部式で出す」
（6.59）まで行かないと動かない。

### 6.63 フィルタの包絡線の在りかが割れた（段 3 の入口）

6.59 で「源の値を書いているコードを起こす」と書いた所。**フィルタの包絡線は
折れ線で、音の構造体の中に状態がある**ことが分かった。

#### 切る高さの足し算の形

```
129AE6  R5 = [音+24]            ; 鍵を押したときに決めた表の値（動かない）
129AEC  R0 = [音+26]            ; ← **包絡線の出力。ここが動く**
129AE0  JSR 127E08 → R14 = R5 + 12C834(パートの塊) + 鍵のぶん + [音+80]
12ACF6  R14 += [音+26]
127E98  [0x43E95E] = R14 & 0x7FF
12E73A  そこから 10ms ごとに 0x00 を書く
```

利用者の曲の ch4 の音色（0,72,5）では `12C834` は 0 を返し、`[音+80]` も 0、
鍵のぶんも 0 だった。**動いているのは `[音+26]` だけ**。

#### 包絡線そのもの（`0x128710`）

```
128710  fenv_step(R4 = 音の構造体):
12871A    増分 = [音+70]                  ; 符号つき word
12871E    増分 == 0x8000 なら → 次の段へ（128766）
128730    [音+66] += 増分                 ; 累算
          増分 >= 0 なら [音+66] >= [音+68] で次の段
          増分 <  0 なら [音+66] <= [音+68] で次の段
128756    [音+26] = [音+66] >> 2          ; ← 出力（算術シフト）
```

実測と合う。`[音+26]` は `0x2e0 → 0x2d2 → 0x2c5 → 0x2b7 → 0x2aa → 0x29c`
（−14, −13, −14, −13, −14）で、切る高さの動きとぴったり同じ。

#### 段の進め方（`0x128766`）

```
128772  R13 = [音+40]            ; 要素データへの指し先
128778  [音+66] = [音+68]        ; 累算を目標にきっちり合わせる
128788  [音+8] を 1 進める       ; 段の番号
  段 1: 速さ = R13[49]、目標のレベルは R13[53] と R13[54]
        （同じなら段 2 へ飛ばす）。深さ 64 で 128A5A を呼ぶ
  段 2: 速さ = R13[50]、レベルは R13[54] と R13[55]
        深さは パートの塊[27]。128A5A を呼ぶ
  それ以外: 終わり（増分を 0 にする）
```

`0x128A5A` が「速さ・レベル・深さ」から増分と目標を作る。表は **0x1E5CD8**、
パート側の足し込みが `[音+94]`・`[音+95]`。

#### つまり実装に要るもの

1. 状態 3 つ（累算・目標・増分）と段の番号を、こちらのスロットに持つ
2. 要素の byte49/50（速さ）と byte53/54/55（レベル）、表 0x1E5CD8 から
   増分と目標を出す（`0x128A5A` の残りを起こす）
3. 10ms ごとに 1 段進めて、`[音+26]` 相当を切る高さに足す

これができれば**写し取りの録画が要らなくなる**。録画をやめられれば、
音色の 1 音目を firmware に鳴らさせる必要も減り、6.62 で「届かない」と
書いた所に手が届く。

#### 式が全部揃った

残りの `0x128A5A`・`0x128BA4`・`0x12897E` も読めた。まとめるとこうなる。

**段を張り替えるとき**（`0x128766` → `0x128A5A` → `0x128BA4`）

```
増分の表  INC_TAB = 0x1E5C58（word が 64 個）
   目盛り  0  1  2  3 …  15 …  48  …  62    63
   値      2  4  6  8 …  32 … 664  … 6192  0x8000（＝すぐ次の段へ）

速さ = 要素の byte49（段 1）または byte50（段 2）
       深さが 64 でなければ 0x1E5CD8[深さ] で頭打ち
       ＋ [音+94]、＋ [音+95]（パート側の足し込み）、0-63 に丸める
増分 = INC_TAB[速さ]

レベル = 要素の byte53/54（段 1）または byte54/55（段 2）
目標 = ((レベル-64)*2 − ((レベル-64)*2 × [音+93]) / 256) × 64
       （`0x12897E`。[音+93] は深さ 0-255）

いまの累算が目標より大きければ、増分の符号を反転する
```

**10ms ごと**（`0x128710`）

```
増分 == 0x8000 なら段を進める
[音+66] += 増分
増分 >= 0 で [音+66] >= 目標、または
増分 <  0 で [音+66] <= 目標  なら段を進める（累算は目標にそろえる）
[音+26] = [音+66] >> 2        ← これが切る高さに足される
```

段は `[音+8]` で数え、1 → 2 → 3（終わり）と進む。段 1 と段 2 で
レベルが同じなら、その段は飛ばす。

#### 実機の値で検算した（全部合った）

音色 Kitayama（0,72,5、記録 0x22052E）を鍵 60・強さ 100 で鳴らして、
20ms と 60ms でワーク RAM を取り、音の構造体を読んだ。

| 中身 | 20ms | 60ms |
|---|---|---|
| 累算 `[音+66]` | 2890 | 2674 |
| 目標 `[音+68]` | 2624 | 2624 |
| 増分 `[音+70]` | -54 | -54 |
| 出力 `[音+26]` | 722 | 668 |
| 段 `[音+8]` | 1 | 1 |
| 深さ `[音+93]` | 72 | 72 |
| 足し `[音+94]` / `[音+95]` | 0 / 18 | 0 / 18 |

* 40ms で累算が 216 減る ＝ 4 段で -54 ずつ。**増分と一致**
* 出力 722 ＝ 2890 >> 2。**式と一致**
* 増分 54 は `INC_TAB` の目盛り 26（2×(26+1)）。
  `26 - [音+95](18) = 8` で、**要素の byte51 が 8**。一致
* 目標 2624 を式で逆に解くと レベル ＝ 92。**要素の byte56 が 92**。一致
* 鍵を押した時点の累算は レベル ＝ 96（**byte55**）から出る 2944 で、
  1 段進んで 2890。一致
* 深さ 72 は **要素の byte49**。一致

つまり `R13 = 要素 + 2` で、

```
はじめの累算 = 目標(byte55)
段 1: 目標 = 目標(byte56)、速さ = byte51
段 2: 目標 = 目標(byte57)、速さ = byte52
目標(レベル) = (x - (x × byte49) >> 8) × 64      x = (レベル-64) × 2
速さ = その byte + [音+94] + [音+95]（0-63 に丸める）
増分 = INC_TAB[速さ]（63 は「すぐ次の段」）
```

`[音+94]`・`[音+95]` は鍵と強さから出る足し込みらしい（この音では 0 と 18）。
そこだけまだ起こしていない。

#### 残っているのは実装だけ

* スロットに状態 4 つ（累算・目標・増分・段の番号）を持つ
* 鍵を押したときに段 1 を張る
* 10ms ごとに 1 段進めて、`cutoff_reg` に `[音+26]` 相当を足す
* `0x128A5A` の深さの頭打ち（表 `0x1E5CD8`）とパートの足し込みを入れる

これができれば**フィルタの録画が要らなくなる**。

#### 道具

* `SMU2000_RAMWRITE=<番地>` … そのバイトを書いた命令の番地と値。
  今回はこれで `0x128760`（包絡線の書き込み）を一発で見つけた
* `SMU2000_RAMTRACE=<命令の番地>` … その辺りの命令が読んだ番地と値
* どちらも `SMU2000_SH2_JIT=0` と一緒に使う

### 6.64 フィルタの包絡線を式で動かした（段 3 の 1 本目）

6.63 の式をそのまま入れた（`nv::fenv_*` と `native_driver::fenv_start/step`）。

#### 効き

| 測り方 | 録画を流す | 式で動かす |
|---|---|---|
| 乾いた音の 2 音目 12-13 秒 | 100% | **99.9%** |
| 利用者の曲・全体 | +0.02 dB | **-0.01 dB** |
| `make test` の native の口 | +0.37 dB | **+0.36 dB** |

録画と同等以上。フィルタについては写し取りの録画に頼らなくなった
（`SMU2000_NO_FENV` で前のやり方に戻せる）。

10ms の目は**録画の 1 段目の時刻**から取る。そこが実機の格子の目そのもの
なので、位相を別に測るより近い。鍵を押した直後の 1 目は実機も値を
動かさないので、1 目ぶん遅らせて進め始める。

#### 離しはまだ録画のまま

離しの段も式にしてみた。実機は鍵を離した時点でもう 1 段張っていて
（`0x128850` が段を 4 にする）、速さは要素の byte53、行き先は byte58。
実測で増分 -38 ＝ `INC_TAB[18]`、`byte53(0) + 足し込み(18) = 18` と一致する。

ところが入れると **13-14 秒が 94.0% → 88.3%** と悪くなった。理由は
**押している間の段がもう 1 つある**こと。段の番号（`[音+8]`）を追うと

```
s=417172 段0（張る）  417539 段1  420183 段2  434295 段3  439217 段4（離し）
```

で、段 3 がある。ところが段 3 では

```
累算 [音+66] = 1024（目標と同じ。止まっている）
増分 [音+70] = -50（そのまま）
出力 [音+26] = 256（動かない）
```

**包絡線は止まっている**のに、レジスタ 0x00 は 1 目あたり -1 で動き続ける。
つまりその動きは包絡線ではなく別の源。パートの塊で動いているのは
**+305（0x131）だけ**（76 → 75）だが、これは切る高さの行列の源
（+125・+127・+212・+213）には入っていない。

#### 追記: 「もう 1 本の道」は無かった。深さの取り違えだった

GrandPno（曲の試験に使っている音色）で同じことをやり直したら話が変わった。

```
音の構造体で動いたバイト（0.10 秒 → 1.40 秒）
   +26/+27  包絡線の出力   247 → 117
   +30/+31  その写し       210 →  80   （差はどちらも -130 で同じ）
   +66/+67  累算           988 → 468   （-4 ずつ。増分と一致）
   +115・+122  音量の包絡線と LFO
パートの塊で動いたバイト
   +305 だけ
```

**動いているのは包絡線だけ**だった。出力が 1 目あたり -1 で下がるのは
累算が -4 ずつ下がるからで、レジスタ 0x00 の -1/目 はそれで説明が付く。
Kitayama で「段 3 では止まっているのに動く」と見えたのは、Kitayama が
段 3 まで進んだあとの話で、GrandPno は段 1 のまま 1.4 秒経っていた。

#### ただし深さ（`[音+93]`）は取り違えていた

```
Kitayama  [音+93] = 72  ＝ 要素の byte49（72）
GrandPno  [音+93] = 111 ≠ 要素の byte49（60）
```

たまたま一致していただけだった。実機は `0x128ADC` で作っていて、
要素の byte46（-64 する）と byte8（表 `0x1E5D58` か `0x1E5DD8` の選択）、
強さ、パートの塊 +210 から出る。

深さは**目標にしか効かない**（増分＝坂の速さには効かない）ので、
段の終わりまで伸ばさない音では差が出ない。いまは byte49 で代用していて、
実測でもそこは 99.9% 合っている。長い音で段が変わる所だけずれる。

**次にやること**: `0x128ADC` を起こして深さを正しく出す。そうすれば
段の終わりが合い、離しの段（6.64）も入れられるようになるはず。

### 6.65 包絡線の深さを解いて、`0x00` は録画を使わなくなった

6.64 で「深さは要素の byte49 らしい」と書いたのは取り違えだった。
Kitayama でたまたま一致していただけで、GrandPno は 111 なのに byte49 は 60。

実機の `0x128ADC` を起こした:

```
深さ = ((36 × (byte46 - 64)) × (0x80 - 表[強さ]) × 2) >> 8
表は byte8 が 0 なら 0x1E5D58、そうでなければ 0x1E5DD8
```

| 音色 | byte46 | byte8 | 式 | 実機 |
|---|---|---|---|---|
| GrandPno | 70 | 1 | 111 | **111** |
| Kitayama | 71 | 0 | 72 | **72** |

深さを正すと段の終わりが合うようになり、前に入れて悪くなった**離しの段**
（速さ byte53、行き先 byte58）もそのまま入った。

| 区間 | 録画 | 式（深さ前） | 式（深さ後） |
|---|---|---|---|
| 12-13 秒 | 100% | 99.9% | **99.9%** |
| 13-14 秒（離しを含む） | 94.0% | 92.9% | **94.0%** |
| 14-15 秒 | 100% | 100% | **100%** |

**レジスタ `0x00` は、押している間も離しの間も録画を使わなくなった。**

パートの塊 +210 が 0 でないときの枝（深さがもう一段変わる）はまだ。
既定の音色では 0。

### 6.66 ここから先の「壁」: 段の時刻の ±1 サンプル

12-13 秒に残る 0.1% を数えると、**1 フレームだけ違う所が 52 個**で、
だいたい段の切れ目に並ぶ。実機の段の間隔を数えると

```
441 サンプル … 115 回
442 サンプル …  17 回
440 サンプル …  17 回
```

**周期は 441 ちょうどで、揺らぎは ±1 の対称**（115×441 + 17×442 + 17×440
を 149 で割るとちょうど 441.0）。実機の 10ms は CPU のサイクルで数える
タイマで進むが、1 サンプルぶんの持ち分は 634.92 サイクルなので、
firmware がその中のどこで書き込みに来るかでサンプルが 1 つ前後する。

こちらは 441 ちょうどで並べるので、その揺らぎは**原理的に真似できない**
（真似するには firmware を走らせるしかない）。

つまり `0x00` については、**式そのものは実機と同じ値を出しているが、
書く時刻が 1 サンプル揺れる**ところが下限になる。乾いた音で 99.9%。

### 6.67 写し取りをやめるのに、あと何本要るか（段 3 の地図）

`nativeplay --nocal` を足した。**写し取りを一切混ぜず、式だけで**スロットの
レジスタを組む。それを実機が鍵を押した瞬間に書く値と、14 音色で比べた。

（測り方の注意: `--nocal` を付けないと `build_note` に写し取りを渡すので、
当然ほとんど一致してしまう。最初そこを間違えて「もう式だけで合っている」と
読み違えた）

#### まず: 鍵と強さで変わるのは 9 本だけ

GrandPno を鍵 48/60/72・強さ 40/100/127 で鳴らして、鍵を押した瞬間の
レジスタ 32 本を比べた。

```
変わる    0x00(鍵強) 0x07(鍵) 0x08(鍵) 0x09(鍵強) 0x11(鍵)
          0x13 0x15 0x16 0x17（鍵。波形の番地とループ）
変わらない 上以外の 23 本
```

**変わる 9 本はすべて既に式で出している。** つまり写し取りが埋めているのは
「音色ごとに一定の 23 本」で、そこは音色の記録から引ければ済む。

#### 式だけで組んだときの食い違い（14 音色）

| レジスタ | 食い違った音色 | 中身 |
|---|---|---|
| `0x00` | 13 | 切る高さ。**実行時は包絡線の式で出しているので実質解決済み**（6.65） |
| `0x04` | 4 | 共振 |
| `0x08` | 4 | 減衰 2 |
| `0x0b` | 4 | ― |
| `0x10` | 4 | 音程のずらし |
| `0x02` | 2 | フィルタの第 2 係数 |
| そのほか | 各 1 | 多要素の音色（EPiano1）の取り違えらしい |

`0x01` は「鍵を押した瞬間は必ず 0xFFFF で、最初の包絡線の目で本当の値に
置き換わる」と分かったので直した（14 音色すべてで一致するようになった）。

#### つまり

**あと 5 本（`0x02`・`0x04`・`0x08`・`0x0b`・`0x10`）を起こせば、写し取りが
要らなくなる**見込み。そうなれば

* 音色の 1 音目を firmware に鳴らさせなくてよくなる
* → キーオンが 2 サンプルずれる問題が消える（6.62）
* → 効果を通した音のずれも消える

段 3 の残りはこの 5 本。どれも「音色ごとに一定」なので、鍵や強さの式では
なく、音色の記録のどのバイトから来るかを当てる作業になる。

### 6.68 音程の包絡線（ピッチ EG）を起こした — `0x0b` と `0x10`

段 3 の残り 5 本のうち `0x10` を追ったら、**native には音程の包絡線が
まるごと無かった**ことが分かった。Violin や金管の「出だしのしゃくり」が
出ていなかった。

#### 何が起きていたか

`0x10` は「行き先の音程のずれ」、`0x0b` の上位バイトは「その速さ」で、
近づけるのはチップの仕事（`swp30.cpp` の `peg_step`）。実機の firmware は

* キーオンの**直前**に `0x10` へ**初めの高さ**を書く
* キーオンの**直後**（15 サンプル後）に `0x10` へ**行き先**を書く

の 2 回しか書かない。ところが写し取りは「包絡線が終わったあとの値」を
拾うので、`0x10` はいつも `4000`（ずれ 0）になっていた。つまり
**写し取りが包絡線を消していた**。

#### 解いた道すじ

1. `--trace-swp` で `0x10` を書く命令が `pc=0x12E004` と分かる
2. `SMU2000_RAMTRACE` で、その値がワーク RAM `0x43E9A0` から来ると分かる
3. `SMU2000_RAMWRITE` で、そこへ書くのは `pc=0x12ABA8` と分かる
4. `tools/dump/sh2dis.py` で `0x12AB70` あたりを読むと、`0x12B860`
   （セント → 音程の目盛りの変換）に通していた
5. さらに遡って `0x12BAC8`-`0x12BBA0` が式の本体だった

```
速さ       = 表 0x1E6C94[ clamp(byte26 + ((64 - パート[26]) >> 2), 0, 63) ]
初めの高さ = 速さが 127（＝即到達）なら byte31、そうでなければ byte30
行き先     = byte31
セント     = (高さ - 64) × 75 を byte21 で割る
             （byte21: 0→>>2 ・1→>>1 ・2→そのまま ・3→<<1）
強さの効き = byte22 が 64 でなければ (36×差)×(0x80-強さ) で目減りさせる
レジスタ   = 0x4000 | (表 0x1E6D14[セント] & 0x3fff)
```

表 `0x1E6D14` はセント → 目盛り（**1 オクターブ = 256**）で、0-4800 の
4801 語。`0x12B860` は符号で分けて引いている。

| 音色 | byte26 | byte30 | byte21 | 式 | 実機 |
|---|---|---|---|---|---|
| Violin(40) | 58 | 18 | 0 | -862 セント → -183 | **7f49** |
| Trumpet(56) | 54 | 52 | 1 | -450 → -96 | **7fa0** |
| MuteTrp(59) | 60 | 38 | 1 | -975 → -208 | **7f30** |
| Fr.Horn(60) | 59 | 44 | 0 | -375 → -80 | **7fb0** |
| Piccolo(72) | 42 | 58 | 1 | -225 → -48 | **7fa0** |
| Flute(73) | 43 | 59 | 1 | -187 → -39 | **7fd9** |

#### 入れた結果

`--nocal`（式だけ）で 14 音色を突き合わせると、**`0x0b` と `0x10` は
食い違いの一覧から消えた**。

| レジスタ | 前 | 後 |
|---|---|---|
| `0x0b` | 4 音色で食い違い | **0** |
| `0x10` | 4 音色で食い違い | **0** |

音（firmware と native を 1 秒ごとに相関で比べた。1 音目は写し取りなので
2 音目・3 音目を見る）:

| 音色 | 前 | 後 |
|---|---|---|
| Violin(40) | 33-43% | **95-99%** |
| Trumpet(56) | 84-87% | **99%** |
| MuteTrp(59) | 42-48% | **98-100%** |
| Flute(73) | 99% | **99.7-100%** |

試し曲（12 パート 30 秒）は全体 **+0.01 dB** で変わらず。`make test` は
12 件とも合、native の口はいちばん違って lofi の +0.36 dB（前と同じ）。

`SMU2000_NO_PEG=1` で前の（包絡線の無い）動きに戻せる。

#### 残っている宿題

* **段は 1 つだけ**入れた（初めの高さ → 行き先）。byte27-29・byte32-34 を
  使う多段の包絡線はまだ（既定の音色では使っていない）
* パートの塊 +98（音程の包絡線の下駄）の枝はまだ。既定では 64 ＝ 0
* Fr. Horn(60) と BrssSec(61) は**レジスタは全部一致している**のに
  相関が上がらない。どちらも 2 要素で、片方が byte72 で遅れて鳴る層。
  LFO の位相か、遅らせる時刻がずれていると思われる（別の宿題）

#### 段 3 に残るのは 3 本

`0x02`・`0x04`・`0x08`。`0x00` は実行時に包絡線の式で出している（6.65）。

### 6.69 共振（`0x04`）と減衰 2（`0x08`）を起こした

#### `0x04` は強さで変わっていた

`0x04` は「byte35 を 1 ビット落として上 5bit に置く」と書いていたが、
実機（`0x12806A` と `0x12810A`）は**強さぶん目減りさせて**いた。

```
目減り = (18 × |byte81 - 64| × (byte81 > 64 ? 0x80 - 強さ : 強さ)) & 0xffff >> 8
値     = max(byte35 - 目減り, 0)
パート の +25 の下駄を足して（負なら足す・正なら大きい方を採る）
レジスタ = ((値 >> 1) & 31) << 11
```

18 音色 × 強さ 30/100/127 の 54 通りで実機と一致した。

| 音色 | byte35 | byte81 | 強さ 30 | 強さ 100 | 強さ 127 |
|---|---|---|---|---|---|
| BriteP(1) | 20 | 71 | 0000 | 1800 | 5000 |
| EPiano2(5) | 18 | 69 | 0000 | 2000 | 4800 |
| FngrBa(33) | 9 | 71 | 0000 | 0000 | 2000 |
| Flute(73) | 4 | 57 | 0000 | 0000 | 0000 |

**写し取りは使えない**（写し取るのは 1 つの強さだけ）。録画の `0x04` も
捨てて、式で出した値に CC71 の差ぶんを乗せるようにした。

#### `0x08` は減衰 2 だけ下限が違った

減衰の速さの表の目盛りは `clamp(byte + 鍵の補正, 1, 63) × 2` としていたが、
**減衰 2（`0x127338`）だけ下限が 0** だった（減衰 1 の `0x1272F4` は 1）。
表の頭は `1,1,2,2,4,4,…` なので、0 と 1 で値が変わる。byte75 が 0 の音色
（Trumpet・BrssSec・SquareLd）で実機は `0100`、こちらは `0200` だった。

#### 測り方の直し

`nativeplay` が音色の**要素 0 で決め打っていた**のを直した。EPiano1 は
強さ 96 で要素が切り替わる音色で、強さ 100 では要素 1 が鳴る。要素 0 の
バイトで測っていたので、`0x04`・`0x07`・`0x08`・`0x11`・`0x13`・`0x15`
の 9 本が「食い違い」に見えていた。直したら **1 本**（`0x00`）になった。

#### 段 3 の残り

| レジスタ | 食い違う音色 | 中身 |
|---|---|---|
| `0x00` | 13 | 切る高さ。**実行時は包絡線の式で出している**（6.65） |
| `0x02` | 2 | フィルタの第 2 係数 |
| `0x05` | 1 | LFO の深さ（Vibes だけ `fa04`） |

`make test` は 12 件とも合。試し曲は全体 +0.01 dB で変わらず。

### 6.70 `0x02` と `0x05` も起こした — 残るは `0x00` だけ

#### `0x02`（フィルタの第 2 係数）

`0x8000 | byte82` としていたが、実機（`0x12AFCE`）は

```
値 = byte82 * 16 + 24 * ((パート[120] - 64) + …) + 0x800
値を 0x800-0xFFF に収めてから & 0x7FF   （＝ 下駄を引く）
レジスタ = 0x8000 | 値
```

既定では `byte82 * 16` そのもの。DistGtr の `0180`（byte82=24）と
Kitayama の `0570`（byte82=87）が実機と一致した。

#### `0x05`（LFO の深さ・音量側）

実機（`0x129B34`）は **byte16 を 2 倍**して下位に置く。既定の音色は
ほとんど byte16=0 で、Vibes だけ 2 → `fa04`。

#### 段 3 の今

`--nocal`（式だけ）で 14 音色を突き合わせると、**食い違うのは `0x00` の
1 本だけ**になった。

| レジスタ | 前（6.67 のとき） | 今 |
|---|---|---|
| `0x00` | 13 | 13（実行時は包絡線の式で出している） |
| `0x04` | 4 | **0** |
| `0x08` | 4 | **0** |
| `0x0b` | 4 | **0** |
| `0x10` | 4 | **0** |
| `0x02` | 2 | **0** |
| そのほか | 各 1 | **0**（要素の取り違えだった） |

#### `0x00` はあと一歩

鍵を押した瞬間の `0x00` は「式の値 ＋ 包絡線の初めのずれ」で、
14 音色中 **8 音色**はこれでぴったり合う（GrandPno・Vibes・DrawOrg・
NylonGt・DistGtr・Violin・FngrBa・Kitayama）。

残る 6 音色（EPiano1・Strngs2・Trumpet・BrssSec・Flute・SquareLd）は
まだ合わない。実機の `0x12AC98` は

```
基準 = 表 0x1E5B58[byte37]（ただし voiceblk[2]==2 なら 0x127FA4 で強さを掛ける）
     + 0x12C1E4（鍵の追従）
     + R11[4]（まだ何か分かっていない語）
0 と 0xFFF に収める
+ 包絡線の今の値
```

で、**`0x127FA4`（強さの倍率）と `R11[4]` がまだ解けていない**。
ここが解ければ写し取りが要らなくなる。

### 6.71 `0x00` も解けた — 写し取り無しで**全レジスタ一致**（ただし既定はまだ切）

残っていた `0x00`（切る高さ）を解いた。実機（`0x12AC98` → `0x127E08` →
`0x12E79C`）はこう組んでいた。

```
基準 = 表 0x1E5B58[byte37] + 鍵の追従（0x12C1E4）      … 0-0xFFF に収める
値   = 基準 + フィルタの包絡線の今の値 >> 2            … 0xFFF に収めて下 11bit
**共振が 4 未満なら 0x7C0 で頭打ち**（0x12E79C）
レジスタ = 0x1000 | 値
```

三つとも新しく分かったこと:

1. **鍵の追従を `build_note` が入れていなかった**。実機は `R11+4` に
   「曲線 × 32」を持っていて、これは既に解いてあった `cutoff_key_curve`
   そのものだった。Flute はこれだけで一致した
2. **包絡線の初めの値**は `byte50`（立ち上がりの速さ）で分かれる。
   63（即到達）なら `byte55`（段 0 の行き先）から始まり、そうでなければ
   `byte54`（既定 64 ＝ 0）から `byte50` の速さで登る。
   GrandPno は前者で 0x400、Flute は後者で 0 だった
3. **共振が 4 未満のときだけ 0x7C0 で頭打ち**。EPiano1 は強さ 100 で
   共振 0 → `0x7C0`、強さ 127 で共振 4 → `0x7FF` と変わる

あわせて**ピッチ EG の速さにも鍵と強さの追従**があった（`0x12BC72`・
`0x12BCB2`）。SquareLd は鍵 60 では即到達（＝ピッチ EG 無し）だが、
鍵 72 では速さ 61、鍵 84 では 60 になり、1 オクターブ下から登ってくる。

#### 結果: 写し取りが要らなくなった

`SMU2000_CUT_EXACT=1` を立てて `--nocal`（写し取りを一切混ぜない）で
測ると、**14 音色 × 鍵 36/60/84 × 強さ 30/100/127 の 126 通りで、
スロットのレジスタが 1 本残らず実機と一致する**。

段 3 の「式だけでレジスタを組む」は、ここで**到達した**。

#### けれども既定はまだ切

既定で入れると試し曲が **+0.36dB 明るく**なる。原因は分かっている:

> **写し取りの無いスロットはフィルタの包絡線が動かない。**
> ドライバの段の進行は `s.cal`（録画）があるスロットだけを回しているので、
> 包絡線の初めのぶんだけフィルタが開いたまま戻らない。

つまり `0x00` の式は正しいが、**それを活かすには包絡線を録画無しでも
動かす**必要がある。そこが次の一歩。

（測り方の直し: `nativeplay` が音色の要素 0 で決め打っていたのも直した。
EPiano1 は強さ 96 で要素が切り替わるので、9 本ぶん測り間違えていた）

### 6.72 写し取り無しでもフィルタの包絡線を動かす

6.71 で分かった「写し取りの無いスロットは包絡線が動かない」を直した。
段の進行は録画（`s.cal->filter_env`）のあるスロットだけを回していたが、
`0x00` を式で出せるようになったので録画は要らない。

* 段を回す輪から `if (!s.cal) continue;` を外した（`SMU2000_CUT_EXACT=1` のとき）
* `fenv_cut` は写し取りが無ければ式（`cutoff_of`）から組む
* CC74 は、写し取りがあればそのときの値からの差、無ければ 64 からの差
* 立ち上がりの段（byte50 の速さで byte54 → byte55）を入れた
* 離しの段は録画が無くても張る

試し曲（乾いた版）は `SMU2000_CUT_EXACT=1` で **+0.36dB → +0.30dB**。
既定（写し取りを使う道）は **-0.01dB** で変わらない。

まだ 0.30dB 明るい。レジスタは鍵を押した瞬間には完全に一致しているので、
残るのは**押している間の段の進み方**。次はそこを実機と突き合わせる。

### 6.73 残った 0.30dB は「値」ではなく「時刻」だった

#### まず、前の測り方は間違っていた

最初に書いた 6.73 は**測り方を間違えていた**。突き合わせ用の
`cuttrace.py` と `keyphase.py` で、native 側に `--native-engine` を
渡し忘れていて、**firmware どうしを比べていた**。だから「1743493 本の
書き込みが 1 本残らず同じ」になったし、「キーオンが 781 回とも同じ
サンプル」にもなった。当たり前である。ここに残して戒めとする。

#### 直して測ったら

**値は合っている。ずれているのは時刻。**

`0x00` の動き（GrandPno・SquareLd・Strings1・EPiano1）:

```
実機 -24:15db 343:15db 782:15da 1223:15d9 1664:15d8 2099:15d8 2113:15d7 …
式     0:15db          785:15da 1226:15d9 1667:15d8          2108:15d7 …
```

* **値の並びは完全に同じ**（15db → 15da → 15d9 → …）
* 時刻が **2-3 サンプル**ずれる
* 実機はキーオンの前（-24）と後（343）に**同じ値を 2 回**書く。
  こちらは 1 回だけ
* 実機は 10ms の目が 441 ちょうどでなく揺らぐ（2099 と 2113）。6.66 で
  書いたとおり、これは原理的に真似できない

フィルタの係数が 2-3 サンプル遅れて書かれても、音にはほとんど効かない。

#### 効いているのは**キーオンの時刻**

試し曲（781 回のキーオン）を突き合わせた:

```
ずれ（サンプル）の多い順: -2:72回 +1:64回 -19:60回 +0:45回 +23:42回
                          -1:36回 +26:33回 -20:28回 +16:22回 -3:20回
平均 -5.92 / 中央 -1 / いちばん大きいずれ 330
```

**キーオンが ±20 サンプルばらつく。** 実機は MIDI を受けてから鍵を押す
までに firmware の取りこぼし待ちがあり、その遅れが音ごとに違う。
こちらは受けた瞬間に押している。

密な曲ではパート同士が打ち消し合うので、この ±20 サンプルが
「打ち消しの量」を変えてしまう。6.73 の 0.30dB はここから来ている。

次は **firmware が MIDI を受けてから鍵を押すまでの遅れ**を測って、
native 側も同じだけ待たせること。

### 6.74 キーオンの時刻は犯人ではなかった — 次は `0x32`（音色ごとのパン）

6.73 で「残りは位相（キーオンの時刻）」と書いたが、**振ってみたら効かなかった**。

`SMU2000_NATIVE_PROC`（バイトを受け終えてから鳴るまでのサンプル数。
既定 32）を足して、試し曲（乾いた版・`SMU2000_CUT_EXACT=1`）を測った:

| 遅れ | 差 |
|---|---|
| 20 | +0.31dB |
| 26 | +0.31dB |
| 32（既定） | +0.30dB |
| 40 | +0.30dB |
| 48 | +0.30dB |

ほとんど動かない。キーオンの ±20 サンプルは、この 0.30dB の主因ではない。

#### `trace_diff` で見えたもの

正しく（`--native-engine` を渡して）記録を取り直し、`tools/trace_diff.py`
で 12 パートの曲を突き合わせた。

**注意**: 音の数が firmware 410 に対し native 725 になる。こちらは
byte72 で遅らせる要素を**別のキーオン**で鳴らすので、数が合わない。
そのせいで時刻での対応づけがずれ、下の表は多めに出ている。

| レジスタ | 違った回数 | 中身 |
|---|---|---|
| `0x00` | 201 | 切る高さ。1 回あたり 225 のずれ |
| `0x09` | 177 | 減衰。1 回あたり 35 と小さい |
| `0x32` | 123 | **パン**。`050b` 対 `060b` のような食い違い |
| そのほか | — | 対応づけのずれで出ているぶんが多い |

128 音色を鍵 60・強さ 100 で当たったときも、`0x32` と `0x33` が
**13 音色**で食い違っていた（WarmPad・PolySyPd など）。音色そのものが
持っているパンと送りを、こちらが写し取りからしか取っていないため。

次はここ。音色の記録のどのバイトがパンと送りを決めるのかを起こす。

### 6.75 音色そのものが持つパン（`0x32`）を起こした

128 音色を当たると `0x32`（パン）が 13 音色で食い違っていた。Warm Pad や
PolySyPd のような、**2 つの要素を左右に振って広げる**音色である。

実機（`0x12AF40` と `0x12B794`）:

```
位置 = clamp(CC10 + 表 0x1E68DC[byte69] - 64, 0, 127)
       （byte69 が 15 のときだけ鍵で 0x1E68EB を引く）
左   = 表 0x1E6B90[パート[14]]        + 表 0x1E6C11[位置]
右   = 表 0x1E6B90[0x80-パート[14]]   + 表 0x1E6C11[0x80-位置]
レジスタ = (左 << 8) | 右      （どちらも 255 で頭打ち）
```

表 `0x1E68DC` は 16 個: `1 7 13 24 31 35 53 64 75 93 97 104 115 121 127 24`。
既定は byte69=7 → 64（中央）。Warm Pad は要素が byte69=2 と 12 で、
引くと 13 と 115。実機は片方に `083c`、もう片方に `3c08` を書いていて、
式と一致した。

表 `0x1E6B90` の中央（64）は 8 で、これが「中央で -3dB」の下駄になる。

`0x32` の食い違いは **13 音色 → 2 音色**になった。

#### 128 音色でいま残っているもの

| レジスタ | 音色数 | 中身 |
|---|---|---|
| `0x33` | 13 | リバーブ送り。パンのある音色で食い違う（次はここ） |
| `0x05` | 11 | LFO の深さ。`voiceblk[11]` の枝がまだ |
| `0x0a` | 6 | LFO の型と音程の深さ |
| `0x10` | 5 | 音程の包絡線 |
| `0x11`・`0x13` | 各 4 | 音程・波形の番地（多要素の音色の取り違えらしい） |

### 6.76 送りはパンのぶん目減りする（`0x33`・`0x34`）

`0x32` を直したら、こんどは `0x33`（リバーブ送り）が同じ 13 音色で
食い違った。実機（`0x12C3F8`）は

```
送りの減衰 = level→減衰 + 表 0x1F2198[パンの位置]
```

表は真ん中（64）が 16 で、左右に振るほど小さくなる（端は 0）。
つまり**パンを振るほど送りが目減りする**。

| 音色 | パンの位置 | 表 | 既定 `2b` からの差 | 実機 |
|---|---|---|---|---|
| Seashore | 7 | 3 | -13 | `1e` |
| Warm Pad | 13 | 4 | -12 | `1f` |
| BowedPad | 31 | 9 | -7 | `24` |
| PolySyPd | 53 | 14 | -2 | `29` |
| （中央） | 64 | 16 | 0 | `2b` |

**切ってある送り（`0xff`）はそのまま**にする。実機も頭打ちなので、
ここでパンのぶん引くと切ったはずのコーラスが開いてしまう
（`0x34` が 13 音色で `ffff` 対 `fff8` になった）。

#### 128 音色でいま残っているもの

| レジスタ | 音色数 |
|---|---|
| `0x05` | 11（LFO の深さ。`voiceblk[11]` の枝がまだ） |
| `0x0a` | 6（LFO の型と音程の深さ） |
| `0x10` | 5 |
| `0x11`・`0x13` | 各 4 |
| `0x00` | 3 |
| そのほか | 各 1-2 |

128 音色 × 32 本 = 4096 本のうち、**食い違うのは 40 本ほど**になった。

### 6.77 LFO（`0x05`・`0x0a`）を起こした — 4096 本のうち残り 25 本

#### 深さは「遅れが 0 のときだけ」

`0x05`（音量側の深さ）と `0x0a` の下位（音程側の深さ）は、どちらも
**遅れ（byte12）と byte13 がどちらも 0 のときだけ**入る（実機の `0x127D18`)。

```
0x05 の下位 = (byte12 か byte13 が 0 でなければ 0)、そうでなければ byte16 × 2
0x0a の下位 = 同じ条件で byte14 × 3
0x0a の上位 = (byte9 が 0 でなければ 0x40) | (byte11 & 0x3f)
```

| 音色 | byte9 | byte11 | byte12 | byte13 | byte14 | byte16 | 実機 `0x0a` / `0x05` |
|---|---|---|---|---|---|---|---|
| Vibes | 1 | 24 | 0 | 0 | 0 | 2 | `5800` / `fa04` |
| PanFlute | 1 | 31 | 0 | 0 | 1 | 1 | `5f03` / — |
| ChiffLead | 1 | 33 | 0 | 0 | 2 | 0 | `6106` / — |
| Shakuhachi | 1 | 31 | 40 | 15 | 7 | 1 | `5f00` / `fa00` |
| Koto | 1 | 31 | 48 | 0 | 0 | 1 | — / `fa00` |
| Rain | **0** | 45 | 0 | 0 | 0 | 31 | `2d00` / — |

Rain だけ byte9 が 0 で、上位の `0x40` が立たない。

#### いまの到達点

128 音色 × 鍵 60 × 強さ 100 で、スロットのレジスタ 32 本を
`--nocal`（写し取りを一切使わない）で実機と比べた:

| レジスタ | 食い違う音色 |
|---|---|
| `0x10` | 5 |
| `0x11`・`0x13` | 各 4 |
| `0x00` | 3 |
| `0x32` | 2 |
| `0x04`・`0x06`・`0x09`・`0x0a`・`0x0b`・`0x15`・`0x17`・`0x33` | 各 1 |

**4096 本のうち 25 本**（0.6%）。残りはどれも要素が 2 つ以上の音色で、
実機がどの要素をどのスロットに置いたかの取り違えが混じっている。

### 6.78 式だけの道の +0.30dB は「密なときだけ」出る

`SMU2000_CUT_EXACT=1`（写し取りを使わない道）の試し曲が +0.30dB 明るい件。
チャンネルを 1 つずつ**抜いて**測った（乾いた版）:

```
全部            +0.30 dB
ch0  を抜く     -0.05 dB     ch6  を抜く     -0.03 dB
ch1  を抜く     -0.04 dB     ch7  を抜く     +0.27 dB
ch2  を抜く     +0.01 dB     ch9  を抜く     -0.09 dB
ch3  を抜く     -0.04 dB     ch10 を抜く     -0.02 dB
ch4  を抜く     +0.04 dB     ch11 を抜く     +0.31 dB
ch5  を抜く     -0.05 dB     ch12 を抜く     +0.29 dB
```

**どれか 1 つ抜くだけで消える**（ch7・ch11・ch12 のように、もともと
薄いパートを抜いたときだけ残る）。つまり**特定のパートのせいではなく、
12 パートが重なったときにだけ出る**。

1 パートずつ鳴らして足すと +0.08dB、まとめて鳴らすと +0.30dB。
実機のほうが混ぜたときに打ち消し合っている（-0.57dB 対 -0.36dB）。

#### 6.74 の書き方を直す

`SMU2000_NATIVE_PROC` を振っても効かなかったのは当然だった。あれは
**native の鍵を全部まとめてずらす**だけなので、パート同士の**相対的な**
ずれは変わらない。打ち消し合いに効くのは相対のずれのほうなので、
あの実験では「キーオンの時刻が犯人かどうか」を確かめられていない。

いま分かっているのは:

* レジスタの**値**は実機と同じ（`0x00` の動きも、離し切るまで一致）
* キーオンの時刻は音ごとに **±20 サンプル**ばらつく（相対のずれ）
* 既定（写し取りを使う道）は同じ曲で **+0.00dB**

つまり既定の道では、写し取った値が「相対のずれのぶん」をたまたま
打ち消していると思われる。式だけの道を既定にするには、**MIDI を受けて
から鍵を押すまでの遅れを、音ごとに実機と同じにする**必要がある。

### 6.79 相対のずれも主因ではなかった

6.78 で「相対のずれを試せていない」と書いたので、試した。
`SMU2000_RX_BYTE`（MIDI の 1 バイトが線を流れる時間。1/64 サンプル単位、
既定 903 ＝ 14.1 サンプル）を振ると、**和音の中の音の相対的なずれ**が変わる。
0 にすれば和音は全部同じ時刻に出る。

| `RX_BYTE` | 式だけ | 既定 |
|---|---|---|
| 0（同時に出す） | +0.26dB | -0.02dB |
| 451（半分） | +0.27dB | -0.02dB |
| 903（既定 ＝ 実機の線の速さ） | +0.30dB | -0.01dB |
| 1806（倍） | +0.24dB | -0.05dB |

**相対のずれを大きく変えても ±0.06dB しか動かない。** 打ち消し合いの差は
時刻のせいではない。

#### いまの整理

| 分かっていること | 根拠 |
|---|---|
| レジスタの値は実機と同じ | 128 音色 × 32 本で食い違い 25 本（0.6%） |
| `0x00` の動きも実機と同じ | 4 音色で離し切るまでサンプル単位で一致 |
| 1 パートずつなら実機とほぼ同じ | 12 パート全部 ±0.1dB 以内 |
| 時刻のずれは効かない | 上の表、および `NATIVE_PROC` の振り |
| それでも 12 パート重ねると +0.30dB | 実機のほうが打ち消し合う（-0.57 対 -0.36dB） |

**値も時刻も合っているのに、重ねると打ち消し合いの量が違う。**
残っているのは「波形そのものの位相」——同じレジスタでも、波形の読み出し
位置や LFO の位相が実機と違えば、重ねたときの打ち消し方は変わる。
そこを見るのが次。

なお**既定の道（写し取りを使う）は同じ曲で ±0.02dB**で、上の揺さぶりにも
びくともしない。利用者に届くのはこちらなので、いま困っていることは無い。

### 6.80 音程の包絡線は**段が続いていた**（1 段しか入れていなかった）

6.68 で入れたピッチ EG は「初めの高さ → 行き先」の 1 段だけだった。
1 パートずつ波形の相関で見たら、リード（SquareLead、ch3）が
**中央 -27%** ——ほとんど無相関だった。音の大きさ（rms）は +0.26dB
しか違わないので、rms だけ見ていたら気づけなかった。

記録を取り直すと、実機はこう書いていた（SquareLead・鍵 76）:

```
実機 -44:7f00(初め -256)  0:4000(行き先 0)  312:7ffd(-3!)  2958:4000
     0x0b は -44:5c00(速さ 92) → 311:0800(速さ 8)
こちら 0:7f00 0:4000     （それきり）
```

**段 1・段 2 がある。** 並びはこう:

| 段 | 速さ | 行き先 |
|---|---|---|
| 0（押した直後） | byte26 | byte31 |
| 1 | byte27 | byte32 |
| 2 | byte28 | byte33 |
| 離し | byte29 | byte34 |

SquareLead は byte27=1・byte32=63 で、鍵 76 の追従 -2 を足すと目盛り 0 →
表で速さ 8、行き先は (63-64)×75>>2 = -18 セント → -3。実機の
`0800` と `7ffd` にぴったり一致した。

#### 進め方

実機の firmware は**チップの「行き先に着いた」印**（内部レジスタ 4 の
bit14、`0x12B81C`）を 10ms ごとに見て次の段へ進む。native の口も同じに
した（`swp30_device::peg_reached`）。刻みはフィルタの包絡線と同じ格子
（録画の 1 段目から取る）の 1 目手前。

結果、実機が 312/2958 で書くところを **313/2959** で書くようになった
（値は完全に一致）。

| 測り方 | 前 | 後 |
|---|---|---|
| ch3（リード）単独の rms | +0.26dB | **+0.02dB** |
| 試し曲（12 パート） | +0.00dB | **-0.00dB** |

#### 分かったこと: rms だけでは足りない

ch3 は rms が合っていても波形が合っていなかった。**1 パートずつ
波形の相関で見る**のが要る。いまの相関（中央）:

```
ch0 ベース   98.9%     ch7 ピアノ   86.8%
ch9 ドラム   92.0%     ch1 パッド   71.3%
ch5 ギター   66.8%     ch3 リード  -38.8%
```

ch3 がまだ低いのは、**音ごとのキーオンの時刻が ±20 サンプルずれる**
から（6.79）。400Hz の矩形波では 20 サンプルが 65 度の位相差になる。
次はここ。

### 6.81 MIDI を受けてから鍵を押すまで — 空いていれば合う、混んでいるとずれる

ch3（リード）の波形が実機と合わない件を追った。ずらしながら相関を取ると

```
10 秒: +36 サンプルずらすと 85.9%    20 秒: +33 ずらすと 99.9%
14 秒: -58 サンプルずらすと 85.2%    26 秒: -12 ずらすと 96.3%
```

**波形そのものは合っていて、時刻が 30-60 サンプルずれている**だけだった。

#### 空いているときは 1 サンプルまで合う

切り分けのために、わざと空いた MIDI で測った（`keylat.py`・
`chordlat.py`・`premsg.py`）。

| 測ったもの | 実機 | 式 |
|---|---|---|
| 1 音だけ、48 回・到着の位相を 45.9 サンプルずつずらす | いつも +73 | **いつも +73**（1 音目だけ +74） |
| 2-8 音の和音 | +74 +117 +159 +202 +243 +286 +329 +369 | +73 +115 +157 +200 +242 +284 +327 +369 |
| 鍵の前に CC1 を 1 個 / 3 個 | +117 / +201 | +115 / +200 |
| 鍵の前にベンドを 1 個 / 9 個 | +117 / +455 | +115 / +454 |
| 鍵の前に CC7 と CC11 | +158 | +157 |

**どれも 1-2 サンプル以内。** MIDI が線を流れる時間（1 バイト 14.1
サンプル）も、受けてからの手間（32 サンプル）も合っている。

#### 混んでいるとずれる

ところが実際の曲（12 パートぶんの CC が流れている）では、ch3 の鍵 41 個の
ずれがこう割れる:

```
  -33 ########    -30 #######    -29 #######
  -32 #######     -31 #
  +15 ######      +16 ##
```

**-30 あたりと +15 あたりの二山**で、差はちょうど 45 サンプル（1ms）。
音色の記憶を使っても（写し取りを挟まなくても）同じなので、写し取りの
せいではない。

45 サンプルは **firmware の主ループが 1 周する時間**とみられる。空いて
いるときは受けた次の周で処理できるが、混んでいると 1 周ぶん待たされる。
こちらは「バイトが届いた時刻＋32」で即座に鳴らすので、その待ちが無い。

#### つまり

**鍵の時刻を 1 サンプルまで合わせるには、firmware の主ループの混み具合を
真似るしかない。** それは「firmware を走らせない」という段 3 の前提と
正面からぶつかる。ここは段 3 の外の話で、別の手（たとえば混み具合を
見積もって待たせる近似）を考えることになる。

なお**音そのもの（レジスタの値）はもう合っている**。ずれているのは
「いつ鳴らすか」だけ。

### 6.82 試験に「波形の形」を足した — porta と dense が低いと分かった

6.80 で「rms だけでは足りない」と分かったので、`make test` に
**波形の相関**の試験（`native の形`）を足した。既定の道と native の口を
1 秒ごとに相関で比べる。

いまの値（中央）:

```
piano   100%    effects 100%    bend   100%    egcc   100%
port_b  100%    lofi    100%    at     100%    sxparam 99%
chord    98%    drums    89%
dense    46%    porta   -26%      ← まだ低い
```

**7 件は 100%**（サンプル単位でそっくり）。残り 2 件がはっきり低い。

#### porta（ポルタメント）: -26%

`SMU2000_NO_PEG=1` でも -18% なので、今回入れた音程の包絡線のせいでは
ない。**前からあった不具合**で、rms しか見ていなかったので気づけて
いなかった。記録を並べると:

```
実機   189690:3a5c 189936:3a91 190376:3ac6 190816:3afb   （240-440 サンプルごと）
こちら 189703:3a5c 190070:3a92 190511:3ac7               （441 ごと。値も 1 ずれる）
```

* 滑る刻みの**格子**が実機とずれている（実機の 2 つ目は 246 サンプル後、
  こちらは 367 サンプル後）
* 値が 1 ずつずれていく（`3a91` 対 `3a92`）
* おまけに**こちらは 0x11 を 26388 回も書いている**（毎サンプル）。
  滑っている間、段の輪が毎サンプル回っている。音は変わらないが無駄

#### dense（60 音の重なり）: 46%

密なときだけ出る話（6.78）と同じ根。

#### 試験の作り

下限は試験ごとに持たせた（`SHAPE_MIN`）。いま出ている値から少し余裕を
引いたもので、**下回ったら落ちる**。porta の -0.35 のように低い下限も、
「ここから悪くなったら気づく」ための線として置いてある。

### 6.83 ポルタメントを直した（-26% → 45%）

6.82 で見つけた porta の不具合を直した。二つあった。

#### 1. 滑る刻みの格子

`glide_next` を「世界共通の 441 の格子」に乗せていたが、実機の 10ms の
目は**その格子とは別の位相**にある。フィルタの包絡線と同じ目
（録画の 1 段目から取った実機の格子）の 1 つ手前に合わせた。

```
実機   189936 190376 190816   （間隔 440）
前     190070 190511 ...      （実機より 134 遅い）
後     189906 190347 190788   （実機より 29 早い ＝ 鍵そのもののずれぶん）
```

#### 2. 0x11 を毎サンプル書いていた

滑っている間、段の輪が回るたびに `0x11` を書いていた。1 音の滑りで
**26388 回**。値は同じなので音は変わらないが、無駄だった。
動いたときだけ書くようにして **21-61 回**になった。

| 試験 | 前 | 後 |
|---|---|---|
| porta の波形の相関（中央） | **-26%** | **45%** |

残る 45% は「鍵そのものが 29 サンプル早い」ぶん（6.81 の、混んでいる
ときに firmware が 1 周ぶん待つ話）。

### 6.84 ドラムはフィルタの包絡線を捨てていた

段の輪で「`0x00` と `0x04` は式で出すから録画の分は捨てる」としていたが、
**ドラムは要素（`s.elem`）を持たない**（`drum_on` は写し取った値をその
まま使う道で、`su.elem = nullptr` にしている）。式は要素が無いと動かない
ので、捨てたぶんが誰にも埋められず、**ドラムだけフィルタの包絡線が
丸ごと消えていた**。

```
実機   -23:161b 347:161b 786:161a 1227:161a 1668:1619 2109:1619 …
直す前   0:161b 785:161b 1226:161b 1667:161b 2108:161b …   （動かない）
```

「**式で出せるときだけ録画を捨てる**」（`s.elem` があるときだけ）に直した。

#### まだ残っているドラムの差

直したあとも波形の相関は 89% のまま。値を数えると

```
実機   1 打につき 162 回書いて 99 通りの値
こちら 1 打につき 172/322 回書いて 48 通りの値
```

**録画の目が実機の半分しかない**。写し取りの録画は 1 音ぶんしか取らない
ので、打ってから鳴り終わるまでの細かい段を取りきれていないとみられる。

ドラムも本当は要素を持っている（キットの表から引ける）ので、**旋律の
音色と同じく式で出すようにするのが筋**。そこが次。旋律側は同じ仕組みで
piano・effects・bend・egcc・port_b・lofi・at の 7 件が 100% になっている。

### 6.85 ドラムの 1 打の記録を引けるようになった

ドラムを式で出すには、まず「その鍵がどの記録を鳴らすか」を引けないと
始まらない。`xg::voices::lookup` はドラムだと 0 を返していた。

実機の `0x134DB8` を起こした:

```
キットの番号 = パートの塊の +0x110
表の先頭     = rd32(0x292250 + (キット & 0x7f) * 4)
ずれ         = rd16(表の先頭 + 鍵 * 2)          （0xFFFF なら鳴らない）
記録         = 0x283DD0 + ずれ
```

（キットの番号の bit7 が立っていないときは別の道へ行く。SFX キットなど。
まだ真似していない）

実機が鳴らした値と突き合わせて確かめた。Standard Kit はキット番号 36 で

| 鍵 | ずれ | 記録 |
|---|---|---|
| 35 | 039C | 28416C |
| 36（バスドラム） | 03C6 | **284196** |
| 38（スネア） | 850E | **28C2DE** |
| 42（ハイハット） | 8562 | **28C332** |
| 49（クラッシュ） | 85E0 | 28C3B0 |

太字は、実機のワーク RAM（ボイスの塊 +48）から読んだ値と一致したもの。

`xg::voices::drum_record(kit, note)` として入れた。

#### 記録の並びはまだ

引けるようになったが、**中身の並びは旋律の要素（84 バイト）とは別**
だった。実機の `0x12AFCE` は、ボイスの塊の +2 が 1（＝ドラム）のとき
フィルタの第 2 係数を **記録の +20** から読む（旋律は +80）。
波形の組も byte2/byte3 には無い。

```
鍵36 の記録の頭 16 バイト: 40 24 7f 00 40 20 20 7f 00 00 01 7f 10 7a 23 4f
鍵38            :          40 39 7f 00 40 7f 7f 7f 00 00 01 74 27 7f 3a 3f
鍵42            :          40 7e 5b 01 4d 20 20 7f 00 00 01 7f 20 7f 5d 25
```

ここを解けば、ドラムも旋律と同じく式で出せる。いまドラムは写し取りの
再生で、録画の目が実機の半分しかない（6.84）。旋律側は同じ仕組みで
7 件が 100% になっているので、伸びしろは大きい。

### 6.86 ドラムの記録の並び — **42 バイト**、9 本のレジスタが解けた

6.85 で引けるようになった記録の中身を、実機がどのバイトを読んだか
（`SMU2000_ROMTRACE` を記録の番地に向ける）と、実機がスロットに書いた
値との突き合わせで解いた。Standard Kit の 4 つの打（鍵 36/38/42/49）で
確かめている。

#### 大きさは 42 バイト

```
鍵 36  40 24 7f 00 40 20 20 7f 00 00 01 7f 10 7a 23 4f 40 40 0c 36 00 40 40 3c ff ff
       4c 00 fc 00 6c 00 11 f2 00 00 00 00 40 00 b0 31 | 40 61 5d 00 …（次の記録）
鍵 38  40 39 7f 00 40 7f 7f 7f 00 00 01 74 27 7f 3a 3f 40 40 0c 36 00 40 40 3c ff ff
       42 01 fd 00 40 00 2e 08 00 00 00 00 00 00 d2 89 | 40 3f 7b 00 …
```

`+42` から次の記録が始まる。

#### 解けたレジスタ（4 打とも一致）

| レジスタ | 式 |
|---|---|
| `0x00` 切る高さ | `0x1000 \| (表 0x1E5B58[+11] & 0x7FF)` |
| `0x02` 第 2 係数 | `0x8000 \| min(0x7FF, +20 × 16)` |
| `0x04` 共振 | `(+12 >> 2) << 11` （旋律は `>> 1`。目盛りが違う） |
| `0x06` 立ち上がり | `表 0x1F4DB8[+13] << 8 \| (+13 == 0x7F ? 0 : 0x7E)` |
| `0x07` 減衰 1 | `表 0x1F4E38[+14] << 8 \| 0x04` |
| `0x08` 減衰 2 | `表 0x1F4E38[+15] << 8 \| ((0x7F - +10) × 2)` |
| `0x12`-`0x17` 波形 | **+26 からの 16 バイトが波形の記録そのもの** |

**旋律と違って速さの目盛りを 2 倍しない**（旋律は `rate_scale` で ×2）。
共振も `>> 2`（旋律は `>> 1`）。ドラムは別の目盛りを使っている。

波形の記録の埋め込みは 4 打とも完全に一致した:

```
鍵 36: +26.. = 4c 00 fc 00 | 6c 00 11 f2 | 00 00 00 00 | 40 00 b0 31
       実機  = 0x12=6c00 0x13=11f2 0x14=0000 0x15=0000 0x16=4000 0x17=b031
鍵 49: +26.. = 3c 02 fe df | 00 01 1f 25 | 00 00 44 e2 | 80 48 b0 95
       実機  = 0x12=0001 0x13=1f25 0x14=0000 0x15=44e2 0x16=8048 0x17=b095
```

#### まだのもの

| レジスタ | 実機の値（4 打） | 様子 |
|---|---|---|
| `0x11` 音程 | 3a93 / 3e50 / 0034 / 00a7 | 打ごとに違う。どのバイトから来るか未解明 |
| `0x0a` LFO | 7000（4 打とも同じ） | 上位 `0x70`。どこから来るか未解明 |
| `0x05`・`0x0b`・`0x10` | fa00 / 0000 / 0000 | 4 打とも同じ。ドラムは音程の包絡線を持たない |
| `0x09` 減衰 | 0012 / 0012 / 001a / 0020 | 打ごとに違う（写し取りの道では強さで動かしている） |
| `0x32`・`0x33` | 0808/1808/1008、184b/182b/1849/182a | 打ごとのパンと送り |

音程（`0x11`）が解ければ、ドラムも写し取り無しで鳴らせる。

### 6.87 ドラムの音程（`0x11`）も解けた — 58 鍵すべて一致

#### どこから来るか

```
0x11 へ書く命令      0x12E00C（スロット + 34）
その値の出どころ     ワーク RAM 0x43E96C
そこへ書く命令       0x12847A
セントを組み立てる所 0x128334-0x128472
セント → 目盛り      0x12C08A（表 0x1E9298。1200 セント = 1024）
```

#### 式

`SMU2000_RAMTRACE` で実機が読んだ値を見たら、こうなっていた:

```
R10 = ボイスの塊[44]  ＝ **XG のドラムセットアップ**（鍵ごとの設定。RAM）
R11 = ボイスの塊[48]  ＝ ドラムの記録
R14 = R10[0]                          （設定の粗調。既定 64）
R14 += 符号つき 記録[+28]              （XG のとき。GM のときは 記録[+27]）
R14 -= 記録[+26]
R14 += パート[8] - 64 + パート[0xC9]   （どちらも既定 0）
R14 *= 100                            ← ここまでが半音
R14 += 記録[+1] - 64                  （セント）
R14 += 設定の微調 - 64                （R10[1]。既定 64）
```

つまり

```
セント = (設定の粗調 + 符号つき記録[+28] - 記録[+26]) × 100 + (記録[+1] - 64)
レジスタ = 表 0x1E9298[|セント|]（負なら符号を分けて (-値) & 0x3FFF）
           波形の形式が 3 なら 0x4000 を立てる
```

| 鍵 | 記録[+26] | 記録[+28] | 記録[+1] | セント | 実機 `0x11` |
|---|---|---|---|---|---|
| 36 | 76 | -4 | 36 | -1628 | **3a93** |
| 38 | 66 | -3 | 57 | -507 | **3e50** |
| 42 | 60 | -4 | 126 | +62 | **0034** |
| 49 | 60 | -2 | 60 | +196 | **00a7** |

Standard Kit の**鳴る鍵 58 個すべてで実機と一致した**。

#### ドラムの記録のまとめ

| ずれ | 中身 |
|---|---|
| +1 | 音程の微調（セント。64 が中央） |
| +10 | 減衰 2 の行き先 |
| +11 | 切る高さ（表 0x1E5B58 の索引） |
| +12 | 共振（`>> 2` して上 5bit） |
| +13 | 立ち上がりの速さ |
| +14 | 減衰 1 の速さ |
| +15 | 減衰 2 の速さ |
| +20 | フィルタの第 2 係数 |
| +26 | 音程の基準（半音。**引く**） |
| +27 | GM のときの半音のずらし |
| +28 | XG のときの半音のずらし（符号つき） |
| +29 | ? |
| +30..+41 | ループ前・ループ長・形式と番地（`0x12`-`0x17`） |

全体で 42 バイト。これで**ドラムも写し取り無しで組める**ところまで来た。

## 7. 失うもの・気をつけること

* **パネル・LCD・サンプリング・SmartMedia・シーケンサは動かない。** native モードは「音源」で、
  「機械」ではなくなる。DAW で鳴らすぶんには困らないが、窓の LCD は firmware 版でしか出せない
* **「実機の firmware をそのまま走らせている」という強みが、その口では無くなる。**
  音が違ったときに「こちらの写し間違い」が原因になりうる。だから 5. の突き合わせを必ず持つ
* 音色の記録の解釈を間違えると、**特定の音色だけ違う**という形で出る。1635 音色ぶんの回帰が要る
* 実機由来のデータ（ROM）の扱いは今までどおり。native driver は ROM を**読む**だけで、中身は配らない

## 8. 折衷の案

| 案 | 中身 | 効き目 |
|---|---|---|
| A | エフェクトだけ C++（[native-dsp.md](native-dsp.md)。**もうある**） | 1 割 |
| B | 起動のときだけ firmware を走らせ、設定が固まったらレジスタを写し取って以後は native | 曲の途中で音色やコントローラが動かない用途なら有効。動くと破綻する |
| C | 全部 native（この文書） | 半分以下（複数インスタンスに効く） |
| D | firmware を走らせる時間を削る（SH-2 の JIT をさらに詰める） | JIT 済みなので、あと 1〜2 割が上限とみている |

順番としては **A（済み）→ 0 と 1 の調べもの → C の 2 段目**が素直。0 と 1 が終われば、
C に進むかどうかを数字で判断できる（84 バイトの何割が機械的に説明できたか）。

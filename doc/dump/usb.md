# USB（M37640）経由のダンプ

**完成（2026-09-07）。** USB ケーブル 1 本で波形 ROM 32MB を約 36 分で吸える。
DIN の MIDI ケーブルも MIDI インターフェースも不要。

実測: 131,072/131,072 ブロック、**57.3 blk/s（理論値 58 の 98.8%）**、加算和 NG 0 個。
書き出した 4 ファイルは MAME 登録のハッシュと一致し、**MIDI 版で吸ったものとも
1 バイト残らず一致**した（独立した 2 経路での相互検証）。

**ダンパを組み立てる**（`build/usbdump64.ydl` は配らない。純正ファームを
含むので、各自の手元で作る）。土台の `roms/mu2000_flash.bin` は
[rom-dump.md](rom-dump.md) の手順で純正アップデータから復元したもの。

```bash
python tools/dump/build_firmware.py --module usbdump --words 64 \
       --base roms/mu2000_flash.bin -o build/firmware_usbdump64.bin
python tools/dump/make_ydl.py --image build/firmware_usbdump64.bin \
       --ref roms/updater/x/mu2r1_uw/part2/images/v200u22k.ydl \
       -o build/usbdump64.ydl
```

`build_firmware.py` が中で `make_usbdump.py` を呼ぶので、ダンパ本体を別に
作る必要はない。`make_ydl.py` は純正の `.ydl` を雛形にして、コマンド列と
デルタタイムをそのまま流用し中身だけ差し替える。

**書き込んで吸う。**

```bash
python tools/dump/stage_ydl.py build/usbdump64.ydl
build/upgrade_dumper/Upgrade.exe                      # 約 12 分
python tools/dump/recv_dump.py --port "Yamaha MU2000-1" --prime-port "Yamaha MU2000-1"     --words-per-block 64 --out roms/dump              # 約 36 分
python tools/dump/verify_roms.py roms/dump
```

HOST SELECT を USB にして PC と直結（ハブは挟まない）。

> **吸い終わったら必ず純正に戻すこと。**
>
> ```bash
> python tools/dump/stage_ydl.py --stock
> build/upgrade_dumper/Upgrade.exe
> ```
>
> このファームは**吸い出し専用の道具**で、入れっぱなしにするものではない。
> `rxisr` は USB から 1 バイト受けるたびに呼ばれ、その中で SWP30 の
> wave direct access を 64 ワード分たたく。**そのレジスタは純正が発音に使うものと同じ**なので、
> 曲を再生すると（＝大量のノートが流れ込むと）ノートオンの処理中に横取りが起き、
> 純正側の待ちループが返らなくなって**本体が固まる**（実機で確認）。
>
> 引き金を送らなければ自作コードは動かないので、繋がなければ無害ではある。
> だが USB に挿したまま音源として使うと踏むので、戻しておくのが安全。

仕組みは一言でいうと、**純正ファームをそのまま動かしたまま、USB の受信割り込みだけを
横取りする**。PC がバイトを 1 個送ると、割り込みの中で SWP30 から 64 ワード読んで
SysEx に組み、純正のドライバに渡して帰る。送らなければ 1 命令も動かない。

以下は、そこへ辿り着くまでの調査と、潰した仮説の記録。

## なぜやりたいか

MIDI 経由のダンプは完成していて、32MB を約 3.8 時間で吸える。USB を使いたい理由は 2 つ。

1. **MIDI インターフェースを持っていない人でも吸える。** USB ケーブル 1 本で済むなら試せる人が大幅に増える
2. 速度。実測できていないが、純正アップデータの USB 書き込み（4.58MB を約 12 分、うち消去 3 分半）
   から逆算すると MIDI の 3 倍程度。リンク自体はもっと速い可能性が高い

## ハードウェア

USB は **M37640M8-101FP（UD 基板 IC3）** が担当する。SH7043 とは 8bit の
パラレルバス（CS3 空間）で繋がっていて、SH-2 から見えるのは 2 番地だけ。

| 番地 | 読み | 書き |
|------|------|------|
| 0xF80000 | 受信バイト | — |
| 0xF80001 | ステータス（bit0 = 受信あり, bit7 = まだ続く） | 送信 1 バイト |

サービスマニュアル（`docs/ref/MU2000_SM.pdf` の UD:IC3 ピン表）より:

- ピン 10 `/RESET` — リセット入力
- ホスト側インタフェース: `/S0`（チップセレクト）`A0`（番地）`/R(E)` `/W(R//W)`
  `/IBF0`（入力バッファフル）`/OBF0`（出力バッファフル）
- ピン 70/71 が USB D+/D−

`/IBF0` `/OBF0` が SH-2 の IRQ2 / IRQ3 に繋がっていると考えられる。

## 割り込み経路

USB の送受信は完全に割り込み駆動で、ポーリングする口は無い。

```
外部割り込み IRQ2 / IRQ3
  -> ベクタ 66 / 67 = ダウンローダのハンドラ 0x0032DE / 0x003318
       R0-R7 と PR を退避し、割り込みスタック（0x402200）に切り替える
  -> RAM の関数ポインタ経由で JSR
       IRQ2（送信）= long @0x401044
       IRQ3（受信）= long @0x401040
  -> そのポインタは、ダウンローダが 0x040100 へ飛ぶ直前に
     本体ファームのヘッダから写してくる（0x000404 のルーチン）
       0x0400D8 -> 0x401044     純正の値 0x00043486
       0x0400DC -> 0x401040     純正の値 0x00043630
```

**つまり本体ファームのヘッダに自前のハンドラ番地を書いておけば、
ダウンローダがそれを据えてくれる。** `tools/dump/build_firmware.py` の `HEADER_PATCH` が
これをやる。実機で「自前ハンドラが据わった」ことまでは確認済み。

## 本体ファーム v2.01 側の実装

USB ドライバは 0x0433B8-0x0436CE に収まっている。

| 番地 | 内容 |
|------|------|
| 0x043486 | 送信ハンドラ。リングから 1 バイト取り出して 0xF80001 へ書く。空なら IPRA の IRQ2 を落とす |
| 0x043630 | 受信ハンドラ |
| 0x40A846 | 送信リングバッファ（128 バイト） |
| 0x43DACD / 0x43DACE | 送信リングの読み位置 / 書き位置 |

## ダウンローダ側の実装

| 番地 | 内容 |
|------|------|
| 0x0006AC | 受信ルーチン。ステータス bit0 を待って 0xF80000 を読み、0xF8 以上（MIDI リアルタイム）を捨ててリングへ積む |
| 0x00071E | 送信ルーチン。0x400014（残数）と 0x400018（ポインタ）から 1 バイト取り出して 0xF80001 へ。空なら IPRA の IRQ2 を落とす |
| 0x00077C | `IPRA \|= 0x0D` — IRQ3（受信）を優先度 13 で許可 |
| 0x000788 | 送信を仕掛ける。0x400014 / 0x400018 を設定し `IPRA \|= 0xD0` |

**M37640 の初期化シーケンスやリセット解除は、ダウンローダにも本体ファームにも存在しない。**
全ファームウェア 4MB を通して 0xF800xx を参照するコードは 11 箇所しかなく、
すべて上記の読み書きだけ。

## 決定的な差分: IPRA

初期化ルーチン（0x000D50）は IPRA-IPRE をすべて 0 にする。
IPRA の IRQ2 / IRQ3 を許可するのは **ダウンロードモードの経路だけ**。
通常起動（0x000BE0 → `JSR 0x040100`）では一度も許可されない。

これが「ダウンロードモードでは USB が列挙され、自作ファームでは列挙されない」ことの
最有力の説明だった。しかし**再現しなかった**（下記）。

## 転送モードと MIDI 受信（実用上の落とし穴）

ダウンローダはワーク RAM 0x401049 に転送モード（0=MIDI, 1=シリアル, 2=USB）を持つ。
HOST SELECT を ADC で読んで決める（0x001098）。

```
0x000EB4: CMP/EQ #$02,R0          ; USB か
0x000EB6: BF     0x0EC2
0x000EB8: word @0xFFFF8352 = 0      ; USB -> SCI 受信を止める
0x000EC2: word @0xFFFF8352 = 0x0D   ; MIDI/シリアル -> 受信を有効に
```

**HOST SELECT が USB のとき、ダウンローダは MIDI IN からの `.ydl` を受け付けない。**
`tools/dump/send_ydl.py` は応答を見ないので、何も書き込まれていなくても進捗だけ進む。
LCD の表示が変わらないことで気づける。ツール側に警告を入れてある。

同じ分岐で SCI1（TO HOST シリアル）の BRR も切り替わる。
モード 1 のとき 0x16（38,400bps）、それ以外は 0x1B（31,250bps）。

## 試して駄目だったこと

すべて実機で確認した。MAME は M37640 をエミュレートしないので検証できない。

| 試したこと | 結果 |
|---|---|
| 何もせず待つ（ダウンローダが整えた状態のまま） | 列挙されない |
| 0xF80001 をポーリングして 0xF80000 を読み捨てる | 状態が進まない。読める値は固定 |
| 自前ハンドラを据え、IPRA を許可し、SR のマスクを下げる | **割り込みが一度も来ない** |
| 割り込みに頼らず 0xF80001 へ直接書く | 何も起きない |
| LED ラッチ 0xE00000 / 0xC80000 を 1 ビットずつ + 全ビット立てる（18 通り） | 変化なし |
| ポート A 上位の丸ごと上書きをやめる（読み変更書きに変更） | 変化なし |

据わったハンドラ番地・IPRA・SR は実機で読み返して確認済み。
**SH-2 側はダウンロードモードと同じ状態にできている。**

## 観測: バスが浮いている

0xF80001 の読み値がおかしい。

- 1 秒に 1 回読むと `0x33`、5µs 間隔で読むと `0x03`（**同じ番地なのに読み方で変わる**）
- 0xF80000 は常に固定値（`0x10`）を返し、読んでも bit0 が落ちない
- ファームウェアを別のものに差し替えると値が変わる（`0x33` → `0x19`）

これらは M37640 がバスを駆動しておらず、直前にバスに乗っていた値の名残を
読んでいるときの典型的な症状。**M37640 は動いていないと考えられる。**

なお、この「連続アクセスで値が化ける」性質は、仮に動かせたとしても
ドライバ側で**アクセス間隔を空ける必要がある**ことを意味する。

## 自作コードの置き場所（重要な見落としだった）

長らく自作コードを **0x041000** に置いていたが、そこには純正のコードが入っている。
つまり「純正の初期化を呼ぶ」実験の間、その一部を自分で壊していた。

本体ファーム領域 0x040000-0x3DFFFF で 0xFF が続く空きは
**0x3CBBB3-0x3DFFFF の 83KB だけ**。ここに置けば純正は無傷で残る。
`tools/dump/build_firmware.py` の `BODY` は 0x3CC000 にしてある。

置き換えたうえで純正の初期化列を全部呼び、割り込みマスクも外したが、
それでも USB は立ち上がらなかった。**初期化列だけでは足りない。**

## 純正ファームの構造（解析結果）

### 起動

```
0x040100: SR のマスクを 0xF0 に
          BSR 0x040192 / JSR 0x1159F0 / BSR 0x040150
          JSR 0x115F62 (R4=1) / JSR 0x115AAC / JSR 0x1155FC / JSR 0x1155C8
          JSR 0x11658A / JSR 0x116098 / JSR 0x0C7694
          JSR 0x11A4F0     ← この中で 0x04347C（USB 受信割込を許可）が無条件に呼ばれる
          JMP 0x040C5C     ← メインループ
```

### メインループはタスクスケジューラ

```
0x040C5C: 制御ブロック 0x040770 から SR / R15 / R12 を復帰
          (R13+0x60) の関数ポインタを呼ぶ
          JSR 0x041E94 / 0x041AAC / 0x041A5C / 0x041B0C / 0x041E50
          JMP 0x041D24
```

呼び先は**リテラルから読まれている**。

| リテラル | 値 |
|---|---|
| 0x040CD0 | 0x00041E94 |
| 0x040CD4 | 0x00041AAC |
| 0x040CD8 | 0x00041A5C |
| 0x040CDC | 0x00041B0C |
| 0x040CE0 | 0x00041E50 |

**4 バイト書き換えるだけで毎周回フックできる。** 命令のコピーもパッチも要らない。
自前の関数は最後に本来の呼び先へ JMP すれば、その RTS でメインループへ帰る。

### USB ドライバ（0x0433B8-0x0436CE）

> **重要な訂正（2026-09-07）**: 0x0433A0 は **M37640 のコマンド口**であって、MIDI データの
> 送り口ではない。ここに MIDI を流し込んでいたのが「USB へ 1 バイトも出ない・本体が
> もたつく・DEMO が固まる」の原因だった。実際に積まれるのは固定長フレームだけである。
>
> ```
> f4 06 02 02 01 00 00 02                    (8 バイト)
> f4 0c 02 03 01 08 00 00 00 00 00 00 00 00  (14 バイト)
> f4 0a 01 03 08 00 00 00 0f 0f 00 00        (12 バイト)
> ```
>
> 先頭 0xF4（MIDI では未定義のステータス）+ 長さ + パラメータ。呼び元は
> 0x43990-0x43A38 の 9 箇所からの BSR だけで、リテラル参照は 0 件だった。

| 番地 | 内容 |
|------|------|
| **0x000437A0** | **MIDI を USB へ 1 バイト送る（R4 = バイト）。これが本命。** 割り込みを止めて ring[書き位置] に入れ、SR を戻して**空きが出るまでスピンで待ち**、書き位置を確定して IPRA \|= 0xC0 |
| 0x00043782 | 同じ処理の、割り込みを止めず待ちもしない版 |
| 0x0433A0 | **M37640 のコマンド口**に積む（R4 = ポインタ, R5 = 長さ）。MIDI には使わない |
| 0x043448 | 状態を取る |
| 0x043460 / 0x043468 | フラグ(0x43DAD0) を 1 / 0 にする |
| 0x043470 / 0x04347C | 受信割込を禁止 / 許可（IPRA の IRQ3 側） |
| 0x043486 | 送信ハンドラ（IRQ2）。リングから 1 バイト取り出して 0xF80001 へ |
| 0x043552 | 受信リングの空き容量を返す |
| 0x04359C | 空きができたら受信割込を再開する |
| 0x043630 | 受信ハンドラ（IRQ3） |

RAM:

| 番地 | 内容 |
|------|------|
| **0x40941A** | **MIDI 送信リング（1024 バイト, マスク 0x3FF）。0xF80000 へ出る** |
| **0x409416 / 0x409418** | **その読み位置 / 書き位置（どちらも word）** |
| 0x40A846 | コマンドリング（128 バイト）。0xF80001 へ出る |
| 0x43DACD / 0x43DACE | コマンドリングの読み位置 / 書き位置 |
| 0x421F04 | 転送モード（2 = USB） |
| 0x40800A/C, 0x40981C/E | 受信リングの位置（サイズ 0x400 と 0x1000） |

## 潰れた仮説: LED ラッチ

`0xE00000` と `0xC80000` の 16 ビットは**全部用途が判明した**。

- 0xE00000 の 8 ビット = LED 8 個
- 0xC80000 の bit6-7 = LED 2 個（MU と PLG-1）
- 0xC80000 の bit0-5 = スイッチ走査の列選択

USB 用の空きビットは無い。1 ビットずつ + 全ビットの総当たり（18 通り）でも変化なし。

## 現在の方針: 純正に乗っかる

M37640 を自力で起こすのは諦めて、**純正ファームを丸ごと動かしたまま割り込ませる**。
差し込む口は 2 つある。

1. 入口 0x040100 で純正の初期化列を全部呼び、純正のメインループへ飛ぶ
2. **呼び水**: メインループのリテラル 0x040CE0 を自前の関数に差し替え、
   最後に本来の呼び先 0x00041E50 へ JMP する
3. **本番**: ヘッダ 0x0400D8（= IRQ2 = USB 送信完了のハンドラ番地）を自前に差し替え、
   純正のハンドラ 0x00043486 を通してから続きを積む
4. どちらも「送信リングに 1 メッセージ分の空きがあれば 0x0433A0 で積む」を呼ぶ

### 実機で分かったこと（2026-09-06 夜）

USB からノートを送ると**音が出た**（HOST SELECT = USB のとき。MIDI 側に倒すと逆に
DIN でしか鳴らない）。つまり

```
ホスト -> M37640 -> /OBF0 -> IRQ3 -> ダウンローダのスタブ 0x003318
  -> RAM の関数ポインタ @0x401040 -> 純正の受信ハンドラ 0x00043630 -> 発音
```

が丸ごと通っている。**RAM 関数ポインタ経由という仕組み自体が生きている**ことの証明で、
我々が送信側 @0x401044 に据えたのと同じ道。据え方は間違っていない。

一方、送信は 1 バイトも出てこなかった。理由は**鶏と卵**。

- IPRA の IRQ2（送信）は 0x433A0 が積むときに初めて立つ（`IPRA |= 0xC0`）
- 立たなければ送信割り込みは上がらない
- 上がらなければ我々の txisr は呼ばれない
- 呼ばれなければ積めない

**最初の 1 個を誰かが積まないと、永久に始まらない。**

### 呼び水（メインループのフック）は当てにならない

MAME で数えたら起動から 8 秒で 1 回だけだった。0x040C5C を読み直すと理由が 2 つある。

1. これはループではなく **RTOS のタスク切り替え入口**（末尾は `JMP 0x041D24` = ディスパッチャ）
2. `[R13+0x60]` のコールバックが 0 以外を返すと **0x000407E0 へ JMP して 5 個の JSR に到達しない**。
   我々のフックは 5 個目なので素通りされうる

```
0x040C5C: OS 制御ブロック 0x040770 から SR/R15/R12 を復帰
0x040C6A: R0 = [0x0407D0]  ; 保留中のコールバック
0x040C6E: 0xFF なら 0x40C84 へ
0x040C72: JSR R0
0x040C78: 戻り値 0 なら 0x40C84 へ
0x040C80: JMP 0x000407E0   ← 0 以外だとここで抜ける。5 個の JSR には来ない
0x040C84: JSR 0x041E94 / 0x041AAC / 0x041A5C / 0x041B0C / 0x041E50   ← 5 個目を差し替えた
```

### 起こし役: 受信割り込み（ヘッダ 0x0400DC）

そこで**受信割り込みにもフックを置いた**。受信は実機で動いていることが確認済みなので、
**PC から何かバイトを送れば必ずここに来る**。

```
rxisr: 純正の受信ハンドラ 0x00043630 を通す -> 空きがあれば 1 個積む -> RTS
```

積めば 0x433A0 が IPRA を立て、送信割り込みの連鎖が始まって自走する。
連鎖が切れても、また送れば必ず再開できる。PC 側は `build/usbrecv.py` と
`tools/dump/recv_dump.py --prime-port` が、**流れが止まっている間だけ**
アクティブセンシング（0xFE）を投げて起こす。

IRQ2 も IRQ3 も IPRA の優先度は 12（0x433A0 が `|= 0xC0`、0x4347C が `|= 0x0C`）。
SH-2 は同レベルで多重割り込みしないので、両方から呼ばれる `fill` が
互いに割り込まれることはない。

### 差し込む口のまとめ（最終形）

**差し替えるのは 1 箇所だけ**に落ち着いた。

| ヘッダ | 差し替え先 | 役目 |
|---|---|---|
| 0x0400DC | rxisr | 純正の受信ハンドラ 0x00043630 を通してから、送信リングに空きがあれば 1 ブロック積む |

使わなかったもの:

- **0x0400D8（送信割り込み）は絶対にフックしない。** 積む → IPRA が立つ →
  送信割り込み → また積む、で永久に回り、割り込み優先度のまま CPU を占有する。
  実機では起動バナーのあと沈黙した
- **0x040CE0（メインループ）も使わない。** 起動直後の制御できないタイミングで
  一度だけ走り、本体の初期化と競合する。また 0x040C5C には 5 個の JSR に
  到達せず抜ける道があるので、そもそも当てにならない

結果としてファームは**完全に受動的**になった。PC がバイトを送ったときだけ
1 ブロック返す。送らなければ 1 命令も動かないので、暴走のしようがない。
起動時の挙動は純正と完全に一致する（MAME で PC ヒストグラムが数値まで一致）。

### 実測（2026-09-07）

| | 値 |
|---|---|
| USB の実効帯域 | **19,500 byte/s**（引き金を 10 倍にしても変わらず頭打ち） |
| 1 メッセージ | 334 バイト（64 ワード = ROM 256 バイト、効率 77%） |
| ブロック速度 | **55 blk/s**（理論値 58 の 95%） |
| 32MB の所要 | **約 36 分**（MIDI 版は約 3.8 時間 = 6 倍強） |

1 メッセージのワード数は `--words` で変えられる（既定 16、実用は 64）。
作業領域が 0xFFFFF000-0xFFFFF16F しか無いので、バッファの都合で 64 が上限。

### 受信側の落とし穴: 毎周の数え上げ

`tools/dump/recv_dump.py` は当初 `while sum(have) < nblocks:` でループしていた。
131,072 バイトの合計を毎周やると **1000 回で 0.26 秒**、毎秒 2000 回まわるので
CPU の半分をそれだけで食う。受信を捌けなくなり、3750 ブロックあたりで停止した。
取得数は変数で持つこと。途中経過の保存（33MB）も、連結してから書くと
余計なコピーが入るので 2 回に分けて書く。

### PC 側の引き金は「返ってきた分だけ」

一定の割合（毎秒 300 個）で投げ続けると、返せる速さを超えたぶんが MU2000 の
USB 受信側に溜まって詰まり、Windows の送信キューも溢れて
`MidiOutWinMM::sendMessage: error` になる。返事待ちを 8 個までに抑え、
リングが満杯で捨てられた引き金は 0.3 秒で失効させる（失効させないと
死んだ枠で窓が埋まって止まる）。

### 補足: 0x040C5C は毎周回まわらない

MAME で**フックが呼ばれた回数を数えたら、起動から 8 秒で 1 回だけだった**。
0x040C5C を読み直すと、これはループではなく **RTOS のタスク切り替え入口**で、

```
0x040C5C: OS 制御ブロック 0x040770 から SR/R15/R12 を復帰
          保留中のコールバック (R13+0x60) を呼ぶ
          JSR 0x041E94 / 0x041AAC / 0x041A5C / 0x041B0C / 0x041E50   ← 5 個目を差し替えた
          JMP 0x041D24   = ディスパッチャ（次のタスクのレジスタを復元して戻る）
```

という構造だった。通常のタスク切り替えは 0x041D24 側だけを通るらしく、
0x040C5C は起動時に 1 回通っただけだった。**ここだけに頼ると 1 個しか送れない。**

そこで、実際にデータを回すのは**送信完了割り込み**に任せる。1 バイト送るたびに
呼ばれるので、メインループの回り方に一切依存しない。呼び水の 1 個で連鎖が始まり、
あとは自走する。

### 送信先を間違えていた（2026-09-07 に判明）

実機で純正に書き戻して同じ道具で測ったところ、**純正なら Identity Reply が返り、送った
MIDI がそのまま USB へ返ってくる**（THRU）。純正の USB 送信経路は「MIDI を送るだけ」で
簡単に動く。出せていなかったのは我々のファームだけだった。

原因は宛先の取り違え。0x0433A0 は M37640 の**コマンド口**で、そこへ 64 バイトの SysEx を
流し込んでいた。実機ではこう見えていた。

- USB へ 1 バイトも出ない
- Domino でエクスクルーシブ受信が失敗する
- ノートを速く鳴らすと発音が遅れ、LCD の表示切替がもたつく
- SEQ -> DEMO が "Please Wait..." のまま固まる

正しい API は **0x000437A0(R4 = 1 バイト)**。空き待ちまで面倒を見てくれるが、
**満杯のまま割り込み文脈で呼ぶとデッドロックする**（同じ優先度 12 の送信割り込みが
走れず、リングが減らない）ので、空き判定は自前で持ったまま呼ぶ。

MAME ではこの故障を再現できない。M37640 をエミュレートしないので txisr も rxisr も
一度も呼ばれず、コマンド口へ流し込んだ影響も出ない。（一度「MAME で再現した」と
書いたが、あれは純正と自作で NVRAM ディレクトリが違って本体の保存状態が違っただけで、
同じ NVRAM なら両者は一致する。）

### 実機が起動しなくなった（2026-09-07）— 待つ版を割り込みから呼んではいけない

宛先を 0x000437A0 に直した版を焼いたら、**LCD に何も出ず本体が沈黙**した。
（ダウンローダは無傷なので [Drum]+[PLAY]+[VALUE+] 起動 → 純正アップデータで復旧できた。）

原因は 2 つが重なったもの。

1. **空き判定の off-by-one。** 「溜まり <= 0x3FF - メッセージ長」で通していたので、
   書き終えたあと溜まりが**ちょうど 1023（満杯）になりうる**
2. **0x000437A0 は空きが出るまでスピンで待つ。** 満杯だと待ちに入るが、呼んでいるのは
   IRQ2（優先度 12）の中。リングを減らす送信割り込みも同じ優先度 12 なので走れない
   → **永久にデッドロック**

しかも当時はメインループのフック（呼び水）が起動直後に走っていたため、
**LCD が描かれる前に固まった**。

対策は 3 つ。

- **待たない版 0x00043782 を使う。** スピンが存在しないので、原理的に固まらない
- 満杯まで詰めない（128 バイトの余裕を残す）
- **メインループのフック（0x040CE0）は使わない。** 起動直後の制御できない
  タイミングで走り、本体の初期化と競合する。起こし役は受信割り込みだけにする

結果、パッチはヘッダ 2 箇所（0x0400D8 / 0x0400DC）と入口 12 バイトだけになり、
**起動時の挙動は純正と完全に一致する**（MAME で PC ヒストグラムが数値まで一致）。
自作コードが動くのは USB の割り込みが上がったときだけ。

### 空きの判定

溜まり = (書き位置 - 読み位置) & 0x3FF、空き = 1023 - 溜まり。
**1 メッセージ分の空きがあるときだけ積む。** 0x437A0 は空きが出るまでスピンするので、
満杯のまま割り込みから呼ぶと固まるため、この判定は必須。

（以下は 128 バイトのコマンドリングを使っていた頃の考察。リングが 1024 バイトに
なったので余裕はあるが、「空になるまで待たない」という原則は変わらない。）

読み位置 0x43DACD と書き位置 0x43DACE が同じなら空。だが 0x43486 を読むと、
**両方のリングが空になった時点で送信割り込みを止めている**（0x434FC 以降で
IPRA のビットを落とす）。止まったあとに 0x433A0 で積み直すと IPRA は立て直されるが、
IRQ が立ち上がり検出なら新しいエッジが来ないので二度と再開しない恐れがある。

なので判定は「空か」ではなく「**1 メッセージ分の空きがあるか**」にした。

```
溜まり = (書き位置 - 読み位置) & 0x7F
溜まり <= 127 - メッセージ長  なら積む
```

これならリングが空になる瞬間が無く、送信割り込みの連鎖が途切れない。
なお 0x433A0 は**空き容量を一切見ずに書き込む**ので、溢れの判定は呼ぶ側の責任。

### レジスタの約束

メインループからは JSR、割り込みからはダウンローダの IRQ2 スタブ（0x0032DE）経由で
呼ばれる。スタブは R0-R7 と PR を退避し、割り込みスタックに切り替えてから JSR する。
よって自前のコードは **R0-R7 だけ使い、R8-R15 は触らない**。PR は入口で退避して戻す。

`tools/dump/make_usbhook.py` がこれを生成する。純正との差分は
入口 12 バイト + ヘッダ 4 バイト + リテラル 4 バイト + 空き領域のコードだけ。

## MAME で実機なしに確かめる

MAME 0.289 の `mu2000` は起動して 100% で回る。フラッシュを差し替えた
`mu2000.zip` を作って `-autoboot_script` で Lua を流せば、実機に焼く前に
かなりのことが確かめられる。フラッシュ 4MB と zip 内 2 個の対応は

```
h[2k] = flash[4k+1], h[2k+1] = flash[4k]      （上位 16bit を下位バイト先で）
l[2k] = flash[4k+3], l[2k+1] = flash[4k+2]    （下位 16bit を下位バイト先で）
```

これで `usbdump` を動かし、**組み上がった 94 バイトの SysEx が
波形 ROM の先頭 16 ワードと完全に一致すること**まで確認済み。

限界もある。M37640（USB）は emulate されないので送信リングは減らず、
**送信割り込みのフックは MAME では一度も呼ばれない**。呼び水の 1 個までしか見えない。

## USB 版ダンパ（tools/dump/make_usbdump.py）

`usbhook` と同じ土台（呼び水 + 送信割り込み）の上に、SWP30 の wave direct access を
載せたもの。送信リングに 1 メッセージ分の空きがあるときだけ、16 ワード読んで SysEx を 1 個積む。

```
F0 43 7D 'M' 'U' 'W' 'D' <ブロック番号 4x7bit> <16 ワード x 5x7bit> <加算和 2x7bit> F7
= 94 バイト（送信リングは 128 バイトなので 1 個ずつ入る）
```

MIDI 版（`make_dumper.py`）と同じ形式なので、受信は同じ `tools/dump/recv_dump.py` を使う。
1 ブロックのワード数だけ違うので `--words-per-block 16` を付ける。

```bash
python tools/dump/stage_ydl.py build/usbdump.ydl
build/upgrade_dumper/Upgrade.exe
python tools/dump/recv_dump.py --port "Yamaha MU2000" --words-per-block 16 --out roms/dump
```

**先に `usbhook` で経路を確かめること。** `build/usbrecv.py` で受けて、
1 個しか届かなければ呼び水だけが効いて送信割り込みのフックが回っていない、
という切り分けになる。

**再送要求は効かない。** USB 版は MIDI IN を見ていないので `--req-port` は付けないこと。
ダンパはブロック 0 から順に送り、最後まで行ったら 0 に戻るので、穴は次の一巡で埋まる。

### 作業領域 0xFFFFF000（SH7043 の内蔵 RAM）

ブロック番号と 94 バイトのバッファを置くために 4 バイト + 94 バイトだけ RAM が要る。
純正ファーム全体で `MOV.L @(disp,PC)` が読むリテラルを全部解決して、内蔵 RAM
（0xFFFFF000-0xFFFFFFFF）を指すものを数えた結果:

| 範囲 | 純正が参照する番地 |
|------|------|
| 0xFFFFF000-0xFFFFF7FF | **0xFFFFF170 だけ**（0x41450 付近から 9 回） |
| 0xFFFFF800-0xFFFFFFFF | 0xFFFFFCE8, 0xFFFFFCEA, 0xFFFFFEFD/FE, 0xFFFFFF54/58, 0xFFFFFFFC（スタック）ほか |

よって 0xFFFFF000-0xFFFFF16F を使う。ただし計算で作ったポインタ経由の使用までは
追えないので、**先頭に合言葉 'MUWD' を置いて毎回検査**し、壊れていたらブロック 0 から
入れ直す。読み側は順不同・重複に強いので実害は出ない。

外した場合の見え方: 合言葉が毎回不一致になり、**ブロック 0 だけが延々と届く**。
そうなったら `--scratch` で別の番地を指定して作り直す。

### SWP30 の取り合い

純正ファームも wave direct access を使う（0x11C1E4, 0x1366A4, 0x136770 の 3 箇所が
0x80011C/0x80019C/0x80021C/0x80029C を触る）。フックが割り込むと互いに化ける可能性がある。

- こちらの化けは**各ブロックの加算和で検出して捨てる**ので実害はない
- 純正側が化けると、最悪その処理が固まる。**吸っている間はサンプリング系の操作をしない**こと

読み出し手順は検証済みの MIDI 版と同一にしてある（トリガ → 固定待ち 40 → ステータス
監視 400 回 → データ読み）。純正が動いているので SWP30 の初期化はしない。

## MIDI IN C・D の口（2026-09-16）

実機の MIDI IN C・D は USB だけの口で、我々のエミュレータでは長らく使えなかった。
**M37640 の ROM は要らなかった。** SH-2 から見えるのは 2 番地と割り込み 2 本だけなので、
そこに代役を置けばファーム自身が残りをやってくれる。

### 番地と割り込み（訂正版）

| 番地 | 読み | 書き |
|------|------|------|
| 0xF80000 | 受信バイト | **MIDI 送信バイト**（リング 0x40941A、0x434FC が出す） |
| 0xF80001 | 状態（bit0 = 受信あり, **bit6 = コマンド**） | コマンド送信バイト（リング 0x40A846、0x434AC が出す） |

書きは**番地で**、読みは**状態の bit6 で**、MIDI とコマンドを分けている。
IRQ3（ベクタ 67）が受信、IRQ2（ベクタ 66）が送信。

### 口は `F5 <n>` で切り替わる

M37640 が SH-2 へ渡すのは**ただの MIDI バイト列**で、その中に `F5 <n>` が挟まる。

```
0x042932  0xF5 と比べる
0x0429EA  次のバイトを 0x40A823（今の口）に入れる
0x0429F4  0x0004437C(R4 = 口, R5 = バイト) を呼ぶ
```

口は **1 始まり**。呼び元から確定した。

| 呼び元 | R4 | 口 |
|---|---|---|
| 0x0427F4（DIN、SCI ch0） | 1 | A（パート 1-16） |
| 0x042AA4（DIN、SCI ch1） | 2 | B（パート 17-32） |
| 0x0429F4（USB） | `@0x40A823` | 3 → **C**（33-48）、4 → **D**（49-64） |

USB の 5-8 番はマイコン側には口があるが、ファームが捨てる。

### PC から送った `F5 nn` は、実機では効かない

MU80・MU100・MU128 のマニュアルには、TO HOST の線で `F5 nn`（ケーブルメッセージ）を送ると
以後のメッセージが口 nn へ行く、と書いてある（issue #24）。MU2000 を USB で繋いで確かめると（2026-09-17、
HOST SELECT = USB、Windows のヤマハの USB ドライバ）、**効かなかった**。口 A〜D の ch1 に別の音色を置き、
`Yamaha MU2000-1` の線に `F5 03` / `F5 02` / `F5 04` を送ってからノートを送っても毎回口 A の音色で鳴り、
`-2` の線に `F5 03` を送っても口 B のまま（音色の帯の形の差 0.01〜0.06dB）。ドライバか M37640 が捨てているのか、
どちらかまでは分けていない。

エミュでは `mu2000::midi_in` が PC から来た `F5 nn`（nn = 1-4）を読み、その入口から後のバイトを口 nn へ回す
（MU128 の TO HOST と S-YXG50 に合わせた。1 本の入口しか無いプラグインでも 64 パートに届く）。
`F5 nn` は firmware には渡さない。そのまま渡すと上の 0x042932 が口の切り替えと読み、代役が挟む `F5 <口>` と食い違う。
範囲外の nn と、番号の来ない `F5` は口を変えない。口は `reset()` で元に戻る。
UTIL>SYS の Thru Port が 1-8 なのは**出力**側の口数で、入力とは別勘定。

### HOST SELECT が USB でないと C・D は通らない

振り分け 0x04437C の中で、口が割り当て外のときだけ転送モード 0x421F04 を見て、
**0（MIDI）なら捨てる**（0x0443A2）。USB（2）なら通る。
だから代役を使うときは HOST SELECT を USB にする必要がある。
ホストスイッチは ADC で読むソフト設定で、8 ビットに落として境で分ける（0x001098）。

| ADC（8 ビット） | モード |
|---|---|
| < 0x20 | 0 = MIDI |
| 0x48-0x6E | 1 = シリアル 38400 |
| 0x7D-0xA3 | 3 |
| **0xBA-0xE0** | **2 = USB** |

### エミュレータ側（src/mu2000.cpp の `usb_line`）

- 溜めに積むとき、口が変わっていれば `F5 <口+1>` を先に挟む
- 1 バイト渡すごとに IRQ3 を上げる。間隔は DIN と同じ 10 ビット分
  （実機の USB も、間隔だけ見れば DIN と大差なかった）
- **IRQ2 を定期的に上げてファームの送信リングを吐かせる。**
  上げないと 0x000437A0 の空き待ちで固まる（実機で本体を沈黙させたのと同じ罠）
- `set_usb_host(true)` を**起動前に**呼ぶ。そのときは A・B も USB 側を通る
  （実機で HOST SELECT を USB にすると DIN が黙るのと同じ）

パート 1 を音量 0 にすると口 A の音だけが消え、パート 33 を音量 0 にすると
口 C の音だけが消えることで、**C がパート 33、D がパート 49 に届いている**ことを確かめた。
MIDI モードの出音は 1 バイトも変わっていない（同じ MIDI で書き出した WAV が完全一致）。

## 未解決

**M37640 が何によって起きるのか**は厳密には不明のままだが、
純正のメインループを回せば起きることは `stockloop` で確認できた。
タスクのどれかが面倒を見ている、という理解でよさそう。

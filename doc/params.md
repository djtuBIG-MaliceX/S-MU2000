# パラメータの層（設計）

音色・エフェクト・パートの設定を、**名前で読み書きする土台**を作る。
いまのエディタとエフェクトの面、これから作る PC 向けの画面、VST3 の
オートメーションの 3 つが、同じものを使う。

設計と、その前提を確かめた実験の記録。作る順の 1〜4 は済み（層の本体は
`src/xg/model.h`、確かめる道具は `src/xgtest.cpp`、画面は `src/ui/editor.cpp` と
`src/ui/effects.cpp`）。

## いまの弱点

エディタとエフェクトの面は **送るだけ**で、覚えているのは「この画面から送った値」
（`src/ui/editor.cpp` の頭の覚え書き）。だから

* パネルで音色を変えると、画面の表示とずれる
* 曲が送ってきたプログラムチェンジやパラメータチェンジが画面に出ない
* 起動したときの値は「実機の初期値に近いはず」の決め打ち
  （NVRAM を残すようにしたので、これはもう当たらない）

画面を増やすほど、この「ずれ」が増える。PC 向けの画面を作る前に直しておく。

## 分かったこと: firmware が自分で答える

実機の MU2000 は、XG の **問い合わせ（パラメータリクエスト）** と
**一括ダンプ要求** に、MIDI OUT から答える。firmware の仕事なので、
こちらでも MIDI OUT の線を拾えば同じ答えが返るはず、と考えて確かめた。

MAME のドライバは CPU の SCI0 の送信線を MIDI OUT に繋いでいる
（`src/mame/ymmu2000.cpp:369`）。こちらは繋いでいなかった。
実験の道具で送信線を拾い、31250bps の枠を読んで並べた:

| 送ったもの | 返ってきたもの |
|---|---|
| マスタボリュームの問い合わせ `F0 43 30 4C 00 00 04 F7` | `F0 43 10 4C 00 00 04 7F F7` |
| パート 1 のプログラムの問い合わせ `… 08 00 03 …` | `… 08 00 03 00 F7` |
| リバーブ種別の問い合わせ `… 02 01 00 …` | `… 02 01 00 01 00 F7`（HALL 1） |
| **プログラムチェンジ `C0 30` を送った後に**、同じ問い合わせ | `… 08 00 03 30 F7` |
| パート 1 の一括ダンプ要求 `F0 43 20 4C 08 00 00 F7` | 52 バイト（パートの設定 41 バイト＋チェックサム） |

4 行目が肝心で、**画面が送った値を覚えているのではなく、音源の中の今の値**が
返る。パネルで変えたものも、曲が変えたものも、NVRAM から戻ったものも、
全部これで読める。RAM の番地を推測して覗く必要が無い。**実機と同じ公式の口**。

起動してから何も頼まないうちは、送信線には 1 ビットも出ていなかった
（勝手に何かを流す作りではない）。

## 形

```
                 音声の糸                               画面の糸
  ┌─────────────────────────────┐        ┌───────────────────────────────┐
  │ mu2000                      │        │ xg::model                     │
  │   MIDI IN A ← 合流 ←────────┼── 輪 ──┼─ 書く（パラメータチェンジ）     │
  │                ↑ 利用者の MIDI      │   頼む（ダンプ要求）           │
  │   MIDI OUT →  枠を読む ─────┼── 輪 ──┼→ 読む → 写し（値の表）          │
  └─────────────────────────────┘        │         ↑                      │
                                         │   定義表（名前・番地・範囲）   │
                                         └───────────┬───────────────────┘
                                          今の面 / PC 向けの画面 / VST3
```

音源に触れるのは今までどおり音声の糸だけ。画面の糸とは錠の無い輪で
バイトをやり取りする（`ui::bridge` と同じ作法）。

## 1. MIDI OUT を拾う（mu2000）

* `write_sci_tx<0>` を繋ぎ、1 ビットずつの呼び出しから枠を組み立てる。
  SCI は 1 ビットにつき 1 回だけ線の値を知らせてくる（`sh_sci.cpp` の
  `tx_async_step`）ので、時刻を見なくても「0 が来たら開始、8 ビット、1 で終わり」
  で読める。実験ではこれで枠ずれ無しに読めた
* 読んだバイトは `mu2000` の中の輪に積み、取り出す口を 1 つ出す
* **実機の MIDI OUT 端子そのもの**なので、gui の出口としても選べるようにした
  （`MIDI OUT`。いままでの A/B の出口は `MIDI THRU A / B` と呼び直した）

**済**: `mu2000::midi_out_take()`。状態の保存には入れない（入れると保存の形が
変わって、DAW に保存した曲が読めなくなる）。読み戻したときは空から始める。

## 2. 定義表

1 行が 1 つのパラメータ。**データとして持つ**（画面ごとに番地を書かない）。

| 欄 | 例 |
|---|---|
| 名前 | `part.volume` |
| 表示名 | `Volume` |
| 番地 | `08 pp 0B`（`pp` はパート番号で置き換える） |
| 大きさ | 1 バイト / 2 バイト（種別の MSB/LSB など） / 4bit ずつ |
| 範囲と初期値 | 0-127、100 |
| 見せ方 | そのまま / 中央 64 で ±（パン） / +1（プログラム） / 表（エフェクト種別） |
| 繰り返し | パート 32 / ドラムセット 2 × 鍵盤 など |
| 裏付け | **実測**（書いて読み返せた） / 資料だけ |

最初に入れるのは、いまの面が使っているものと、ダンプの 1 塊ぶん:

* システム（マスタチューン・ボリューム・トランスポーズ）
* エフェクト（リバーブ・コーラス・バリエーションの種別とリターン、
  インサーション 1/2 の種別とパート。`doc/effects.md` で実測済みの番地）
* マルチパート 1 塊（上のダンプで返ってきた 41 バイト）

ドラムセットアップ、エフェクトの細かいパラメータ（1-16）、A/D パート、
プラグインボードは後。

**番地の裏付けは firmware に取らせる**（「7. 確かめ方」）。資料を写し間違えても、
読み返しで食い違うので分かる。

## 3. 写し

画面の糸が持つ、値の表。

* 値ごとに「いつ確かめたか」を持つ。まだ一度も読んでいない値は **不明** として
  出す（決め打ちの初期値を出さない。それが今のずれの元）
* 書いたら、返事を待たずに写しも書き換える（つまみが遅れて見えないように）。
  あとで読み返して食い違えば読んだほうに合わせる
* **読み返しは塊で頼む**。1 つずつ問い合わせるより往復が少ない。マルチパート
  1 塊が 52 バイトで、31250bps の線を 17ms ほどで通る。32 パート全部でも
  0.6 秒くらい

いつ読み返すか。firmware は **変わったことを自分からは知らせない**ので、
こちらから頼む:

| きっかけ | 読むもの |
|---|---|
| 面を開いた・パートを選んだ | 見えている塊 |
| パネルのボタンやダイヤルを触った（0.2 秒おさまってから） | 見えている塊 |
| 曲や DAW から CC・PC・SysEx が来た（同上） | 見えている塊 |
| 何も無いとき | ゆっくり全部を一巡り（1 秒に 1 塊くらい） |

頼んだ返事が戻る前に次を頼まない（1 つずつ）。音声が止まっている間
（VST3 で再生していない等）は返事が来ないので、そのまま待つ。

## 4. 合流（問い合わせを割り込ませる）

問い合わせは MIDI IN から入れるしかない。**利用者の MIDI の流れと混ぜる**
ことになるので、ここが一番危ない。

* いまも画面のつまみは同じことをしていて、隙がある。gui の音声の糸は
  ブロックの頭で「画面から来たバイト → MIDI 入力のバイト」の順に流す。
  MIDI 入力のバイトは **1 バイトずつ** 輪から取るので、ブロックの境目で
  メッセージが途中まで読まれていると、次のブロックで画面の SysEx が
  **その途中に挟まる**。まれだが、問い合わせを定期的に流すと当たりやすくなる
* **済（書く側で揃える形にした）**: 読む側で組み立て直すのではなく、
  **書く側がメッセージを最後まで書いてから、読んでよい位置を 1 回で進める**。
  音声の糸からは完成したメッセージしか見えないので、音声の糸に仕事が増えない
  * `midi_in`（Windows のコールバック）: 位置を進めるのはメッセージが終わった
    ときだけ。何枚かに分かれて届く SysEx は `F7` まで待つ。SysEx の途中の
    リアルタイム（クロック）は SysEx と一緒に読ませる。入りきらないメッセージは
    丸ごと捨てる
  * `ui::bridge::send`: 同じく 1 回で進める。**書き手が 2 本あった**（画面の糸と
    MIDI ファイルを流す糸）ので、書き手どうしは錠で順番にした。前は書き込み位置を
    取り合って壊れることがあった。読み手は錠に触らない
  * 試験: コールバックの糸と音声の糸を並べて走らせ、短いメッセージ 14 万通・
    分割した SysEx 4 万通を流して、取り出しがメッセージの途中で終わった回数 0。
    bridge は書き手 2 本で 56 万通、送った数と読めた数が一致、途中で切れたのも 0
* Windows の MIDI 入力は、ランニングステータスを省かずに渡してくる
  （`MIM_DATA` は毎回ステータス付き）。挟んでも後ろのメッセージが化けない
* VST3 はイベントがもともとメッセージ単位なので、この心配は少ない

問い合わせは **口 A** から入れる。返事は MIDI OUT に 1 本で出てくる。

利用者が外から送ったダンプ要求の返事も同じ線に出る。層は自分が頼んだものの
返事でなくても、読める形なら写しに取り込めばよい（害は無く、得しかない）。

## 5. 糸の分担

| | 音声の糸 | 画面の糸 |
|---|---|---|
| 音源に触る | ○ | × |
| 合流（メッセージ単位で流し込む） | ○ | |
| MIDI OUT の枠読み、バイトを輪へ | ○ | |
| SysEx を組み立てて読む、写し、定義表 | | ○ |
| いつ頼むかを決める | | ○ |

音声の糸でやるのはバイトの受け渡しだけにして、SysEx の解釈は持ち込まない
（音声の糸を重くしない）。

gui と VST3 で違うのは、画面の糸が「窓」か「プラグインの画面／コントローラ」か
だけ。層そのもの（`xg::model`）は Windows にも画面にも依存しない C++ にする。
そうすると `render` のような窓の無い道具からも試験できる。

## 6. 使う側

* **いまのエディタとエフェクトの面**: `m_cc` / `m_fx` に覚えている値をやめ、
  写しを読んで描く。「この画面を送り直す」ボタンは要らなくなる
* **PC 向けの画面**: 定義表を並べれば一覧・つまみ・保存と読み込みが作れる。
  塊ごとのダンプを保存すれば、そのまま「音色のファイル」になる
* **VST3**: XG のパラメータを DAW に見せて、オートメーションで動かせるようにする。
  番号は今あるもの（A の CC 0-2095、出力 4096、状態 4097、B の CC 8192-10287）と
  重ならないよう、65536 番から置く。DAW に見せる本数は絞る（全部だと数千本になる）。
  **済（VST3・CLAP）**: パート 64 × 19 本、マスター 27 本、インサーションのパラメータ 4 × 16 本。[automation.md](automation.md)

## 7. 確かめ方

番地や大きさの間違いは **firmware に見つけさせる**。

1. 定義表の 1 行ずつ、範囲の端と真ん中の値をパラメータチェンジで書く
2. 同じ番地を問い合わせる
3. 書いた値が返れば「実測」。返らなければ、番地か大きさか範囲が違う

ダンプの塊についても、塊を頼んで、定義表の並びどおりに切り出した値が
1 つずつの問い合わせと一致するかを見る。

ROM が要るので `make test` の ROM ありの段に足す。音は見ないので速い。

### 確かめた結果（`make test` の 5 番、8 秒ほど）

| | |
|---|---|
| 書いて読み返す | 定義表 64 行 × パート 1・17・32 で 424 回、**食い違い 0** |
| 一括ダンプと 1 つずつの問い合わせ | 120 個、食い違い 0 |
| プログラムチェンジと CC7 で変えた値 | 層の頼み方（`want_part` → `poll`）で読めた。口 B のパート 19 も |
| `model::set` でバンクを書く | すぐ効いた |

最初に回したときは 21 回食い違った。**番地の間違いは 1 つも無く**、全部
firmware の決まりだった:

* **バンクは SysEx で書いても、次にプログラムを書くまで効かない**
  （CC0/CC32 → PC と同じ作り）。`model::set` はバンクを書くと、写しにある
  今のプログラムも続けて送る
* **エレメントリザーブは全パートの合計に枠がある**。既定で 32 パートが 2 ずつ
  取っているので、32 は載らない。4 は通る
* **キーアサインは 0-1 まで**。資料の 2（INST）は受け付けない

システムとエフェクトの塊も一括ダンプに答えた（`00 00 00` 7 バイト、
`02 01 00` / `02 01 20` / `02 01 40` がリバーブ・コーラス・バリエーション、
`03 00 00`〜`03 03 00` がインサーション 1-4）。切り出した値は 1 つずつの
問い合わせと全部一致（パートと合わせて 141 個）。

## 画面に繋いだ（作る順の 4）

* **音声の糸**: `ui::driver::pump_out` がブロックの終わりに MIDI OUT のバイトを
  `ui::bridge` の輪へ移す（gui と VST3 の両方）。問い合わせは `bridge::ask` の
  別の輪から口 A へ入れ、**外の MIDI THRU には流さない**。音源の時計
  （`bridge::audio_ms`）もここで進める
* **画面の糸**: `ui::panel::tick` をタイマー（30 コマ／秒）から呼ぶ。返事を層に
  読ませ、面を開いている間は見えている塊を 1 秒ごとに頼む。パートを選んだとき・
  面を開いたとき・ダイヤルを回したときはすぐ頼む
* **書いた直後は返事で上書きしない**（0.5 秒）。書く前に頼んだ読み返しが書いた後に
  届くと、つまみが一瞬古い値へ戻って見えるため。`xgtest` で確かめている
* エディタのつまみは全部マルチパートの塊の中のものにした。CC11・CC5・CC1 は
  firmware に問い合わせる口が無いので外し、Dry・Note Shift・Detune に替えた
* パートは 32 個とも選べる

## RAM から読む（問い合わせをやめた）

画面は 1 秒ごとに一括ダンプを頼んでいたが、頼みごとは MIDI IN に入るので LCD の受信マークが
点きっぱなしになった。**エミュレータの中の firmware のワーク RAM を直に読む**ことにした。

* 1 項目ずつパラメータチェンジで書いて、RAM の変わった所を探した（`src/xg/ram.h`）
* パートの塊は 0x134 バイトずつ、中は XG のマルチパートの番地そのまま。**口ごとに
  パート 10 が先頭、1-9、11-16 の固定の並び**（ドラムかどうかによらない）
* システムは 0x4226C1、エフェクトは 0x40CAD8 から 5 つの塊（中は XG の並び）
* CC1・CC11・ピッチベンド・ホールドもパートの塊の中にある（XG に番地の無いもの）
* xgtest の 5 番: パート 1・10・17・26・32 の 41 項目とシステム・エフェクトの 221 個を、
  問い合わせの返事と突き合わせて食い違い 0

音声の糸が 25ms ごとに写して bridge で渡す（`xg_snapshot`）。層の問い合わせの仕組み
（`want_*` / `poll`）は xgtest と外のエディタとの試験のために残している。

# 今後の課題

実機と突き合わせて「合っている」ところまでは来た（発音指示 2851 件一致、振幅
88.7% が 10% 以内）。ここから先に残っているものを、**直す順**に並べてある。

順番の理由は 3 つ。(1) 直したことで音が変わったと気づける仕組みが先に要る。
(2) 遅れの半分は音源ではなく外の配管なので、安い手から取る。(3) 速さの話は
待ち時間の下限を決めるので、詰めるなら最後にまとめて。

---

## やる順

### 1. `make test` と基準の波形をこのリポジトリに置く — 済（doc/testing.md）

いま回帰試験が**別のリポジトリに散っている**。基準の WAV と MAME 側の改造が
`MU2000` 側にあり、`statetest` と `verify` はあるが Makefile に試験の的が無い。

この状態では、以下のどれを直しても「音が変わったことに気づけない」。
design.md が移植で一番怖いと書いた事態そのもの。

やったこと（くわしくは doc/testing.md）:

* `make test` で verify → statetest → 鳴らし比べ 7 件 → スレーブ別糸の確認まで。
  ROM が無い機械では verify だけが走る。ひと回し 40 秒
* **WAV は置かない。**1 件 4MB になるうえ、ROM から起こした音を配ることに
  なるので、同梱しない立場と合わない。代わりに音から測った数（PCM の
  ハッシュ・keyon・包絡線・直流）を `tests/*.json` に置いた。全部で 40KB
* 鳴らす MIDI も置かず `tools/make_test_midi.py` が毎回組む

途中で**出る音が実行ごとに変わる**のが見つかったので直した。デバイスの状態に
初期値の無い要素があり、firmware がそれを読む経路があったため、起動時の引数の
文字列がそこに残っていると音が変わっていた（パスの区切りで keyon が 1 サンプル
ずれる）。`swp30.h`・`sh_*.h`・`sci4.h`・`hd44780.h` の要素に初期値を書いた。
**MAME 上流にも同じ穴がある**はずなので、送れる。

### 2. 出力をデバイスの形式に合わせ、遅れの内訳を数字にした — 済（一部）

**先に前提を直す。** ここに「MIDI をサンプル単位にすれば平均 15ms 消える」と
書いていたのは誤り。DAW は未来のイベントを渡してくるのでサンプル単位化が効くが、
実時間の MIDI 入力は**必ず過去に届く**。ブロックの頭で流すのは「できる限り早く」
であって、遅らせてはいない。サンプル単位化で消えるのは**ブロックの中のずれ**
（連打やアルペジオの刻みが境界に丸まる）で、平均の遅れではない。

やったこと:

* **デバイスが言ってくる形式のまま開くようにした。** この機械は 48000Hz の
  float を言ってきて、44100/16bit は素では通らない。つまり今までは
  **毎サンプル Windows の変換器（既定の品質）を通っていた**。`ui::resampler`
  （VST3 にあった窓関数付き sinc を出したもの）で自前に変換する。
  正弦で測った誤差は 100Hz-5kHz で -92dB、15kHz で -86dB
* `live.exe` が独自に持っていた WASAPI の手順を `ui::audio_out` に寄せた。
  gui と二重だったものが 1 つになり、変換もどちらにも入る
* `audio_out::start` の**宙ぶらりんの参照**を直した。立ち上がりの首尾を
  start のローカルに置いてスレッドが参照で掴んでいたので、スレッドが
  run() を抜けた後にそこへ書いていた（最適化を上げると落ちる）
* デバイスとの折衝の結果を表に出した（`48000 Hz 2 ch float / 溜め 30.0 ms /
  周期 10.0 ms / 変換 自前 sinc`）

**溜めをどこまで詰められるかを測った**（`dense` = 16 パート同時の重い側）。

| ブロック | ぶん | 平均 | 99% | 最悪 | 超過 |
|---|---|---|---|---|---|
| 1323 | 30.0ms | 16.9 | 21.3 | 21.7 | 0/500 |
| 480 | 10.9ms | 6.3 | 8.2 | **9.2** | 0/1379 |
| 256 | 5.8ms | 3.3 | 4.6 | 5.2 | 0/2584 |
| 128 | 2.9ms | 1.7 | 2.4 | 3.7 | **2**/5168 |

音源は実時間の 58% を食う。周期 10ms では最悪 9.2ms でぎりぎり間に合い、
溜め 30ms なら 20ms の余裕が残る。**溜めを 20ms にすると余裕が 10ms になって
最悪値とほぼ並ぶ**ので、いま詰めると時々切れる。README が「待ち時間の下限は
音源の速さで決まる」と書いているのはこのこと。数字が出た。

この機械では `IAudioClient3` の共有モードの最小周期も 10ms（既定と同じ）で、
そちらから取れるものは無かった。

#### 追記: 溜めを満杯にしていたのを直した

実機と並べて聞いた実測で **0.117 秒** 遅れていた（Domino → exe → 出力 と、
Domino → exe の THRU → USB → 実機 → S/PDIF の比較）。探したら作りの問題が
あった。

**起きるたびに溜めを満杯まで書いていた**（`want = buf_frames - padding`）。
満杯に保つと、新しく書いた音は常に「溜め一杯ぶん」待たされる。30ms 頼んだら
30ms そのまま遅れる。いまは `target` までしか書かない。

`--exclusive` も足した。Windows の混ぜ合わせを通らないので、そこが丸ごと消える。

| | 溜め（平均/最悪） | デバイス | 出るまで | 遅れ |
|---|---|---|---|---|
| 共有 目標 20ms（新しい既定） | 10 / 20 | 0 | 約 10-20ms | 0 回 |
| 独り占め 10ms | 0 / 10 | 10 | 約 10ms | 0 回 |
| 独り占め 4ms（音源なしで確認） | 0 / 4 | 4 | 約 4ms | — |

`GetStreamLatency` は共有モードで 0 を返す（役に立たない）。`IAudioClient3` の
共有モード最小周期もこの機械では 10ms で既定と同じだった。

#### 決着: 117ms → 16ms

実機と並べて波形で測って **16ms**（60fps で 1 フレーム）。生演奏に使える。
効いたのは 3 つで、うち 2 つはこちらの欠陥だった。

**(1) 独り占めの周期がデバイスの単位と噛み合っていなかった。** ドライバは
何を頼んでも「通った」と返してくる（3ms でも 5ms でも器はその通りに返る）が、
カードは 1024 サンプル単位で動いていた。480 フレーム（10ms）は 1024 を
割り切らないので、**切り刻まれたような音**になっていた。2 の冪に丸めて解決。

  切り分けの手順が効いた。デバイスへ渡すバイト列をそのまま WAV に落として
  調べたら、440Hz の正弦が 1 サンプルの差まで期待どおりで飛びも 0 個だった。
  「こちらのデータは正しい、崩れているのは渡した後」と分かった時点で、
  疑うところが受け渡しの作法に絞れた。

**(2) 形式。** この機械の独り占めが受けるのは 48000/16bit と 24bit in 32bit
だけで、float は全滅。**24bit in 32bit（業務用の本来の形）を先に試す**ように
した。16bit も「通る」と言うが扱いが怪しい。

**(3) インターフェース側の設定**（これはこちらから触れない）。
Buffer Size 1024 → 256、Sample Rate 48000 → 44100。後者は MU2000 が 44100
でしか動かないので、**こちらの変換が丸ごと消える**という副産物もあった。

同じ機械で並べた最後の数字:

| | まだ鳴っていない量 |
|---|---|
| 共有 | 47.5ms（こちらの溜めは 10ms。差の 37ms は Windows とドライバ） |
| 独り占め | 11.6ms（周期そのもの。余分なし） |

**出口を選べるようにした**（`--audio`、名前の一部で指定、gui.ini に記憶）。
Windows の「既定の再生デバイス」は勝手に変わり、実際この作業中に別の口へ
移った。聞いている口が決まっているなら指定したほうがよい。

`--exclusive --latency 5` なら周期 5.8ms まで行けるが、たまに間に合わない
（音源の 1 ブロックの最悪が 3.4ms、余裕 5.8ms）。**ここから先は音源を
速くする話**（6 番）。

残り:

* **曲の再生（`--play`）をサンプル単位にする。** ここは player が未来の譜面を
  持っているので、サンプル単位化が本当に効く唯一の場所。いまは別スレッドが
  実時間で輪に積んでいて、音声側がブロックの頭でまとめて飲む。音声スレッドの
  標本時計で流せば `render.exe` と同じ音になり、`make test` で画面側の経路も
  見られるようになる
* 溜めを詰めるのは 6 番（速くする）の後

### 3. 30Hz 以下の残りは MEG（エフェクト DSP）が作っている — 出どころを特定

30Hz 以下が 5.3% 残っている（実機 0.13%）。**積算器の丸めだという読みは外れで、
出どころは MEG だった。** 順に潰した記録を残す。

#### 1. ミキサの丸め（`mixer_att`、`swp30.cpp:2701`）— 違った

`>>` が負の側で −∞ へ落ちるので偏るはず、という筋で最近接と 0 方向の二通りを
試した。**直流は 0.3% も動かない。**

| | floor（いま） | 最近接 | 0 方向 |
|---|---|---|---|
| piano | 4.239 | 4.172 | 4.216 |
| chord | 24.785 | 24.689 | 24.719 |
| dense | 169.789 | 169.271 | 169.384 |

理由は後で分かった。MU2000 の使う経路は**減衰なし**のモード（`mixer_step` の
mode 1-3）で、そこでは `mixer_out[] += input` と足すだけで丸めが無い。
`mixer_att` はほとんど呼ばれていない。

#### 2. 声ごとのフィルタ（Chamberlin と iir1）— 違った

再帰積分器の中の丸めは直流に化けやすいので、`filter_block::step` と
`iir1_block::step` の `>>` を全部最近接にした。**piano 4.239 → 4.250。**
iir1 は 0.00%（この曲では通っていない）。

#### 3. 声の出口を直に測った — 声は直流を持っていない

`render --dump-dac` で 1 声の中身を 1 秒ぶん出し、段ごとの平均を取った
（piano の減衰中）。

| 段 | 平均 | 最大 |
|---|---|---|
| wave（読んだ生のサンプル） | −36.9 | 12272 |
| filt（フィルタ後） | −1150.3 | 301049 |
| out（音量をかけた後） | **−0.175** | 1470 |

声の出口はほぼ 0。**直流は声より後で入っている。**

#### 4. MEG の出口に乗っていた

同じ記録に MEG のレジスタも入っている。ミキサが DAC に入れている線
（`m_m[0x20]`, `m_m[0x21]`）の平均は **+354 / +356 で、最大が 2667**。
出力の 13% が直流。

送りを 0 にした MIDI（CC91/93/94 = 0）で裏を取った。

| | 発音中 | 減衰後（最大 93） |
|---|---|---|
| リバーブ有り（XG の既定） | +6.10 | **+4.96** |
| 送りを 0 | +2.47 | **−0.016** |

**尾の直流はまるごと MEG。** XG の初期状態はリバーブが入っているので、
全部の音に乗る。残る +2.47 は乾いた側の話で、こちらは振幅の 0.1%。

#### 5. MEG の中のどこか — 半分は `meg_pack24`

`meg_pack24`（`swp30.cpp:3226`）の `p >> 15` は、MEG が 1 サンプルに 384 歩
走るあいだ何度も通る。ここを最近接・0 方向にすると:

| | floor（いま） | 最近接 | 0 方向 |
|---|---|---|---|
| piano | 4.239 | **2.237** | 2.425 |
| chord | 24.785 | 22.278 | 22.233 |
| dense | 169.789 | 167.470 | 167.435 |
| effects | 8.149 | 6.818 | 6.016 |

**軽い曲では半分が消えるが、重い曲ではほとんど動かない。** 残りは振幅に
比例しているので、純粋な切り捨てではなく掛け算側の非対称（`m1_expand`、
飽和モード、リバーブ RAM の詰め方 18bit）が怪しい。

#### 6. 重い曲の直流の大半は、圧縮サンプルのループの読み落とし（2026-09-14）

doc/upstream.md の 12。ループを 2 つ進みで跨ぐと差分を 1 つ落とし、積算器のずれが
溜まっていた。直すと dense の直流が **172.6 → 18.6**、30Hz 以下が **17.6% → 9.6%**。
piano・chord・effects は動かない（ループを跨ぐときに 1 つずつしか進まない音）。
上の表の「重い曲ではほとんど動かない」はこれで説明がつく。軽い曲に残る分は
`meg_pack24` の側。

#### 7. 音が止んでも 0 に戻らない — 直した（2026-09-14、upstream 18）

丸めが 2 か所違っていた（p を詰めるときの切り捨ての向きと、リバーブ RAM の e = 0 の負の値の反転）。両方直すと実機と同じくぴったり 0 に戻る。以下は調べた時点の記録

実機はパフォーマンスモードで 1 音鳴らして離すと、しばらくして S/PDIF が**ぴったり 0**
（-240dB）になる。エミュは離したあと -78dBFS の雑音と直流 8.1e-4 が残り続ける
（鳴らす前は 0）。

* MEG のディザ（`rand() & 0x07e0`）を全部外しても変わらない（-78.6dBFS、直流 7.9e-4）。
  ベロシティ 40 で倍音の間の床がエミュだけ +10〜17dB 高いのも、これで変わらなかった
* `meg_pack24` を 0 方向の切り捨て（`p / 32768`）にすると**直流は 5.4e-6 に消える**が、
  雑音は -79.8dBFS で残る。最近接（`(p + 0x4000) >> 15`）は直流 1.3e-4、雑音 -79.6dBFS
* 無音の区間で 0 でないのは、プログラム頭のマスター EQ の段（r64-r77、`<< 2`・`<< 4` の
  nodither の書き込み）が ±300 前後、リバーブの r0a-r17 が ±数十。DAC の m30/m31 は ±550 で、
  出力の最大 15LSB と合う。**リミットサイクル**

**2026-09-16 の測り直し**: パフォーマンスモードの 100 パフォーマンス（実機 XG ではなく PFM、S/PDIF）を、1 件ごとに全チャンネルのオールサウンドオフで前の音の尾を断ってから選び直す形で録り直した（scratchpad の pn100b.mid・pncmp3.py）。帯の食い違いの平均は 0.765dB。実機どうしの再現性は 0.0〜1.1dB なので、これより小さい差は測れない。悪い順は 012 Old EP 3.91、067 Crypt 3.42、076 Orion 2.67、004 Analog Age 2.23、088 Tiny Pipe 2.14dB。どれも倍音そのものは合っていて、**倍音の間と上の床がエミュだけ 5〜20dB 高い**のが効いている。012 Old EP で、基音の倍音の山と倍音の間の床の比を測ると実機 96.6dB・エミュ 84.8dB（11.8dB の差）。エミュの中を段ごとに見ると（PFM_DUMP で m レジスタを 1 秒ぶん）、声が MEG に入る時点（m2c）で 89.9dB、MEG を出た所（m30）で 84.1dB。床の形は、声の段は 500Hz から 16kHz まで平らな -87dB（丸め誤差らしい）、MEG を通ると 1.5kHz が -76.5dB の山なりに変わる。MEG のディザ（rand() & 0x07e0）を外しても 84.5→84.8dB と変わらない（9/14 と同じ）。つまり残っているのは MEG の段の丸め（または限界周期）。次はここ。

**2026-09-16 の続き（丸めの候補を 3 つ潰した）**: 床の出どころを探して、次の 3 つを切り替えて測ったが、どれも効かなかった。(1) MEG のディザ（`rand() & 0x07e0`）を外す → 山と床の比は 84.5→84.8dB（変わらない。9/14 と同じ）。(2) `meg_pack24` の丸めを -∞ 側・近い方（2 通り）に変える → XG の試験（E.Piano にリバーブ HALL 1）で 91.5・91.5・91.3・91.4dB、PFM の 012 でも -∞ 側にして床は ±0.00dB。ただし -∞ 側は音を離したあと 0 に戻らなくなる（残り 8）ので、今の 0 側が正しい。(3) リバーブ RAM の 11bit 仮数を近い方へ丸める → XG の試験で 91.5→91.8dB（0.3dB だけ）。遅延メモリへ書く値の丸め（今は -∞ 側）は 0 側にしても変化なし。なお床の差そのものは、倍音 6 本で音量を合わせて測り直すと、012 Old EP で**倍音は ±1dB 以内・倍音の間の床が +2〜+9dB（平均 +4.5dB）**。最初に書いた 11.8dB は、音量合わせを帯の中央値で取っていたための過大評価。段ごとでは、声が MEG に入る所で床は 500Hz〜16kHz まで平らな -87dB（白い雑音＝丸め誤差らしい）、MEG を通ると 1.5kHz が -76.5dB の山なりに変わる（帰還のある段で形が付く）。次の候補は AWM2 の声の道（補間・フィルタ・音量の掛け算）と、MEG の段の語長。切り分けには「XG モードでエフェクトを全部切った素の音」を実機と比べるのが要る（実機のモードを XG に戻してもらう必要がある）。

**2026-09-16 の結び（床の正体は、声を重ねたときの干渉だった）**: XG モードに戻して切り分けた（scratchpad の xgfloor.mid・modfx.mid・layers.mid、floorcmp.py）。エフェクトを全部切って 1 音だけ鳴らすと、倍音の間の床は実機と **+0.16 / -4.65 / -0.02dB**（SineLead・E.Piano・Strings）で、こちらが高いということはない。リバーブを足しても -2.5〜-0.1dB。変調系のインサーション（PHASER 1・CHORUS 1・CELESTE 1・ENS DETUNE・FLANGER 1・SYMPHONIC）でも ±0.35dB に収まる。つまり声の道も MEG も、単音では実機と同じ静けさ。 ところが**同じ音色・同じ音を複数のパートに重ねる**と差が出る: 1 パート -0.06dB、2 パート +1.76dB、4 パート **+4.17dB**、4 パートでも少しずつ音程をずらすと +0.47dB。重ねた音は互いに打ち消し合って深い谷を作るので、谷の深さが声の立ち上がりの時刻の差（数サンプル）に非常に敏感になる。エミュの 4 声は MIDI のバイトの間隔どおり 42 サンプル（0.95ms）ずつずれて立ち上がる。実機も同じはずだが、upstream.md の 36 で詰めた鍵の時刻の精度は ±16 サンプルなので、その差が谷の埋まり方として出ている。 100 パフォーマンスで床の差を出すと**中央値 +0.36dB**、+3dB を超えるのは 7 件だけ（012 Old EP +7.6、076 Orion +7.1、007 Super Bass +6.7、026 Sparkle Pad +4.3、004 Analog Age +3.9、067 Crypt +3.8、074 AfricanGrand +3.1）。どれも倍音は ±1dB 以内で合っていて、層を重ねるパフォーマンスばかり。つまり残っているのは「声の立ち上がりの時刻をもっと合わせる」話で、雑音や丸めの話ではない。

**2026-09-16 夜の測り直し（物差しの誤りを直し、実機どうしの限界を出した）**: 3 つ分かった。
(1) **これまでの数字には測り方の誤りが混じっていた。** 帯を比べる前の音量合わせに「全 22 帯の中央値」を
使っていたので、信号の無い静かな帯（床）に引っ張られていた。いちばん悪いとされていた 012 Old EP は、
全帯が揃って -3.9dB ずれているだけで**中身は一致**していた（波形の相関 1.000、1.2 秒まるごと）。
音量合わせを**信号のある帯だけ**（山から 40dB 以内）で取るように直した（scratchpad の pncmp4.py）。
(2) **実機どうしの再現性は 0.216dB**（同じ pn100b.mid を 2 回録って比べた。pn100b_hw.wav / pn100b_hw2.wav）。
これがこの物差しの限界で、これより小さい差は測れない。

位相と違って立ち上がりのばらつきに強いので、こちらで比べた。

#### 次に見るところ

* リバーブ RAM の読み書き（`m_ram_read` / `m_ram_write` の詰め方）
* 掛け算と飽和（`mmode` の各枝、`d.clamp`）
* 直流が振幅に比例する＝利得の非対称。**片側だけ 1 LSB 損をする**形を探す
* 包絡線はどの変種でも 0.3% 以内しか動かない（倍音は動かない）ので、
  この辺りを触っても君の「極は 6/256 で正しい」という結論は崩れない

直流は `make test` の指紋（`dc`）に入っているので、触れば差分で見える。

### 4. 不揮発メモリの保存 — 済。起動状態のキャッシュは見送り

**NVRAM を残すようにした**（`src/nvram.h`）。実機の電池で保持されるワーク RAM
（0x400000-0x43ffff、256KB）を、`%LOCALAPPDATA%\S-MU2000\nvram\<プログラム ROM
のハッシュ>.bin` に置く。

先に試して分かったこと:

* **firmware はこの RAM を読んで起動する。** 残した RAM で起動すると、工場出荷の
  初期化を飛ばすぶん起動が 7.9 秒 → 5.4 秒（音の時間）に縮む
* **XG のマスタボリュームまで残る**（絞ってから入れ直すと、ピーク 9779 → 136
  のまま）。実機も同じ firmware なので同じはず
* RAM は起動しただけで 742 バイト変わる

扱い:

| | 読む | 書く |
|---|---|---|
| `gui` / `live` | 起動の前 | 終わるとき（音を止めてから。**起動できていたときだけ**） |
| VST3 | 起動の前 | **書かない**。変えたものは DAW のプロジェクトに残る。何枚挿しても取り合わない |
| `render` / `make test` | 読まない | 書かない。試験は毎回工場出荷状態から |

書くときは一時ファイルに書いてから置き換える。`live` は Ctrl+C でもすぐには
死なず、止めて残してから終わる。工場出荷状態に戻すのは `--factory`（gui と
live）か、gui の右クリックの「工場出荷状態に戻す」。

**起動状態のキャッシュは見送った。** MEG と CPU を速くした結果、起動はもう
壁時計で約 1〜1.5 秒（VST3 で残した設定から 0.78 秒）しかかからない。
キャッシュで縮むのはそのうち 1 秒ほどで、しかも NVRAM を残すと終わるたびに
RAM が変わるので、「この NVRAM から起動した後の状態」はほとんど当たらない。

（**状態の大きさは既に手当てされていた。** `state_pack`（`src/state.h:120`）が
同じバイトの続きを縮めていて、VST3 はその形で保存している。実測で 6.09MB →
472,821 バイト（7.8%）。ここは課題ではない）

### 5. VST3 のイベントバスを 2 本にする — 済

CC などのパラメータも口ごとに持つ（B は 8192 番から。A・出力レベル・状態の

残り: 実際の DAW で 2 本目のバスが選べるか（DAW による）。

### 次: パラメータの層 — 設計した（doc/params.md）

### 6. 速くする — CPU 側（CMT）と MEG は済

**実時間比 58% → 38% まで来た。** 独り占めモードで 128 フレーム（2.9ms）が
超過 0 で回る。

#### 測り方

`build/blocktime.exe <rom> <MIDI> <フレーム数> [秒] [回数]` で 1 ブロックの所要時間の
分布と、CPU・SWP30・その中の MEG の内訳が出る。

**同じ区間を繰り返して中央値を出す。** 起動直後の状態を保存しておき、毎回そこへ
戻して流すので、どの回も同じ仕事になる。**最初の 20 秒は捨てる**。この機械
（Ryzen 7 9700X）では走り始めの十数秒だけ 13-25% 速く出て、その後に落ち着く。
鳴らし続けるときの速さは落ち着いた後のほうなので、そちらを測る。慣らしの後は
回ごとの幅が 1-2% に収まる（1 回きりで測っていた頃は ±10% 揺れていた）。
ビルドごとのコードの並びによる揺れはこれでは消えないので、小さな差は疑うこと。

部分ごとに止めて値段を測った（16 パート同時、256 フレーム）:

| 止めたもの | 基準比 |
|---|---|
| **MEG** | **−39.6%** |
| AWM2 とミキサ | −14.6% |
| スレーブの SWP30（別糸で並走） | −2.2% |

#### 済: CMT が 16 サイクルごとに CPU を止めていた

`doc/design.md` が予告していた**メモリバスの線形探索は犯人ではなかった**
（64KB 単位のページ表にしたら逆に遅くなった。プログラム ROM は最初の領域
なので走査は 1 回目で当たる）。

本当の犯人は CMT。MU2000 の firmware は COR=1・1/8 で走らせていて合わせが
16 サイクルごとに起き、そのたびに CPU を止めて周辺 10 個に予定を聞き直して
いた。「次の予定」の 99.8% がこれ。割り込みは切ってあるので予定に入れる
必要が無く、読まれたときに計算すれば足りる。

**CPU の時間が 46% 減った**（実行ループが 1 サンプルあたり 80.5 周 → 1.5 周）。
命令の切れ目が動くので発音の時刻が最大 1 サンプルずれるが、声の中身
（サンプル番地・ピッチ・形式）は完全に同じ。MAME にも同じ穴があるので
[doc/upstream.md](upstream.md) に控えた。

| ブロック | 前（平均/最悪） | 後（平均/最悪） |
|---|---|---|
| 1323（30ms） | 16.9 / 21.7 | 11.5 / 16.7 |
| 480（10.9ms） | 6.3 / 9.2 | 4.2 / 7.5 |
| 256（5.8ms） | 3.3 / 5.2 | 2.2 / 4.4 |
| 128（2.9ms） | 1.7 / 3.7（2 回超過） | **1.1 / 2.2（超過 0）** |

#### 済: MEG の判定を前倒しした（-42%）

1 サンプルに 384 命令 × 2 チップ。命令ごとの判定のうち、プログラムと番地の
割り当て（`m_map`）だけで決まるものを、プログラムが変わったときに 1 回だけ
解いて命令表にした（`meg_state::build_ops()`）。1 サンプルぶんは
`run_program()` がまとめて回す。番地の解決（`resolve_address()` の 8 段の探索）
も命令表に焼いたので、`map_w` でも解き直させる。命令表は状態の保存に入れない。

音はビット単位で同じ（`make test` 全件一致）。

| 16 パート同時・256 フレーム | 前 | 後 |
|---|---|---|
| MEG（1 サンプル、マスタ） | 4357 ns | **2525 ns** |
| 1 ブロックの平均 | 2.52 ms | 2.03 ms |
| 実時間に対する割合（平均） | 43.4% | **34.9%** |

（この表は慣らしの後の数。前に書いた 38% は慣らし無しで測った値なので、
並べて比べるなら 43.4% のほう）

いまの内訳は **CPU 3.8µs、MEG 2.5µs、AWM2 とミキサ 1.5µs**（1 サンプル）。
次に大きいのは CPU。

**効かなかったもの**（どれも音は同じだった。同じ回り道をしないために残す）:

|---|---|

掛け算（mmode 2）、ALU の組み合わせは 1 チップで 33〜35 種類、

#### 済: MEG の JIT（2026-09-14）

`src/mame/sound/swp30_jit.cpp`。firmware が書いた MEG のプログラムを、プログラムか番地の
割り当てが変わるたびに x86-64 の機械語に訳す（Windows x64 のみ）。訳した物はどこにも
残さない（firmware 由来のものを配らないため、実行時に作って捨てる）。

* 命令ごとの判定は訳すときに決める。3 命令遅れの書き込みと 2 命令遅れのメモリポート・t の値は、
  輪のどの枠かが訳すときに決まるので反映する位置に直に置く。サンプルを跨ぐ頭と終わりの
  数命令だけ輪そのものを使う
* 定数・番地表・LFO は実行時に読む。乱数は同じ順に同じ回数引く
* 分岐（bit 0x3f）を含むプログラム（LO-FI・DYNA 系）は、輪を毎命令で読み書きする形で訳す（2026-09-15 から。前は解釈実行に任せていた）
* `SMU2000_MEG_JIT=0` で切れる

**音はビット単位で同じ**: `make test` 全件、PFM の 100 パフォーマンス（C4）、XG でバリエーション
116 種類をインサーションで・リバーブとコーラスの全種類を、JIT 有りと無しで描いて WAV が
1 バイトも違わない。

| dense・512 フレーム | 解釈実行 | JIT |
|---|---|---|
| MEG（マスタ、1 サンプル） | 1893 ns | **731 ns** |
| MEG（スレーブ、別糸） | 1709 ns | **480 ns** |
| 1 ブロックの平均（実時間比） | 29.7% | **24.3%** |

前に試して遅くなった「ALU を種類ごとの関数にして命令表から呼ぶ」（上の表）と違い、
p が命令から命令へ流れる所を呼び出し無しの一続きの機械語にしたのが効いた。
残りで大きいのは CPU（3.1µs）。Mac（arm64）版の JIT はまだ無い。

#### 済: MEG の JIT の定数の焼き込みと、書き込みの前倒し（2026-09-15）

測ると（自作のサンプリングで、dense、1 本の糸）時間の 41% が MEG の JIT、25% が SH2 の JIT、33% が C++ だった。
MEG の中では、ディザ付きでレジスタへ書く命令が 35%。ビット単位で同じまま、次をやった:

* **定数を焼き込んだ版を別に作る**。firmware は MEG の定数をエフェクトを組むときにまとめて書き、そのあとはほとんど変えない
  （dense で 30 秒に 3000 回、PFM でパフォーマンスを替えるたびに約 1200 回）。定数が 8192 サンプル変わらなければ、
  今の定数を即値にした版を作って使い、1 つでも変わったらすぐ定数を読む版に戻す。係数 0 の掛け算は省き、
  p が変わらない命令（`p = 0 * x + p`）は丸ごと省く。変わった数は swp30_device が持つ（状態の保存の並びは変えない）
* **3 命令遅れの書き込みを、読まれない所では書いた場所で直に入れる**。読む命令の 1 つ前か 2 つ前に同じレジスタへの
  書き込みが無いレジスタだけ（サンプルを跨ぐ分と、終わりの 3 命令が書くレジスタは除く）
* 乱数の種を回しているあいだレジスタに置く。pack24 の限界を即値でなくレジスタから使う

dense で MEG がマスタ 約 773 → 約 650ns、スレーブ 627 → 約 500ns（揺れ 2〜4%）。`SMU2000_MEG_BAKE=0` / `SMU2000_MEG_EARLY=0` で切れる。

同じ夜に続けてやったこと（どれもビット単位で同じ。make test、PFM 100 個、XG の効果全種類 470 秒、1 サンプルごとの
CPU レジスタの畳み値、保存した状態のバイト列で確かめた）:

* MEG: 飽和の限界もレジスタに置いた。LFO の値（`get_lfo`）を関数を呼ばずに機械語で求める
* SH2: レジスタだけの命令が続くあいだは pc を書かない（`SMU2000_SH2_LAZYPC=0` で切れる）。
  遅延スロットの命令も、pc を使わない普通の命令なら機械語で書く（`SMU2000_SH2_SLOTNATIVE=0`）。
  解釈実行に落ちていた命令の大半が、rts や bsr のあとの遅延スロットの NOP・`mov.l @r15+` だった
* SWP30: ミキサは振り分け先のある入力だけ回す。着いているピッチ EG は関数を呼ばない

| | 前（2026-09-15 の夜の頭） | 後 |
|---|---|---|
| PFM を 1 本の糸で 76 秒ぶん描く（m1.mid） | 約 9.4 秒 | 約 7.3 秒 |
| dense を 16 台同時に 20 秒ぶん | 5.38 秒 | 4.91 秒 |
| dense 1 台（別スレッドあり）20 秒ぶん | 2.42 秒 | 2.30 秒 |

続けて（どれもビット単位で同じ）:

* MEG の JIT: リバーブ RAM の詰め方と戻し方を分岐なしにした（符号は音しだいで予測が外れる）。PFM 76 秒で約 2%
* MEG の JIT: 分岐を含むプログラム（LO-FI・DYNA 系）も訳す。飛ばす位置は swp30_device に持つ（保存しない）。
  飛ばされた命令は輪に入れる書き込みを消して t の値だけ入れる。エフェクト 116 種類の 480 秒で解釈実行と WAV が同じ、34.9 → 33.7 秒
* ミキサの足し込みの分岐をなくした（減衰なし = 減衰 0、0xff 以上は並びに入れない）
* MEG の LFO を書いたときに命令表と JIT を作り直さない（LFO の値は実行時に読む）。PFM の描画では差が見えなかった

見送ったもの:

* 64 声の輪の頭（鳴っているか・ピッチ EG）を印のビットで飛ばす。envelope の状態を変える所が多く、印の付け忘れで
  ずれる危険に対して 3% ほど
* firmware の待ちのループ（0x115e0e、CMT のコンペアマッチの印を読んで回る）の早送り。PFM の演奏中の CPU は
  主に 0x127746 からの 64 要素を回す本物の仕事で、待ちは数 %
* MEG の JIT は 1 命令あたり約 7 クロックまで来ている。掛け算・ディザ・24bit への詰めがあるので、ビット単位で
  同じまま大きく縮める余地は少ない

#### 済: ミキサの振り分けを前もって解く（2026-09-14）

1 本の糸で回して 1ms ごとに命令の位置を取ったら、ミキサ（`mixer_step`）が 12% あった。
毎サンプル 96 入力 × 16 出力の route を解いていたのを、route / vol が書かれたときだけ
入力ごとの「足し先と減衰」の並びにするようにした。SWP30 マスタが 1979 → 1750 ns。

#### 済: SH2 の JIT（2026-09-14）

同じ取り方で CPU が全体の約半分。firmware の熱い所は 0.2ms ごとに 64 声・16 パートの作業域を
回す本物の仕事で、暇な待ちループではなかった（飛ばせない）。そこで `src/mame/cpu/sh2_jit.cpp`
でプログラム ROM の上の命令を分岐までのひと続きごとに x86-64 に訳す（Windows x64 のみ、実行時に作って捨てる）。

* 1 命令ごとに `execute_run()` の 1 周と同じ順で「pc を進める → 実行 → 割り込みの印を見る → icount を減らす」をする
* よく使う命令（実行回数の約 97%）は機械語で直に書く。メモリはプログラム ROM とワーク RAM だけを直に触り、
  ほかは解釈実行と同じ関数を通す。周辺に触った命令のあとで印や pc の変化があればブロックを抜ける
* 遅延スロットの命令・珍しい命令は `execute_one` を呼ぶ。m_delay か割り込みの印が立っているときは入らない
  （初めは印を見ずに入って、起動中の割り込みが 1 命令遅れた。chord と dense の指紋で見つかった）

#### 外からの指摘（2026-09-13、Mac で動かした人）

Nuked-SC55 を大幅に軽くした人が、このリポジトリを Mac（Standalone / AU / VST3）で

  384 命令 × 2 チップ

* SH2 のほうも重そう

* VST3 は `process()` の中で直接作っている。別スレッドは読み込み直後の起動だけ。
  gui.exe は WASAPI のイベント駆動の糸で作っている。見たのが古い版か、どこを指しているかは未確認

  Apple Silicon で 1 コアに収まっていないなら、音声スレッドで締め切りを落として
  振り切れるのは自然

  100 種類以上を 1 つずつ実機と突き合わせることになる。issue #1 の 3 件

  この物差しが使えなくなる。音の再現を優先する（持ち主の方針）

    全エフェクトに一度で効き、結果は今と同じ。プログラムが変わるのは種類を変えたときだけ
  * **SH2**: firmware の暇な待ちループを見つけて飛ばす、ブロック単位でまとめて実行する
* Mac 対応の変更を共有してもらえるなら、取り込みを相談する余地がある（持ち主の判断）

#### ピッチ EG の残り（issue #3 の DX Hard などは直した。doc/upstream.md の 13）
